## Goal

A real person, on a real iPhone and a real mid-range Android, taps a real WhatsApp message, joins, answers,
installs the app to their home screen, and gets back in a week later without signing in again. Everything
this product claims that a headless browser cannot prove is proved here, once, in writing, before release.

## Context

`CLAUDE.md` asks for "Manual check on a real iPhone and a real Android device: install to home screen, open
a deep link from WhatsApp, respond, and share." Four things end up here because nothing else can carry them:

- **iOS installability.** [D44](../00-decisions.md) rules that Lighthouse's installability audit covers
  Android Chrome only. iOS coverage is this story plus a build check for `apple-touch-icon` and
  `apple-mobile-web-app-capable`.
- **The 60-second budget.** [D21](../00-decisions.md) removed the wall-clock assertion from
  [S2.5](S2.5-deep-link-return-path.md) and moved it here: a stopwatch on a real mid-range Android, on
  mobile data, p50 over three runs, times pasted into the PR.
- **The WhatsApp in-app browser.** [D45](../00-decisions.md) says Android may open the link in a Chrome
  Custom Tab sharing Chrome's session, and iOS opens a WebKit view that does not. Both the detection and
  the [D47](../00-decisions.md) "you'll sign in once more" copy are guesses until someone taps them.
- **The `wa.me` fragment.** [D52](../00-decisions.md) names it explicitly: percent-encoding failure only
  shows up on a real phone, when the message arrives truncated at the `#`.

[D56](../00-decisions.md) settles how this story is signed off: it can never run in CI, so it is done when
`docs/device-pass.md` is committed with device, OS version, browser version, date and tester, and pasted
into the PR. The definition-of-done exemptions are written into this story's own block below rather than
left to inference.

This is a check, not a discovery exercise. [S7.3](S7.3-end-to-end-journey.md) is green before this starts.
Anything found here is a bug in the story that owns the screen, fixed there, and the pass is re-run.

## Scope

**In**

- `docs/device-pass.md`: a fixed checklist, filled in and committed, one section per device.
- One pass on a real iPhone running current iOS Safari.
- One pass on a real mid-range Android running current Chrome.
- Real WhatsApp: a real message, in a real group, tapped from the app.
- The timing measurement from [D21](../00-decisions.md).
- A build-time check that `index.html` carries `apple-touch-icon` (180x180) and
  `apple-mobile-web-app-capable` ([D44](../00-decisions.md)) — the only automated part of this story.
- Re-running the affected sections after any fix the pass forces.

**Out**

- A device lab, BrowserStack, or any paid cross-device service. Two phones and a stopwatch.
- Automating any of this. If it could be automated it would be in [S7.3](S7.3-end-to-end-journey.md).
- Testing older OS versions, tablets, desktop browsers, or Android browsers other than Chrome. One current
  iPhone, one current mid-range Android. Widen it when a real player reports a real problem.
- Fixing what the pass finds inside this story's PR. Findings go to the owning story.
- Performance profiling beyond the single p50 number.
- Accessibility auditing, battery, or data-usage measurement. Not asked for.

## Acceptance criteria

Each criterion is independently checkable by a person.

- [ ] **AC1** — `docs/device-pass.md` is committed, containing one section per device, each with: device
      model, OS version, browser version, app release string (the `pfc-release` meta value), date, tester
      name, and a pass/fail plus a note for every numbered step below. No step is left blank
      ([D56](../00-decisions.md)).
- [ ] **AC2** — Both devices complete the full journey from a real WhatsApp message: tap link, cold preview,
      join, register, land on the exact event, tap YES, and see the response persist after force-quitting
      and reopening.
- [ ] **AC3** — The cold preview on both devices shows the team name, title, date line and location, one
      `Join {team}` button, and **no** notes ([D7](../00-decisions.md)).
- [ ] **AC4** — iPhone, WhatsApp webview: the escape prompt appears after the response and the install
      guide does not ([D46](../00-decisions.md)). The copy-link button copies the app root, the copy states
      the player will sign in once more, and pasting into Safari lands on sign-in
      ([D47](../00-decisions.md)).
- [ ] **AC5** — iPhone, Safari: the [S2.8](S2.8-add-to-home-screen-guide.md) guide shows the iOS steps with
      the real share icon, Add to Home Screen works, and the installed icon is the 180x180
      `apple-touch-icon`, not a screenshot of the page.
- [ ] **AC6** — Android, Chrome: either the `beforeinstallprompt` Install button appears and installs, or
      the written fallback steps appear and installing through the three-dot menu works
      ([D45](../00-decisions.md)). Which branch occurred is recorded.
- [ ] **AC7** — Both devices, launched from the home-screen icon: the app opens in standalone with no
      browser chrome and no address bar, and neither the escape prompt nor the install guide appears
      ([D44](../00-decisions.md), [D46](../00-decisions.md)).
- [ ] **AC8** — Both devices, launched from the home-screen icon at least 24 hours after the last use: the
      session is restored, there is no flash of the login screen, and no password is typed
      ([S2.6](S2.6-session-persistence.md), [D59](../00-decisions.md)). The gap between the two launches is
      recorded as a timestamp pair, not asserted from memory.
- [ ] **AC9** — Tapping a second event's WhatsApp link **while the app is installed** opens the event.
      Which surface it opened in — the installed app or the browser — is recorded per platform, because it
      differs and the answer is worth writing down.
- [ ] **AC10** — Manager share, both devices: the native share sheet opens, WhatsApp is offered, and the
      message that arrives in the group matches the [D13](../00-decisions.md) format **with the link intact
      and tappable**. A screenshot of the received message is committed alongside the checklist
      ([D52](../00-decisions.md)).
- [ ] **AC11** — Manager records attendance on the Android device at 375px-class width: the
      [D42](../00-decisions.md) three-state segmented control is tappable with a thumb, no horizontal
      scroll, and the setting survives a reload.
- [ ] **AC12** — Timing, on the mid-range Android, on mobile data, not wifi: from tapping the WhatsApp link
      to the YES confirmation being on screen, as a brand new user each time. Three runs, each time
      recorded, p50 under 60 seconds ([D21](../00-decisions.md)). Each run uses a fresh number from the
      reserved range ([D58](../00-decisions.md)) and Chrome data cleared between runs.
- [ ] **AC13** — Safe areas, both devices: the fixed bottom nav clears the home indicator, and on
      `/#/event/:id` the YES / NO buttons are not underneath the nav, because that route hides it
      ([D41](../00-decisions.md)).
- [ ] **AC14** — Aeroplane mode, both devices, app installed: relaunching loads the cached shell rather than
      a browser error page, and attempting a response shows the [D48](../00-decisions.md) line
      "Couldn't save. Tap again." rather than a crash or a silent no-op.
- [ ] **AC15** — After a deploy: with the app already installed, relaunch twice and confirm the release
      string has changed ([D43](../00-decisions.md)). This is the manual confirmation of the automated
      check in [S7.3](S7.3-end-to-end-journey.md), and it is the check that matters, because the stale
      shell breaks every WhatsApp link at once.
- [x] **AC16** — A build-time test asserts `index.html` contains
      `<link rel="apple-touch-icon" sizes="180x180" ...>` and
      `<meta name="apple-mobile-web-app-capable" content="yes">` ([D44](../00-decisions.md)). This is the
      only part of the story that runs in CI.
- [ ] **AC17** — Steps 19 and 20 are completed and recorded: a join link pasted into WhatsApp arrives
      whole, including everything after the `#`, and tapping it reaches the join screen; and one reminder
      message sent from a real phone reads differently from the initial share and names no player.
- [ ] **AC18** — Every failed step has a one-line note naming the story that owns the fix. The pass is not
      signed off until those fixes have landed and the affected sections have been re-run and re-recorded.

## Implementation notes

### The artifact

`docs/device-pass.md` is committed as a template first, empty, and filled in per pass. Keep prior passes:
append a new dated section rather than overwriting, so a regression across releases is visible.

```markdown
# Device pass

## 2026-XX-XX — iPhone 13, iOS 18.3, Safari 18.3 — release a1b2c3d — tester: NAME

| # | Step | Result | Note |
|---|---|---|---|
| 1 | Tap share link from WhatsApp group | pass | |
| 2 | Cold preview: team, title, date, location, Join button, no notes | pass | |
...
```

The step numbering is fixed by the checklist below and does not change between passes, so two passes can be
diffed.

### Setting up a run

1. Deploy to `app.phibsboro.ie` from `main` ([S0.5](S0.5-deployment.md)). The pass runs against the
   **live site**, not a preview build — it is the only story that does, and that is the point.
2. Use the production Supabase project. Create a throwaway team, "Device pass", through
   [S6.1](S6.1-teams.md) so the pass never writes into a real squad, and deactivate it afterwards
   ([D50](../00-decisions.md)) rather than deleting it — teams are never hard-deleted.
3. Numbers for the test registrations come from the reserved range
   ([D58](../00-decisions.md), and see [S7.3](S7.3-end-to-end-journey.md) open question 1). They are
   deliberately not dialable.
4. A second WhatsApp account, or a group containing only the tester, supplies the real message. Do not use
   a squad group.

### Devices

"Mid-range Android" means a phone of the class a player actually owns: a Samsung A-series, a Pixel A, or a
Moto G of the current or previous generation. A flagship measures nothing useful for AC12. Record the exact
model. The iPhone should be whatever is current; iOS Safari is the same engine across models, so the model
matters less there than the OS version.

### The one automated bit

`src/test/index-html.test.ts` reads `index.html` from disk and asserts the two tags in AC16. It runs in the
`check` job with the rest of Vitest. It exists because those two tags are easy to lose in a refactor and
their absence is invisible until someone tries to install on an iPhone.

## Data and API surface

No migration, no RPC, no schema change, no query key. The pass writes real rows to the production database
through the normal UI: one team, one or two events, a handful of registrations from the reserved number
range, their responses and their attendance.

Cleanup is by deactivation, not deletion ([D50](../00-decisions.md)): set the "Device pass" team inactive
when the pass is signed off. Its events, responses and attendance stay, invisible to every non-admin. No
step in this story deletes anything, and nothing here is a reason to add a delete path.

## UI states

Not a UI story. It adds no screen and changes none. It observes, on real hardware, the states
[S7.1](S7.1-state-coverage-audit.md) audited: the loading skeleton on a cold deep link over mobile data,
the [D48](../00-decisions.md) failure line in aeroplane mode, and the populated state of every screen in
the checklist.

## Test plan

- **Unit** — `src/test/index-html.test.ts` only: the two iOS meta tags (AC16).
- **Integration / RLS** — None. [S1.4](S1.4-rls-test-suite.md) must still pass, untouched.
- **E2E** — None added. [S7.3](S7.3-end-to-end-journey.md) must be green before the pass starts; a manual
  pass over a broken journey wastes a tester.
- **Manual** — The eighteen steps above, on two devices, recorded in `docs/device-pass.md`, plus the
  committed screenshot of the received WhatsApp message and the three timing figures.

## Open questions

1. **What happens if the p50 comes in over 60 seconds?** Proposed default: it is a finding, not a release
   blocker on its own. Record the number, name the slowest step from the run notes, and raise it against
   the story that owns that step. The figure is a budget to aim at, and a number in the file beats a claim
   in a meeting.
2. **How often is the pass re-run?** Proposed default: before the first release, and thereafter on any
   change to [S0.4](S0.4-pwa.md), [S2.7](S2.7-escape-the-whatsapp-browser.md),
   [S2.8](S2.8-add-to-home-screen-guide.md) or [S5.2](S5.2-share-action.md). Those four are the stories
   whose failures are invisible to CI. A full re-run for a copy change on the home screen is waste.
3. **Does the pass run against production or against a staging Supabase project?** Proposed default:
   production, on the deactivated "Device pass" team. There is no staging project in the stack table, and
   inventing one is scope. The real WhatsApp, real DNS and real service-worker behaviour are exactly what
   this story exists to check.
4. **Who is the tester?** Proposed default: whoever merged the release, with a second person for the first
   pass. The name goes in the file either way, so the answer is recorded rather than assumed.
