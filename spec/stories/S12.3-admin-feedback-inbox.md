## Goal
An admin can read every feedback report in one place, newest first, see who sent it and the context, and mark
it resolved once handled — so tester feedback is triaged in-app, not lost in chats.

## Context
[W1/W2](../00-decisions-v1.2.0.md). Lives under the admin surface (the admin god-mode area, Epic 11).
Read-list shape mirrors the S3.5/S11.3 history screens (newest first, "Show more", four states).

## Scope
**In**
- An admin-only route, e.g. `/admin/feedback`, linked from the admin screen (and the admin nav).
- A list of feedback newest first: reporter name, category, message, when, status. Open shown before
  resolved (or a filter toggle Open / All).
- The captured `context` (route, release, device) visible per row, e.g. an expandable line — enough to
  reproduce a bug.
- A "Mark resolved" action per open item, via `resolve_feedback` (S12.1) — optimistic, with the row moving to
  resolved. Idempotent.
- Four states: loading skeleton, empty ("No feedback yet."), error (inline retry), populated + "Show more".
- Optional: a small unresolved-count badge on the admin nav entry.

**Out**
- Replying to the reporter (no messaging).
- Editing or deleting feedback.
- Non-admin access (RLS refuses it; the route guard mirrors S2.9).

## Acceptance criteria
- [ ] **AC1** — An admin sees every feedback row, newest first; a non-admin cannot reach the route or read the
  data (RLS returns nothing).
- [ ] **AC2** — Each row shows reporter name, category, message, relative time, and status.
- [ ] **AC3** — The context (at least route + release) is viewable per row.
- [ ] **AC4** — "Mark resolved" sets `status = resolved` (stamping `resolved_at`/`resolved_by = ` the admin)
  and moves the row; tapping an already-resolved item does nothing.
- [ ] **AC5** — Four states handled; the list pages with "Show more" (25/page) like S3.5/S11.3.

## Implementation notes
- `src/features/feedback/routes/FeedbackInboxScreen.tsx`; `useFeedbackInbox` (infinite query, `feedbackKeys`)
  and `useResolveFeedback` (calls `resolve_feedback`) in `src/api/feedback.ts`.
- Reuse the S3.5 list shell (skeleton / empty / error / "Show more") — do not hand-roll a new one.
- Names come from `profiles` via an inner join on `user_id` (an admin may read `profiles`); render times
  through `formatEventTime` (D35), never ad-hoc.
- Route-guard the screen to admins (S2.9) as convenience; RLS is the enforcement layer.

## Data and API surface
Read `feedback` (+ `profiles` join) as admin (S12.1). `useFeedbackInbox`, `useResolveFeedback`. `feedbackKeys`
under their own prefix so a resolve invalidates only the inbox.

## UI states
| Screen | Loading | Empty | Error | Populated |
|---|---|---|---|---|
| `/admin/feedback` | skeleton rows | "No feedback yet." | inline retry | list, open first, "Show more", resolve action |

## Test plan
- **Unit** — the inbox screen's four states off a mocked hook; resolve calls the RPC and moves the row.
- **Integration / RLS** — S12.1 covers admin-read and the resolve write; add a negative (non-admin read).
- **E2E** — optional: submit (S12.2) then see it in the inbox and resolve it (local stack).
- **Manual** — read a real tester's report and resolve it.
