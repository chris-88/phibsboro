## Goal

A player who taps a squad join link, or an event link, in WhatsApp can create an account with three fields
and one button, and is signed in and in the squad when the button returns. No SMS, no code, no email, no
confirmation step, no second screen.

## Context

This is the narrow part of the funnel. Everything upstream — the manager creating the event, the share
message, the tap in the group chat — is wasted if this screen asks for anything more than name, number and
password. `CLAUDE.md` section "Epic 2" fixes the field list and forbids widening it.

Decisions this story is built on, all in [00-decisions.md](../00-decisions.md):

- **D6** — an event id is a valid entry credential, not only an invite token. S2.1's gate reads: reachable
  with a valid invite token **or** a valid event id; a bare visit to `/#/register` with neither is rejected.
- **D37** — that gate is **UX, on membership**. It is not a security boundary. The anon key is public, so
  anyone can call `auth.signUp` directly and create an account. What the gate protects is the
  `team_members` row, and that is protected by the join RPCs and RLS, not by this screen. No policy
  anywhere may assume that only invitees hold accounts.
- **D19** — whether Supabase phone sign-up works with no SMS provider configured is proved as the first
  task of S1.2. If it does not, the fallback is a synthetic email derived from the number, confined to
  `src/lib/auth.ts`. This story calls that helper and never `supabase.auth.signUp` directly, so the
  outcome is a one-file change here.
- **D35** — `toE164()` is delivered by S1.5. S2.1 and S2.2 both use it, unmodified, so a number typed one
  way at signup signs in when typed the other way.
- **D51** — numbers are unique and unverified, and there is no self-service correction. A typo here is
  fixable only by an admin. The duplicate-number copy therefore has to be plain enough that a player who
  fat-fingers their own number understands what happened.
- **D34** — `/register` is in the route list.

Phone confirmation is off, so `signUp` returns a live session in the same call. Nothing in the app may
treat the number as proof of identity.

## Scope

**In**

- The `/#/register` screen: name, mobile number, password, one submit button.
- `toE164` normalisation on submit, and the inline validation that goes with it.
- A length-only password strength hint. Minimum 8 characters, no composition rules.
- The pending-join store — the invite token or event id captured before registration and consumed after —
  including its `localStorage` persistence, because it must survive a cold start.
- Sign-up, then the join RPC, then redirect, as one user-visible action.
- Mapping every sign-up failure to plain copy, duplicate number included.
- The shared "that link isn't working" screen, reused later by [S2.4](S2.4-join-by-link.md) and
  [S2.3](S2.3-password-reset-by-manager.md).

**Out**

- `/#/join/:token` and `/#/event/:id` themselves. They are [S2.4](S2.4-join-by-link.md) and
  [S3.3](S3.3-event-detail-screen.md). S2.1 owns only the store they write into and the screen they send
  the player to.
- Restoring the intended route after auth. That is [S2.5](S2.5-deep-link-return-path.md). S2.1 calls
  `nextRouteAfterAuth()`, which returns `/` until S2.5 replaces its body.
- Any profile edit: no avatar, no position, no date of birth, no second name field. The trigger writes the
  profile row; there is no client write to `profiles` ever.
- Terms, marketing consent, club membership forms. Out of scope in the brief, and out of scope here.
- Email anywhere in the UI. Even if D19 lands on the synthetic-email fallback, the player never sees or
  types an address.
- Rate limiting. That is [S2.2](S2.2-sign-in.md) and D36.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [x] **AC1** — `/#/register` with no pending join and no token in the URL renders the "ask your manager
  for a new link" screen with a **Sign in** button, and no form. It never renders a blank page, a stack
  trace, or a half-usable form.
- [x] **AC2** — Arriving from `/#/join/{token}` or `/#/event/{id}`, the screen names the team: "You're
  joining Firsts". The name comes from `lookup_team_invite` or `get_event_preview`, never from a `teams`
  select.
- [x] **AC3** — The form has exactly three inputs: name, mobile number, password. A DOM assertion counting
  `input` elements inside the form returns 3.
- [x] **AC4** — `087 123 4567`, `0871234567`, `+353 87 123 4567` and `+353871234567` all submit the string
  `+353871234567`. A landline, a short number and free text are refused inline before any network call.
- [x] **AC5** — The mobile field opens a numeric keypad on iOS and Android (`type="tel"`,
  `inputMode="tel"`, `autoComplete="tel"`).
- [x] **AC6** — A password under 8 characters blocks submit with an inline message. At 8 or more, submit is
  enabled whatever the characters are. The strength hint never blocks anything.
- [x] **AC7** — On success the user has a session, exactly one `team_members` row, and a `profiles` row
  carrying the typed name and the normalised number — all without a second screen, a confirmation prompt,
  or a code. From an invite token the row is on the invite's team with the invite's role; from an event id
  it is on the event's team with role `player` (D6). The role is never read from a client argument.
- [x] **AC8** — An already-registered number renders "That number is already registered." with a **Sign
  in** link that carries the number through to the sign-in screen prefilled. No Postgres error text, no
  `duplicate key value violates unique constraint`, no toast with a status code.
- [x] **AC9** — Registering with an expired, revoked or unknown token creates no `team_members` row and
  lands on the "ask your manager for a new link" screen, with the account created and signed in — the
  player is told what to do next, not silently stranded.
- [x] **AC10** — The pending join survives a cold start: set it, kill the tab, reopen `/#/register` from a
  fresh load, and the team name is still shown and the join still happens.
- [x] **AC11** — The pending join is cleared after a successful join, and is ignored and cleared if it is
  older than 24 hours or fails to parse.
- [x] **AC12** — Submitting twice quickly creates one account. The button is disabled while the mutation is
  in flight and shows a pending label.
- [x] **AC13** — If `signUp` resolves with no session — the symptom of phone confirmations being switched
  back on — the screen shows a generic failure with a retry, and the condition is reported to Sentry. It
  never shows a "check your messages" prompt, because no message is ever sent.
- [x] **AC14** — At 375px every control is at least 44px high and the submit button is reachable with one
  thumb. The bottom nav is hidden on this route (D41).

## Implementation notes

Files:

```
src/features/auth/RegisterScreen.tsx      route component for /register
src/features/auth/RegisterForm.tsx        RHF form, three fields
src/features/auth/LinkProblem.tsx         shared dead-link screen (S2.4 and S2.3 reuse it)
src/features/auth/schemas.ts              phoneField, registerSchema, signInSchema (S2.2 imports)
src/features/auth/pendingJoin.ts          the capture/consume store
src/features/auth/passwordHint.ts         pure length-only hint
src/features/auth/afterAuth.ts            nextRouteAfterAuth(); S2.5 replaces the body
src/api/auth.ts                           useRegister(), and later useSignIn()
src/lib/auth.ts                           signUpWithIdentifier / signInWithIdentifier (D19 seam)
```

**The D19 seam.** Every auth call in the app goes through `src/lib/auth.ts`:

```ts
export async function signUpWithIdentifier(
  phoneE164: string,
  password: string,
  name: string,
): Promise<{ session: Session }>

export async function signInWithIdentifier(
  phoneE164: string,
  password: string,
): Promise<{ session: Session }>
```

On the phone path the first is
`supabase.auth.signUp({ phone: phoneE164, password, options: { data: { name } } })`. On the D19 fallback it
is `supabase.auth.signUp({ email: syntheticEmail(phoneE164), password, options: { data: { name, phone: phoneE164 } } })`
where `syntheticEmail('+353871234567') === '353871234567@phibsboro.invalid'`. Nothing outside this file
knows which path is live. Both throw a typed `AuthFailure` (below) rather than leaking the Supabase error.

**Schema.** One phone field, exported once, used by registration, sign-in and nothing else:

```ts
export const phoneField = z
  .string()
  .min(1, 'Mobile number')
  .transform((raw, ctx) => {
    const e164 = toE164(raw)
    if (e164 === null) {
      ctx.addIssue({ code: z.ZodIssueCode.custom, message: "That doesn't look like a mobile number" })
      return z.NEVER
    }
    return e164
  })

export const registerSchema = z.object({
  name: z.string().trim().min(1, 'Your name').max(80),
  phone: phoneField,
  password: z.string().min(8, 'At least 8 characters'),
})
export type RegisterInput = z.input<typeof registerSchema>
export type RegisterValues = z.output<typeof registerSchema>
```

Gotcha: the schema transforms, so input and output types differ. Declare the hook as
`useForm<RegisterInput, unknown, RegisterValues>({ resolver: zodResolver(registerSchema) })`, otherwise
`handleSubmit` hands you the raw string and `noUncheckedIndexedAccess`-grade strictness will not save you.
Do not trim the password; trim the name only.

**Password hint.** Length only, so it is honest and testable:

```ts
export type PasswordHint = 'short' | 'ok' | 'better'
export const passwordHint = (pw: string): PasswordHint =>
  pw.length < 8 ? 'short' : pw.length < 12 ? 'ok' : 'better'
```

Rendered as one line of text under the field — "At least 8 characters" / "That'll do" / "Good". No meter
bar with colours, no zxcvbn dependency, no composition advice.

**Pending join.** The capture point is S2.4 and S3.3; the store is here, because registration is built
first and because it must outlive a browser restart (D1's cold-start requirement applies to this as much
as to the intended route).

```ts
export type PendingJoin =
  | { kind: 'token'; token: string }
  | { kind: 'event'; eventId: string }

export function setPendingJoin(join: PendingJoin): void   // writes { ...join, savedAt: Date.now() }
export function readPendingJoin(): PendingJoin | null     // null if absent, unparseable, or > 24h old
export function clearPendingJoin(): void
```

`localStorage` key `pfc.pendingJoin`, JSON, parsed through a Zod schema inside `readPendingJoin`, wrapped
in try/catch so a full or disabled store degrades to "no pending join" rather than throwing. This is UI
state about the current visit, not server data, so `localStorage` plus a Zustand mirror for the current
render is correct; it never caches a row.

**Team name before auth.** With a token, `supabase.rpc('lookup_team_invite', { p_token })`; with an event
id, `supabase.rpc('get_event_preview', { p_event_id })`. Both are granted to `anon` and both return zero
rows on any failure, so a zero-row result is AC9's dead-link case and is not distinguishable from expiry —
by design. Query keys `teamKeys.lookup(token)` and `eventKeys.preview(eventId)` from S1.5's factory,
`staleTime: 60_000`.

**The mutation.** One mutation, three steps, in `src/api/auth.ts`:

```ts
export function useRegister(): UseMutationResult<{ teamName: string }, AuthFailure, RegisterValues>
```

1. `signUpWithIdentifier(phone, password, name)`. If the result has no session, throw
   `{ kind: 'no_session' }` and `Sentry.captureMessage('signUp returned no session')`.
2. Read the pending join and call the matching RPC — `join_team_by_token(p_token)` or
   `join_team_by_event(p_event_id)`. Retry once on a network error only, never on `invalid_invite`.
3. `clearPendingJoin()`, `queryClient.invalidateQueries({ queryKey: userKeys.current() })`, then
   `navigate(nextRouteAfterAuth(), { replace: true })`.

Step 2 failing after step 1 succeeding is a real state and is specified, not hand-waved: the account
exists and the session is live, so keep them, and render `LinkProblem` with a **Go to home** button rather
than rolling anything back. Deleting a freshly created auth user from the browser is impossible anyway.

**Error mapping.** One pure function, unit tested, so the copy cannot drift:

```ts
export type AuthFailure =
  | { kind: 'duplicate_phone' }
  | { kind: 'invalid_invite' }
  | { kind: 'weak_password' }
  | { kind: 'no_session' }
  | { kind: 'network' }
  | { kind: 'unknown' }

export function mapAuthError(err: unknown): AuthFailure
```

`duplicate_phone` covers all three shapes the platform can produce: a GoTrue `AuthApiError` with status
422 and code `phone_exists` or `user_already_exists`, an email-path `email_exists` on the D19 fallback, and
a Postgres `23505` on `profiles_phone_key` raised by the S1.2 trigger. All three render one sentence:

> That number is already registered. **Sign in**

The link is `navigate('/login', { state: { phone } })` so S2.2 can prefill (see
[S2.2](S2.2-sign-in.md)). `invalid_invite` renders `LinkProblem`. Everything else renders an inline line
above the button with the button still enabled: "Couldn't create your account. Try again."

**Route guard.** `/register` is public, and `RegisterScreen` redirects a user who already has a session to
`nextRouteAfterAuth()` — a signed-in player who taps a join link should be joined without re-authenticating
(S2.4), not shown a signup form. The redirect uses `replace` so back does not bounce.

**Layout.** Full-screen route, bottom nav hidden (D41), a back affordance only when there is history to go
back to. Labels above inputs, not placeholders-as-labels. `autoComplete`: `name`, `tel`, `new-password`.
The submit button is full width, `min-h-tap`, pinned at the end of the form flow so it sits under the thumb
at 375px.

## Open questions

1. **What if D19 lands on the email fallback and a player later needs their number corrected?**
   `set_member_phone` (D51) updates `auth.users.phone` and `profiles.phone`; on the fallback it must also
   rewrite the synthetic address. Proposed default: the RPC derives the address from the number, so a
   correction rewrites both columns in the same transaction. Flagged to
   [S6.4](S6.4-member-administration.md); no change here.
2. **Non-Irish numbers.** Proposed default: any valid E.164 is accepted. `+353` is assumed only for a bare
   `08…`. A player with a UK number types `+44…` and it works.
3. **Duplicate names in a squad — two players called John Byrne.** Proposed default: allowed, no check, no
   disambiguation. Managers know which is which, and a uniqueness rule on names would fail registration for
   the wrong reason.
4. **Should the number field render a country-code selector?** Proposed default: no. One plain field,
   `+353` assumed. A selector is a fourth control on a three-field screen.

## Build notes — deviations from this spec

| Spec said | Built as | Why |
|---|---|---|

| `AuthFailure` is a bare discriminated-union type | `AuthFailure` is an `Error` subclass with a `kind` discriminant, mirroring the existing `AppError` | `@typescript-eslint/only-throw-error` (strict) forbids throwing a plain object, and the mutation must throw its failure. The class carries the same `.kind` the spec branches on, and keeps the original error on `.cause` for Sentry. |
| `useRegister`'s step 3 navigates | `useRegister` does `clearPendingJoin()` + invalidate on success; the **component** navigates in its `mutate({ onSuccess })` | `navigate` is a hook; a query hook cannot call it. | `signInWithIdentifier` throws `no_session` when the session is absent | It does not — `signInWithPassword` types `data.session` as non-null on success, so the guard is dead code (lint flags it). `signUpWithIdentifier` keeps the `no_session` throw, where `data.session` is `Session \| null`. | Honest to the platform types; the AC13 no-session path is a sign-**up** symptom only. |
| A dead token before submit still shows the form so the account is created (AC9 "account created") | A lookup that resolves to null (dead token at load) shows `LinkProblem` **before** the form, creating no account; the "account created then LinkProblem" state is reached only by the revoked-between-lookup-and-join race, which the mutation's `invalid_invite → onDeadLink` branch handles. | `lookup_team_invite`/`get_event_preview` validate the same conditions the join RPC does, so an already-dead token would only waste a registration. Both paths satisfy AC9's binding outcome: no `team_members` row, land on `LinkProblem`, not stranded. |
| The pending-join store keeps a Zustand mirror for the current render | `localStorage` only; `RegisterScreen` reads it once via a `useState` initializer | No AC needs cross-component reactivity — the join does not change during a visit. `localStorage` remains the single source of truth for cold-start survival (AC10). |

### Verification notes
