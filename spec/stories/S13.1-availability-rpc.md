## Goal
The database can tell a team member who is available for one of their events — the available members' names
plus the availability counts — without ever revealing who declined or has not answered.

## Context
[W3/W4](../00-decisions-v1.2.0.md). `CLAUDE.md` makes RLS the enforcement layer, so "who's in" cannot be a
relaxed SELECT policy plus UI hiding — that leaves who-declined readable over the API. Instead a
`SECURITY DEFINER` RPC returns exactly the player-visible slice. The counts reuse S4.3's derivation (squad =
`team_members`, awaiting = squad − responded). See [data-model-v1.2.0.md](../data-model-v1.2.0.md).

## Scope
**In**
- `event_availability(p_event_id uuid)` returning one row: `available_names text[]`, `available_count`,
  `unavailable_count`, `awaiting_count`, `squad_size` (data-model-v1.2.0).
- `SECURITY DEFINER`, `set search_path = ''`, `revoke ... from public, anon; grant ... to authenticated`.
- Guards: event exists, its team is active, and `is_team_member(event.team_id)` — otherwise returns no rows
  (never an error, per S1.3).
- Returns available **names only**; unavailable/awaiting produce **counts only**, never names or ids.
- The `event_responses` SELECT policy is unchanged — a player still cannot read another player's row directly.
- RLS suite rows (S1.4 grows): a member gets the available names + correct counts; a non-member and anon get
  nothing; the function leaks no decliner/awaiting name for any input.

**Out**
- Any UI (S13.2).
- Attendance (past) visibility — this is upcoming availability only.
- A manager-facing change — managers already have the full breakdown (S4.3/S4.4), untouched.

## Acceptance criteria
- [ ] **AC1** — A team member calling `event_availability` for an event of their team gets the names of those
  who responded Available, and the four counts, with `awaiting = squad_size − available − unavailable`.
- [ ] **AC2** — The result never contains the name or id of anyone Unavailable or Awaiting (assert the array
  holds only available members, and no other identity field is returned).
- [ ] **AC3** — A non-member of the team, and anon, get no rows (not an error).
- [ ] **AC4** — Counts match S4.3's manager view for the same event (same squad denominator).
- [ ] **AC5** — A cancelled or unknown event returns no rows.
- [ ] **AC6** — The `event_responses` SELECT policy is unchanged (a player reading `event_responses` directly
  still sees only their own row) — asserted by the existing S1.4 rows still passing.

## Implementation notes
- SQL `language sql`; join `team_members` (denominator) to `event_responses` (this event) left-outer, count
  by response; aggregate available names with `array_agg(p.name order by p.name)` filtered to `available`.
- Names from `profiles`. Order the names (e.g. by name) so the UI list is stable.
- Add the RPC in a new migration; regenerate `src/lib/database.types.ts` (the return type appears under
  `Functions`).

## Data and API surface
New RPC `event_availability`. No table/column change; no policy change. A Zod schema for the RPC return in
S13.2, or here if convenient.

## UI states
Not a UI story.

## Test plan
- **Unit** — none (pure SQL; the count logic is asserted via RLS).
- **Integration / RLS** — AC1–AC6 as member / non-member / anon; a fixture event with a known mix of
  available/unavailable/awaiting so the counts and the names are exact.
- **E2E** — none.
- **Manual** — none.
