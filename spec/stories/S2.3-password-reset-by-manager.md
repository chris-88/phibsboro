## Goal

A player who has forgotten their password messages the manager. The manager opens the squad's member list,
taps **Reset password** on that player's row, copies a link, and pastes it into WhatsApp. The player taps
it, types a new password, and is signed in. No SMS, no email, no admin console, no SQL. This is the only
recovery path in the product.

## Context

`CLAUDE.md` S2.3 opens with "Managers and admins issue a one-time reset link for a member of their team"
and closes with "Managers can only reset players on teams they manage". Those are two different rules, and
the wider one lets a manager take over a co-manager's or an admin's account. The decision record settles
it; this story implements the narrow rule and nothing wider.

Decisions this story is built on, in [00-decisions.md](../00-decisions.md):

- **D10** — a manager may reset only a user who holds `role = 'player'` on a team they manage, who holds
  no `manager` role on **any** team, and who is not an admin. Only an admin may reset a manager. Nobody
  resets an admin through the app; that is a SQL job. Enforced in `issue_reset_token`, not in the UI. The
  UI hides the action for the same reasons, and says so as convenience only.
- **D11** — redemption happens in Postgres. `redeem_reset_token(p_token, p_new_password)` is
  security-definer, writes `crypt(p_new_password, gen_salt('bf'))` to `auth.users.encrypted_password`,
  marks `used_at`, revokes the user's other live tokens, deletes their refresh tokens, and returns the
  user's phone. There is no Edge Function and no service-role key anywhere near the browser.
- **D27** — `reset_tokens` carries `revoked_at`, `issued_at` and `team_id`. Issuing revokes every live
  token for that user in the same transaction, which is how "issuing a new link invalidates any previous
  one" is actually true rather than merely stated.
- **D5, D62** — the token is 32 bytes from `gen_random_bytes(32)`, base64url, generated inside the RPC,
  stored in plaintext in a table no client can select, and never logged, never sent to Sentry, never put
  in a query string the app constructs. Sentry truncates anything after `/#/reset/` (D16).
- **D34** — the reset link is `/#/reset/{token}` and the route is in the S0.3 list.
- **D19** — sign-in after redemption goes through `signInWithIdentifier` in `src/lib/auth.ts`.

Both halves of the RPC contract already exist when this story starts: S1.3 writes the functions and S1.4
tests them. S2.3 is the two screens and the plumbing between them.

## Scope

**In**

- The **Reset password** action mounted into the row-action slot [S6.4](S6.4-member-administration.md)
  leaves on each member card, and the dialog it opens. This story owns the whole issuing half: the
  predicate, the component, the dialog, the copy and the mutation. S6.4 owns none of it.
- `useIssueResetToken()` in `src/api/reset.ts`, calling `issue_reset_token(p_user_id, p_team_id)`.
- Copying the link to the clipboard with `copyText()` from `src/lib/clipboard.ts`
  ([S6.2](S6.2-team-join-links.md)), and the fallback when the clipboard API is unavailable. The link
  itself comes from `resetUrl()` in `src/lib/paths.ts` ([S0.3](S0.3-routing.md)).
- The `/#/reset/:token` set-password screen: one password field, submit, redeem, sign in, land home.
- Mapping `not_authorised` and `invalid_token` to plain copy.
- Hiding the action for targets a manager may not reset — convenience only, mirroring the RPC rule.

**Out**

- The member list itself, its query, its cards and its other row actions. Those are
  [S6.4](S6.4-member-administration.md), built first. This story adds one action component into the slot
  S6.4 leaves.
- Sending anything. No `wa.me`, no `navigator.share()`, no message template. The manager copies a link and
  pastes it themselves. Share is [S5.2](S5.2-share-action.md) and is for events, not for credentials — a
  reset link in a group chat would be an account handed to twenty people.
- Self-service reset of any kind. See [S2.2](S2.2-sign-in.md).
- Resetting an admin, and granting or revoking roles. D2 and D9.
- Changing a member's phone number. That is `set_member_phone`, admin-only, owned by
  [S6.4](S6.4-member-administration.md) (D51).
- Any new table, column or RPC. Everything this story calls is delivered by
  [S1.3](S1.3-rls-policies-and-rpcs.md).

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — A manager viewing their own team's member list sees **Reset password** on the row of a
  player, and does not see it on the row of a co-manager or of an admin.
- [ ] **AC2** — The rule is enforced in `issue_reset_token`, not the screen: a manager calling the RPC
  directly with a co-manager's or an admin's `user_id` gets `not_authorised` and no row is written. Covered
  by [S1.4](S1.4-rls-test-suite.md); this story asserts the UI renders that error as "You can't reset that
  person." rather than a raw Postgres message.
- [ ] **AC3** — An admin sees the action on every row except another admin's, and may reset a manager.
- [ ] **AC4** — Issuing returns a dialog showing the full link, `resetUrl(token)`, a **Copy link** button, and one line stating what it is: "One
  use. Expires in 24 hours. Send it to {name} on WhatsApp."
- [ ] **AC5** — **Copy link** calls `copyText()` from `src/lib/clipboard.ts` and puts the exact URL on the
  clipboard. Where `copyText()` returns false, the URL is shown in a read-only input, pre-selected, with
  "Copy this link" above it. The dialog is never a dead end, and no second clipboard routine is written.
- [ ] **AC6** — The dialog states that the link is shown once, and that closing it means issuing a new one.
  There is no re-copy path for a reset token: `reset_tokens` is not selectable and no lookup RPC exists, by
  design.
- [ ] **AC7** — Issuing a second link for the same player invalidates the first. Redeeming the first then
  fails with the same opaque error as an unknown token.
- [ ] **AC8** — The issued token is scoped to one user, usable once, and dead after 24 hours. The
  integration test asserts the new `reset_tokens` row has that `user_id` and that `team_id`, `used_at` and
  `revoked_at` null, and `expires_at` within a minute of `issued_at + interval '24 hours'`; that redeeming
  it a second time raises `invalid_token`; and that a row backdated past its expiry raises the same.
- [ ] **AC9** — `/#/reset/{token}` renders a set-password screen for a signed-out visitor, for a
  signed-in visitor, and for a visitor signed in as somebody else. The token is not validated before
  submit, because no lookup RPC exists for it; the screen says nothing about the link's state until the
  player tries it.
- [ ] **AC10** — A password under 8 characters blocks submit inline. The same `passwordHint` line from
  [S2.1](S2.1-registration.md) appears, and blocks nothing at 8 or more. The password is never trimmed.
- [ ] **AC11** — On success the player holds a session for **their own** account, whatever session existed
  in that browser beforehand, and lands on `nextRouteAfterAuth()` with a "Password changed." confirmation.
- [ ] **AC12** — A used, expired, revoked or unknown token all produce the identical screen: "That link's
  expired or already been used. Ask your manager for a new one.", with a **Sign in** button. Nothing
  distinguishes the four cases, in the UI or in anything the app logs.
- [ ] **AC13** — The old password no longer works after redemption, and the new one does. Checked against
  the local stack.
- [ ] **AC14** — Redemption deletes the target's refresh tokens, so a session open on another device stops
  working at its next refresh. Asserted in the integration test, whatever the UI chooses to say.
- [ ] **AC15** — The token never appears in a Sentry event, a breadcrumb, a console line, or a
  `document.title`. A test drives the redeem screen with a stubbed Sentry transport and asserts no captured
  payload contains the token string.
- [ ] **AC16** — At 375px every control in the dialog and on the reset screen is at least 44px high, and
  the reset screen hides the bottom nav (D41).

## Implementation notes

Files:

```
src/features/auth/ResetPasswordScreen.tsx    route component for /reset/:token
src/features/teams/IssueResetLinkAction.tsx  the member-row button and its dialog
src/api/reset.ts                             useIssueResetToken(), useRedeemResetToken()
src/features/auth/schemas.ts                 setPasswordSchema added beside registerSchema
```

**The manager half.** S6.4 renders member cards and leaves a row-action slot; this story mounts
`<IssueResetLinkAction teamId={teamId} member={member} />` into it. The component renders nothing when
`canIssueReset(member, currentUser)` is false — a pure predicate in `src/features/teams/` that mirrors D10:

```ts
export function canIssueReset(
  member: { userId: string; role: MemberRole; isManagerElsewhere: boolean; isAdmin: boolean },
  viewer: { isAdmin: boolean; managesThisTeam: boolean },
): boolean
```

Admins: true unless the target is an admin. Managers: true only when `managesThisTeam` and the target's
role on this team is `player` and `isManagerElsewhere` is false and `isAdmin` is false. `isManagerElsewhere`
and `isAdmin` come from the fields S6.4's directory read already exposes; if it does not expose them,
default the predicate to false for managers and let the RPC be the rule — the UI is convenience, never the
boundary, and it is better for a manager to see one action that fails cleanly than for the screen to
invent authority.

```ts
export type ResetFailure =
  | { kind: 'not_authorised' }   // issue_reset_token raised not_authorised (D10)
  | { kind: 'invalid_token' }    // redeem_reset_token raised invalid_token — unknown, used, revoked, expired
  | { kind: 'network' }
  | { kind: 'unknown' }

export function mapResetError(err: PostgrestError | unknown): ResetFailure

export function useIssueResetToken(): UseMutationResult<
  { token: string },
  ResetFailure,
  { teamId: string; userId: string }
>
```

`mapResetError` reads the Postgres error message the RPC raised, matches the two literal strings above,
and falls through to `network` on a fetch failure and `unknown` otherwise. It is the only place either
string appears, and it is unit tested, so the two copy lines below cannot drift.

Calls `supabase.rpc('issue_reset_token', { p_user_id, p_team_id })`. No query invalidation — nothing the
client can read changes. `not_authorised` maps to "You can't reset that person."; anything else to
"Couldn't create a link. Try again." with the button enabled.

**The link.** This story builds no URL. `resetUrl(token)` is already exported from `src/lib/paths.ts`
([S0.3](S0.3-routing.md)), the one file under `src/` permitted to contain the literal `/#/` (S0.3 AC8) and
the one place `VITE_APP_BASE_URL` is turned into an absolute link. Import it:

```ts
import { resetUrl } from '@/lib/paths'
```

No string building at the call site, no second module, no `src/lib/urls.ts`.

**Clipboard.** `await copyText(url)` from `src/lib/clipboard.ts` inside the button's click handler, so the user
gesture is intact; it needs a secure context, which the deployed site and `vite preview` both are. Catch
and fall back to the read-only input with `select()` called on mount. Show a transient "Copied" label on
the button for two seconds. Do not auto-copy on dialog open — Safari refuses a clipboard write that is not
directly in a gesture.

**The player half.** `ResetPasswordScreen` reads `:token` from the route params and renders the form
immediately:

```ts
export const setPasswordSchema = z.object({
  password: z.string().min(8, 'At least 8 characters'),
})
```

No `.trim()`. Trimming a password silently changes it and then the sign-in that follows fails for a reason
nobody can see.

```ts
export function useRedeemResetToken(): UseMutationResult<void, ResetFailure, { token: string; password: string }>
```

1. `const { data: phone } = await supabase.rpc('redeem_reset_token', { p_token: token, p_new_password: password })`
2. `await signInWithIdentifier(toE164(phone) ?? phone, password)` — the same helper S2.1 and S2.2 use
   (D19). The normalise is not decoration: the RPC reads `auth.users.phone`, which Supabase stores
   **without** the leading `+` (D35), while every other caller of `signInWithIdentifier` passes full
   E.164. Sending the bare `353871234567` signs nobody in on the phone path, and on the D19 fallback
   derives the wrong synthetic address. If `toE164` returns null, throw `invalid_token` rather than
   guessing.
3. `queryClient.invalidateQueries({ queryKey: userKeys.current() })`, then
   `navigate(nextRouteAfterAuth(), { replace: true })` and a "Password changed." toast.

Do not sign the existing session out before step 1. If the redeem fails, an unrelated user has been signed
out for nothing. Step 2 replaces the session anyway, and the server has already killed the target's other
refresh tokens.

The RPC raises `invalid_token` for unknown, used, revoked and expired alike, so the client has one branch:
render the shared `LinkProblem` screen from [S2.1](S2.1-registration.md) with the AC12 copy. The
`replace: true` on the post-success navigate matters here beyond tidiness — Back must not return to a URL
containing a spent token.

**Grant check before building.** The data model lists `redeem_reset_token` as granted to `anon`. A player
who is still signed in on that handset calls it as `authenticated`, which would fail on the grant. The
grant must include both roles. That is a one-line addition to [S1.3](S1.3-rls-policies-and-rpcs.md) and a
test in [S1.4](S1.4-rls-test-suite.md); it is raised as open question 1 below rather than silently
assumed.

**Copy, in full**, so nobody writes their own:

correction inside S1.3's migration set, not here.

## Test plan

- **Unit** — `resetUrl` is [S0.3](S0.3-routing.md)'s and tested there. This story asserts that the token is not
  URL-encoded twice; `canIssueReset` over the full D10 truth table (manager→player, manager→co-manager,
  manager→admin, manager→player-who-manages-another-team, admin→manager, admin→admin); `mapResetError`
  turning `not_authorised` and `invalid_token` into their two copy strings, and an unrecognised
  Postgres error into `unknown`; the Sentry stub assertion in AC15.
- **Integration / RLS** — against the local Supabase stack: a manager issues for a player on their team and
  gets a 43-character base64url token whose row carries that `user_id`, that `team_id`, null `used_at` and
  `revoked_at`, and `expires_at` 24 hours after `issued_at` (AC8); the same manager is refused for a
  co-manager and for an admin;
  issuing twice leaves exactly one live row and the first token then fails to redeem; redeeming marks
  `used_at` and returns the phone in whatever form `auth.users.phone` holds, and the test asserts the
  client's `toE164` normalise makes the following `signInWithIdentifier` succeed; redeeming the same token
  twice fails the second time; an expired row
  fails; after redemption the old password fails `signInWithPassword` and the new one succeeds; the
  target's `auth.refresh_tokens` rows are gone. The negative authorisation cases are owned by
  [S1.4](S1.4-rls-test-suite.md) and asserted again here only at the boundary the UI touches.
- **E2E** — Playwright: manager signs in, opens the member list, issues a link, reads it from the dialog,
  a second browser context opens `/#/reset/{token}`, sets a password, lands signed in as that player;
  reloading the same URL afterwards shows the dead-link screen.
- **Manual** — On a real phone: **Copy link** works in mobile Safari and in Chrome, the pasted link opens
  correctly from WhatsApp, and the reset screen is usable with a password manager offering to save the new
  password.

## Open questions

1. **Is `redeem_reset_token` granted to `authenticated` as well as `anon`?** The data model lists `anon`
   only, and a player tapping the link on a handset with a live session calls it as `authenticated`.
   Proposed default: grant to both, as a one-line correction in
   [S1.3](S1.3-rls-policies-and-rpcs.md) with a matching S1.4 test. The alternative — signing the visitor
   out before redeeming — logs out an unrelated user on a failure and is worse.
2. **Should the success screen say "you've been signed out on your other devices"?** It is true (D11) and
   it is the kind of thing a player notices later. Proposed default: do not say it. One extra sentence on
   a screen whose job is to finish, and the case is rare. Revisit if anyone asks why their tablet logged
   out.
3. **Should a manager be able to see that a live reset link exists for a player?** `reset_tokens` is not
   selectable and adding a "reset pending" indicator means a new read RPC. Proposed default: no. Issuing
   again is cheap and revokes the old one, so a manager who is unsure just issues another.
4. **Expiry — 24 hours.** Proposed default: as specified by the brief and D27. If players routinely miss
   it, the fix is the manager issuing a fresh link, not a longer-lived credential.
