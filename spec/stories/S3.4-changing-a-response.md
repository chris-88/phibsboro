## Goal

A player who said Yes on Tuesday and pulls a hamstring on Thursday changes the answer to No, and the
manager's counts follow. The moment the event kicks off, the buttons stop working and the screen says why,
instead of accepting a tap and losing it.

## Context

The brief's S3.4 is three lines: players may change their answer until `starts_at`, after `starts_at` the
controls are disabled with an explanatory line, and the rule is enforced in the database, not only the UI.

Two of those three are already owned elsewhere, which leaves this story small and sharp.

The **database half** is [S1.3](S1.3-rls-policies-and-rpcs.md). [D12](../00-decisions.md) moved it there
deliberately: the player INSERT and UPDATE policies on `event_responses` carry
`WITH CHECK (user_id = auth.uid() AND EXISTS (SELECT 1 FROM public.events e WHERE e.id = event_id AND
e.status = 'scheduled' AND e.starts_at > now() AND public.is_team_member(e.team_id)))`, and S1.4 proves it
with four tests. A rule discovered in Epic 3 that belonged in the blocking gate is a rule that shipped.
S3.4 adds no enforcement and must not weaken any of it.

The **change itself** — switching between the two answers, the optimistic write, the rollback, the "tap
the same answer twice" no-op — is already built. [S3.3](S3.3-event-detail-screen.md) comes first in the
build order ([D20](../00-decisions.md), position 19 against this story's 24) and owns
`useSetResponse`, `AvailabilityButtons`, and the `serverNow()` clock. S3.3's own scope line says so: "The
after-`starts_at` disabled state and its explanatory copy — S3.4."

So this story owns exactly the closed window: deciding it, rendering it, closing it on screen at kick-off
without a reload, and making a server refusal land on the right state rather than a generic failure line.
It also lifts the cancelled case out of S3.3's hardcoded string into the same decision function, so S3.1's
next-event card and S3.3's detail screen cannot drift apart.

Decisions relied on:

- [D12](../00-decisions.md) — the cut-off is an RLS `WITH CHECK`, owned and tested by S1.3 and S1.4.
- [D48](../00-decisions.md) — the optimistic contract, and the requirement that the disabled state be
  computed against a server timestamp fetched with the event, never the device clock. No offline queue.
- [D61](../00-decisions.md) — a response cannot be cleared. Tapping the current answer is a no-op and no
  deselect affordance exists. Clients have no DELETE on `event_responses`.
- [D60](../00-decisions.md) — a cancelled event reads "This one's off." with the controls disabled.
- [D22](../00-decisions.md) — managers are squad members and respond through the same control. No role
  branch anywhere in this feature.
- [D35](../00-decisions.md) — every date on screen comes from `formatEventTime()`.

## Scope

**In**

- `responseWindow()`, one pure function deciding open or shut, why, and what line to render.
- `useResponseWindow()`, which feeds it `serverNow()` and re-evaluates it at kick-off.
- The started copy, and the move of the cancelled copy into the same function.
- Wiring `disabled` and `disabledReason` on `AvailabilityButtons` at both current call sites.
- One edit to `useSetResponse`'s `onError`: a `42501` refusal settles the screen into the closed state
  instead of showing "Couldn't save. Tap again."
- One added case in S1.4's existing `event_responses` suite: a genuine change, available → unavailable,
  on a scheduled future event.

**Out**

- The RLS policy. S1.3 writes it, S1.4 proves it. Not touched here.
- `AvailabilityButtons`, `useSetResponse` and `serverNow()` as artifacts — S3.3 created them
  and this story extends them in place. No fork, no second component.
- The event detail screen's layout, preview, join button and 404 — S3.3.
- The next-event card and the upcoming list that will consume this — S3.1 and S3.2.
- Manager counts and the response list — S4.3 and S4.4. This story only leaves S3.3's `eventKeys.all`
  invalidation alone, which already covers them ([D23](../00-decisions.md)).
- Any way back to awaiting (D61), any offline or retry queue (D48), any nudge at a non-responder (S5.3).

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [x] **AC1** — On a scheduled event whose `starts_at` is in the future, a player holding `available` taps
      NO and the row's `response` becomes `unavailable` with `updated_at` advanced. The reverse also works.
      Exactly one row exists for `(event_id, user_id)` throughout.
- [x] **AC2** — Tapping the currently selected answer fires no request and writes no cache. No control on
      any screen returns the player to awaiting.
- [x] **AC3** — The current answer survives a reload and is unmistakable: the selected button is
      `variant="default"` with `aria-pressed="true"`, the other `variant="outline"` with
      `aria-pressed="false"`.
- [x] **AC4** — On a scheduled event whose `starts_at` has passed, both buttons are `disabled` and the line
      "Too late now. This started {short}." is rendered beneath them, where `{short}` is
      `formatEventTime(starts_at, 'short')` — for example "Too late now. This started Sat 14 Mar, 7.30pm."
- [x] **AC5** — On a cancelled event, whatever its `starts_at`, both buttons are `disabled` and the line
      reads "This one's off." ([D60](../00-decisions.md)). Cancelled beats started: exactly one line is
      ever rendered, and on a cancelled past event it is this one.
- [x] **AC6** — At exactly `starts_at` the window is shut. `responseWindow()` compares with `<=`, matching
      the policy's `starts_at > now()`, so the UI never offers a tap the database would refuse.
- [x] **AC7** — The decision uses `serverNow()`, not `Date.now()`. With the device clock set ten minutes
      fast, an event starting in five minutes still accepts a response; with it ten minutes slow, an event
      that started two minutes ago is already disabled.
- [x] **AC8** — A player sitting on the screen when `starts_at` passes sees the buttons disable themselves
      and the AC4 line appear, with no reload and no tap, within two seconds of kick-off.
- [x] **AC9** — When the write is refused with Postgres code `42501`, `useSetResponse().showRetryLine`
      is `false`, so the inline "Couldn't save. Tap again." line is **not** shown. The optimistic patch is
      rolled back, the event is refetched, and the screen settles into the AC4 or AC5 state.
- [x] **AC10** — Any other failure still behaves as S3.3 specified: `showRetryLine` is `true`, the
      previous answer is restored, both buttons stay enabled, "Couldn't save. Tap again." renders in the
      `aria-live="polite"` region, and the next successful write clears it.
- [x] **AC11** — Bypassing the UI does not bypass the rule. A signed-in player upserting directly against a
      past event, a cancelled event or another team's event is refused, and a DELETE affects zero rows —
      the four S1.4 cases from D12, unmodified and still green.
- [x] **AC12** — Both buttons are at least 44px high at 375px ([D40](../00-decisions.md)) and the disabled
      line does not push either under the page fold on an iPhone SE.
- [x] **AC13** — `responseWindow()` is the only place in `src/` that decides whether a response may be
      taken. S3.3's hardcoded `disabledReason="This one's off."` is removed as part of this story. S3.3's
      `CancelledBanner` above the title (its AC14) is untouched and still renders.

### The decision

```ts
// src/features/availability/response-window.ts
import type { Database } from '@/lib/database.types'
import { formatEventTime } from '@/lib/time'

type EventStatus = Enums<'event_status'>

export type ResponseWindow =
  | { open: true }
  | { open: false; reason: 'cancelled' | 'started'; message: string }

export function responseWindow(
  event: { status: EventStatus; starts_at: string },
  now: Date,
): ResponseWindow
```

Three rules, in this order:

1. `event.status === 'cancelled'` → `{ open: false, reason: 'cancelled', message: "This one's off." }`
2. `Date.parse(event.starts_at) <= now.getTime()` → `{ open: false, reason: 'started' }` with the
   message `Too late now. This started {short}.`, where `{short}` is
   `formatEventTime(event.starts_at, 'short')`
3. otherwise `{ open: true }`

Cancelled first, so a cancelled past event reads "This one's off." and not both lines (AC5). The comparison
is `<=` because the policy is `>` (AC6). The function takes `now` as an argument and reads no clock of its
own, so the truth table is a plain Vitest fixture with no fake timers, and the copy is asserted in the same
test as the decision that produces it.

### Closing the window on screen

```ts
// src/features/availability/use-response-window.ts
export function useResponseWindow(
  event: { status: EventStatus; starts_at: string },
): ResponseWindow
```

It calls `responseWindow(event, serverNow())` on every render — `serverNow()` from S3.3's
`src/lib/serverClock.ts`, which is `Date.now()` plus the skew captured from the `Date` response header of
every PostgREST call. No polling. In one `useEffect` keyed on `event.starts_at` and `event.status`, compute
`delta = Date.parse(event.starts_at) - serverNow().getTime() + 1000` and, when `0 < delta <= 6 * 60 * 60 *
1000`, arm a single `setTimeout` that bumps a `useState` counter. That re-render re-reads `serverNow()`,
which has now passed `starts_at`, and the window flips (AC8). Clear the timeout on unmount and on a change
of either key. Outside the six-hour clamp, arm nothing: the app will have been backgrounded and S3.3's
refetch-on-focus re-arms it with a fresh skew.

`Date.now()` appears in this feature only inside `serverNow()`'s own module, which S3.3 owns. The elapsed
interval is measured by `setTimeout`, not by re-reading a wall clock, so a device clock that is wrong by
ten minutes shifts nothing.

### Wiring the existing control

`AvailabilityButtons` already takes `disabled?: boolean` and `disabledReason?: string`. Every call site
becomes one line, so S3.1's card and S3.3's screen cannot disagree:

```tsx
const responseState = useResponseWindow(event)   // not `window` — do not shadow the global
<AvailabilityButtons
  eventId={event.id}
  current={myResponse}
  disabled={!responseState.open}
  disabledReason={responseState.open ? undefined : responseState.message}
/>
```

Delete S3.3's hardcoded cancelled string at the same time (AC13). The component itself is unchanged: it
still renders `disabledReason` beneath the grid in the existing `aria-live="polite"` region, and still
returns early when the tapped value equals `current` (D61). Add one guard inside it for defence in depth —
return early when `disabled` — so a stray tap on a disabled button in a browser that mishandles
`pointer-events` still fires nothing.

### The refusal path

S3.3's `useSetResponse` has `onError` restore the snapshots and let the component show "Couldn't save. Tap
again." That is right for a dropped connection and wrong for the one error this story exists to handle: a
`42501` from the D12 `WITH CHECK` means the window shut between render and tap — a stale screen, not a
retryable failure, and "Tap again." would be a lie.

Amend `onError`:

```ts
onError: (error, vars, context) => {
  restore(context)                                   // unchanged
  if (error.code === '42501') {                      // new row violates row-level security policy
    queryClient.invalidateQueries({ queryKey: eventKeys.all })
    return                                           // swallow: the refetch produces the correct screen
  }
  // fall through: showRetryLine below drives the inline line, buttons stay enabled
}
```

Swallowing means the component must not key its inline line on `mutation.isError` alone once this lands.
The distinction is made once, in `src/api/availability.ts`, and never in a component:

```ts
export type SetResponseMutation =
  UseMutationResult<void, PostgrestError, SetResponseVars> & { showRetryLine: boolean }

export function useSetResponse(): SetResponseMutation {
  const mutation = useMutation({ /* unchanged */ })
  // a 42501 is a stale screen, not a retryable failure, so it never shows the line
  return { ...mutation, showRetryLine: mutation.isError && mutation.error.code !== '42501' }
}
```

`AvailabilityButtons` renders "Couldn't save. Tap again." on `showRetryLine`, not on `isError`. That is
the only change to S3.3's component beyond the `disabled` guard above, and the exported hook keeps its
existing mutation surface, so no other call site changes.

`onSettled` is unchanged and still invalidates `eventKeys.all`, which is the prefix S4.3's counts key sits
under (AC in S4.3, [D23](../00-decisions.md)).

### Gotchas

- Do not disable the buttons while the mutation is pending. The optimistic patch already shows the new
  state, and disabling produces a dead-feeling double tap on a slow connection.
- Do not send `updated_at` from the client. The `before update` trigger maintains it, and a client value
  would make AC1 unverifiable.
- `serverNow()`'s skew is zero until the first PostgREST response lands. Nothing on the event screen is
  decided before the event query resolves, so this is harmless — but do not call `useResponseWindow` with
  a placeholder event during loading. Render the skeleton instead.
- A manager viewing their own team's event uses this same control (D22). There is no role branch.

## Test plan

- **Unit** — `responseWindow()` in Vitest, fixed UTC instants, `TZ=UTC` pinned in `vitest.config.ts`
  ([D53](../00-decisions.md)): scheduled one second before `starts_at` → open; exactly at `starts_at` →
  `started`; one second after → `started`; cancelled and future → `cancelled`; cancelled and past →
  `cancelled`, proving precedence; and the `started` message asserted verbatim against a known instant, so
  the copy and `formatEventTime(…, 'short')` are both covered. Then `useResponseWindow` with
  `vi.useFakeTimers()` and a stubbed `serverNow`: mount on an event five seconds out, advance six seconds,
  assert the returned window flips to `started` with no refetch; assert no timer is armed when
  `starts_at` is eight hours away. Then `useSetResponse`'s `onError` with a stubbed client: a `42501`
  rejection rolls back, invalidates `eventKeys.all` and leaves `showRetryLine` false; a network rejection
  rolls back and sets `showRetryLine` true.
- **Integration / RLS** — the four D12 cases in S1.4's `tests/rls/event-responses.test.ts` must still pass
  untouched: respond before start succeeds, after `starts_at` refused, on a cancelled event refused, DELETE
  refused. This story adds a fifth to the same file: as a seeded player, upsert `available`, then upsert
  `unavailable`, on a scheduled future event — both succeed, exactly one row exists, `response` is
  `unavailable`, and the second `updated_at` is strictly greater than the first.
- **E2E** — `tests/e2e/change-response.spec.ts` against the seeded local stack via `vite preview`
  ([D17](../00-decisions.md), `timezoneId: 'Europe/Dublin'`): sign in as a seeded player; open the seeded
  scheduled event; tap YES; assert pressed; tap NO; reload; assert NO still pressed and YES not. Then open
  the seeded past event — assert both buttons disabled and the started line; and the seeded cancelled
  event — assert both disabled and "This one's off.". The seed provides a past and a cancelled event per
  team for exactly this ([D3](../00-decisions.md), [D15](../00-decisions.md)).
- **Manual** — on a real phone, set the system clock ten minutes fast and open an event starting in five
  minutes: the buttons must still work, and the tap must succeed. Set it ten minutes slow on an event that
  started two minutes ago: the buttons must already be disabled. Then sit on an event starting in under a
  minute and watch the control disable itself without touching the screen.

## Open questions

1. **Is the `Date` response header actually readable?** S3.3's `serverNow()` reads
   `res.headers.get('Date')` from the Supabase fetch wrapper, but `Date` is not a CORS-safelisted response
   header, so it is only visible if Supabase sends `Access-Control-Expose-Headers` including it. **Proposed
   default:** verify it against the local stack on the first day of this story with a one-line console
   check. If it is null, fall back to a PostgREST computed column, which needs no CORS cooperation and is a
   six-line forward-only migration — `create function public.server_now(public.events) returns timestamptz
   language sql stable set search_path = '' as $$ select now() $$;`, granted to `authenticated`, selected as
   an extra field on S3.3's `EVENT_SELECT` and passed into `responseWindow()` instead of `serverNow()`. The
   pure function does not change either way; only its second argument does.
2. **Should an uncancelled event reopen?** **Proposed default:** yes, with no special handling. S4.2
   restoring `status = 'scheduled'` reopens the D12 policy on its own provided `starts_at` is still ahead,
   and `responseWindow()` follows the row. Nothing here needs to know.
3. **Is the six-hour timer clamp right?** **Proposed default:** yes. Beyond six hours the app has been
   backgrounded and the focus refetch re-arms with fresh skew; arming a twelve-hour timer in a webview that
   will be killed inside a minute buys nothing.
