## Goal

A manager standing on the sideline marks who turned up, one tap per player, and can correct it a week
later. This is the last step of the one journey that matters, and it is what gives
[S3.5](S3.5-own-attendance-history.md) anything to show a player.

## Context

`CLAUDE.md` S4.5: a per-player attended / did not attend toggle, editable after the fact, defaulting to
blank rather than to "attended", a bulk action for available players, and `recorded_by` and `updated_at`
recorded. Decisions in [00-decisions.md](../00-decisions.md) this is built on:

- **D25** — absence of an `attendance` row means "not recorded". `attended` is `boolean not null`, and
  "not recorded" is never stored as a value. So the brief's "defaults to blank" is the absent row, and
  clearing the toggle **deletes** the row. The bulk action inserts rows only for current members whose
  response is `available`.
- **D42** — the control is the three-state segmented control on line two of the `PlayerResponseCard` that
  [S4.4](S4.4-player-response-list.md) already renders inert. This story supplies the props that make it
  live. One component, not two.
- **D22 / D33** — only current members appear, so only current members can be marked. A leaver's historic
  attendance row stays in the table, read-only, and is not shown.
- **D40** — every control is at least 44px at 375px.
- **D48** — the optimistic-write pattern borrowed from the player response: snapshot, roll back, inline
  "Couldn't save. Tap again.", invalidate on settle.

Attendance is not availability. It does not feed S4.3's counts, which stay Available / Unavailable /
Awaiting / squad size (D22). It has no cut-off either: D12's `starts_at` rule applies to
`event_responses` only.

`recorded_by` is already enforced, and this story must not re-enforce it.
[S1.3](S1.3-rls-policies-and-rpcs.md)'s `attendance_manager_all` policy carries
`with check (... and recorded_by = (select auth.uid()))`, its AC13 says a row carrying anyone else's uid is
**refused**, and [S1.4](S1.4-rls-test-suite.md) matrix row 22 proves it. So the client always sends
`recorded_by: user.id`, and a forged value is rejected with `42501` rather than silently rewritten. A
`before insert` trigger stamping `auth.uid()` would run ahead of the `with check` and quietly turn that
negative test green, which is the one thing this story may not do. `updated_at` is stamped by S1.1's
`attendance_set_updated_at` trigger and is not sent either. This story ships no migration.

## Scope

**In**
- The live three-state attendance control on every `PlayerResponseCard` at `/manage/event/:id`.
- `useSetAttendance(eventId)` — upsert for attended and absent, delete for not recorded.
- `useBulkMarkAttended(eventId)` — one statement filling blanks for available members.
- Per-row saving and per-row error states, and the disabled state for a cancelled event.

**Out**
- Any change to the card markup. S4.4 fixed it; this story passes props.
- Attendance for people no longer in the squad. Their rows are read-only history (D33).
- Showing who recorded it and when. Stored for audit, not displayed (see open questions).
- Attendance percentages, streaks or any per-player statistic. Out of scope in `CLAUDE.md`.
- The player-facing history screen. [S3.5](S3.5-own-attendance-history.md) owns it, reads its own key, and
  is not invalidated from here.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [x] **AC1** — Every card carries an enabled three-state control: `Not recorded | Attended | Absent`. A
      member with no `attendance` row shows `Not recorded` selected, never `Attended`.
- [x] **AC2** — Tapping `Attended` writes `attended = true`; tapping `Absent` writes `attended = false`.
      Both are upserts on the `(event_id, user_id)` primary key, so tapping twice leaves one row.
- [x] **AC3** — Tapping the already-selected `Attended` or `Absent`, or tapping `Not recorded`, deletes
      the row. A subsequent read returns no row for that pair and the card reads `Not recorded`.
- [x] **AC4** — Every insert and update sends `recorded_by: user.id`, so the row records who acted, and
      `updated_at` moves, stamped by S1.1's trigger. A client sending anyone else's uuid is **refused**
      with Postgres code `42501` by S1.3's `with check` — not silently corrected.
- [x] **AC5** — The bulk action writes `attended = true` for exactly those current members whose response
      is `available` **and** who have no `attendance` row. It never overwrites an existing row, so a
      player already marked `Absent` stays `Absent`; it touches nobody who is `unavailable` or awaiting,
      and nobody who has left the team.
- [x] **AC6** — The bulk button is disabled when zero current members are `available`, and after a run an
      `aria-live="polite"` line states the number written: "Marked 12 as attended." A run that writes
      nothing says "Nothing to mark."
- [x] **AC7** — Attendance is editable at any time. There is no `starts_at` cut-off in either direction,
      and an event that finished a month ago can still be corrected.
- [x] **AC8** — On an event with `status = 'cancelled'`, every attendance control and the bulk button are
      disabled with the line "Cancelled — nothing to record." Existing rows stay visible and unchanged.
      This is UI only; RLS does not forbid the write, and the spec says so.
- [x] **AC9** — A tap updates the card immediately. On failure the previous state is restored and an
      inline "Couldn't save. Tap again." appears under that card with the control still enabled. Other
      cards are unaffected.
- [x] **AC10** — While a row is saving, only that row shows a saving state, and the list does not reorder:
      the S4.4 sort is on availability, which attendance never changes.
- [x] **AC11** — A player has no write path at all — no insert, update or delete on `attendance` — and a
      manager writing attendance for an event on a team they do not manage affects zero rows. Both
      asserted in S1.4.
- [x] **AC12** — S4.3's counts do not move when attendance changes, and neither the directory nor the
      responses query is refetched by an attendance write.
- [x] **AC13** — Loading, empty, error and populated states render as specified below.

## Implementation notes

### Mutations

`src/api/attendance.ts`. Both hooks act on the `eventKeys.attendance(eventId)` key S4.4 first consumed.

```ts
export type AttendanceInput = { userId: string; attended: boolean | null }

export function useSetAttendance(eventId: string): UseMutationResult<void, PostgrestError, AttendanceInput>
export function useBulkMarkAttended(eventId: string): UseMutationResult<number, PostgrestError, string[]>
// PostgrestError, not AppError: these are table writes, not RPCs, so they follow S4.1's convention.
```

Single write:

```ts
if (attended === null) {
  await supabase.from('attendance').delete()
    .eq('event_id', eventId).eq('user_id', userId)
} else {
  await supabase.from('attendance')
    .upsert({ event_id: eventId, user_id: userId, attended, recorded_by: user.id },
            { onConflict: 'event_id,user_id' })
}
```

Bulk write — one statement, and `ignoreDuplicates` is what makes AC5 true rather than a race:

```ts
// userIds: current members whose response is 'available', taken from the cached roster rows
await supabase.from('attendance')
  .upsert(userIds.map((user_id) => ({ event_id: eventId, user_id, attended: true, recorded_by: user.id })),
          { onConflict: 'event_id,user_id', ignoreDuplicates: true })
  .select('user_id')   // only the rows actually inserted → the number announced in AC6
```

`ignoreDuplicates: true` compiles to `on conflict do nothing`, so an existing `Absent` survives. Do not
loop the single-write mutation to implement bulk: a squad of twenty would fire twenty requests and twenty
possible rollbacks.

Optimistic handling on both hooks, per D48:

- `onMutate` — `cancelQueries` on `eventKeys.attendance(eventId)`, snapshot it, write the new value into
  the cache, return the snapshot.
- `onError` — restore the snapshot and add the `userId` to a `Set` of failed rows held in component state,
  so the card renders its inline line. Clear the entry on the next mutation of that row.
- `onSettled` — invalidate `eventKeys.attendance(eventId)` **only**. Not `eventKeys.all`, which S4.1 and
  S4.2 use: that would refetch the responses and the directory, move nothing, and make the counts flicker
  (AC12).

### Component wiring

No new components. `PlayerResponseList` now passes down:

```tsx
<PlayerResponseCard
  row={row}
  onAttendanceChange={(userId, attended) => setAttendance.mutate({ userId, attended })}
  saving={savingUserIds.has(row.userId)}
  disabledReason={event.status === 'cancelled' ? 'Cancelled — nothing to record.' : undefined}
/>
```

The control is the shadcn `ToggleGroup`, `type="single"`. Radix emits `''` when the active item is tapped
again, which is exactly AC3. Keep the mapping in one exported function so it is unit-testable and not
repeated:

```ts
export function toAttended(value: string): boolean | null
// 'attended' → true | 'absent' → false | 'none' | '' → null
```

The bulk button sits in the "Who's in" section header beside S4.3's counts: shadcn `Button`,
`variant="secondary"`, label "Mark available as attended", `min-h-tap`. Its `disabled` state comes from the
cached roster — zero rows with `response === 'available'` — so it needs no extra query. No confirmation
dialog: the action is per-player reversible and repeatable, and a dialog in a wet car park is friction.

## Test plan

- **Unit** — Vitest on `toAttended` for all four inputs. Vitest with a mocked Supabase client on
  `useSetAttendance`: a `null` input issues a delete and never an upsert, and a rejected mutation restores
  the previous cache value exactly. Vitest on the helper that builds the bulk payload from roster rows: it
  picks only `response === 'available'`, and returns `[]` for an all-unavailable squad.
- **Integration / RLS** — two cases added to the S1.4 suite: a player attempting insert, update and
  delete on `attendance` is denied on all three; a manager writing attendance for an event on a team they
  do not manage affects zero rows. The forged-`recorded_by` case is already S1.4 matrix row 22 and is not
  duplicated here.
- **E2E** — Playwright against the seed: as a manager, open a past seeded event, mark one player attended
  and one absent, reload, assert both stuck; clear one and assert `Not recorded` after reload; run the
  bulk action and assert the previously-marked `Absent` player is untouched while the blank available
  players flip to attended; assert the announced number equals the number of cards that changed. This leg
  is reused by [S7.3](S7.3-end-to-end-journey.md).
- **Manual** — On a real phone, mark ten players in under a minute without mis-taps. Check the control is
  comfortably thumb-sized and the list does not jump under the finger.

## Open questions

1. Should the card show "Recorded by Anne, Tuesday" from `recorded_by` and `updated_at`? **Default: no.**
   The columns are written for audit, not display, and the card has no room.
2. Should attendance be recordable before the event starts? **Default: yes**, no restriction. A manager
   marking a known no-show in advance is harmless, and a cut-off is one more rule to explain.
3. Should the bulk action have a matching "clear all"? **Default: no.** A destructive bulk delete for a
   rare case, and every row can already be cleared individually.
