## Goal
The database can hold a matchday squad for a match: which players are picked, their shirt numbers, and the
captain — writable only by a manager of that team, and only for players who marked themselves available.

## Context
[V6](../00-decisions-v1.1.0.md) makes the squad its own table `event_squad`, distinct from `event_responses`
(availability) and `attendance`. [V7](../00-decisions-v1.1.0.md): the pool is available responders only. RLS
mirrors attendance (S4.5): managers write their team's, players read their team's.

## Scope
**In**
- Migration creating `event_squad(event_id, user_id, shirt_number, is_captain, recorded_by, updated_at)` with
  PK `(event_id, user_id)`, unique `(event_id, shirt_number)`, unique-partial one-captain-per-event, check
  `shirt_number between 1 and 20`, FKs on delete cascade, index on `event_id`.
- RLS: enabled; select for team members, insert/update/delete for team managers and admins; nothing for anon.
- The "available only" rule: a write for `(event_id, user_id)` requires an
  `event_responses.response='available'` row — enforced in the write path (a policy `with check` subquery,
  or a security-definer RPC `set_squad_member`/`remove_squad_member`; choose and document).
- Zod schema + generated types + a typed read hook shape (the hook UI is S9.2).
- S1.4 additions: positive and negative tests for every path.

**Out**
- The selection UI ([S9.2](S9.2-squad-selection-screen.md)) and the share ([S9.3](S9.3-match-share-rewrite.md)).

## Acceptance criteria
- [ ] **AC1** — Migration creates `event_squad` with the keys, uniques, checks, FKs and index above; runs clean on the live DB; `test:rls` still green.
- [ ] **AC2** — RLS: a **manager** of the team can insert/update/delete a squad row for an available player on their match; a manager of another team cannot (42501); a **player** can select their team's squad rows but not write any; **anon** gets nothing. Each has a passing positive and negative S1.4 test.
- [ ] **AC3** — Writing a squad row for a player with **no `available` response** is refused (the V7 rule), and the refusal message names no column/constraint; tested both via the RPC/policy and by SQL.
- [ ] **AC4** — Two players cannot share a shirt number in one match (unique violation surfaced cleanly); at most one captain per match (unique-partial); `shirt_number` outside 1–20 is rejected.
- [ ] **AC5** — Deleting an event or a profile cascades its `event_squad` rows; removing a player's membership does **not** delete historic squad rows (consistent with D33 — squad rows are keyed on user_id, survive membership removal).
- [ ] **AC6** — `recorded_by` is the acting manager's uid and cannot be forged (as attendance, S4.5); `updated_at` is set on write.

## Implementation notes
- Migration `NNNN_event_squad.sql` — table + RLS + policies + (if chosen) the security-definer
  `set_squad_member(p_event_id, p_user_id, p_shirt_number, p_is_captain)` and `remove_squad_member(...)` /
  `clear_squad(p_event_id)` RPCs. Prefer RPCs for the multi-condition write (available-check + number
  uniqueness + captain uniqueness) so the error vocabulary stays in the six-word set (extend if needed and
  record it). Mirror the S4.5 attendance authorisation (`is_team_manager(team_id) or is_admin()`).
- Helper predicate reuse: `event_team_id(event_id)` already exists (S1.3) — use it in the policy/RPC.
- `src/api/squad.ts` — the read hook (`useEventSquad(eventId)`) and the write mutations; `squadRowSchema` in
  `src/features/events/schema.ts`. Regenerate types.
- S1.4: new `tests/rls/squad.test.ts` — every AC2/AC3/AC4 path, positive and negative, cleaning up.

## Data and API surface
New table `event_squad` + policies + (RPCs). `useEventSquad`, `setSquadMember`/`removeSquadMember`/
`clearSquad` mutations under `src/api/`. `squadRowSchema`. Regenerated types. S1.4 suite grows.
