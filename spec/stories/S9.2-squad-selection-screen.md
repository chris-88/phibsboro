## Goal
From the Squad tab (or a link on the match), a manager picks the matchday squad for a match from the players
who said they're available, gives each a shirt number, and marks the captain — ready to share.

## Context
The picker lives in the **Squad tab's Matchday section** ([S10.3](S10.3-manager-squad-tab.md)/[V12](../00-decisions-v1.1.0.md))
and is also reachable by a "Pick squad" link on the match manager view (S4.3) — two entry points, one editor.
Pool = available responders ([V7](../00-decisions-v1.1.0.md)). Writes go through the S9.1 mutations/RPCs.
Numbers 1–20, one captain.

## Scope
**In**
- A squad picker route `/squad/event/:id` (guard `'manager'`) — the editor for one match's squad. Reached
  from the Squad tab matchday list (S10.3) and from a **"Pick squad"** link added to the match manager view
  (S4.3).
- The picker: the match's **available** players (from S9.1's read of squad + the S4.4 available slice), each
  addable with a shirt number (1–20) and a captain toggle; selected players show their number; a running
  "{n} / 20" count.
- Optimistic add/remove/renumber/captain through the S9.1 mutations, rollback on error.
- Guards: a number is offered once; the captain toggle clears any previous captain; a picked player who has
  since gone unavailable is shown flagged (still removable) per V7; the pool never offers a non-available
  player.
- The Squad tab matchday row and the match view show the resulting squad status ("18 picked", captain).
- Four states: loading, empty (no available players yet), error, populated. Manager-only (RLS enforces).

**Out**
- The tab shell / members section ([S10.3](S10.3-manager-squad-tab.md)).
- The share text ([S9.3](S9.3-match-share-rewrite.md)) — this story ends at a persisted, displayed squad
  (the Share button is wired by S9.3).

## Acceptance criteria
- [x] **AC1** — Opening a match's picker (from the Squad tab matchday list **and** from the match view's "Pick squad" link) shows the available players, each addable with a number; both entry points land on the same editor for that event.
- [x] **AC2** — Adding a player with a number persists an `event_squad` row (verified by SQL); removing deletes it; both update optimistically and roll back with a message on failure.
- [x] **AC3** — A shirt number is usable only once per match; the UI prevents a duplicate and the DB backs it up; numbers are 1–20; adding beyond 20 is prevented (the "{n} / 20" count enforces it).
- [x] **AC4** — Marking a captain sets `is_captain` and clears any previous captain; at most one "(C)".
- [x] **AC5** — A picked player who becomes unavailable is shown flagged and is removable/renumberable; the pool never offers a non-available player (V7).
- [x] **AC6** — Training/social have no picker (matchday squads are match-only); their Squad-tab rows / match views show no "Pick squad".
- [x] **AC7** — A player or a manager of another team cannot open or write a squad (guard + RLS); the picker is manager-only.
- [x] **AC8** — Readable and thumb-usable at 375px; adding + numbering is quick (tap, not free typing where avoidable); targets ≥44px.

## Implementation notes
- `src/features/events/squad-picker-screen.tsx` at `/squad/event/:id`. The Squad tab matchday row (S10.3)
  and a new "Pick squad" link on the S4.3 manager view both route here.
- Reads `useEventSquad(eventId)` (S9.1) + the available slice of the response list (reuse S4.4's query,
  filter `response==='available'`) — do not refetch differently.
- Number assignment: tap-to-add assigns the lowest free number with an explicit override (fastest for naming
  a XI+subs); shadcn Select/stepper for the override. Optimistic on `eventKeys`; rollback on error.
- Captain toggle: one call setting the new captain and unsetting the old (the S9.1 RPC).

## Data and API surface
Reads: `useEventSquad`, the response list (available filter). Writes: `setSquadMember`, `removeSquadMember`,
captain toggle (S9.1). New route `/squad/event/:id`. A "Pick squad" link on the S4.3 view.

## Build notes — deviations from this spec

| Spec said | Built as | Why |
|---|---|---|
| "Captain toggle: **one call** setting the new captain and unsetting the old (the S9.1 RPC)." | `useSetCaptain` composes **two** `set_squad_member` calls — first clear the previous captain, then set the new one — with a single optimistic cache edit and rollback. | The S9.1 RPC has no captain-swap: `set_squad_member` *raises* `captain_taken` if a different captain already exists (the unique-partial index is its backstop), so a single call cannot move the armband. Clearing the old captain first, in the same mutation, keeps it one user gesture and one rollback; a refetch on settle reconciles the rare mid-swap failure to a valid (no-captain) state. No new migration/RPC. |
| "Optimistic add/remove/renumber/captain through the S9.1 mutations." | The S9.1 `useSetSquadMember`/`useRemoveSquadMember`/`useClearSquad` hooks (which shipped invalidate-only in S9.1, unused until now) were made **optimistic** in place, and `useSetCaptain` added, all on `eventKeys.squad(eventId)`. | The S9.1 hooks were never consumed before S9.2, so adding `onMutate`/`onError` rollback to them (rather than forking new hooks) keeps "one write path" — the picker fills and empties under the thumb, the RPC is still the only writer. |
| Matchday row / match view "until S9.2 lands" showed "Squad not picked". | Both now read the per-match `event_squad` cache and show `squadStatusText` — "Squad not picked", then "{n} picked" / "{n} picked · captain named". The Squad-tab row and the match view's new "Pick squad" card both route to `/squad/event/:id`. | Fulfils the scope line "the Squad tab matchday row and the match view show the resulting squad status". |
