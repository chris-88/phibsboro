## Goal

An admin can pick any team in the club and then use the ordinary manager screens for it: see the events,
create one, read the counts, record attendance, manage the squad. A manager who looks after two teams
gets the same picker. Nothing is duplicated: there is one manager area and the team it is pointed at is a
setting, not a second code path.

## Context

The brief's S6.3 is one sentence, "Admin can view and administer any team's events", with no criteria.
[D50](../00-decisions.md) fixes it: the admin team picker lists all teams, active first, inactive in a
second section; selecting one renders the identical manager event views scoped to that team, **with no
separate code path**. That last clause is the whole story. An admin-only copy of the manager screens
would double the surface of Epic 4 and drift the first time one side is fixed.

This is story 39 in the build order ([D20](../00-decisions.md)), after every screen it scopes. The Epic 4
hooks were written taking a `teamId` argument already; what is missing is the thing that decides which
`teamId`, and the picker that changes it.

Decisions this story rests on:

- [D2](../00-decisions.md) — admin is club-wide. An admin may belong to no team at all and must still be
  able to administer every one, so nothing in the manager area may key off membership.
- [D8](../00-decisions.md) — `teams` select returns teams you belong to, plus every team when
  `is_admin()`. The picker needs no RPC; RLS already returns the right rows.
- [D50](../00-decisions.md) — an inactive team is hidden from every non-admin list, refuses event insert,
  and refuses both join RPCs, while its existing events, responses and attendance stay readable.
- [D34](../00-decisions.md) — the route list is fixed and already includes everything needed. This story
  adds no route.
- [D41](../00-decisions.md) — the fixed bottom nav carries an Admin item for admins.
- `CLAUDE.md` section 2 — Zustand is for UI state only and never caches server data. The selected team id
  is a UI preference; the teams themselves stay in TanStack Query.

## Scope

**In**

- A team picker in the manager area header, listing the teams the caller can manage.
- A single source of truth for the active team: `useActiveTeam()`, backed by [S4.1](S4.1-create-event.md)'s
  existing Zustand store `src/features/teams/manageStore.ts`, extended here with the `persist`
  middleware. One store, not a second one.
- Every manager screen — `/manage`, `/manage/event/new`, `/manage/event/:id`,
  `/manage/team/:teamId/members` — reading the team from that hook rather than assuming one.
- Active-first ordering with a separate Inactive section, and the create-event control disabled with an
  explanation on an inactive team.
- A link from each row of the S6.1 `/admin` teams list into that team's manage view. The members link on
  the same row is already there from [S6.2](S6.2-team-join-links.md).
- Auto-switching the selection when an admin opens an event that belongs to another team.

**Out**

- Any duplicate admin variant of a manager screen. If a file named `Admin*` mirrors a `Manage*` screen,
  this story has failed.
- Cross-team aggregate views: no club-wide event list, no combined calendar, no totals across teams. One
  team at a time.
- A team query parameter or a `/manage/:teamId` route. The route list is fixed and the selection is a
  preference, not an address. Rejected explicitly in Open question 3. This supersedes
  [S4.1](S4.1-create-event.md)'s implementation note that `/manage/event/new` reads `?team=<uuid>`: that
  read is deleted here and the persisted store keeps S4.1 AC8 true on a hard refresh.
- Any change to what a manager or admin may *do* on a team. That is entirely S1.3, unchanged here.
- Editing teams. That is [S6.1](S6.1-teams.md); the picker links to it.

## Implementation notes

No migration. No RPC. No route. This story is a hook, a store, a picker and a handful of call-site edits.

### Files

```
src/features/teams/manageStore.ts                  // extended: S4.1's store gains persist
src/features/teams/hooks/useManagedTeams.ts
src/features/teams/hooks/useActiveTeam.ts
src/features/teams/components/TeamPicker.tsx
src/features/teams/components/ManageHeader.tsx     // new: team name or picker, mounted by the four screens below
src/features/teams/routes/AdminTeamsScreen.tsx     // extended: each row gains the manage-view link (AC1)
src/features/events/ManageEventsScreen.tsx         // edited: reads useActiveTeam(), mounts ManageHeader
src/features/events/NewEventScreen.tsx             // edited: same, and the ?team= read is deleted
src/features/events/ManagerEventScreen.tsx         // edited: setSelectedTeamId(event.team_id) on load (AC7)
src/features/teams/routes/TeamMembersScreen.tsx    // edited: route param wins, store follows
```

There is no `ManagerHeader` in the codebase before this story — no Epic 0 or Epic 4 story creates one —
so `ManageHeader.tsx` is new here and the four screens mount it themselves. `AppShell`
([S0.2](S0.2-ui-system.md)) stays untouched: it takes a title, it does not own team selection.

### Store

Zustand with the `persist` middleware, holding one string and nothing else. No server data, per the
conventions.

```ts
// src/features/teams/manageStore.ts — S4.1's store, now persisted
type ManageState = {
  selectedTeamId: string | null
  setSelectedTeamId: (id: string) => void
}

export const useManageStore = create<ManageState>()(
  persist(
    (set) => ({ selectedTeamId: null, setSelectedTeamId: (id) => set({ selectedTeamId: id }) }),
    { name: 'pfc.selectedTeamId' },
  ),
)
```

`persist` writes `{"state":{"selectedTeamId":"<uuid>"},"version":0}` under that key, which is what AC6
means by "stored under `pfc.selectedTeamId`". Keep S4.1's names; renaming the store to match this story's
prose would touch every S4.x call site for nothing.

### Which teams can this person manage

```ts
// src/features/teams/hooks/useManagedTeams.ts
export function useManagedTeams(): { teams: Team[]; isLoading: boolean; isError: boolean }
```

It reads `useTeams()` from [S6.1](S6.1-teams.md) — RLS already limits the rows — and filters:

- `user.isAdmin` from `useCurrentUser()` (S2.9): every returned row is manageable, membership or not.
- otherwise: `teams.filter((t) => user.roleForTeam(t.id) === 'manager')`. A manager who is a **player** on
  a second team must not see that team in the picker, which is why membership role, not mere membership,
  is the filter. Do **not** use `user.isManagerOf(teamId)` here — it returns true for an admin on every
  team, which is right for permission checks and wrong for building a non-admin's list.

Sorting lives here, once: active first, then `Intl.Collator('en-IE', { sensitivity: 'base' })` on name.

### Resolving the active team

```ts
// src/features/teams/hooks/useActiveTeam.ts
export function useActiveTeam(): {
  teamId: string | null
  team: Team | null
  canManageMany: boolean
  isLoading: boolean
  isError: boolean
}
```

Resolution order, and it must be exactly this:

1. `manageStore.selectedTeamId`, if it appears in `useManagedTeams().teams`;
2. otherwise the first team in that list;
3. otherwise `null`.

When 1 falls through to 2 the hook writes the resolved id back to the store, so a stale id is corrected
once rather than on every render. Guard that write behind an effect keyed on the resolved id, or it
loops.

`/manage/event/:id` (AC7) calls `setSelectedTeamId(event.team_id)` in an effect once the event query resolves, so
the header and the members link follow the event. The event query itself is keyed on the event id and
does not depend on the selection.

### Call-site edits

`ManageEventsScreen.tsx`, `NewEventScreen.tsx` and `ManagerEventScreen.tsx` currently obtain `teamId` from
S4.1's store directly, and `NewEventScreen.tsx` additionally reads `?team=<uuid>`. Replace all of that with
`useActiveTeam()` and delete the query-param read. The data hooks themselves do not change signature —
`useTeamEvents(teamId)`, `useCreateEvent()` and the rest already take a `teamId` — so the diff is one line
per screen plus a null guard rendering the "no resolvable team" state from the table below. If any Epic 4
hook turns out to resolve the team internally, fix it at the hook rather than layering a second mechanism
on top; that is the retrofit risk in the header table.

`/manage/team/:teamId/members` keeps its route parameter and is the authority for that screen; the picker
navigates to a new `teamId` rather than relying on the store. The store still follows, so the header
matches.

### Picker

shadcn `Select` on every width: it is one tap, it renders a native-feeling sheet on iOS, and it needs no
custom dismissal handling. Group with `SelectGroup` and a `SelectLabel` of "Inactive" for the second
section. Inactive rows carry an "Inactive" `Badge`. The trigger shows the team name truncated with
`truncate` and the badge when the active team is inactive, so an admin is never quietly editing a
retired team.

### Gotchas

- An admin's `useTeams()` returns every team, including ones with no members and no events. The picker
  must not hide them: a freshly created team is exactly the one an admin wants to select next.
- Do not put the selection in the TanStack Query cache to "share" it. It is not server state, and a cache
  invalidation would silently reset the header.
- Clearing site data resets the selection to the first managed team. That is correct behaviour, not a bug
  to work around.
- The bottom nav's Manage item routes to `/manage`, which resolves through this hook. It must never
  encode a team id.

## Test plan

- **Unit** — Vitest + RTL. `useActiveTeam` resolution: a stored id that is still visible is kept; a stored
  id that is not returns the first managed team and writes it back once; no managed teams returns null and
  fires no write. `useManagedTeams` excludes a team where the caller's role is `player`, includes every
  team for an admin, and orders active-before-inactive then case-insensitively by name. Picker rendering:
  hidden for a single-team manager, shown for an admin with one team, inactive group labelled and badged.
  A team switch clears the previous team's list from view rather than showing it while the new one loads.
- **Integration / RLS** — extends S1.4: an admin with zero `team_members` rows can select any team, insert
  an event on an active one, be refused the insert on an inactive one, and write `attendance` for an event
  on a team they do not belong to. A manager's `teams` select returns only their own teams, so the picker
  cannot be widened from the client.
- **E2E** — Playwright against the seeded local stack: the seeded admin signs in, opens `/#/admin`, picks
  the second team, sees that team's seeded events and not the first team's, opens one, records attendance
  for a player, reloads the page and confirms the second team is still selected.
- **Manual** — at 375px on a real phone: switch teams from the header, confirm the name truncates rather
  than wrapping, and confirm the inactive badge is visible before any edit. Recorded in
  [S7.4](S7.4-device-pass.md).

## Open questions

1. **Should the manager area default to the last team used or the first alphabetically?** Proposed
   default, written into AC6: last used, falling back to the first managed team, active ones first. An
   admin swapping between two squads on a Saturday morning should not re-pick every time.
2. **Should an inactive team be selectable at all?** Proposed default: yes, read plus attendance, no new
   events. D50 keeps a deactivated team's history readable to admins, and the only screen that reads it is
   this one. Hiding inactive teams entirely would make that guarantee unreachable through the app.
3. **Should the selection be addressable, as `/#/manage?team={id}`?** Proposed default: no. D34 fixed the
   route list, a preference is not an address, and the one case that wants a link — "look at this team" —
   is served by the `/admin` list and by `/#/manage/event/{id}`, which already switches teams on its own
   (AC7).
4. **Does any Epic 4 hook resolve the team internally rather than taking it as an argument?** Unknown
   until those stories are built. Proposed default: this story fixes any that do, at the hook, and does
   not add a compatibility layer. If more than one or two turn out to, raise it rather than absorbing the
   rework silently.
