## Goal

Below the next-event card, a player sees everything else that is coming up, in order, with what they said
about each one. A cancelled fixture is shown as cancelled rather than quietly disappearing, so nobody turns
up to a pitch for a match that was called off.

## Context

`CLAUDE.md` asks for a chronological list under the card showing "time, type, and the player's own status",
with Available / Unavailable / Awaiting per row and cancelled events "shown as cancelled, not hidden
silently". The relevant decisions in [00-decisions.md](../00-decisions.md):

- **D60** cancelled events never occupy the next-event card, but they do appear in this list, marked.
- **D12** absence of an `event_responses` row means awaiting. It is never stored as a value, so "Awaiting"
  is derived, not read.
- **D32** a player reads only their own response rows. There is no "14 available" figure on this screen and
  there cannot be one.
- **D41** `/` is inside the app shell, so the list is bottom-padded to clear the fixed nav and the last row
  is never trapped underneath it.
- **D39** `event_responses(user_id)` is indexed.
- **D22** a player may be on more than one team, so rows carry the team name when that is true.

This story adds no query. [S3.1](S3.1-home-screen-with-next-event.md) already ships `useUpcomingEvents()`,
which returns every upcoming event across the player's teams with their own answer attached; this story
renders the tail of that same array. Two stories, one round trip, one cache entry.

Row taps go to [S3.3](S3.3-event-detail-screen.md) at `/event/:id`. Nothing on a row is interactive except
the row itself.

## Scope

**In**
- `UpcomingEventsList`, mounted by `HomeScreen` in the slot S3.1 reserved.
- `UpcomingEventRow`: date and time, type badge, title, own-status pill, team name when multi-team,
  cancelled marker.
- `ResponsePill`, a three-state pill (Available / Unavailable / Awaiting). This is the availability pill
  [S4.4](S4.4-player-response-list.md)'s card line one renders against another player's row (D42), so it
  takes a value, not a hook call. [S3.5](S3.5-own-attendance-history.md) does **not** use it: history shows
  attendance, and its `AttendancePill` is a different three-state component.
- Exclusion of the event already shown in the next-event card, so it appears once on the screen.
- Loading, empty and error behaviour for the list region specifically.

**Out**
- The query — [S3.1](S3.1-home-screen-with-next-event.md) owns `useUpcomingEvents()`.
- The next-event card and the screen's overall state machine — S3.1.
- Answering YES or NO from a row. Rows navigate; they do not respond. The controls are on the card and on
  the event screen, where they are 44px and unambiguous.
- Past events and attendance — [S3.5](S3.5-own-attendance-history.md).
- Filters, a team switcher, a month picker, a search box, pagination, infinite scroll. A squad has a handful
  of upcoming fixtures; all of them fit.
- Grouping by month or by team. Strict chronological order, one flat list.
- Calendar subscription or export. Not in the brief.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [x] **AC1** — The list renders every upcoming event across the player's teams **except** the one shown in
      the next-event card. No event appears twice on the screen.
- [x] **AC2** — Rows are in ascending `starts_at` order. Two events at the same instant are ordered by `id`,
      so the order is stable across refetches.
- [x] **AC3** — Each row shows `formatEventTime(starts_at, 'short')` — "Sat 14 Mar, 7.30pm" — and no other
      date formatter is used in the file.
- [x] **AC4** — Each row shows a type badge reading "Match" or "Training", using the same
      `EventTypeBadge` component as the card and the event screen.
- [x] **AC5** — Each row shows exactly one status pill: "Available" when the player's response is
      `available`, "Unavailable" when it is `unavailable`, "Awaiting" when there is no response row (D12).
      The three are distinguishable without relying on colour alone.
- [x] **AC6** — A cancelled event is present in the list, carries a "Cancelled" marker, and its title is
      visually de-emphasised. It is not removed, not greyed to illegibility, and its existing status pill is
      still shown.
- [x] **AC7** — The team name is shown on every row when the player belongs to more than one team, and on no
      row when they belong to exactly one.
- [x] **AC8** — Tapping anywhere on a row navigates to `/#/event/{id}`. The whole row is the target and its
      hit area is at least 44px tall.
- [x] **AC9** — At 375px the row lays out without horizontal scroll. A 60-character title truncates to one
      line with an ellipsis and keeps its full text in the accessible name.
- [x] **AC10** — With a next-event card present and no further upcoming events, the list region shows
      "Nothing else coming up." and no empty list frame.
- [x] **AC11** — With no upcoming events at all, the list region renders nothing. S3.1's empty state owns
      the screen; there are not two empty messages.
- [x] **AC12** — While the shared query is pending, the list region shows three skeleton rows of the same
      height as real rows, so the screen does not shift when data arrives.
- [x] **AC13** — When the shared query errors, the list region renders nothing. S3.1's `ErrorState` and
      Retry own the failure; the screen does not show the same error twice.
- [ ] **AC14** — Answering a **list** event changes that row's pill without a reload: tap a row, answer
      YES on `/event/:id`, go back to `/`, and the row reads "Available". `useSetResponse`'s `onMutate`
      writes into `eventKeys.upcoming` and its `onSettled` invalidates it, so the pill is already correct
      before the refetch lands. Answering on the card moves no row's pill, because the card's event is
      excluded from the list (AC1).
- [ ] **AC15** — The last row is fully visible above the fixed bottom nav on a 375x667 viewport, including
      on a device with a home indicator (`env(safe-area-inset-bottom)` padding applied by the shell).

### Deriving the list from the shared query

```ts
// src/features/events/components/UpcomingEventsList.tsx
export function UpcomingEventsList({ excludeEventId }: { excludeEventId: string | null }): JSX.Element | null
```

`HomeScreen` already holds the query result and has already computed `pickNextEvent(events)` for the card.
It passes that event's id down; the list filters on it. Do not re-run `pickNextEvent` inside the list, and
do not call `useUpcomingEvents()` a second time — TanStack Query would dedupe it, but two components
deciding independently which event is "next" is how the same fixture ends up rendered twice.

```ts
const rows = events.filter((e) => e.id !== excludeEventId)
```

That is the whole derivation. Ordering, the server-clock horizon, the team filter and the own-response
filter are all already applied by the query (see S3.1's implementation notes, including the two filters that
look optional and are not).

### The row

One `<li>` per event containing a single `<Link to={`/event/${id}`}>` that fills it, so the hit area is the
row. Not a `<div onClick>`: a link gives the WhatsApp webview a working long-press and gives the keyboard a
focus stop for free.

Layout at 375px, two lines, no table:

```
┌─────────────────────────────────────────────┐
│ Sat 14 Mar, 7.30pm      ⟨Match⟩  ⟨Available⟩│   line 1: meta row, pills right-aligned
│ Kilbarrack away · Firsts                    │   line 2: title, then team when multi-team
└─────────────────────────────────────────────┘
```

- Line 1 is `flex items-center gap-2`; the date takes the remaining width, the badge and the pill are
  `shrink-0`.
- Line 2 is the title with `truncate`, and the team name after a middot in muted text. The `<Link>` carries
  an `aria-label` built from the untruncated title, the date line and the status, so a screen reader and
  the Playwright accessible-name assertion both get the full string (AC9).
- Minimum height `min-h-16` (64px), comfortably over the 44px floor, with a divider between rows rather
  than a card per row — twenty stacked cards at 375px is all border and no content.

Cancelled rows (AC6): the title gets `line-through text-muted-foreground`, and a "Cancelled" pill is
rendered **before** the status pill. Do not drop the status pill: the player's answer from before the
cancellation is still their answer, and hiding it makes the row look like it was never responded to.

### ResponsePill

```ts
// src/features/availability/components/ResponsePill.tsx
export type ResponsePillProps = {
  response: Enums<'availability_response'> | null
}
export function ResponsePill({ response }: ResponsePillProps): JSX.Element
// null → "Awaiting"
```

shadcn `Badge`. Three variants mapped from the S0.2 theme tokens — no hex values in the component. Each
variant carries a distinct glyph as well as a distinct token, so the three are separable in greyscale and by
anyone who cannot tell the two colours apart (AC5): a tick for available, a cross for unavailable, a dash
for awaiting. The glyph is `aria-hidden`; the word is the accessible text.

This is the component [S4.4](S4.4-player-response-list.md) reuses for the availability pill on its card
line one; it renders it against another player's response, which is why the prop is a value and not a hook
call. [S3.5](S3.5-own-attendance-history.md) does not reuse it — attendance is a different three-state set
and ships as `AttendancePill` there.

### List states

The list is a region inside S3.1's screen, not a screen of its own, so its states are subordinate:

```tsx
if (query.isPending) return <UpcomingEventRowSkeleton count={3} />
if (query.isError)   return null            // S3.1 renders the error once (AC13)
if (rows.length === 0) {
  return excludeEventId === null
    ? null                                   // S3.1's screen-level empty state owns it (AC11)
    : <p>Nothing else coming up.</p>         // (AC10)
}
return (
  <section aria-labelledby="also-coming-up">
    <h2 id="also-coming-up" className="text-sm text-muted-foreground">Also coming up</h2>
    <ul>…</ul>
  </section>
)
```

The heading is a landmark for a screen reader and removes the ambiguity of a bare divider under the card.
It is rendered only in the populated branch: an empty or errored region has nothing to head.

Those four branches are the whole component. S7.1's audit should be able to read them without following a
chain of ternaries.

### Freshness

None of its own. The list re-renders when the shared query refetches — on focus, after 30 seconds of
staleness, and on `useSetResponse`'s `onSettled` invalidation. AC14 is satisfied by the S3.3 `onMutate`
writing into `eventKeys.upcoming`, so a row's pill is already correct when the player navigates back from
`/event/:id`.

### Horizon

The query's `.limit(50)` is the only bound, and it is a guard rather than a page size. No "show more"
control, no infinite scroll, no date-range picker. If a team ever posts more than fifty future fixtures,
that is a conversation with the club, not a feature.

`teams` (embedded) and `event_responses` (embedded, filtered to the caller). See
[S3.1](S3.1-home-screen-with-next-event.md).

**Tables written** — none. This story has no mutation.

**RPCs called** — none.

**Zod schemas added** — none. `upcomingEventRowSchema` from S3.1 already covers the shape.

**Query keys introduced** — none. The list reads `eventKeys.upcoming(userId)` through the result S3.1's

## Open questions

1. Should a player see fixtures for a team whose `active` flag is false? **Default:** the question does not
   arise in practice — a deactivated team cannot have new events created and its existing future events are
   rare. Show them; suppressing them would need a `teams.active` read on every row for no player benefit, and
   D50 does not hide existing events from members.
2. How far ahead should the list go? **Default:** everything the query returns, capped at 50 rows. The S4.6
   generator caps a series at 16 weeks and 20 events (D30), so the realistic ceiling is well inside that.
3. Should a row show the location? **Default:** no. Two lines at 375px already carry date, type, status,
   title and team. The location is one tap away on the event screen, and adding it forces the title to
   truncate harder.

## Build notes — deviations from this spec

| Spec said | Built as | Why |
|---|---|---|
| `UpcomingEventsList({ excludeEventId })` — single prop | `UpcomingEventsList({ query, excludeEventId, showTeamName })` | The state pseudocode reads `query.isPending`/`query.isError`/`query.data`, and the DoD forbids a second `useUpcomingEvents()` call. So `HomeScreen` passes the query result it already holds down to the list, rather than the list re-calling the hook. `showTeamName` is likewise lifted from the screen (which already knows `memberships.length > 1`) so the row does not re-read memberships. No second hook call, no second `pickNextEvent`. |
| `ResponsePill` prop `response: Enums<'availability_response'> \| null` | `response: AvailabilityResponse \| null` | `AvailabilityResponse` is the codebase's local alias for exactly that enum (parity-asserted in `availability/schema.ts`), and it is the type of `UpcomingEvent.myResponse`, so the pill takes the value the row already holds without a cast. Structurally identical. |
| AC14 (answer a list event, go back, pill updates) ticked by unit test | Left unticked | The optimistic write into `eventKeys.upcoming` lives in S3.1's `useSetResponse` and is unit-tested there; the list purely reads `query.data`, so it re-renders on that cache change. The full tap-through-navigate-back path is the Playwright test, which needs the local Docker Supabase stack (unavailable here). Verify with `npm run test:e2e` once Docker is up. |
| AC15 (last row above the fixed nav, safe-area) ticked | Left unticked | The clearance is the app shell's footer padding (`pb-[calc(var(--spacing-tap)+env(safe-area-inset-bottom)+1rem)]`), unchanged by this story; the list adds no bottom padding of its own. Confirmed only by reading the shell — the device/Playwright viewport pass is not run here. |
| S3.1's home-screen test asserted a cancelled fixture was absent from the whole screen | Assertion narrowed to "not the card heading" | Since S3.2 the cancelled fixture correctly appears in the list below the card, marked cancelled (D60, AC6), so it is no longer absent from the screen — only from the card. |
