## Goal

A player signs in once and stays signed in. Reopening the app next Tuesday, or next March, goes straight
to their team's next event. They never see the login screen again unless the refresh token genuinely
expires.

## Context

Password recovery in this app costs a manager a manual step: no SMS, no email, no self-serve reset, only
a link a manager issues by hand ([S2.3](S2.3-password-reset-by-manager.md)). So every forced re-login is
a support ticket in a WhatsApp group. Sessions are therefore deliberately long, and the app's job is to
restore them quietly.

This story is also the front half of the deep-link path. `CLAUDE.md` demands "No flash of the login
screen while the session is being restored", and the reason is not polish: a flash means the router has
already navigated, and [S2.5](S2.5-deep-link-return-path.md)'s destination is lost.

Decisions from [00-decisions.md](../00-decisions.md):

- **D59** — this story is restated as **configuration plus a proxy**. JWT expiry 3600s, refresh token
  rotation on, inactivity window 365 days, `persistSession: true` and `autoRefreshToken: true`, all
  committed in `supabase/config.toml`. The 24-hour and season-long claims are checked by reading the
  committed config, not by waiting. A Vitest test stubs an expired access token and asserts one silent
  refresh with no navigation to `/login`; a Playwright test reloads with a stored session and asserts no
  login flash.
- **D10** — redeeming a reset token deletes the target's refresh tokens, so a player whose password a
  manager reset **is** signed out on their other device. That is the intended blast radius, and this
  story handles it as an ordinary expiry, not an error.
- **D43** — the service worker is `autoUpdate` and reloads once on `controllerchange`. The session must
  survive that reload.
- **D47** — escaping the WhatsApp webview to Safari is a new browsing context with no session. A second
  sign-in there is expected and admitted in S2.7's copy. No transfer is attempted.
- **D19** — whether the underlying auth is phone or the synthetic-address fallback is settled in S1.2.
  Nothing in this story depends on which, because both produce an ordinary GoTrue session.

## Scope

**In**
- The Supabase client's auth options, in one place.
- The committed auth configuration, and the record of the hosted project matching it.
- `AppBoot`, the boot gate wrapped round S2.9's `SessionProvider`: nothing renders routes until the
  three-state status settles.
- The static-shell splash, and the handover to React without a flash.
- Sign-out, and what it must clear.
- Behaviour when a refresh genuinely fails, and when the app is resumed after a long background.

**Out**
- The sign-in and registration screens. [S2.2](S2.2-sign-in.md), [S2.1](S2.1-registration.md).
- The route guard and `useCurrentUser()`. [S2.9](S2.9-auth-guard-and-role-context.md); this story only
  fixes the `loading` contract it must honour.
- Restoring the intended route. [S2.5](S2.5-deep-link-return-path.md).
- Resuming a pending join. [S2.4](S2.4-join-by-link.md).
- Rate limiting. [S2.2](S2.2-sign-in.md), per D36.
- Any "remember me" control. There is no such control; every session is long lived.
- Offline support beyond what the D43 service worker already gives the shell.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — `supabase/config.toml` is committed beside the migrations and sets: `jwt_expiry = 3600`,
      refresh token rotation enabled, a reuse interval, no absolute session timebox, and an inactivity
      window of 365 days. A reviewer can read the values in the diff (D59).
- [ ] **AC2** — `docs/supabase-config.md` records the hosted project's matching Auth settings, the date
      checked and by whom, because the hosted dashboard is not in the repo. Re-checked at every release
      that changes auth.
- [ ] **AC3** — The Supabase browser client is created exactly once, in `src/lib/supabase.ts`, with
      `persistSession: true`, `autoRefreshToken: true`, `detectSessionInUrl: false` and an explicit
      `storageKey`. `grep -rn "createClient(" src/` returns one hit.
- [ ] **AC4** — `detectSessionInUrl` is false and there is a comment saying why: GoTrue's URL parsing
      would fight HashRouter over the fragment that carries every deep link.
- [ ] **AC5** — With a stored session whose access token expired more than an hour ago, opening the app
      restores it silently: one refresh, no navigation to `/login`, no password prompt (D59).
- [ ] **AC6** — Exactly one refresh request is made for one expired token. No refresh storm when several
      queries mount at once.
- [ ] **AC7** — No login flash. From a cold start with a valid stored session, the sign-in heading is
      never in the DOM. Asserted by a Playwright listener that fails the test if it ever appears, not by
      a screenshot.
- [ ] **AC8** — There is exactly one auth subscription in the app, S2.9's `SessionProvider`, exposing
      `SessionState` with `status: 'loading' | 'signedIn' | 'signedOut'`, and the S2.9 guards treat
      `loading` as **wait**, never as signed out. `grep -rn "onAuthStateChange" src/` returns one hit.
      This is the single line that makes AC7 and [S2.5](S2.5-deep-link-return-path.md) work.
- [ ] **AC9** — The splash rendered during `loading` is the same markup as the static shell in
      `index.html`, so the handover to React produces no visible change. Verified by two screenshots at
      375px being byte-identical.
- [ ] **AC10** — On a genuine refresh-token failure, the user is sent to `/#/login` with the line "You've
      been signed out. Sign in again.", the TanStack Query cache is cleared, and the route they were on is
      stored as the intended route (S2.5) so they return to it.
- [ ] **AC11** — Signing out clears the session, calls `queryClient.clear()`, and removes
      `pfc.pendingJoin` and `pfc.intendedRoute`. Signing in as a second user on the same device shows
      none of the first user's cached data.
- [ ] **AC12** — Resuming the app after a long background — tab hidden, or the installed PWA reopened —
      issues at most one `getSession()` before the first data query, so no screen renders an auth error
      that a refresh would have fixed.
- [ ] **AC13** — A session survives the D43 service-worker update reload.
- [ ] **AC14** — Nothing outside `src/lib/supabase.ts` reads the auth storage key directly.
      `grep -rn "pfc.auth" src/` returns one hit.
- [ ] **AC15** — No access token, refresh token or phone number reaches Sentry from this story's code
      paths. The D16 scrubber covers the number; the tokens are simply never put in a message.
- [ ] **AC16** — There is no "remember me" checkbox, no session-length setting and no timeout copy
      anywhere in the UI.
- [ ] **AC17** — The brief's two longevity claims each have a named proof, and neither is proved by
      waiting (D59). "Reopening after 24 hours does not force a re-login" is AC5's Vitest proxy: a stored
      session whose access token expired 25 hours ago restores with one refresh and no `/login`
      navigation. "A player should not need to re-enter a password for a full season" is AC1 plus the
      config-drift test: `jwt_expiry`, rotation on, no absolute timebox, 365-day inactivity window.

## Implementation notes

### Configuration

```toml
# supabase/config.toml
[auth]
jwt_expiry = 3600
enable_refresh_token_rotation = true
refresh_token_reuse_interval = 10

[auth.sessions]
timebox = "0h"              # no absolute cap: a player should not be logged out mid-season
inactivity_timeout = "8760h" # 365 days
```

The CLI version must support `[auth.sessions]`; pin the CLI version in
[S0.7](S0.7-ci-pipeline.md) so this does not silently become a no-op. If the pinned CLI does not support
it, the local stack keeps its default and `docs/supabase-config.md` carries the hosted values, with a
line saying which half is asserted where. Do not invent a key the CLI ignores and call it done.

### The client

```ts
// src/lib/supabase.ts   (created by S1.5; these options are fixed here)
export const supabase = createClient<Database>(
  env.VITE_SUPABASE_URL,                    // from @/lib/env — the only env reader (S1.5 AC6)
  env.VITE_SUPABASE_ANON_KEY,               // public, not a secret (D38)
  {
    auth: {
      persistSession: true,
      autoRefreshToken: true,
      // HashRouter owns the fragment. Every deep link is "#/event/...", and GoTrue's
      // URL parsing would try to read it as an auth response. There is no external
      // callback in this app (D1), so there is nothing for it to find.
      detectSessionInUrl: false,
      storageKey: 'pfc.auth',
      flowType: 'implicit',   // S1.5 sets this; there is no PKCE callback to land on (D1)
    },
  },
)
```

### The boot gate

[S2.9](S2.9-auth-guard-and-role-context.md) already ships the subscription, in
`src/features/auth/session-provider.tsx`:

```ts
export type SessionState =
  | { status: 'loading';  session: null }
  | { status: 'signedOut'; session: null }
  | { status: 'signedIn';  session: Session }
```

Do not add a second provider with a second vocabulary. This story fixes that provider's boot contract and
adds the splash gate around it, in `src/app/app-boot.tsx`:

```tsx
// src/app/app-boot.tsx
export function AppBoot({ children }: { children: ReactNode }): ReactElement
// renders <AppSplash /> while useSession().status === 'loading', children otherwise
```

- The provider's mount effect: `supabase.auth.getSession()` once, then
  `supabase.auth.onAuthStateChange((event, session) => …)`, unsubscribed on unmount. One subscription in
  the app (AC8).
- Set `status` from the first resolution. Never start at `'signedOut'`; an optimistic signed-out start is
  exactly the flash AC7 forbids.
- Events handled: `INITIAL_SESSION`, `SIGNED_IN`, `TOKEN_REFRESHED`, `USER_UPDATED` set the session;
  `SIGNED_OUT` runs the teardown below. Any other event is ignored, not thrown on.
- `AppBoot` wraps the router, so no route — guarded or not — resolves against an unknown session.

Order at the root, which [S2.5](S2.5-deep-link-return-path.md) depends on:

```tsx
// src/main.tsx
<QueryClientProvider client={queryClient}>
  <SessionProvider>              // S2.9: the one subscription
    <AppBoot>                    // 1. session   (this story) — splash until status settles
      <RouterProvider router={router} />
    </AppBoot>
  </SessionProvider>
</QueryClientProvider>
```

The two later gates live **inside** the router, in the root route element, because both call
`useNavigate()` and a component above `<RouterProvider>` has no router:

```tsx
// src/app/root-layout.tsx — the element of the route table's root route (S0.3)
<PendingJoinGate>     // 2. pending join     (S2.4) — renders "Joining {team}…" while it works
  <IntendedRouteGate> // 3. intended route   (S2.5) — navigates once, replace: true
    <Outlet />
```

[S0.3](S0.3-routing.md) creates the router with `createHashRouter(routes)`. Move that call into
`src/app/router.ts` and import the instance from `src/main.tsx`, so non-React code — the teardown below —
can call `router.navigate()`. That is the only change this story makes to S0.3's wiring.

### The splash, and no flash

Put the splash markup in `index.html` inside `<div id="root">`: club crest centred, background from the
theme token, nothing else. React's first paint replaces it with the identical `<AppSplash />` component,
so nothing moves. Both read their colour from the same CSS custom property, declared once in the S0.2
token layer — no hardcoded hex (`CLAUDE.md` §3).

### Teardown

```ts
// src/features/auth/session-provider.tsx
import { router } from '@/app/router'

function teardown(reason: 'signed-out' | 'expired') {
  queryClient.clear()
  clearPendingJoin()                                            // S2.1's module, S2.4's key
  if (reason === 'expired') setIntendedRoute(currentHashPath()) // S2.5's module, S2.9's name
  else clearIntendedRoute()
  router.navigate('/login', { replace: true })                  // not useNavigate: this runs above the router
}
```

`currentHashPath()` reads `window.location.hash.slice(1)` and returns `/` when it is empty; it never
returns an absolute URL, because `setIntendedRoute` would reject one anyway (S2.5 AC10).

`SIGNED_OUT` fires both when the user taps sign out and when a refresh genuinely fails, so the handler
distinguishes them by whether a sign-out was requested, held in a module ref set just before
`supabase.auth.signOut()`. The expiry case carries the copy in AC10; the deliberate case carries none.

A player whose password a manager has just reset (D10) arrives here on their other device. That is
correct. No special copy, no explanation the app cannot verify.

### Long background

`visibilitychange` to visible, and the PWA `resume` path, both call `supabase.auth.getSession()` once
before any refetch. Debounce so a rapid hide/show does not fire twice. TanStack Query's
`refetchOnWindowFocus` will fire in the same tick; the `getSession()` promise is awaited first so queries
do not race an expired token. Supabase v2 coordinates cross-tab refresh with `navigator.locks`, which is
absent on older iOS Safari; on mobile the app is effectively single-tab, so accept the degradation rather
than building around it.

### What not to build

No custom refresh timer. No token inspection in application code. No `jwt-decode`. No storing the session
in Zustand — it is server state by any reading, and `CLAUDE.md` §2 bans that. The Supabase client is the
only owner.

## Data and API surface

**Tables** — none.

**RPCs** — none.

**Auth calls** — `supabase.auth.getSession()`, `supabase.auth.onAuthStateChange()`,
`supabase.auth.signOut()`. `signInWithPassword` and `signUp` belong to
[S2.2](S2.2-sign-in.md) and [S2.1](S2.1-registration.md).

**Zod schemas** — none. The session is Supabase's type, used as given.

**Query keys** — none added. This story clears the whole cache on a session change; it populates nothing.

**Client state** — `AuthStatus` in React context. `localStorage` keys touched: `pfc.auth` (Supabase's, by
Supabase only), and on teardown `pfc.pendingJoin` and `pfc.intendedRoute`.

## Test plan

- **Unit** — Vitest with a mocked Supabase client. A stored session whose `expires_at` is in the past
  triggers exactly one refresh and resolves `status` to `signedIn`, with no navigation (D59, AC5, AC6). The
  same test with `expires_at` 25 hours in the past is AC17's 24-hour proof. `SIGNED_OUT` with a sign-out ref set clears the cache and both keys and does not store an
  intended route; without it, stores the current path and shows the expiry copy. `getSession()` rejecting
  resolves to `signedOut`. Two `visibilitychange` events within the debounce window produce one
  `getSession()`.
- **Integration / RLS** — none. No policy changes; [S1.4](S1.4-rls-test-suite.md) must still pass. Add a
  config assertion to the `check` job: a test parses `supabase/config.toml` and fails if `jwt_expiry`,
  rotation or the inactivity window drift from the values in AC1. This is how D59's claim stays true.
- **E2E** — `tests/e2e/session.spec.ts` against `vite preview` and the local stack (D17): sign in, save
  `storageState`, open a new page with it, and assert with a `page.on('domcontentloaded')` guard that the
  sign-in heading never appears and the home screen renders (AC7). Second spec: reload twice across a
  service-worker update and assert the session survives (AC13, with D43's release-string check). Third:
  sign out, then assert the previous user's event titles are absent from the next sign-in (AC11).
- **Manual** — install to the home screen, sign in, close the app, leave it a day, reopen. Land on home
  with the next event, not on the login screen. Recorded in `docs/device-pass.md` for
  [S7.4](S7.4-device-pass.md).

## Open questions

1. **Does the pinned Supabase CLI support `[auth.sessions]`?** Proposed default: if not, set the hosted
   project by hand, record it in `docs/supabase-config.md`, and assert only the client-side half in CI.
   Recheck at the next CLI bump. The story does not wait on this.
2. **What happens to a player whose refresh token expires while offline in a car park?** Proposed
   default: `getSession()` resolves `signedOut`, the login screen renders with its offline line, and
   nothing is lost because no response was in flight. There is no offline write queue (D48).
3. **Should the expiry line say why?** Proposed default: no. The app cannot tell a genuine expiry from a
   manager-issued reset (D10) from a revoked token, and guessing wrong in copy is worse than saying
   nothing. One line, no cause.
