## Goal

A player taps History in the bottom nav and sees the past events they were part of, newest first, each
marked Attended, Absent or Not recorded. Nothing on the screen is editable. It exists so a player can check
what the manager wrote down without asking, and so a manager who got it wrong gets told.

## Context

The brief's S3.5 is two lines: a simple list of past events with attended / did not attend, read-only for
players. Four decisions fill in what it leaves unsaid.

[D25](../00-decisions.md) settles the third state: absence of an `attendance` row means "not recorded", it
is never stored as a value, and `attended` is `boolean not null`. This screen renders three states, not
two. [D33](../00-decisions.md) settles who can still read what: the player select policies on
`event_responses` and `attendance` key on `user_id = auth.uid()` with no membership test, and a player may
additionally select any `events` row for which they hold a response or attendance row — so a player who
left a team keeps their history, and S6.4's retention promise means something. [D34](../00-decisions.md)
adds the route, `/history`, which the brief's supposedly-fixed route list omits, and
[D41](../00-decisions.md) puts History in the fixed bottom nav for every role.
[D39](../00-decisions.md) adds the `attendance(user_id)` index that makes the read cheap.

Two things this screen must not become. It is not a stats screen: appearance counts, percentages, streaks
and "played 14 of 20" are player stats, which `CLAUDE.md` puts out of scope outright. And it is not a second
availability screen: it shows what happened, not what the player said beforehand.

One vocabulary across the app. [S4.4](S4.4-player-response-list.md) and
[S4.5](S4.5-record-attendance.md) label the manager's three-state control `Not recorded | Attended |
Absent`. This screen uses the same three words, so a player and a manager describing the same row use the
same term. That is a deliberate reading of the brief's "attended / did not attend".

The build order ([D20](../00-decisions.md)) puts this at 34, after S4.5, so there is real recorded
attendance to read rather than a screen of Not recorded.

## Scope

**In**

- The `/history` route and screen, reached from the bottom nav.
- One paged read: past events the player may see, with their own attendance row embedded.
- `filterHistory()`, the pure function deciding which past events are this player's.
- Three-state rendering per row, and a fourth presentation for a cancelled past event.
- Rows link to `/#/event/:id`, where S3.3 and S3.4 already render the read-only past state.
- Paging: 25 rows a page behind a "Show more" button.
- Loading, empty, error and populated states.

**Out**

- Any aggregate, count, percentage, streak or ranking. Out of scope in `CLAUDE.md`, permanently.
- Any edit affordance. Attendance is written by managers only (S4.5); the player grant is select-only and
  this feature contains no write of any kind.
- The player's own availability answer per row. History answers "were you there", not "did you say you
  would be". One pill per row.
- Any view of anyone else's history. S4.4 is the manager's per-event list; there is no per-player view for
  managers in v1.
- Filtering or grouping by team, type or date. A flat list, newest first.
- Export, share, print, calendar.

### The read

One select against `events` with the caller's own attendance embedded. RLS does the narrowing: the player
select policy on `attendance` is `user_id = auth.uid()`, so the embedded array holds at most the caller's
own row and AC6 holds without a client-side filter.

```ts
// src/api/attendance.ts
export const HISTORY_SELECT =
  'id, team_id, type, title, starts_at, status, attendance!attendance_event_id_fkey(attended)' as const

const PAGE_SIZE = 25

type HistoryPageParam = { page: number; cutoffIso: string }

supabase
  .from('events')
  .select(HISTORY_SELECT)
  .lt('starts_at', param.cutoffIso)
  .order('starts_at', { ascending: false })
  .range(param.page * PAGE_SIZE, param.page * PAGE_SIZE + PAGE_SIZE - 1)
```

Driven by `useInfiniteQuery` with

```ts
initialPageParam: { page: 0, cutoffIso: deviceNowIso() },
getNextPageParam: (last, _pages, lastParam: HistoryPageParam) =>
  last.length === PAGE_SIZE ? { page: lastParam.page + 1, cutoffIso: lastParam.cutoffIso } : undefined,
```

The cutoff is carried in the page param rather than recomputed per page. Offset paging against a moving
`lt` boundary duplicates or skips a row whenever an event crosses into the past between page one and page
two; pinning it to the first page's value removes that. A "Show more" button, not an intersection
observer: a season is sixty rows, not six thousand.

The screen sees one hook, already flattened and filtered, so `HistoryScreen.tsx` holds no paging logic:

```ts
// src/api/attendance.ts
export function useAttendanceHistory(userId: string): {
  rows: HistoryRow[]              // every page flattened, then filterHistory()
  status: 'pending' | 'error' | 'success'
  hasNextPage: boolean            // drives "Show more"; raw page length, not filtered length
  isFetchingNextPage: boolean
  fetchNextPage: () => void
  refetch: () => void             // wired to the error state's Retry
}
```

```ts
// src/api/queryKeys.ts — S1.5's userKeys, imported here, not redeclared
  history: (userId: string) => ['history', userId] as const,
```

The key is player-scoped and sits outside `eventKeys.all`, so S3.4's response invalidation and S4.5's
`eventKeys.attendance(eventId)` invalidation (S4.4's key, `['events', 'attendance', eventId]`) do not
churn it. A manager correcting attendance is picked up on this player's next visit or focus refetch,
which is soon enough.

### Normalising the embed

The embed returns `attendance: { attended: boolean }[]` of length 0 or 1. Collapse it in the schema, so no
component ever sees an array:

```ts
// src/features/attendance/schema.ts   (attendanceRowSchema itself is S1.5's)
export type AttendanceState = 'attended' | 'absent' | 'not-recorded'

export const historyRowSchema = eventRowSchema
  .pick({ id: true, team_id: true, type: true, title: true, starts_at: true, status: true })
  .extend({ attendance: z.array(z.object({ attended: z.boolean() })).max(1) })
  .transform(({ attendance, ...row }) => {
    const first = attendance[0]
    return {
      ...row,
      attendance: (first === undefined
        ? 'not-recorded'
        : first.attended
          ? 'attended'
          : 'absent') satisfies AttendanceState,
    }
  })

export type HistoryRow = z.infer<typeof historyRowSchema>
```

`noUncheckedIndexedAccess` is on, so the `undefined` check is required by the compiler rather than added
out of caution. Parse with `z.array(historyRowSchema).parse(data)` in the query function, so a shape change
in PostgREST fails at the boundary and not three components deep.

### The cutoff, and why the device clock is allowed here

[S3.4](S3.4-changing-a-response.md) forbids the device clock, because there the boundary is a permission
the server enforces and a wrong clock produces a tap the server refuses. Here the boundary only decides
whether an event that started three minutes ago appears in this list or in S3.2's upcoming list. Nothing
depends on the two agreeing to the second, and no write is gated on it. So `cutoffIso` is the device clock,
read once, when the first page param is built, and pinned there for every later page. It never enters
the query key, which would churn on every render, and it is never re-read per page. One named helper, so
the single place this feature reads the device clock is greppable. S1.5's lint rules ban `toLocaleString`
and `Intl.DateTimeFormat`, not `new Date()`, so this one is a review check, not a compiler one:

```ts
// src/lib/time.ts — beside formatEventTime (S1.5)
export const deviceNowIso = (): string => new Date().toISOString()
```

### The pre-join filter

The player read policy on `events` grants every event on every team they currently belong to, including
events from before they joined. Left alone, someone joining in March opens History and finds the previous
September onwards, all Not recorded. Filter against the memberships `useCurrentUser()` already exposes
(S2.9), which carry `joinedAt` ([D26](../00-decisions.md)):

```ts
// src/features/attendance/history-filter.ts
import type { TeamMembership } from '@/features/auth/use-current-user'

export function filterHistory(
  rows: readonly HistoryRow[],
  memberships: readonly TeamMembership[],
): HistoryRow[]
```

Keep a row when its `attendance` is not `'not-recorded'`, **or** when the player holds a membership of
`row.team_id` whose `joinedAt <= row.starts_at`. Drop it otherwise. A row for a team the player has left has
no membership and survives on its recorded result alone, which is AC7.

The filter runs after paging, so a page can render fewer than 25 rows. That is accepted: "Show more" is
driven by the raw page length, never the filtered length, so the player can always keep going and never
faces a dead button with rows still behind it.

### The row

`HistoryRow.tsx` renders a shadcn `Card` wrapped in a React Router `Link` to `/event/${id}`:

- Line one — the title, with the pill right-aligned.
- Line two — `formatEventTime(starts_at, 'short')`, a middot, then "Training" or "Match" via S3.3's
  `EventTypeBadge`.
- `min-h-14`, comfortably over the 44px floor with two lines of text.

`AttendancePill` is a shadcn `Badge`, and every variant carries its word:

| Row | Label | Variant |
|---|---|---|
| `attended` | Attended | `default` |
| `absent` | Absent | `outline` |
| `not-recorded` | Not recorded | `secondary` |
| `status === 'cancelled'` | Cancelled | `secondary`, and no attendance pill is rendered |

Location and notes are not shown. The row is a link; the detail screen has them.

### Gotchas

- Name the FK hint in the embed (`attendance!attendance_event_id_fkey`). `events → attendance` resolves
  today through the one FK between them, so the hint is not strictly required; name it anyway, because an
  ambiguous embed fails at runtime and not at build, and a second FK added later would break this query
  silently. The name is Postgres's default for `attendance.event_id references events(id)`.
- Do not add a `user_id` filter to the embed. RLS already restricts it to the caller, and a parameterised
  filter invites someone later to reuse this hook for a manager view the policy would refuse anyway. This
  is the opposite of S3.3's `event_responses` embed, where the manager policy is wide and the filter is
  correctness — the difference is that a player has no wider read here at all.
- Flatten all `useInfiniteQuery` pages before filtering, not per page and then concatenate, or a membership
  boundary straddling a page edge behaves differently on each side.
- Pad the list container with the shell's bottom-nav offset plus `env(safe-area-inset-bottom)`, or the last
  row hides under the nav on an iPhone.
- Cancelled events are in the list (AC4) and are also subject to the pre-join filter. A cancelled event
  before the player joined, with no attendance row, is correctly dropped.

## Data and API surface

**Tables** — `events` (SELECT), `attendance` (SELECT, own rows only, as an embedded resource). No INSERT,
UPDATE, UPSERT or DELETE anywhere in this story.

**RPCs** — none. Team names are not shown, so `team_member_directory` is not needed.

**Zod** — `historyRowSchema` and the `AttendanceState` union, added to `src/features/attendance/schema.ts`,
derived from S1.5's `eventRowSchema` rather than hand-written.

**Query keys** — `userKeys.history(userId) = ['history', userId]`, an infinite query. Nothing invalidates
it; it refetches on focus.

**Mutations** — none.

## Open questions

1. **Does the seed carry enough attendance to test this?** S1.2's seed creates a past event per team but
   says nothing about recorded attendance. **Proposed default:** extend the seed so one named player has
   one attended, one absent and one unrecorded past event, plus one cancelled past event — three extra
   `attendance` rows, no schema change, no new fixture set ([D15](../00-decisions.md)). Raise it against
   S1.2 rather than inventing a second fixture here.
2. **Should History mix every team into one list, or split by team?** **Proposed default:** one mixed list
   with no team label. A player is normally in one squad and the brief asks for a simple list. If
   multi-squad players turn out to be common, add the team name to line two — not a filter, not tabs.
3. **Should a past event the player answered but was never marked at appear?** It does today, through the
   membership branch of `filterHistory`, which covers every realistic case. **Proposed default:** leave
   `event_responses` out of this query entirely. If a leaver's answered-but-unrecorded events ever matter,
   add a second embed, not a second query.
4. **How far back should History go?** **Proposed default:** all of it, paged. Nothing is ever deleted
   ([D33](../00-decisions.md)) and a season is under a hundred rows, so a cap would cost more than it saves.
