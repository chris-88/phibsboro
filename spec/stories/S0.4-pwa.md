## Goal

A player can add the app to their home screen and launch it in standalone mode, and a deploy reaches them
without them clearing anything. This is the half of the journey that happens after the first Yes: the
player keeps the app, and the next event is one tap from the home screen rather than a scroll through
WhatsApp.

## Context

The brief's S0.4 asks for a manifest, icons, a service worker, installability on iOS and Android, and
"Service worker does not serve stale app shell after a deploy" — without naming a caching strategy. With
HashRouter every deep link is served by the same `index.html`, so one stale shell breaks every link the
club has ever sent. Two decisions settle it:

- [D43](../00-decisions.md) — `vite-plugin-pwa` with `registerType: 'autoUpdate'`. Navigations are
  network-first with a 3-second timeout falling back to the cached shell. Hashed build assets are
  cache-first. Supabase REST and RPC requests are never cached. `skipWaiting` and `clientsClaim`, and one
  reload on `controllerchange`. The staleness criterion is a two-build reload test in CI.
- [D44](../00-decisions.md) — Lighthouse installability covers Android Chrome only. iOS coverage is the
  S7.4 device pass plus a build check that `apple-touch-icon` and `apple-mobile-web-app-capable` are
  present. One helper, `isStandalone()`, is the only standalone check in the codebase, because the
  `display-mode: standalone` media query does not match on iOS.

D43 says the staleness check runs "in the `e2e` job". There is no `e2e` job until S7.3, so this story adds
its own `pwa` job instead. Same check, earlier, with no Supabase stack behind it.

This story builds after S0.5 ([D20](../00-decisions.md)) so installability and standalone launch are
checked on a real HTTPS origin — a service worker will not register otherwise, except on `localhost`.
It is exempt from the S1.4 gate ([D55](../00-decisions.md)): it touches no team data.

S0.5 already landed `playwright.config.ts` and the `smoke-deployed` project. This story adds a second
project, `pwa`, to that same config. S2.5 and S7.3 add theirs to it too; there is one harness, never two.

## Scope

**In**
- `vite-plugin-pwa` configured per D43, with the manifest and Workbox options defined in testable modules.
- Manifest, icon set including a maskable icon and a 180x180 `apple-touch-icon`, iOS meta tags.
- Service worker registration with a single reload on `controllerchange`, and an update check when the tab
  becomes visible.
- `isStandalone()` in `src/lib/`.
- A `pwa` Playwright project added to the S0.5 config, and a `pwa` CI job: the two-build staleness test,
  an offline shell test, and a Lighthouse installability gate against `vite preview`.

**Out**
- The install prompt UI and the `beforeinstallprompt` capture — that is S2.8.
- The WhatsApp webview escape prompt — S2.7.
- Push notifications, background sync, periodic sync. Out of scope in the brief; not scaffolded, not
  TODO'd.
- Offline data. The shell loads offline; every data screen shows its error state. There is no write queue
  and no cached Supabase response.
- The bottom nav's safe-area padding and the full-screen route rule — S0.2 ([D41](../00-decisions.md)).

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — A manifest is served at `/manifest.webmanifest` with `id`, `start_url` and `scope` all `/`,
      `display: 'standalone'`, `name: 'Phibsboro FC'`, `short_name: 'Phibsboro'`, and `theme_color` and
      `background_color` equal to the S0.2 theme tokens, and `dist/index.html` carries
      `<link rel="manifest" href="/manifest.webmanifest">`. `src/pwa/manifest.test.ts` reads
      `src/index.css`, extracts `--pwa-theme-color` and `--pwa-background-color`, and asserts each equals
      the matching manifest field, so a token change that misses the manifest fails the build.
- [ ] **AC2** — Icons exist at 192x192 and 512x512 with `purpose: 'any'`, a 512x512 with
      `purpose: 'maskable'`, and `public/apple-touch-icon.png` at 180x180. `src/pwa/icons.test.ts` reads
      the PNG IHDR chunk of each file (bytes 16-23, two big-endian uint32s) and asserts the width and
      height equal the size declared in the manifest, so a resized or swapped icon fails the build.
- [ ] **AC3** — `index.html` contains `<link rel="apple-touch-icon">`, `<meta name="apple-mobile-web-app-capable" content="yes">`,
      `<meta name="apple-mobile-web-app-title" content="Phibsboro">` and a `theme-color` meta whose value
      equals the manifest's `theme_color`. Asserted in `src/pwa/icons.test.ts`, which reads `index.html`
      from disk — this is the whole of the iOS automated coverage ([D44](../00-decisions.md)).
- [ ] **AC4** — Lighthouse's `installable-manifest` and `service-worker` audits pass against
      `vite preview`, gated in CI. No other Lighthouse category is enabled or asserted.
- [ ] **AC5** — Stale shell, the load-bearing one: build A is served and loaded; `dist/` is replaced with
      build B carrying a different `pfc-release`; after two reloads the release meta on screen is build B's.
      Runs in the `pwa` CI job.
- [ ] **AC6** — With the service worker active and the network offline, reloading `/#/` renders the app
      shell rather than the browser's offline page. Asserted with `context.setOffline(true)`.
- [ ] **AC7** — The generated service worker declares exactly one runtime-caching route, matching
      navigations only, with `networkTimeoutSeconds: 3`. A unit test asserts the exported Workbox options
      object, so no route matching `VITE_SUPABASE_URL` can be added without failing.
- [ ] **AC8** — A cold hard-load of `/#/event/<uuid>` with the service worker controlling resolves to the
      event route, not to the 404 screen, and not to `/`. This is the WhatsApp link, and it is the reason
      the story exists.
- [ ] **AC9** — `isStandalone()` is exported from `src/lib/standalone.ts`, covers both the media query and
      the iOS `navigator.standalone` flag, and is the only standalone check in the codebase. A rule
      appended to `scripts/check-conventions.mjs` (S0.2) fails `npm run lint` if `display-mode: standalone`
      or `navigator.standalone` appears anywhere under `src/` outside `src/lib/standalone.ts`.
- [ ] **AC10** — The service worker is disabled in `npm run dev` (`devOptions.enabled: false`), so a
      development reload never serves a cached bundle, and `navigator.serviceWorker.controller` is null on
      `http://localhost:5173`.
- [ ] **AC11** — The update reload happens at most once per activation. A `controllerchange` fired twice
      does not produce a reload loop; asserted by a unit test on the registration module.
- [ ] **AC12** — Installing on a real iPhone and a real Android device, launching from the home screen, and
      confirming standalone mode, is recorded in `docs/device-pass.md` by S7.4. This story ships the build
      checks; iOS installability is signed off there ([D44](../00-decisions.md), [D56](../00-decisions.md)).
- [ ] **AC13** — Nothing in the service worker or the manifest requests notification, push or background
      sync permission. Grep for `Notification`, `pushManager` and `periodicSync` returns nothing.

```
public/icons/icon-192.png

src/pwa/manifest.test.ts          AC1
src/pwa/icons.test.ts             AC2, AC3
playwright.config.ts              extended: adds the `pwa` project alongside S0.5's `smoke-deployed`
tests/e2e/global-setup.pwa.ts           builds build-a and build-b for AC5
tests/e2e/pwa-update.spec.ts            AC5
tests/e2e/pwa-offline.spec.ts           AC6, AC8
scripts/check-conventions.mjs     extended: the standalone-check rule, AC9
```

Defining the manifest and Workbox options as TypeScript modules rather than inline literals in
`vite.config.ts` is the whole trick that makes AC1 and AC7 unit-testable.

### Plugin configuration

```ts
// vite.config.ts
VitePWA({
  registerType: 'autoUpdate',
  injectRegister: null,          // registered explicitly in src/main.tsx
  manifest,                      // from src/pwa/manifest.ts
  workbox: workboxOptions,       // from src/pwa/workbox.ts
  devOptions: { enabled: false },
})
```

```ts
// src/pwa/workbox.ts
export const workboxOptions = {
  globPatterns: ['**/*.{js,css,html,svg,png,webmanifest}'],
  navigateFallback: null,        // the NetworkFirst route below owns navigations instead
  cleanupOutdatedCaches: true,
  clientsClaim: true,
  skipWaiting: true,
  runtimeCaching: [
    {
      urlPattern: ({ request }: { request: Request }) => request.mode === 'navigate',
      handler: 'NetworkFirst',
      options: {
        cacheName: 'pfc-shell',
        networkTimeoutSeconds: 3,
        expiration: { maxEntries: 1 },
        cacheableResponse: { statuses: [200] },
      },
    },
  ],
} as const
```

`navigateFallback` is null on purpose. Left at its default, Workbox registers a navigation route served
straight from the precache — cache-first — which is exactly the stale shell the brief forbids. Everything
that is not a navigation and not a precached asset falls through to the network with no handler, which is
how Supabase REST and RPC traffic stays uncached without naming it.

### Manifest

```ts
// src/pwa/manifest.ts
// The two hex literals below must equal --pwa-theme-color and --pwa-background-color in src/index.css.
// manifest.test.ts parses that file and fails if they drift. This file is the only hex-literal exemption.
const THEME_COLOR = '#0b3d2e'
const BACKGROUND_COLOR = '#ffffff'

export const manifest = {
  id: '/',
  name: 'Phibsboro FC',
  short_name: 'Phibsboro',
  description: 'Training and match availability for Phibsboro FC.',
  start_url: '/',
  scope: '/',
  display: 'standalone',
  orientation: 'portrait',
  theme_color: THEME_COLOR,
  background_color: BACKGROUND_COLOR,
  icons: [
    { src: '/icons/icon-192.png', sizes: '192x192', type: 'image/png', purpose: 'any' },
    { src: '/icons/icon-512.png', sizes: '512x512', type: 'image/png', purpose: 'any' },
    { src: '/icons/icon-512-maskable.png', sizes: '512x512', type: 'image/png', purpose: 'maskable' },
  ],
} as const
```

The two hex values are declared once in the S0.2 token layer, `src/index.css`, as `--pwa-theme-color` and
`--pwa-background-color`, and repeated in `src/pwa/manifest.ts` because a manifest cannot read CSS. That
repetition is why AC1's test parses `src/index.css` and compares. `src/pwa/manifest.ts` is the one path
added to the hex-literal allowlist in `scripts/check-conventions.mjs` (S0.2 AC3); nowhere else under
`src/` may carry a hex colour. `start_url` stays `/` even though a player may install from
`/#/event/abc123`; the installed app opens on home, which is what a returning player wants.

### Registration

```ts
// src/pwa/registerServiceWorker.ts
import { registerSW } from 'virtual:pwa-register'

let reloading = false

export function registerServiceWorker(): void {
  if (!('serviceWorker' in navigator)) return
  navigator.serviceWorker.addEventListener('controllerchange', () => {
    if (reloading) return
    reloading = true
    window.location.reload()
  })
  const update = registerSW({ immediate: true })
  document.addEventListener('visibilitychange', () => {
    if (document.visibilityState === 'visible') void update()
  })
}
```

Called from `src/main.tsx` after render. The visibility check matters more than it looks: a player who
installed the app in March opens it on a Tuesday night, and that is the moment to pick up April's build.

### isStandalone

```ts
// src/lib/standalone.ts
export const isStandalone = (): boolean =>
  matchMedia('(display-mode: standalone)').matches ||
  (navigator as Navigator & { standalone?: boolean }).standalone === true
```

Verbatim from [D44](../00-decisions.md). S2.7 and S2.8 both call it; neither writes its own.

### Playwright harness

S0.5 created `playwright.config.ts` with the `smoke-deployed` project. This story adds a second project:

```ts
{
  name: 'pwa',
  testMatch: /pwa-.*\.spec\.ts/,
  globalSetup: './tests/e2e/global-setup.pwa.ts',
  use: { baseURL: 'http://127.0.0.1:4173', timezoneId: 'Europe/Dublin' },  // D53
}
```

with `webServer: { command: 'npm run preview -- --port 4173', url: 'http://127.0.0.1:4173', reuseExistingServer: !process.env.CI }`
at the top level. S7.3 later adds `e2e`. Playwright never drives the live site except for the S0.5
`smoke-deployed` project ([D17](../00-decisions.md)).

### The two-build staleness test

`tests/e2e/global-setup.pwa.ts` builds twice into `.playwright/build-a` and `.playwright/build-b` with
`VITE_SENTRY_RELEASE=build-a` and `build-b`, so the `pfc-release` meta tag S0.5 publishes differs between
them. The test copies build A over `dist/`, loads the page, waits
for `navigator.serviceWorker.ready`, copies build B over `dist/`, then reloads twice and asserts
`meta[name="pfc-release"]` reads `build-b`. Two reloads, not one, and the spec says why: the first reload
is served from cache while the new worker installs and takes control; the `controllerchange` reload is the
one that lands the new shell. Anything that needs a third reload is a bug in this story.

### CI job

S0.4 adds a `pwa` job to `.github/workflows/ci.yml` (S0.7): `npm ci`, `npx playwright install --with-deps chromium`,
`npm run build`, `npx playwright test --project=pwa`, then `treosh/lighthouse-ci-action` against
`http://127.0.0.1:4173` with only `installable-manifest` and `service-worker` audits asserted. It needs no
Supabase stack and no repository secret, so it runs on fork pull requests ([D14](../00-decisions.md)).

## Data and API surface

None. This story touches no table, calls no RPC, adds no Zod schema and no query key. The service worker
is configured so that it never caches a Supabase response, which is the only way it relates to server state
at all.

## UI states

Not a UI story. It adds no screen and changes no screen's content. The only visible behaviour it
introduces is a single silent reload when a new build takes control, which is deliberately not announced:
a "new version available" toast is a decision for nobody to make at a car park in the rain.

## Test plan

- **Unit** — `src/pwa/manifest.test.ts` asserts the manifest fields and that its colours equal the S0.2
  tokens (AC1); `src/pwa/workbox.test.ts` asserts exactly one runtime-caching route, `mode === 'navigate'`,
  `networkTimeoutSeconds: 3`, and no route matching the Supabase origin (AC7);
  `src/pwa/registerServiceWorker.test.ts` asserts one reload for two `controllerchange` events and an
  update call on `visibilitychange` (AC11); `src/lib/standalone.test.ts` covers the media query true case,
  the iOS `navigator.standalone` true case, and both false (AC9); `src/pwa/icons.test.ts` reads each PNG's
  IHDR dimensions and asserts `index.html` carries the four iOS and theme-colour tags plus the manifest
  link (AC2, AC3); the `scripts/check-conventions.mjs` standalone rule has a fixture case that fails on a
  stray `display-mode: standalone` (AC9); and a grep test for `Notification`, `pushManager` and
  `periodicSync` over `src/` and `dist/sw.js` (AC13).
- **Integration / RLS** — none. This story predates the schema and is exempt from the S1.4 gate
  ([D55](../00-decisions.md)).
- **E2E** — `tests/e2e/pwa-update.spec.ts` for the two-build staleness check (AC5);
  `tests/e2e/pwa-offline.spec.ts` for the offline shell (AC6) and the controlled cold deep link (AC8); the
  Lighthouse gate (AC4). All against `vite preview`.
- **Manual** — on the deployed site: install to the home screen on a real iPhone (Share → Add to Home
  Screen) and a real Android (Chrome install prompt), launch each from the home screen, confirm no browser
  chrome, open a `/#/event/<id>` link from a WhatsApp message and confirm it lands on the event. Recorded
  in `docs/device-pass.md` under S7.4.

## Open questions

1. **Where do the icons come from?** Default: generate all four from a single 1024x1024 source crest at
   `design/icon-source.png`, with the maskable variant padded to the 80% safe zone. If the club has no
   usable crest file, ship a plain lettermark on the theme background and replace it later — the sizes and
   filenames do not change, so it is a one-commit swap.
2. **Should the app announce an update instead of reloading silently?** Default: reload silently, as
   specified. A reload mid-tap is the only failure mode, and it is rare because navigations already fetch
   the network first. Revisit only if a player reports losing a half-typed form, and note there is no
   half-typed form on the player side.
3. **Is `orientation: 'portrait'` too strict?** Default: keep it. Every screen is a one-thumb phone screen
   at 375px; nothing in the app benefits from landscape. Dropping the field is a one-line change if a
   tablet ever matters.
