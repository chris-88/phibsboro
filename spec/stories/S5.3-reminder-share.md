## Goal

Two days before the match, eight players still have not answered. The manager taps "Send a reminder" on
the event and gets a short message stating how many are outstanding, with the same link. Nobody is named
and nobody is singled out in the group chat.

## Context

The first share goes out the moment an event is created. The chase happens later, and a manager who has
to retype it will instead start tagging individuals in the group, which is exactly the behaviour the club
does not want. So the reminder is a second button, not a second workflow.

Decisions this story rests on, from [00-decisions.md](../00-decisions.md):

- **D13** fixes the reminder as the same header block with a different last line:
  `{n} still to answer. Yes or no: {url}`. No club signature, no sender name, no extra emoji. Asserted
  byte for byte.
- **Q9** settles the count question: a number, never a name. The brief's "does not name individual
  non-responders in v1" is the same rule, stated from the other side.
- **D22** defines the count. Squad is every current `team_members` row for that team regardless of role,
  so a manager who plays is chased along with everyone else. Awaiting is squad size minus responses from
  current members, computed as of now.
- **D23** makes counts poll rather than stream: [S4.3](S4.3-manager-event-view.md) sets
  `refetchInterval: 30_000` and `refetchOnWindowFocus: true` on the two queries the counts derive from,
  and a response mutation invalidates them. The number in the reminder is therefore at most thirty seconds
  stale, which for a message a human is about to send by hand is fine.
- **D52 / S5.2** own the transport. This story generates a different string and hands it to the same
  `ShareButton`.

## Scope

**In**
- `buildReminderMessage(event, outstanding)` added to `src/lib/shareMessage.ts`, beside
  [S5.1](S5.1-message-generator.md)'s `buildShareMessage`.
- A secondary "Send a reminder" control on `/manage/event/:id`, under the primary share button.
- The rules for when it is offered at all.
- Vitest coverage of the new variant, including that it names nobody.

**Out**
- Any automated or scheduled sending. There is no timer, no cron, no Edge Function, no push notification.
  The manager taps a button when they feel like it. This is on CLAUDE.md's out-of-scope list and no stub
  is left behind.
- Naming, tagging or @-mentioning non-responders, in this or any later version of the message. The
  function takes a count, not a list, so the capability does not exist.
- A direct message to one player. There is no per-player share, and no phone number leaves the app.
- A record of reminders sent. No `reminded_at` column, no table, no rate limit. A manager who taps it
  twice sends two messages, exactly as if they had typed them.
- A separate reminder for attendance or anything after the event.
- A new query. The count comes from `deriveCounts()` over the two queries
  [S4.3](S4.3-manager-event-view.md) already runs on this screen.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — `buildReminderMessage(event, outstanding)` returns the identical header block to
      `buildShareMessage(event)` — emoji and title, date line, location, optional notes, blank line —
      followed by exactly `{n} still to answer. Yes or no: {url}`.
- [ ] **AC2** — The reminder differs from the initial share. A test asserts
      `buildReminderMessage(e, 3) !== buildShareMessage(e)` and that only the final line differs.
- [ ] **AC3** — The output contains no player name and no phone number, for any input. The function's
      signature makes this structural: it accepts a `number`, never a list of people.
- [ ] **AC4** — `{n}` is the `awaiting` field of the `Counts` object `deriveCounts()` in
      `src/lib/counts.ts` returns ([D22](../00-decisions.md)) — squad size minus responses from current
      members — and equals the "Awaiting" tile rendered on the same screen at the moment of the tap. The
      component never calls `deriveCounts()` itself; it receives the same object the tile is rendered
      from.
- [ ] **AC5** — `buildReminderMessage` throws a `RangeError` for any `outstanding` that is not a positive
      integer — `0`, a negative, `1.5`, `NaN` — and the UI never lets it happen: the control is not
      rendered when awaiting is zero.
- [ ] **AC6** — The control is hidden when the event is `cancelled`, when `starts_at` has passed, and when
      awaiting is zero. Nothing is rendered in its place and no copy is added to
      [S4.3](S4.3-manager-event-view.md)'s counts block — the "Awaiting 0" tile already says it, and the
      primary share button from [S5.2](S5.2-share-action.md) is still there.
- [ ] **AC7** — The control renders into the same `data-slot="share"` region as
      [S5.2](S5.2-share-action.md)'s button, directly beneath it, visually secondary and still at least
      44px high. Label: "Send a reminder". The number lives in the message, not on the button, so it is
      stated once.
- [ ] **AC8** — Tapping it uses the same [S5.2](S5.2-share-action.md) transport: native share sheet where
      available, `wa.me` with a percent-encoded body otherwise, copy as last resort. No second
      implementation of the cascade.
- [ ] **AC9** — The message is rebuilt from the current cached count on every render, so a reminder tapped
      after a refetch carries the new number, not the number that was on screen when the page loaded.
- [ ] **AC10** — `{n} = 1` produces "1 still to answer." No special-casing, no "1 player", no pluralisation
      helper.

## Implementation notes

**The generator.** Added to the S5.1 module, reusing the module-private `eventHeader()` so the two
variants can never drift apart:

```ts
// src/lib/shareMessage.ts — added by this story
export function buildReminderMessage(event: ShareEvent, outstanding: number): string {
  if (!Number.isInteger(outstanding) || outstanding < 1) {
    throw new RangeError('buildReminderMessage: outstanding must be a positive integer')
  }
  return [
    ...eventHeader(event),
    `${outstanding} still to answer. Yes or no: ${eventUrl(event.id)}`,
  ].join('\n')
}
```

Worked example, for the test:

```
⚽ Kilbarrack away
Saturday 14 March, 7.30pm
Fairview Park pitch 3

8 still to answer. Yes or no: https://app.phibsboro.ie/#/event/9f1c...
```

**The control.** In the same header block as the primary share button on `/manage/event/:id`:

```tsx
// src/features/events/components/RemindButton.tsx
import { serverNow } from '@/lib/serverClock'
import type { Counts } from '@/lib/counts'
import { buildReminderMessage } from '@/lib/shareMessage'
import { ShareButton } from '@/features/events/components/ShareButton'

type RemindButtonProps = { event: EventRow; counts: Counts | undefined }

const open =
  event.status === 'scheduled' && new Date(event.starts_at) > serverNow()   // D48, never Date.now()

if (!open || counts === undefined || counts.awaiting < 1) return null

return (
  <ShareButton
    variant="secondary"
    label="Send a reminder"
    message={buildReminderMessage(event, counts.awaiting)}
  />
)
```

`counts` is the `Counts` object [S4.3](S4.3-manager-event-view.md) already derives in a `useMemo` from
`useEventResponses` and `useTeamMembers`. Pass it down as a prop rather than calling `deriveCounts()` a
second time, so the number on the button's message and the number in the "Awaiting" tile cannot disagree.
S4.3 renders its count tiles only when both queries have data, because a count built from one loaded query
and one empty fallback is a wrong number (S4.3 AC13). Apply the same rule to this prop: pass `undefined`
until both have data, and the guard above hides the control for exactly the cases where there is no
trustworthy number.

`ShareButton` is [S5.2](S5.2-share-action.md)'s component, unchanged. This story adds no transport code.

**Gotchas.**

- Build the message during render, from the `counts` prop, so the string is ready before the tap.
  [S5.2](S5.2-share-action.md) AC4 forbids awaiting anything inside the click handler, and awaiting a
  refetch there would cost the user gesture and kill the share sheet on iOS.
- Do not guard the button on either query's `isFetching`. A background poll every thirty seconds must not
  make the button flicker or disable under the manager's thumb; render from the last good data.
- The "past" check uses `serverNow()` from `src/lib/serverClock.ts` (D48), not `Date.now()`. A phone with
  a wrong clock must not hide a reminder that is still valid, or offer one that is not.
- The count derivation is a pure function in `src/lib/counts.ts` (D22) and already excludes responses from
  people who have left the team. Do not recompute anything here; read `awaiting`.
- Awaiting can be zero because nobody has joined the team yet, not because everyone answered. In that case
  [S4.3](S4.3-manager-event-view.md)'s empty state — "No one has joined this team yet", plus the join-link
  share button from [S6.2](S6.2-team-join-links.md) — is already showing, and this control stays hidden.
  That is the right outcome: the fix is a join link, not a reminder.

## Data and API surface

No new tables, no RPCs, no mutations, no Zod schemas, no query keys. Nothing is written when a reminder is
shared.

Reads: none of its own. The component takes the event row and the derived `Counts` object as props from
[S4.3](S4.3-manager-event-view.md)'s screen, which holds `eventKeys.detail(eventId)`,
`eventKeys.responses(id)` and `teamKeys.members(teamId)` from the factories in `src/api/queryKeys.ts`.
This story subscribes to nothing and configures nothing — the polling interval belongs to S4.3.

## Open questions

1. **Should the reminder be offered anywhere other than the event screen — a list of events with
   outstanding responses, say?** **Proposed default: no.** A manager opens the event they care about.
   A cross-event chase list is a new screen and new queries for a squad of twenty.
2. **Is "1 still to answer" acceptable, or does it want pluralising?** **Proposed default: leave it.**
   D13 fixes the string and Q9 fixes the shape; a pluralisation helper for one case is not worth the
   branch. If the club objects, it is a one-line change to the template and its test.
3. **Should a reminder mention the deadline — "answers by Thursday"?** **Proposed default: no.** The app
   has no deadline concept, only `starts_at`, and inventing one would mean a new column. The date line is
   already in the message.
