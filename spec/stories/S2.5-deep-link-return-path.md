## Goal

A player taps an event link in WhatsApp, registers or signs in, and the next screen they see is that
event, ready to answer. Not the home screen, not a list they have to hunt through. This is the hinge of
the only journey that matters, and it is the one piece of it that nothing else tests.

## Context

`CLAUDE.md` marks this a **critical UX requirement**. HashRouter is used precisely so that
`/#/event/abc123` survives a hard refresh on GitHub Pages: the fragment never reaches the server, so
Pages always serves `index.html` and the router resolves the route on the client. That solves the URL.
It does not solve the interruption — an unknown user must register before they can answer, and the
destination has to survive that.

Decisions from [00-decisions.md](../00-decisions.md):

- **D1** — the duplicate `S2.2 Deep link return path` block in the brief is deleted, and this story
  absorbs it. It covers **both** unauthenticated entries: the new user who registers, and the existing
  user who signs in. Its criterion "including when auth redirects through an external callback" is
  dropped: there is no external callback. Phone confirmation is off, no SMS is sent, no OTP step exists,
  and `signUp` and `signInWithPassword` both resolve in the same document. **No `/auth/callback` route is
  added anywhere.** The intended route is held in `localStorage` under `pfc.intendedRoute` to survive a
  cold start, never in a redirect.
- **D21** — the 60-second figure is removed from this story's automated criteria. The Playwright test
  asserts the shape of the path — no more than three screens and one form submit — and the stopwatch
  moves to [S7.4](S7.4-device-pass.md) on a real mid-range Android, p50 over three runs.
- **D7** and **D6** — a stranger can read the event before joining, so the deep link has something to
  render on arrival and something to render again on return.
- **D47** — escaping the WhatsApp webview to Safari costs a second sign-in. A different browser has its
  own `localStorage`, so the intended route does **not** follow. That is admitted in the copy, not hidden.

`src/lib/intended-route.ts` is delivered earlier, by
[S2.9](S2.9-auth-guard-and-role-context.md), because its route guard is the first writer, and it ships
there as three functions: `setIntendedRoute`, `takeIntendedRoute`, `clearIntendedRoute`. This story keeps
those names and adds to them: the validation, the TTL, `peekIntendedRoute`, and the ordering against
[S2.4](S2.4-join-by-link.md)'s pending join.

`nextRouteAfterAuth()` in `src/features/auth/afterAuth.ts` is delivered by
[S2.1](S2.1-registration.md) returning `/`, and both [S2.1](S2.1-registration.md) and
[S2.2](S2.2-sign-in.md) already call it with `replace: true` after a successful `signUp` or
`signInWithPassword`. This story replaces its body. That is the warm path — a form submit in a live
document — and the root hook below is the cold path. They cannot double-navigate, because
`takeIntendedRoute()` clears on read: whichever runs first consumes the value and the other gets `null`.

## Scope

**In**
- Capturing the intended route before any navigation away from it.
- Validating, expiring and consuming it exactly once.
- The boot ordering: session, then pending join, then intended route, then the first content screen.
- The Playwright coverage the brief demands, and the `e2e` job that runs it. This story adds the `e2e`
  project to [S0.5](S0.5-deployment.md)'s `playwright.config.ts` and the `e2e` job to
  [S0.7](S0.7-ci-pipeline.md)'s `.github/workflows/ci.yml`: local Supabase stack, `npm run db:reset`,
  a build from `.env.test`, `vite preview`, Playwright ([A5](../00-decisions.md)). No repository secret,
  so it runs on fork pull requests. [S7.3](S7.3-end-to-end-journey.md) extends both later.

**Out**
- Which team the user joins on the way. That is [S2.4](S2.4-join-by-link.md).
- Restoring the session itself, and the no-flash rule for the login screen. That is
  [S2.6](S2.6-session-persistence.md).
- The route guard that triggers the redirect. That is [S2.9](S2.9-auth-guard-and-role-context.md).
- The event screen and its preview. That is [S3.3](S3.3-event-detail-screen.md).
- Timing budgets. [S7.4](S7.4-device-pass.md), per D21.
- Carrying a route between browsers, or between the WhatsApp webview and Safari. Impossible, and D47 says
  so out loud.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — An anonymous tap on `/#/event/{id}`, followed by registration, lands on `/#/event/{id}`
      for that exact id. Not home, not a list.
- [ ] **AC2** — The same tap followed by sign-in lands on the same screen.
- [x] **AC3** — The route is written to `localStorage` under `pfc.intendedRoute` **before** any navigation
      away, by both writers: the S2.9 guard on a blocked route, and the S3.3 anonymous affordances on
      `/event/:id` (both the Join button and the "Already registered? Sign in" link). The S2.1 and S2.2
      screens write nothing and clear nothing when they link to each other, so a value stored on arrival
      survives a bounce between register and sign-in.
- [x] **AC4** — The stored value is the hash path only, for example `/event/9f1c…`. Never an absolute URL,
      never including the origin, never including the `#`.
- [ ] **AC5** — It survives a cold start. Redirect to `/#/login`, kill the tab, reopen the app root, sign
      in: the event screen renders.
- [ ] **AC6** — It survives a reload part-way through registration, with the form half filled.
- [x] **AC7** — The pending join from [S2.4](S2.4-join-by-link.md) completes before the route is restored,
      so the event screen renders with availability controls, not with the "Join {team}" preview.
- [x] **AC8** — It is consumed exactly once. After landing, `pfc.intendedRoute` is absent, and a later
      manual visit to `/#/` stays on `/#/`.
- [x] **AC9** — `/login`, `/register`, `/join/:token` and `/reset/:token` are never stored as an intended
      route. They are waypoints, not destinations.
- [x] **AC10** — A stored value that does not match one of the S0.3 route patterns, or that begins `//`,
      or that contains `://`, or that is longer than 512 characters, is discarded and home is used. An
      attacker who can write `localStorage` cannot turn this into an open redirect.
- [x] **AC11** — A stored value older than 60 minutes is discarded and home is used.
- [ ] **AC12** — Exactly one content screen renders after the form submit. No home screen, no list, no
      login screen appears in between, even for a frame.
- [ ] **AC13** — Playwright asserts the new-user path from deep link to submitted Yes visits exactly the
      hash paths `['/event/{id}', '/register', '/event/{id}']` — three screens, one form submit (D21).
- [ ] **AC14** — Launching the installed PWA from the home-screen icon after the flow opens home, because
      the intended route was consumed. It never reopens a stale event.
- [x] **AC15** — No route, component or file named `callback` exists under `src/` (D1).
- [x] **AC16** — With `localStorage` unavailable — iOS private mode, or `setItem` throwing — the flow
      still works inside the tab via an in-memory fallback, and degrades to home on a cold start rather
      than throwing. No unhandled rejection, no error boundary.
- [x] **AC17** — A restored route pointing at an event on a team the user has not joined renders the S3.3
      preview with a Join button. That is a correct outcome, not a failure.
- [x] **AC18** — A restored route pointing at a deleted or unknown event renders the S3.3 not-found state,
      not the 404 route and not a blank screen.
- [ ] **AC19** — The path works in the WhatsApp in-app webview on iOS and Android, in mobile Safari, in
      mobile Chrome, and in the installed PWA. Playwright covers Chromium and WebKit; the two webviews and
      the installed app are checked by hand and recorded in `docs/device-pass.md` for
      [S7.4](S7.4-device-pass.md), because no CI browser is a WhatsApp webview. A failure in any of the
      four is a failure of this story, not of S7.4.
- [x] **AC20** — Both consumers are wired: `nextRouteAfterAuth()` returns the stored route after a form
      submit, and the root hook restores it on a cold start. Signing in twice in a row — once from a
      guarded redirect, once from the menu — navigates to the stored route the first time and to `/` the
      second, because the value was consumed (AC8).

### The store

```ts
// src/lib/intended-route.ts — S2.9 ships the first three names; keep them.
const KEY = 'pfc.intendedRoute'
const TTL_MS = 60 * 60 * 1000

/** Path only, e.g. "/event/9f1c...". No origin, no "#". Silently ignores a path on the deny list. */
export function setIntendedRoute(path: string): void

/** Reads, validates, clears, returns. Null when absent, stale, invalid or denied. */
export function takeIntendedRoute(): string | null

/** Same validation, no clear. For the boot gate deciding whether to wait. */
export function peekIntendedRoute(): string | null

export function clearIntendedRoute(): void

/** Exported for its own tests and for the lint-visible allowlist. */
export function isRestorableRoute(path: string): boolean
```

```ts
// src/features/auth/afterAuth.ts — S2.1 ships this returning '/'
export function nextRouteAfterAuth(): string {
  return takeIntendedRoute() ?? '/'
}
```

Stored as `{"path":"/event/9f1c...","at":1757600000000}`. Every access is wrapped in `try/catch`; on a
throw, fall back to a module-level variable, which survives navigation within the tab but not a cold
start. Malformed JSON is treated as absent.

Validation, in `isRestorableRoute(path: string): boolean`, applied on write **and** on read:

```ts
// reject: anything not starting with a single "/", anything containing "://" or "\", length > 512
// reject: /login, /register, /join/*, /reset/*        (waypoints, AC9)
// accept: only paths matching a pattern in the S0.3 route table (D34):
//   /  /event/:id  /history  /manage  /manage/event/new  /manage/event/:id
//   /manage/team/:teamId/members  /admin
```

Matching is done with `matchRoutes` from `react-router` — v7 in library mode, and
[S0.3](S0.3-routing.md) forbids installing `react-router-dom` — against the route objects built from the
`AppRouteMeta[]` table in `src/routes.tsx`, so the allowlist cannot drift from the router. A path that
matches only the catch-all `*` is rejected. Importing the table costs nothing at runtime: it is data, and
the manager and admin screens behind it are still lazy (S0.3).

### Who writes it

| Writer | When | Value |
|---|---|---|
| `RequireAuth` (S2.9) | A guarded route is hit with no session | `location.pathname + location.search` |
| S3.3 affordances | Anonymous visitor taps "Join {team}" **or** "Already registered? Sign in" on `/event/:id` | `/event/{id}` |
| S2.1 / S2.2 | Linking to each other ("I already have an account") | Nothing written, nothing cleared — whatever is already stored is preserved (AC3) |

Nothing else writes it. `/join/:token` does not: a squad link has no destination beyond home, and D34's
route table has no screen for it after joining.

### The restore, and its order

One hook, mounted once, in the router's root element — not above `<RouterProvider>`, where `useNavigate`
has no router to talk to. [S2.6](S2.6-session-persistence.md)'s session gate sits above the router and
passes its status down through context. The order is the whole story:

1. **Session** — [S2.6](S2.6-session-persistence.md) resolves `useSession().status` to `signedIn` or
   `signedOut` (S2.9's `SessionState`). While `loading`, nothing below runs and nothing navigates.
2. **Pending join** — [S2.4](S2.4-join-by-link.md)'s `usePendingJoinResume()` reaches `done`. This is why
   the deep-linked event renders as a member (AC7).
3. **Intended route** — `takeIntendedRoute()`. Non-null, and different from the current path, means
   `navigate(path, { replace: true })`. `replace` matters: the back button must not walk the user back
   into the registration form.
4. **Render** — the destination mounts and fetches. Only now does the gate drop its splash.

```ts
// src/features/auth/use-intended-route.ts
export function useIntendedRoute(enabled: boolean): void
// enabled === (useSession().status !== 'loading' && pendingJoin status === 'done')
// Runs its navigate exactly once per mount, guarded by a useRef. It uses useNavigate(), so it is called
// from the router root element, never from a provider above the router.
```

If the user is signed out, the hook does nothing at all and the value stays stored — an anonymous visitor
sitting on `/event/:id` reading the preview must keep their destination if they wander to `/login`.

### The cold-start case, spelled out

WhatsApp taps are usually cold. The sequence on a cold start at `/#/login` with a stored route:

```
index.html served (SW network-first, D43)  ->  static shell painted
React mounts, session status 'loading'     ->  same shell, no flash (S2.6)
getSession() resolves                      ->  'signedIn' or 'signedOut'
pending join resumes (S2.4)                ->  'done'
takeIntendedRoute() -> "/event/9f1c..."    ->  navigate(replace)
```

The fragment is never sent to the network, so neither Pages nor the service worker can lose it. Say this
in a comment; someone will otherwise try to "fix" it with a `404.html` redirect shim.

### What deliberately does not work

Copying the link out of the WhatsApp webview into Safari (D47) starts a new browsing context with its own
`localStorage`. There is no stored route and no session. The player lands on `/#/login`, signs in, and
gets home. The S2.7 copy already warns them: "You'll sign in once more." Do not attempt a transfer.

## Data and API surface

None. This story reads and writes `localStorage` only. It calls no RPC, adds no table, adds no query key,
and adds no Zod schema. Its entire server-side surface is the ordering guarantee it gives
[S2.4](S2.4-join-by-link.md)'s mutation.

## UI states

This story adds no screen. It governs the boot gate that stands in front of every screen, so the gate's
states are specified here and its markup is [S2.6](S2.6-session-persistence.md)'s.

| Screen | Loading | Empty | Error | Populated |
|---|---|---|---|---|
| `AppBoot` gate, `src/app/app-boot.tsx` (all routes) | The static shell from `index.html`, held while session and pending join resolve. Never the login screen, never a flash of home | No stored route is the normal case: the router renders whatever the URL already says, usually `/` | A stale, invalid or denied stored value is discarded silently and home renders. A failed pending join surfaces S2.4's inline line on home; the gate itself never shows an error | The intended screen mounts, with its own four states owned by its own story |

## Test plan

- **Unit** — `intended-route.ts` under Vitest: round trip; `at` older than 60 minutes discarded;
  malformed JSON treated as absent; `setItem` throwing falls back to memory and does not throw; each
  denied pattern rejected (`//evil.com`, `https://evil.com`, `/login`, `/register`, `/join/abc`,
  `/reset/abc`, a 600-character path, `/nope`); `takeIntendedRoute()` clears on read and a second call
  returns null. `nextRouteAfterAuth()` returns the stored route once and `/` on the next call.
  `useIntendedRoute` with a mocked router: navigates once, with `replace: true`, does not
  navigate when already on the path, does not navigate while `enabled` is false, and does not navigate at
  all when `nextRouteAfterAuth()` already consumed the value.
- **Integration / RLS** — none. No policy changes, and [S1.4](S1.4-rls-test-suite.md) must still pass
  untouched.
- **E2E** — `tests/e2e/deep-link.spec.ts`, driving `vite preview` against the seeded local stack (D17,
  D58), with `timezoneId: 'Europe/Dublin'` (D53). Specs:
  1. **New user.** Open `/#/event/{seeded id}` with a clean context. Tap Join. Register with a
     run-scoped number from the reserved prefix. Assert the landed URL hash equals `/event/{id}`, that
     YES and NO are enabled, and that the collected hash-path sequence is exactly
     `['/event/{id}', '/register', '/event/{id}']` (AC13). Then tap YES and assert the response persists
     across a reload.
  2. **Existing user, cold start.** Open the same link signed out, let the guard redirect, close the
     context, open a new page at the app root reusing the same storage state, sign in, assert the event
     screen.
  3. **Consumed once.** After spec 1, navigate to `/#/`, reload, assert the URL stays `/#/`.
  4. **Poisoned value.** Seed `localStorage['pfc.intendedRoute']` with `{"path":"https://evil.example",
     "at":Date.now()}`, sign in, assert the app lands on `/#/` and never navigates off-origin.
  The hash-path sequence is collected with `page.on('framenavigated')` plus a `hashchange` listener
  installed by `page.addInitScript`, pushed onto `window.__pfcPathLog`, and read back at the end.
- **Manual** — tap a real share message in WhatsApp on an iPhone and on an Android handset, as a user
  with no account, and confirm the event screen is the first thing with content on it. The stopwatch is
  [S7.4](S7.4-device-pass.md)'s.

## Open questions

1. **Is 60 minutes the right TTL?** Proposed default: yes. It is long enough for a player to be
   interrupted mid-registration and come back, short enough that next week's launch of the installed app
   does not reopen last week's event. If it proves short in the S7.4 device pass, raise it to 24 hours;
   the constant is in one place.
2. **Should a returning signed-in player be re-landed on an event they never answered?** Proposed
   default: no. The intended route is consumed on first use and never re-armed. Chasing non-responders is
   [S5.3](S5.3-reminder-share.md)'s job, over WhatsApp, where the squad already is.
3. **Should the guard preserve a `search` string?** Proposed default: yes, it is stored, but no route in
   D34's table uses one today. If one is added later the validation already allows it.
