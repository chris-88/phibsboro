## Goal

A manager opening an event sees who is coming. One card per squad member, name and answer, with the
people who have not answered at the top so the manager knows exactly who to chase. This fills the "Who's
in" slot [S4.3](S4.3-manager-event-view.md) left empty, and it sits between "manager sees counts" and
"manager records attendance" in the one journey that matters.

## Context

`CLAUDE.md` S4.4 asks for "Rows of player name, availability, attendance", sorted awaiting first, readable
at 375px without horizontal scroll. Two decisions in [00-decisions.md](../00-decisions.md) change what that
means in practice, and both win over the brief's wording:

- **D42** — three columns plus a 44px attendance control cannot fit 375px as a table. It is a card list at
  every width, and the story is renamed **Player response list**. The same card serves
  [S4.5](S4.5-record-attendance.md), so there is one component, not two.
- **D22** — squad is every current `team_members` row for the team, regardless of role. Managers are in
  the list because managers play. Rows belonging to people who have since left are retained in the
  database (**D33**) but excluded from this list and from S4.3's counts, so the two always agree.

Two more constraints apply. **D8**: another person's name never comes from `profiles`, which a client can
read only one row of. Names come from `team_member_directory(p_team_id)`, which also returns `phone` to a
manager — this screen must not render it. **D32**: a player may read only their own response and
attendance rows, so the list is manager-and-admin only; that is RLS, and the S2.9 route guard is
convenience.

This story is read-only. The attendance control is rendered in its "not recorded" state and is inert until
S4.5 supplies the handler.

## Scope

**In**
- The "Who's in" region of `/manage/event/:id`, replacing S4.3's "Player list coming next." placeholder.
- `buildRoster()`, a pure join-and-sort over members, responses and attendance rows.
- `useEventAttendance(eventId)` and `eventKeys.attendance(eventId)`, the one new query this needs.
- `PlayerResponseList` and `PlayerResponseCard`, including the inert three-state attendance control. Line
  one renders [S3.2](S3.2-upcoming-events-list.md)'s `ResponsePill` from
  `src/features/availability/components/`, imported, never copied ([D42](../00-decisions.md)).
- Loading, empty, error and populated states for the list region.

**Out**
- Writing attendance. The control is inert here; S4.5 makes it work.
- The event header, the four counts, their polling and their error handling — S4.3 owns all of it, and
  this story adds no second fetch of responses or of the directory.
- Phone numbers, join dates, remove and change-role actions. [S6.4](S6.4-member-administration.md) owns
  the member screen.
- Search, filter, or a "left the squad" section. Rejected in [00-decisions.md](../00-decisions.md).
- Naming non-responders in a reminder. [S5.3](S5.3-reminder-share.md) sends a number, never a name.
- Virtualisation. A squad is twenty-odd rows.

## Implementation notes

### Pure derivation

`src/lib/roster.ts`. No imports from `src/api/`, no Supabase client, so its Vitest cases below run with
no database — the same rule `deriveCounts()` follows in `src/lib/counts.ts`. The tests ship with this
story, not with [S7.2](S7.2-unit-tests.md), which adds no roster cases (D57).

```ts
import type { Database } from '@/lib/database.types'

type Role     = Enums<'member_role'>
type Response = Enums<'availability_response'>

export type RosterMember     = { userId: string; name: string; role: Role }
export type RosterResponse   = { userId: string; response: Response }
export type RosterAttendance = { userId: string; attended: boolean }

export type RosterRow = {
  userId: string
  name: string
  role: Role
  response: Response | null   // null means awaiting (D25)
  attended: boolean | null    // null means not recorded (D25)
}

export function buildRoster(
  members: readonly RosterMember[],
  responses: readonly RosterResponse[],
  attendance: readonly RosterAttendance[],
): RosterRow[]
```

Rules, each of which is a unit test:

- Members drive the output. Responses and attendance are looked up by `userId` through a `Map`; an entry
  with no matching member is dropped (D22, D33).
- Sort rank: `response === null` → 0, `'available'` → 1, `'unavailable'` → 2.
- Within a rank, compare with a module-level `new Intl.Collator('en-IE', { sensitivity: 'base' })`, then
  `userId` ascending.
- Never sort in place; the inputs are `readonly` and come straight from the query cache.
- `noUncheckedIndexedAccess` is on, so every `Map.get` is narrowed with `?? null`, never `!`.

`buildRoster` and `deriveCounts` take the same two arrays in the same shapes. Keep the directory row type
shared between them so a change to the RPC breaks both at typecheck, not one at runtime.

### The one new query

`src/api/events.ts`, beside S4.3's `useEvent` and `useEventResponses`:

```ts
export function useEventAttendance(eventId: string): UseQueryResult<RosterAttendance[]>
// supabase.from('attendance').select('user_id, attended').eq('event_id', eventId)
// Two columns, so the row type is the picked shape, never the full AttendanceRow: parse each row with
// attendanceRowSchema.pick({ user_id: true, attended: true }) and map to { userId, attended }.
// Manager policy is scoped by the owning event's team (D33), so a leaver's rows come back and
// buildRoster drops them.
```

`eventKeys.attendance(eventId)` is already in the `eventKeys` factory in `src/api/queryKeys.ts`, declared
by [S1.5](S1.5-typed-data-layer-and-shared-helpers.md) and first consumed here. Its shape is
`['events', 'attendance', eventId]`. Do not declare a second factory and do not write a literal key
(S1.5 AC15). It sits under the `['events']` prefix, so
`invalidateQueries({ queryKey: eventKeys.all })` still reaches it. Give it the same D23
options S4.3 passes to the other two from the screen — `{ refetchInterval: 30_000, refetchOnWindowFocus: true }` — so all three
refresh together. No Supabase Realtime.

`ManagerEventScreen` already holds the directory and response queries. It adds this third one and derives
once, mirroring how it derives counts:

```ts
const rows = useMemo(
  () => buildRoster(directory.data ?? [], responses.data ?? [], attendance.data ?? []),
  [directory.data, responses.data, attendance.data],
)
```

That single owner is what makes AC9 structural rather than a convention: there is nowhere else for a
second fetch to come from. The roster is derived server state; it never goes near Zustand.

### Components

`src/features/events/PlayerResponseList.tsx` and `PlayerResponseCard.tsx`, beside `ManagerEventScreen.tsx`
and `EventCountsPanel.tsx`.

```tsx
export type PlayerResponseCardProps = {
  row: RosterRow
  /** Omitted in S4.4, supplied by S4.5. Absent means the control renders disabled. */
  onAttendanceChange?: (userId: string, attended: boolean | null) => void
  /** True while this row's write is in flight: the control stays visible and goes disabled. */
  saving?: boolean
  /** Set means disabled, with this line rendered under the control. S4.5 passes the cancelled-event
   *  line; S4.4 never passes it. */
  disabledReason?: string
}
```

Card layout, per D42:

- Line one — name (`truncate`, `flex-1`, `min-w-0`), then the availability pill, `shrink-0`, right
  aligned.
- Line two — a full-width three-state segmented control, `min-h-tap`, ordered
  `Not recorded | Attended | Absent`.

The pill is the shadcn `Badge`, with three variants added against S0.2's existing theme tokens — no hex in
the component. Awaiting must be legible rather than decorative: it is the state a manager is scanning for.

The segmented control is the shadcn `ToggleGroup`, `type="single"`, `disabled` when `onAttendanceChange`
is undefined, when `saving` is true, or when `disabledReason` is set — all three branches exist now so
S4.5 changes no markup. S4.5 changes no markup, only the props passed in — that is this story's specific gate.

Wrap the list in `<ul>`/`<li>`; the pill carries an `aria-label` so a screen reader reads "Dara Byrne,
awaiting". No `<table>` anywhere; D42 settled it.

## Test plan

- **Unit** — Vitest on `buildRoster`: awaiting-first ordering; name tie-break across mixed case and
  fadas; `userId` tie-break for two identical names; orphaned response dropped; orphaned attendance
  dropped; empty squad returns `[]`; a member with attendance but no response yields
  `{ response: null, attended: true }`; inputs are not mutated. One test asserts `buildRoster` and
  `deriveCounts` agree on the same fixture — the card states sum to the counts.
- **Integration / RLS** — none new. The policies this screen leans on are already asserted in S1.4:
  manager reads every response and attendance row for events on their teams; a player reading a
  teammate's row gets zero rows; `team_member_directory` returns `phone` to a manager and null to a
  player; a signed-in user with no memberships gets zero rows everywhere.
- **E2E** — Playwright at 375×667 against the seed: sign in as a manager, open a seeded event with a mix
  of available, unavailable and awaiting members, assert the rendered name order matches the expected
  sequence, assert `scrollWidth === clientWidth`, assert no seeded phone number appears in the page text,
  assert the attendance control is disabled, and assert exactly one network request each for the
  directory and responses.
- **Manual** — Open the list on a real iPhone SE. The awaiting group should be obvious at a glance without
  reading each pill, and a long Irish name should truncate rather than push the pill off screen.

## Open questions

1. Should a card label a member whose role is `manager`? A manager who plays appears in the list like
   anyone else, which may briefly confuse. **Default: no label in v1.** The list is the squad, and D22
   says the squad includes managers.
2. Should the manager see their own card? **Default: yes**, in its natural sort position with no special
   styling. They are a member and their answer counts. S4.3 already sends them to `/#/event/{id}` to set
   it.
3. Should the card show when the answer was given, from `event_responses.updated_at`? **Default: no.** It
   is one more thing on a 375px card and nothing in the journey needs it.
