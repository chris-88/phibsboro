## Goal

A player who already has an account gets back in with their number and their password on one screen. A
player who has forgotten the password is told, in one line, what actually happens next: ask the manager.
No self-service recovery is offered, because there is no channel to verify anyone on. An existing player
who taps a WhatsApp event link and finds themselves signed out is back on that event having typed two
things.

## Context

Auth is mobile number plus password (`CLAUDE.md`, Epic 2 preamble). Phone confirmation is off, so there is
no OTP, no magic link and no email. That has two consequences this story has to carry honestly.

First, **recovery costs a manager a manual step**, so a forgotten password is a real support event. The
screen says so plainly rather than showing a dead "Forgot password?" link.
[S2.3](S2.3-password-reset-by-manager.md) is the other half.

Second, **the number is the account identifier and it is unverified**. Sign-in errors must not distinguish
"no such number" from "wrong password", or the screen becomes a tool for testing which of the squad's
numbers hold accounts.

Decisions this story is built on, in [00-decisions.md](../00-decisions.md):

- **D1** — the duplicate S2.2 "Deep link return path" block in the brief is deleted. S2.2 is sign in.
  There is no external auth callback anywhere in this app; `signInWithPassword` resolves in place. Return
  path is [S2.5](S2.5-deep-link-return-path.md).
- **D36 (as amended by [A15](../00-decisions.md))** — "rate limit failed attempts per number" is replaced by three checkable things: Supabase's own
  limits committed in `supabase/config.toml`, a 30-second UX lockout after five consecutive failures on
  the typed number, and a written statement that brute force is bounded by Supabase and by the 8-character
  minimum, not by the app. The browser talks to GoTrue directly with a public key; a client-side counter
  is a courtesy, not a boundary, and the spec says so.
- **D35** — `toE164()` from S1.5 is shared with S2.1 through one exported `phoneField`. This is the whole
  reason `087` and `+353 87` reach the same account.
- **D19** — sign-in goes through `signInWithIdentifier` in `src/lib/auth.ts`, not `supabase.auth`
  directly, so the phone-versus-synthetic-email outcome stays in one file.
- **D59** — session longevity and silent refresh belong to [S2.6](S2.6-session-persistence.md). This story
  only creates the session.

## Scope

**In**

- The `/#/login` screen: mobile number, password, one submit button.
- Shared `phoneField` normalisation, imported from [S2.1](S2.1-registration.md), not re-implemented.
- Non-distinguishing failure copy, with the number retained and the password cleared.
- The forgotten-password line, and the copy that goes with it.
- The UX lockout: five consecutive failures on one number, 30 seconds, with a countdown.
- The `[auth.rate_limit]` block in `supabase/config.toml`, committed with values.
- Prefill from the sign-in link on the registration screen, and from the last number used on this browser.
- `nextRouteAfterAuth()` after success.

**Out**

- Any self-service password reset: no "email me a link", no SMS code, no security questions. There is no
  channel. [S2.3](S2.3-password-reset-by-manager.md) is the only recovery path.
- Restoring the intended route. [S2.5](S2.5-deep-link-return-path.md) replaces the body of
  `nextRouteAfterAuth()`; this story ships it returning `/`.
- Consuming a pending join. An existing player who taps a join or event link while signed out arrives
  here with `pfc.pendingJoin` already set by [S2.4](S2.4-join-by-link.md); S2.4 owns calling the join RPC
  after the session exists. This story must leave the stored value alone — see AC15.
- Session restore, silent refresh, and the no-flash-of-login requirement. [S2.6](S2.6-session-persistence.md).
- Sign out. That is a menu item owned by [S2.9](S2.9-auth-guard-and-role-context.md).
- Any server-side attempt counter, `auth_attempts` table or RPC. Explicitly rejected in
  [00-decisions.md](../00-decisions.md); the client can skip them, so they buy nothing.
- Biometric unlock, remember-me checkboxes, "trust this device". Sessions are long-lived by configuration
  (D59); a checkbox would imply a choice that does not exist.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — `/#/login` renders two inputs and one submit button. Nothing else takes input.
- [ ] **AC2** — A player who registered with `+353 87 123 4567` signs in by typing `087 123 4567`, and the
  reverse. A unit test asserts both forms produce the identical string through the same exported
  `phoneField` that [S2.1](S2.1-registration.md) uses.
- [ ] **AC3** — A wrong password shows an inline error under the password field, keeps the typed number
  exactly as typed, clears the password, and moves focus to the password field. The page does not
  navigate, reload or clear the form.
- [ ] **AC4** — An unknown number and a wrong password produce the **same** message: "That number and
  password don't match." Nothing in the UI, the DOM or the network response the app surfaces reveals
  whether the number exists.
- [ ] **AC5** — The screen carries one line of recovery copy: "Forgotten your password? Ask your manager to
  send you a reset link." It is text, not a link to a flow, and there is no route behind it.
- [ ] **AC6** — After five consecutive failures on the same normalised number, submit is disabled for 30
  seconds with a visible countdown line. Typing a different number clears the lockout for that number
  only. A successful sign-in resets the counter.
- [ ] **AC7** — The lockout survives a page reload, and is per-browser. The spec text and the UI copy both
  treat it as a courtesy, and nowhere claims it stops an attacker.
- [ ] **AC8** — `supabase/config.toml` contains an `[auth.rate_limit]` block with committed values, and a
  Vitest test reads the file and fails if the block or the `sign_in_sign_ups` key is missing.
- [ ] **AC9** — Arriving from the registration screen's duplicate-number link prefills the number field and
  puts focus on the password field.
- [ ] **AC10** — On success, `userKeys.current()` is invalidated and the app navigates to
  `nextRouteAfterAuth()` with `replace: true`, so Back does not return to the sign-in screen.
- [ ] **AC11** — A user who already has a session and opens `/#/login` is redirected to
  `nextRouteAfterAuth()` rather than being shown the form.
- [ ] **AC12** — A network failure shows "Couldn't reach the server. Try again." with the button enabled
  and the typed number intact, and does **not** count towards the five-failure lockout.
- [ ] **AC13** — At 375px both inputs and the button are at least 44px high, and the button is reachable
  one-handed with the keyboard open. No bottom nav renders here: D41's nav is built from the signed-in
  user's memberships, and a visitor on `/#/login` has no session, so there are no items to draw. The
  screen must not reserve space for it.
- [ ] **AC14** — No password value is ever written to `localStorage`, a query string, a log line, or
  Sentry. The Sentry scrubber (D16) covers the number; the password never reaches a breadcrumb because the
  field is excluded from breadcrumb capture.
- [ ] **AC15** — Signing in with a `pfc.pendingJoin` present leaves that value untouched and unexpired:
  `useSignIn` never reads, writes or clears it. A unit test signs in with a pending join set and asserts
  `readPendingJoin()` still returns the same value afterwards, so [S2.4](S2.4-join-by-link.md) can consume
  it once the session exists.

## Implementation notes

Files:

```
src/features/auth/SignInScreen.tsx        route component for /login
src/features/auth/SignInForm.tsx          RHF form, two fields
src/features/auth/signInLockout.ts        pure lockout module, injected clock
src/features/auth/schemas.ts              signInSchema added beside registerSchema (S2.1)
src/api/auth.ts                           useSignIn() added beside useRegister()
supabase/config.toml                      [auth.rate_limit] values committed
```

**Schema.** Reuse, do not re-derive:

```ts
export const signInSchema = z.object({
  phone: phoneField,                       // the same export S2.1 uses (D35)
  password: z.string().min(1, 'Password'), // no 8-char rule here: old accounts are not re-validated
})
```

The minimum length belongs on registration and on reset, not on sign-in. Enforcing 8 here would lock out
nobody today and would be one more way to leak that an account exists.

**Mutation.**

```ts
export function useSignIn(): UseMutationResult<void, AuthFailure, z.output<typeof signInSchema>>
```

Calls `signInWithIdentifier(phone, password)` from `src/lib/auth.ts`. On success:
`recordSuccess(phone)`, write `pfc.lastPhone`, `queryClient.invalidateQueries({ queryKey: userKeys.current() })`,
`navigate(nextRouteAfterAuth(), { replace: true })`. On failure, run the error through `mapAuthError` from
S2.1, extended with one member:

```ts
| { kind: 'invalid_credentials' }   // GoTrue 400, code 'invalid_credentials'
```

`invalid_credentials` and "user not found" both map to this one member, which is how AC4 is guaranteed in
code rather than by discipline. `over_request_rate_limit` (GoTrue 429) maps to a separate line — "Too many
tries. Wait a minute." — because telling a player to retype a correct password would be wrong.

**Lockout.** Pure module, clock injected, so it is unit-testable without timers:

```ts
export type LockoutState = { failures: number; lockedUntil: number | null }

export function recordFailure(phoneE164: string, now: number): LockoutState
export function recordSuccess(phoneE164: string): void
export function checkLockout(phoneE164: string, now: number): LockoutState
```

Five consecutive failures set `lockedUntil = now + 30_000`. State lives in `localStorage` under
`pfc.signInLockout` as a record keyed by E.164, pruned of entries older than an hour on read, wrapped in
try/catch. Only `invalid_credentials` counts; network and rate-limit failures do not (AC12). The countdown
renders with a `setInterval` cleared on unmount, and the button re-enables without a reload.

Write this in the UI copy as a delay, never as a security claim: "Too many tries. Try again in 24s."

**Rate limits in config.** The committed block, beside the migrations, so the value is reviewable in a
diff:

```toml
[auth.rate_limit]
sign_in_sign_ups = 30   # per 5 minutes per IP
token_refresh    = 150  # per 5 minutes per IP
```

If the Supabase CLI version in use names these keys differently, the committed file wins and the test in
AC8 is updated to match — the point is that the numbers are in the repo and change under review, not that
a particular key name is memorised.

**Prefill.** Precedence: `location.state.phone` passed by the registration screen, then `pfc.lastPhone`
written after a **successful** sign-in only, then empty. Never prefill from a failed attempt, and never
store the password. When prefilled, focus goes to the password field; otherwise to the number field.

**Recovery copy.** One paragraph, under the button, no link:

> Forgotten your password? Ask your manager to send you a reset link.

Do not add "we've emailed you", "check your messages", or a support address. There is no email, no SMS and
no inbox. [S2.3](S2.3-password-reset-by-manager.md) is what the manager does next.

**What actually bounds brute force**, stated here so nobody designs against the lockout later: Supabase
Auth's own per-IP limits above, the 8-character minimum set at registration, and the fact that an attacker
needs a squad member's mobile number to start. The in-app lockout is UX. RLS is the enforcement layer for
everything a session can then do.

**Layout.** Full-screen route. The D41 bottom nav is absent rather than hidden: it renders from the
signed-in user's memberships and there is no session on this screen. The number field carries
`type="tel"`, `inputMode="tel"` and `autoComplete="tel"` — the same three attributes as
[S2.1](S2.1-registration.md) AC5, so the numeric keypad opens — and the password field
`autoComplete="current-password"`, so iOS and Android password managers fill both. A
show/hide password toggle at 44px, defaulting to hidden — typing a password one-handed in a car park is
the case this screen exists for.

## Test plan

- **Unit** — `signInSchema` normalisation parity with `registerSchema`, asserted as one test that runs the
  same four input forms through both and compares outputs; `mapAuthError` maps GoTrue 400
  `invalid_credentials` and a user-not-found response to the identical member; `signInLockout` with an
  injected clock across 4, 5 and 6 failures, expiry at 30s, per-number isolation, success reset, corrupt
  and throwing `localStorage`; a config test that parses `supabase/config.toml` and asserts the
  `[auth.rate_limit]` block exists with a numeric `sign_in_sign_ups`; a pending-join test that sets
  `pfc.pendingJoin`, runs a successful `useSignIn`, and asserts `readPendingJoin()` is unchanged (AC15).
- **Integration / RLS** — against the local stack: sign in as each seeded role and assert a session plus
  the expected `team_members` rows through `useCurrentUser`'s query; a wrong password returns a 400 whose
  body the app never renders; a signed-in player still fails every denied path in the S1.4 matrix, so
  holding a session is not authority.
- **E2E** — Playwright: wrong password keeps the number and clears the password; correct password lands on
  `/`; a session already present at `/#/login` redirects without the form appearing.
- **Manual** — On a real iPhone and a real Android: the saved credential autofills both fields in one tap;
  the show/hide toggle works with the keyboard up; the form is usable inside the WhatsApp in-app browser.

## Open questions

1. **Lockout threshold and duration — five failures, 30 seconds.** Proposed default: as written. It stops
   a thumb-typo loop and irritates nobody who knows their password. If the club reports lockouts in
   practice, raise the count, not the duration.
2. **Should `pfc.lastPhone` be stored at all on a shared handset?** Proposed default: yes. It is the
   player's own number on their own phone, it is the single biggest saving on a re-sign-in after the
   WhatsApp-browser escape (D47), and clearing it on sign-out is a one-line change if the club objects.
3. **Copy for the non-distinguishing error.** Proposed default: "That number and password don't match."
   Any variant is fine as long as it never names which half was wrong.
4. **Do we show a "Create account" link on the sign-in screen?** Proposed default: only when a pending join
   exists. Without one, [S2.1](S2.1-registration.md) rejects the visit, so an always-present link would be
   a route to a dead end.
