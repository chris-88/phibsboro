## Goal

Create the database the whole product sits on: eight tables, four enums, the keys, the foreign keys, the
checks and the indexes, applied by a migration that runs clean from empty. After this story a developer
can run `supabase db reset` and get the exact schema every later story is written against. Nothing is
readable or writable by a client yet — RLS is on everywhere with no policies, so the database denies by
default until [S1.3](S1.3-rls-policies-and-rpcs.md) opens the doors deliberately.

## Context

Section 5 of [CLAUDE.md](../../CLAUDE.md) sketches the model. [data-model.md](../data-model.md) settles it,
and where the two disagree the settled file wins. The differences this story inherits:

- **D3** — eight tables, not "six". `profiles`, `teams`, `team_members`, `team_invites`, `reset_tokens`,
  `events`, `event_responses`, `attendance`. There is no `clubs` table and there never will be.
- **D2** — admin is a club-wide flag, `profiles.is_admin`. `member_role` has no `admin` member.
- **D4** — `profiles.id` **is** the `auth.users` id. Every user-referencing column targets `profiles(id)`.
- **D5** — composite primary keys on the three join tables, unique on both token columns and on `phone`.
- **D6** — `events.id` is a `uuid` with a `gen_random_uuid()` default, because the share link is a bearer
  join credential. Sequential or short ids are a security bug here, not a style choice.
- **D24** — closed value sets are Postgres enums, so `supabase gen types typescript` emits unions and not
  `string`. A text column would collide with the ban on `any`.
- **D15** — the seed moves out of this story. S1.1 is migrations only. The seed is a Node script owned by
  [S1.2](S1.2-profile-provisioning-and-seed.md), because Supabase Auth users cannot be created in SQL.
- **D18** — the deploy workflow applies migrations before publishing the bundle, so the migration this
  story writes is the first thing that workflow has to push.
- **D62** — token columns are plaintext in tables no client can select. No hashing.

Policies, helper functions and RPCs are **not** in this story. Turning RLS on with zero policies is the
deny-all starting point [S1.3](S1.3-rls-policies-and-rpcs.md) builds from, and D54 already requires
`team_invites` and `reset_tokens` to stay policy-free forever.

One deviation from D14, now recorded as [A5](../00-decisions.md). D14 says the CI `db` job is added by
S1.4. S1.1 is the first story that needs a Postgres in the runner, so it creates that job and S1.4 extends
it with the seed step and the RLS project. The job's shape is unchanged.

## Scope

**In**
- One migration creating four enums and eight tables with every column, default, check, key, foreign key
  and index listed in [data-model.md](../data-model.md).
- `pgcrypto` available in the `extensions` schema, for the token generation S1.3 will do.
- An `updated_at` trigger function, attached to `events`, `event_responses` and `attendance`.
- `alter table ... enable row level security` on all eight tables, with no policies.
- Explicit `revoke all` on `team_invites` and `reset_tokens` from `anon` and `authenticated`.
- A `db` job in `.github/workflows/ci.yml` that brings up the local Supabase stack, resets it, and runs
  the structural assertions in `tests/db/schema.test.ts`.
- `supabase/migrations/README.md` stating the forward-only rule, and the CI step that enforces it.
- `npm run db:reset` and `npm run db:types` scripts.

**Out**
- Every RLS policy, helper function and RPC — [S1.3](S1.3-rls-policies-and-rpcs.md).
- The `profiles` insert trigger and the seed — [S1.2](S1.2-profile-provisioning-and-seed.md).
- The generated `src/lib/database.types.ts` file, the Zod schemas and any query hook —
  [S1.5](S1.5-typed-data-layer-and-shared-helpers.md). This story only proves the generator runs.
- `supabase/seed.sql`. Deliberately absent: the CLI would run it automatically on `db reset`, and the seed
  is a Node script instead (D15).
- Any `clubs`, `club_members`, `fixtures`, `results` or `payments` table. Out of scope, permanently.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — `supabase db reset` applies every migration to an empty database and exits 0, twice in a
      row, with no warnings about failed statements. Afterwards `select extensions.gen_random_bytes(32)`
      succeeds, so S1.3's token generation has its dependency already in place.
- [x] **AC2** — `select tablename from pg_tables where schemaname = 'public'` returns exactly these eight
      names and no others: `attendance`, `event_responses`, `events`, `profiles`, `reset_tokens`,
      `team_invites`, `team_members`, `teams`.
- [x] **AC3** — four enums exist with exactly these labels in this order: `event_type
      ('training','match')`, `event_status ('scheduled','cancelled')`, `availability_response
      ('available','unavailable')`, `member_role ('player','manager')`. `member_role` has no `admin`
      label (D2).
- [x] **AC4** — every column in [data-model.md](../data-model.md) exists with the stated type, nullability
      and default. A column not in that file does not exist. Asserted column by column against
      `information_schema.columns`.
- [x] **AC5** — every foreign key has the `on delete` behaviour the model states: `profiles.id`
      references `auth.users (id)` on delete cascade (D4); `user_id` columns cascade; every `team_id`
      restricts; `event_id` columns cascade; and `created_by` / `recorded_by` are nullable and set null.
      No user-referencing column anywhere targets `auth.users` except `profiles.id` (D4). Asserted
      against `pg_constraint`, listed as `(table, column, target, action)`.
- [x] **AC6** — primary keys are composite on `team_members (team_id, user_id)`, `event_responses
      (event_id, user_id)` and `attendance (event_id, user_id)`, with no surrogate `id` column on any of
      the three (D5).
- [x] **AC7** — unique constraints exist on `profiles.phone`, `team_invites.token` and
      `reset_tokens.token`, and a unique index on `lower(btrim(teams.name))`. Inserting a second team
      named `firsts` when `Firsts` exists raises `23505`.
- [x] **AC8** — both partial unique indexes exist and bite: `team_invites (team_id, role) where active`
      rejects a second live invite for the same team and role; `events (team_id, starts_at) where
      series_id is not null` rejects a second generated event in the same slot while permitting a
      hand-created event at that time.
- [x] **AC9** — the lookup indexes exist: `events (team_id, starts_at)`, `team_members (user_id)`,
      `event_responses (user_id)`, `attendance (user_id)` (D39), and the partial
      `reset_tokens (user_id) where used_at is null and revoked_at is null`.
- [x] **AC10** — every check constraint rejects its bad case: an empty or whitespace-only `name`, `title`
      or `location`; a `title` over 80 characters; `notes` over 500; a `phone` of `0871234567`,
      `+353 87 123 4567` or `353871234567` (no `+`, or containing spaces).
- [x] **AC11** — `rowsecurity` is true for all eight tables in `pg_tables`, and no table is `force row
      level security`, so security-definer functions owned by `postgres` still work (D54).
- [x] **AC12** — with at least one row present in every one of the eight tables, inserted first by a
      service-role client so the check is not vacuous, both the `anon` client and a freshly signed-in
      `authenticated` client select zero rows from all eight, and every insert, update and delete is
      refused. There are no policies yet; this is the deny-all baseline the S1.4 suite later inherits.
- [x] **AC13** — `team_invites` and `reset_tokens` have zero privileges granted to `anon` or
      `authenticated` in `information_schema.role_table_grants` (D54's explicit deny-all list).
- [x] **AC14** — updating a row in `events`, `event_responses` or `attendance` advances `updated_at` even
      when the statement does not mention the column, and leaves `created_at` unchanged. The other five
      tables have no `updated_at` column and no `before update` trigger at all; asserted by the absence of
      the column in `information_schema.columns` and of the trigger in `pg_trigger`.
- [x] **AC15** — deleting a `teams` row that has any event, member, invite or reset token raises a foreign
      key violation rather than succeeding (D31: deactivate, never delete).
- [x] **AC16** — deleting an `events` row removes that event's `event_responses` and `attendance` rows and
      leaves `team_members` untouched. Deleting a `profiles` row removes that user's memberships,
      responses and attendance, and leaves every `created_by` and `recorded_by` reference to them null,
      with the `events` and `attendance` rows themselves intact.
- [x] **AC17** — `supabase gen types typescript --local` exits 0 and its output contains
      `event_type: "training" | "match"`, proving the enums generate as unions and not `string` (D24).
- [ ] **AC18** — `supabase db diff --schema public --local` reports no differences immediately after a
      reset, so the migration files are the whole truth about the schema.
- [ ] **AC19** — the CI `db` job runs AC1 to AC18 and AC20 on every pull request against the CLI's local
      stack, using no repository secret (D14, D38).
- [x] **AC20** — `supabase/migrations/README.md` exists and states the forward-only rule: a merged
      migration file is never edited, corrections ship as a new timestamped migration, and there are no
      down migrations. A CI step fails the `db` job if a pull request modifies or deletes a migration file
      that already exists on `main` (`git diff --diff-filter=MD --name-only origin/main -- supabase/migrations`
      must be empty), so the rule is enforced and not merely written down (D18).

## Implementation notes

Create the migration with `supabase migration new schema`, which yields a timestamped file such as
`supabase/migrations/20260912093000_schema.sql`. One file. It is long, and that is fine — it is the only
statement of the schema.

```sql
-- supabase/migrations/20260912093000_schema.sql

create extension if not exists pgcrypto with schema extensions;

create type public.event_type            as enum ('training', 'match');
create type public.event_status          as enum ('scheduled', 'cancelled');
create type public.availability_response as enum ('available', 'unavailable');
create type public.member_role           as enum ('player', 'manager');

create table public.profiles (
  id         uuid primary key references auth.users (id) on delete cascade,
  name       text not null check (char_length(btrim(name)) between 1 and 80),
  phone      text not null unique check (phone ~ '^\+[1-9][0-9]{7,14}$'),
  is_admin   boolean not null default false,
  created_at timestamptz not null default now()
);

create table public.teams (
  id         uuid primary key default gen_random_uuid(),
  name       text not null check (char_length(btrim(name)) between 1 and 60),
  active     boolean not null default true,
  created_at timestamptz not null default now()
);
create unique index teams_name_key on public.teams (lower(btrim(name)));

create table public.team_members (
  team_id   uuid not null references public.teams (id)    on delete restrict,
  user_id   uuid not null references public.profiles (id) on delete cascade,
  role      public.member_role not null default 'player',
  joined_at timestamptz not null default now(),
  primary key (team_id, user_id)
);
create index team_members_user_id_idx on public.team_members (user_id);

create table public.team_invites (
  id         uuid primary key default gen_random_uuid(),
  team_id    uuid not null references public.teams (id) on delete restrict,
  token      text not null unique,
  role       public.member_role not null,
  active     boolean not null default true,
  expires_at timestamptz,
  created_by uuid references public.profiles (id) on delete set null,
  created_at timestamptz not null default now()
);
create unique index team_invites_one_live_idx
  on public.team_invites (team_id, role) where active;

create table public.reset_tokens (
  id         uuid primary key default gen_random_uuid(),
  user_id    uuid not null references public.profiles (id) on delete cascade,
  team_id    uuid not null references public.teams (id)    on delete restrict,
  token      text not null unique,
  issued_at  timestamptz not null default now(),
  expires_at timestamptz not null default (now() + interval '24 hours'),
  used_at    timestamptz,
  revoked_at timestamptz,
  created_by uuid references public.profiles (id) on delete set null
);
create index reset_tokens_live_idx on public.reset_tokens (user_id)
  where used_at is null and revoked_at is null;

create table public.events (
  id         uuid primary key default gen_random_uuid(),
  team_id    uuid not null references public.teams (id) on delete restrict,
  type       public.event_type not null,
  title      text not null check (char_length(btrim(title))    between 1 and 80),
  location   text not null check (char_length(btrim(location)) between 1 and 120),
  notes      text check (notes is null or char_length(notes) <= 500),
  starts_at  timestamptz not null,
  status     public.event_status not null default 'scheduled',
  series_id  uuid,
  created_by uuid references public.profiles (id) on delete set null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create index events_team_starts_idx on public.events (team_id, starts_at);
create unique index events_series_slot_idx
  on public.events (team_id, starts_at) where series_id is not null;

create table public.event_responses (
  event_id   uuid not null references public.events (id)   on delete cascade,
  user_id    uuid not null references public.profiles (id) on delete cascade,
  response   public.availability_response not null,
  updated_at timestamptz not null default now(),
  primary key (event_id, user_id)
);
create index event_responses_user_idx on public.event_responses (user_id);

create table public.attendance (
  event_id    uuid not null references public.events (id)   on delete cascade,
  user_id     uuid not null references public.profiles (id) on delete cascade,
  attended    boolean not null,
  recorded_by uuid references public.profiles (id) on delete set null,
  updated_at  timestamptz not null default now(),
  primary key (event_id, user_id)
);
create index attendance_user_idx on public.attendance (user_id);
```

Then the `updated_at` trigger. One function, three triggers. It is not `security definer`; it runs as the
writer and only touches `new`.

```sql
create or replace function public.set_updated_at()
returns trigger
language plpgsql
set search_path = ''
as $$
begin
  new.updated_at := now();
  return new;
end;
$$;

create trigger events_set_updated_at
  before update on public.events
  for each row execute function public.set_updated_at();
-- and the same for public.event_responses and public.attendance
```

Then deny-all. This is the last block in the file.

```sql
alter table public.profiles        enable row level security;
alter table public.teams           enable row level security;
alter table public.team_members    enable row level security;
alter table public.team_invites    enable row level security;
alter table public.reset_tokens    enable row level security;
alter table public.events          enable row level security;
alter table public.event_responses enable row level security;
alter table public.attendance      enable row level security;

revoke all on public.team_invites from anon, authenticated;
revoke all on public.reset_tokens from anon, authenticated;
```

Gotchas worth stating once, so nobody rediscovers them:

- **Do not use `force row level security`.** The S1.3 RPCs are `security definer` owned by `postgres`,
  which is also the table owner. Forcing RLS would apply policies to those functions and break every join,
  invite and reset path.
- **Supabase's default privileges** already grant `anon` and `authenticated` table-level rights in
  `public`. RLS is the boundary, per D38. The two explicit `revoke` statements are belt and braces on the
  two tables that must never be reachable directly.
- **`search_path`** is empty in every function this project writes, so every object is schema-qualified,
  including `extensions.gen_random_bytes` in S1.3. `gen_random_uuid()` has been in `pg_catalog` since
  Postgres 13, so it needs no qualification in a DDL default, which is resolved at `create table` time
  against the migration's own session.
- **`gen_random_bytes` lives in `extensions`** on Supabase, not `public`. The extension line above is
  usually a no-op on a hosted project and is kept so a bare local reset works.
- **No `supabase/seed.sql`.** `supabase db reset` runs that file automatically if it exists, which would
  silently split the seed across two mechanisms. The seed is `supabase/seed/seed.ts` (D15).
- **Forward-only.** A merged migration is immutable. There is no down migration, and `supabase migration
  repair` is a production incident tool, not a workflow.

Scripts in `package.json`:

```json
"db:reset": "supabase db reset",
"db:types": "supabase gen types typescript --local --schema public > src/lib/database.types.ts",
"test:db":  "vitest run tests/db"
```

Ship `db:reset` in exactly that form. [S1.2](S1.2-profile-provisioning-and-seed.md) extends it to
`"supabase db reset && tsx supabase/seed/seed.ts"` when the seed script exists (D15). Do not commit the
extended form here — it would fail on a clean checkout.

The structural assertions live in `tests/db/schema.test.ts`, Vitest, connecting with `pg` straight to the
CLI's local database at `postgresql://postgres:postgres@127.0.0.1:54322/postgres` — a published constant,
committed in `.env.example`, not a secret (D38). Assertions read `information_schema` and `pg_catalog`
rather than hard-coding DDL strings, so they survive formatting changes. AC12's denial checks use two
supabase-js clients built from the local anon key, one anonymous and one signed in as a throwaway user
created through the service-role helper.

The CI `db` job, added to `.github/workflows/ci.yml`:

```yaml
db:
  runs-on: ubuntu-latest
  env: { TZ: UTC }
  steps:
    - uses: actions/checkout@v4
      with: { fetch-depth: 0 }          # AC20 needs origin/main to diff against
    - uses: actions/setup-node@v4
      with: { node-version-file: .nvmrc, cache: npm }
    - uses: supabase/setup-cli@v1
      with: { version: '${{ env.SUPABASE_CLI_VERSION }}' }   # pinned by S0.7 AC8, never `latest`
    - run: supabase start
    - run: supabase db reset
    - run: npm ci && npm run test:db
    - name: Enums generate as unions          # AC17
      run: |
        supabase gen types typescript --local > /tmp/types.ts
        grep -qF 'event_type: "training" | "match"' /tmp/types.ts
    - name: Migrations are the whole schema   # AC18
      run: |
        test -z "$(supabase db diff --schema public --local)"
    - name: Merged migrations are immutable   # AC20
      run: |
        test -z "$(git diff --diff-filter=MD --name-only origin/main -- supabase/migrations)"
```

Each assertion is a block scalar, not an inline `run:`, because the AC17 pattern contains a colon and a
pipe and would not survive a plain YAML scalar. No secrets, so fork pull requests run it (D14).
`TZ: UTC` is pinned per D53.

## Test plan

- **Unit** — none. This story adds no application code.
- **Integration / RLS** — `tests/db/schema.test.ts` covers AC2 to AC16: table list, enum labels, column
  shapes, foreign key actions, keys, unique and partial indexes, check constraints, `rowsecurity` on every
  table, the absence of `anon` and `authenticated` grants on the two RPC-only tables, `updated_at`

## Open questions

1. **Does S1.1 or S1.4 create the CI `db` job?** D14 assigned it to S1.4, but S1.1 is the first story
   needing Postgres in the runner. *Default, already written above: S1.1 creates the job with the reset
   and the schema assertions, S1.4 extends the same job with the role-based suite. No change to D14's
   shape or its no-secrets rule.*
2. **Postgres major version.** The migration needs 13 or later for core `gen_random_uuid()`; every other
   construct here is far older. Supabase's hosted default is 15. *Default: pin `[db] major_version` in
   `supabase/config.toml` to whatever the hosted project runs, so the local stack and production cannot
   drift, and assert the version once in `tests/db/schema.test.ts`.*
3. **Should `events.starts_at` carry a sanity check, say no earlier than 2020?** A typed year of `0224`
   would otherwise store happily. *Default: no check. S4.1's Zod schema owns the input range; a database
   check would also block the seed's past events and any historical backfill.*
