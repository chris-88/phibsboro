## Goal

Every pull request is checked automatically: types, lint, formatting, unit tests and a production build.
`main` refuses a merge until those checks are green, so the S0.5 deploy only ever runs on a commit that
passed. Later stories bolt their own jobs onto the file this story creates rather than each inventing a
pipeline.

## Context

Three stories and the definition of done in `CLAUDE.md` assume a pipeline nobody was asked to build:
S1.4 says "Runs in CI", S7.3 says "Runs in CI against a seeded Supabase project", and the definition of
done says "tests for that story pass in CI". [D14](../00-decisions.md) adds this story to Epic 0 and puts
it third in the [D20](../00-decisions.md) build order, ahead of Epic 1.

Two constraints shape the whole file. **No test job may require a repository secret**
([D14](../00-decisions.md), [D38](../00-decisions.md)), so pull requests from forks work and
`pull_request_target` is never used; hosted credentials belong to the S0.5 deploy workflow alone.
And `TZ: UTC` is set on every job ([D53](../00-decisions.md)), because a Dublin date assertion that passes
locally in July fails on a UTC runner in January.

This story owns the workflow file and the `check` job. It does not own the jobs that need a database or a
browser — it declares where they go and who adds them.

## Scope

**In**
- `.github/workflows/ci.yml`, triggered on `pull_request` and on `push` to `main`.
- The `check` job: typecheck, lint, format check, unit tests, production build, and the env-parity script.
- The conventional-commit check on the pull request title, which [S0.1](S0.1-project-scaffold.md) open

  job that starts the local stack.
- Branch protection on `main`: required checks, and the rule that the deploy workflow re-runs nothing.
- `docs/ci.md`: one page naming each job, its owning story, and what it must never do.

**Out**
- The `db` job. [S1.1](S1.1-schema.md) is the first story that needs a Postgres in the runner and creates
  it; [S1.4](S1.4-rls-test-suite.md) extends it with the seed step and the RLS project. This story leaves
  the seam and nothing else.
- The `pwa` job ([S0.4](S0.4-pwa.md)) and the `e2e` job ([S2.5](S2.5-deep-link-return-path.md) creates it
  with the first spec, [S7.3](S7.3-end-to-end-journey.md) extends it).
- `playwright.config.ts`. [S0.5](S0.5-deployment.md) creates it with the `smoke-deployed` project.
- The deploy workflow. That is [S0.5](S0.5-deployment.md), a separate file, triggered on `push` to `main`,
  and it runs no tests.
- Coverage thresholds. [S7.2](S7.2-unit-tests.md) adds `--coverage` and the floor to this job.
- Any npm script. [S0.1](S0.1-project-scaffold.md) owns `package.json`; this story calls its four names

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [x] **AC1** — `.github/workflows/ci.yml` runs on `pull_request` (all branches) and on `push` to `main`.
      `pull_request_target` appears nowhere in the repository.
- [x] **AC2** — The `check` job runs, in order and each as its own step so a failure names itself:
      `npm ci`, `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test`, `npm run build`,
      `node scripts/check-env-parity.mjs`. A failure in any one fails the job.
- [x] **AC3** — The job sets `env: { TZ: UTC }` ([D53](../00-decisions.md)), and uses
      `actions/setup-node@v4` with `node-version-file: .nvmrc` and `cache: npm`, so the runner and
      [S0.1](S0.1-project-scaffold.md) AC13's pin can never drift apart.
- [ ] **AC4** — No job in this workflow reads `secrets.*`. Grepping the file for `secrets.` returns
      nothing, and a pull request opened from a fork runs every job to completion.
- [x] **AC5** — `permissions` is declared at the workflow level as `contents: read` and nothing else.
- [x] **AC6** — A `concurrency` group keyed on the ref cancels a superseded run, so a force-push does not
      leave two runs racing.
- [x] **AC7** — The `pr-title` job fails a pull request whose title is not a conventional commit, and
      names the allowed types in the failure message. It runs only on `pull_request`.
- [x] **AC8** — The Supabase CLI version is pinned to an exact version string in one workflow-level
      `env` key, `SUPABASE_CLI_VERSION`, never `latest`. Every later job that runs `supabase/setup-cli`
      reads that key ([S2.6](S2.6-session-persistence.md) depends on the pinned CLI supporting
      `[auth.sessions]`).
- [ ] **AC9** — `main` is protected: `check` and `pr-title` are required status checks, direct pushes are
      refused, and the branch requires a pull request. Recorded in `docs/ci.md` with a screenshot-free
      description of the settings, because branch protection is not a file in the repo.
- [x] **AC10** — `docs/ci.md` lists every job the pipeline will hold — `check`, `pr-title`, `db`, `pwa`,
      `e2e` — with its owning story and a one-line statement of what it does. A later story adding a job
      adds its row and adds the job to the required checks.
- [ ] **AC11** — A pull request that deliberately breaks one thing — a type error, a lint error, an
      unformatted file, a failing test, a `VITE_` key present in `.env.example` and missing from the
      deploy workflow — fails the `check` job, one case at a time. Recorded in the story's PR.
- [ ] **AC12** — The workflow completes in under four minutes on a clean cache for the Epic 0 codebase,
      and the `check` job is the only job present until [S1.1](S1.1-schema.md) adds `db`.

## Implementation notes

### The file

```yaml
# .github/workflows/ci.yml
name: CI
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

env:
  TZ: UTC
  SUPABASE_CLI_VERSION: '2.22.6'   # exact, never `latest` — S2.6 needs [auth.sessions]

jobs:
  check:
    runs-on: ubuntu-latest
    env: { TZ: UTC }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version-file: .nvmrc
          cache: npm
      - run: npm ci
      - run: npm run typecheck
      - run: npm run lint
      - run: npm run format:check
      - run: npm test
      - run: npm run build
      - run: node scripts/check-env-parity.mjs

  pr-title:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Conventional commit title
        env:
          TITLE: ${{ github.event.pull_request.title }}
        run: |
          echo "$TITLE" | grep -Eq '^(feat|fix|chore|docs|refactor|test|build|ci|perf|revert)(\([a-z0-9.-]+\))?!?: .+' \
            || { echo "PR title must be a conventional commit, e.g. 'feat(events): create event form'"; exit 1; }
```

The title is passed through `env:` and quoted, never interpolated into the shell line — a pull request
title is attacker-controlled text.

`npm test` is [S0.1](S0.1-project-scaffold.md)'s `vitest run`.
[S7.2](S7.2-unit-tests.md) changes that one step to `vitest run --coverage` and adds the threshold; it
changes nothing else in this job.

### The seams

Later stories append jobs to this file. The rules they inherit, written here so nobody re-derives them:

| Job | Owner | Adds | Notes |
|---|---|---|---|
| `check` | S0.7 | typecheck, lint, format, unit, build, env parity | The only job that exists at the end of this story |
| `pr-title` | S0.7 | conventional-commit title gate | `pull_request` only |
| `db` | [S1.1](S1.1-schema.md), extended by [S1.4](S1.4-rls-test-suite.md) | local Supabase stack, `supabase db reset`, structural tests, then the seed and the RLS suite | Needs `fetch-depth: 0` for S1.1 AC20 |
| `pwa` | [S0.4](S0.4-pwa.md) | build, Playwright `pwa` project, Lighthouse installability | No stack, no secret |
| `e2e` | [S2.5](S2.5-deep-link-return-path.md), extended by [S7.3](S7.3-end-to-end-journey.md) | local stack plus seed, `vite preview`, Playwright | [D17](../00-decisions.md): never the live site |

Every one of them sets `env: { TZ: UTC }`, uses `node-version-file: .nvmrc`, and reads
`${{ env.SUPABASE_CLI_VERSION }}` rather than pinning its own. None of them reads a secret: the Supabase
CLI's local anon and service-role keys are published constants committed in `.env.example`
([D38](../00-decisions.md)).

### Branch protection

Configured in repository settings, not in a file, which is why AC9 makes `docs/ci.md` the record:

- `main` requires a pull request; no direct pushes.
- Required status checks: `check` and `pr-title` now; `db` from S1.1, `pwa` from S0.4, `e2e` from S2.5.
- "Require branches to be up to date before merging" on, so a green check means green against the tip.

The S0.5 deploy workflow triggers on `push` to `main`, which only happens on a merge, and re-runs no
tests ([D14](../00-decisions.md)). The pipeline gates the merge; the merge gates the deploy.

## Open questions

1. **Should `check` run on a matrix of Node versions?** Proposed default: no. One version, pinned by
   `.nvmrc`, matching what S0.5 deploys with. A matrix tests a configuration nobody ships.
2. **Should the pinned Supabase CLI version be bumped automatically?** Proposed default: no. A manual
   bump in its own pull request, because the CLI decides whether `[auth.sessions]` in
   [S2.6](S2.6-session-persistence.md) is honoured or silently ignored, and that is not a change to make
   while asleep.

## Build notes — deviations from this spec

A bare step would fail every run between the two. The guard goes away when S0.5 adds the file; a failing script still fails the job. |
| AC3 pins the runner to [S0.1](S0.1-project-scaffold.md) AC13's Node | `node-version-file: .nvmrc`, which S0.1 built as `24`, not the `22` its own spec assumed | S0.1's deviations table records the bump. Pinning by file rather than by literal is what keeps the two from drifting, so nothing in this file changes. |
| AC12 — "the `check` job is the only job present" | `check` and `pr-title` | AC7 in the same story requires `pr-title`. Read as: no job that needs a database or a browser, which is what [S1.1](S1.1-schema.md) and [S2.5](S2.5-deep-link-return-path.md) add. |
| AC4 — "a pull request opened from a fork runs every job to completion" | Not verified | Needs a fork and a hosted Actions run. The structural half is verified: `secrets.` and the privileged fork trigger appear nowhere in the repository, which is the property that makes the fork case work. AC4 left unticked. |
| AC9 — `main` is protected | Settings written down in `docs/ci.md`, protection not applied | Requiring a pull request on `main` now would refuse the very pushes that put this workflow onto `main`, and `check` and `pr-title` do not exist as check *names* until the workflow has run once. The maintainer applies it after the first push. AC9 left unticked. |
| AC11 — five deliberate breakages, recorded in the story's PR | Four run locally against the exact step commands, each confirmed red and then green | A type error (`TS2532`), a lint error (`no-explicit-any`), an unformatted file, and a failing test all fail their step. The fifth case needs `scripts/check-env-parity.mjs` and a deploy workflow, neither of which exists until S0.5. AC11 left unticked; S0.5 completes it. |
| AC12 — "under four minutes on a clean cache" | Not verified | No hosted runner is reachable from the build machine. Locally the six product steps take about 25 seconds in total, so the budget is not in doubt, but the number is unmeasured. AC12 left unticked. |

The workflow was validated by parsing `.github/workflows/ci.yml` with `js-yaml` in a throwaway script and
asserting the trigger, permissions, concurrency, job list, step order, `setup-node` inputs and the pinned
CLI version, plus the `pr-title` regex against seven real titles. No test was committed: this story's test
plan says it has none of its own, and `js-yaml` is not a dependency this project should carry.
`supabase@2.22.6` was confirmed to be a real published version before the pin was kept.
