## Goal

One test walks the entire journey the product exists for: a manager creates Saturday's match, shares it,
a brand new player opens that link, registers, lands on the exact event, says yes, the manager sees the
count move, and the manager records who turned up. When it is green, the product works. When it is red,
something real is broken.

## Context

`CLAUDE.md` names the journey once and then repeats that nothing outside it matters:
**Create event → Share to WhatsApp → Player taps link → Yes/No → Manager sees counts → Manager records
attendance.** This story is that sentence, executed.

[D57](../00-decisions.md) makes this the only genuinely new test artifact in Epic 7 — every other story
ships its own tests, and [S7.1](S7.1-state-coverage-audit.md) and [S7.2](S7.2-unit-tests.md) verify rather
than backfill. So the journey spec covers the seams between stories, not the insides of them.

The decisions that shape it:

- [D17](../00-decisions.md) — Playwright drives `vite preview` on `http://127.0.0.1:4173`, built from
  `.env.test` against the local Supabase stack. It never touches `app.phibsborofc.com`.
- [D14](../00-decisions.md) and [D38](../00-decisions.md) — the `e2e` job uses no repository secret, so it
  runs on a fork pull request. The Supabase CLI's local keys are published constants, committed.
- [D58](../00-decisions.md) — `npm run db:reset` ([S1.1](S1.1-schema.md), extended by
  [S1.2](S1.2-profile-provisioning-and-seed.md) to run the seed after the migrations) runs before
  Playwright, so every run starts identical, and the registering player's number comes from a reserved
  range so a half-finished run never blocks the next one.
- [D53](../00-decisions.md) — `TZ=UTC` on the job, `timezoneId: 'Europe/Dublin'` on the Playwright project.
- [D6](../00-decisions.md) — the new player arrives on `/#/event/{id}` with no invite token. The event link
  is the join credential.
- [D46](../00-decisions.md) — the escape prompt and the install guide are mutually exclusive, so the
  journey runs on an Android-Chrome leg for the install guide and a separate WhatsApp-webview leg for the
  escape prompt.
- [D21](../00-decisions.md) — no wall-clock assertion. The 60-second budget is measured on a real phone in
  [S7.4](S7.4-device-pass.md).
- [D43](../00-decisions.md) — the service-worker staleness check runs in this job.

## Scope

**In**

- `tests/e2e/journey.spec.ts`: the full MVP journey, one linear test, two browser contexts.
- `tests/e2e/escape-prompt.spec.ts`: the WhatsApp-webview leg ([D46](../00-decisions.md), [D47](../00-decisions.md)).
- `tests/e2e/install-guide.spec.ts`: the Android install-button path and its written-steps fallback ([D45](../00-decisions.md)).
- Extending `playwright.config.ts` with the two device projects, the Dublin timezone and the web server.
- Extending `.github/workflows/ci.yml` with the `e2e` job: local Supabase stack, `npm run db:reset`,
  build from `.env.test`, run Playwright, upload the report on failure.
- `.env.test`, committed, pointing at `http://127.0.0.1:54321`.
- Shared fixtures: a run-scoped phone number, a sign-in helper, a service-role helper used only for
  setup and for reading back what the UI wrote.

**Out**

- Testing every branch of every screen. Feature stories own those. This spec asserts the seams.
- Running against the deployed site. [D17](../00-decisions.md) forbids it; the post-deploy smoke job
  belongs to [S0.5](S0.5-deployment.md).
- A wall-clock performance assertion ([D21](../00-decisions.md)).
- Real WhatsApp. `navigator.share` is stubbed and the `wa.me` link is asserted as a URL, never opened.
  [S7.4](S7.4-device-pass.md) is where a message actually gets sent.
- Visual regression, accessibility audits, load testing, cross-browser matrices beyond the two projects named.
- Any new product behaviour. If the journey cannot be walked, the fix belongs in the story that owns the
  broken screen, not here.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — `tests/e2e/journey.spec.ts` passes end to end on the `android-chrome` project against a
      freshly reset and seeded database, and covers, in this order: manager signs in; manager creates a
      match this coming Saturday; manager shares it; a brand new user opens the shared link in a clean
      browser context; registers with name, number and password; lands on `/#/event/{id}`; taps YES; sees
      the install guide — the spec dispatches a synthetic `beforeinstallprompt` on load, so the context
      resolves `installable` and a real Install button appears ([D45](../00-decisions.md),
      [S2.8](S2.8-add-to-home-screen-guide.md)); the manager's open counts move; the manager records
      attendance.
- [ ] **AC2** — The link the new user opens is **extracted from the captured share message**, not
      constructed by the test. The test asserts the captured message has the
      [D13](../00-decisions.md) shape — five lines, `⚽` first character, the date line equal to
      `formatEventTime(starts_at, 'share')`, the location line, a blank line, then
      `Are you available? {url}`. The assertion is made by calling `buildShareMessage()` from
      `@/lib/shareMessage` on the event the test created and comparing the two strings, so the format lives
      in one place. The id in the URL must equal the id in the manager's own address bar.
- [ ] **AC3** — The new user's context is created with `browser.newContext()` and carries no cookies, no
      `localStorage` and no service worker from the manager's context. Asserted by checking
      `localStorage.length === 0` before the first navigation.
- [ ] **AC4** — Before registering, the cold arrival renders the [D7](../00-decisions.md) preview: team
      name, type, title, location and date line, one primary button reading `Join {team name}`, **no**
      notes text anywhere in the DOM, and no availability control. The event is seeded with a non-empty
      `notes` value specifically so this assertion can fail.
- [ ] **AC5** — After registration the player is on `/#/event/{id}` for the same id, not on `/`. Asserted
      against `page.url()`, and again by the event title being visible.
- [ ] **AC6** — Tapping YES leaves the YES control in its selected state after a full page reload, proving
      the write reached Postgres and was not only optimistic.
- [ ] **AC7** — The manager page is already open when the player responds. After
      `page.bringToFront()` the counts update **without a navigation or reload**
      ([D23](../00-decisions.md)), and the four numbers satisfy
      `available + unavailable + awaiting === squad`, with `available === 1`,
      `squad === seededSquadSize + 1`.
- [ ] **AC8** — The new player's name appears in the manager's response list
      ([S4.4](S4.4-player-response-list.md)) with an Available pill. The name comes from
      `team_member_directory` ([D8](../00-decisions.md)), so this also proves the directory RPC is reachable
      to a manager.
- [ ] **AC9** — The manager sets that player's attendance to attended. After a reload the segmented control
      still reads attended, and a service-role read asserts the `attendance` row has
      `attended = true` and `recorded_by` equal to the manager's uuid ([S4.5](S4.5-record-attendance.md)).
- [ ] **AC10** — `tests/e2e/escape-prompt.spec.ts`, on the `whatsapp-ios` project, asserts that after the
      first response the escape prompt is shown, the install guide is **not** present in the DOM
      ([D46](../00-decisions.md)), the copy-link button copies the **app root** URL rather than the event
      URL, and the copy reads that the player will sign in once more ([D47](../00-decisions.md)).
- [ ] **AC11** — `tests/e2e/install-guide.spec.ts`, on the `android-chrome` project, asserts two paths:
      with a synthetic `beforeinstallprompt` dispatched, a real Install button appears and the escape
      prompt does not; with none dispatched, the context resolves `android-inapp` after the 3-second wait,
      so the **escape prompt** appears and the install guide does not. The written Android steps are then
      asserted only after opening the header menu item, which is where
      [S2.8](S2.8-add-to-home-screen-guide.md) puts them ([D45](../00-decisions.md),
      [D46](../00-decisions.md)).
- [ ] **AC12** — The `e2e` job, created by [S2.5](S2.5-deep-link-return-path.md), is extended here. It runs on
      `pull_request` and on `push` to `main`, and requires **no repository secret**. Verified by running
      the workflow from a fork.
- [ ] **AC13** — `npm run db:reset` runs before Playwright in the job, so every run starts from the same
      database. Two separate checks: run the suite twice with the reset in between and both pass; then run
      it twice **without** a reset in between and the second run still passes, because the run-scoped
      reserved-range number is different and no assertion depends on a row the first run left behind
      ([D58](../00-decisions.md)). A second run that fails means the spec has hidden state.
- [ ] **AC14** — No `page.waitForTimeout` appears anywhere in `tests/e2e/`, enforced by an ESLint
      `no-restricted-syntax` rule scoped to that directory. Every wait is a web-first assertion.
- [ ] **AC15** — The suite runs green three times consecutively in CI with zero retries consumed. The
      Playwright HTML report showing `0 flaky` is pasted into the PR.

## Implementation notes

### Playwright configuration

```ts
// playwright.config.ts
export default defineConfig({
  testDir: 'tests/e2e',
  timeout: 60_000,
  expect: { timeout: 10_000 },
  fullyParallel: false,
  workers: 1,
  retries: process.env.CI ? 1 : 0,
  reporter: [['list'], ['html', { open: 'never' }]],
  use: {
    baseURL: 'http://127.0.0.1:4173',
    timezoneId: 'Europe/Dublin',
    locale: 'en-IE',
    trace: 'on-first-retry',
    video: 'retain-on-failure',
  },
  webServer: {
    // `preview` already pins 4173 with --strictPort (S0.1)
    command: 'npm run preview',
    url: 'http://127.0.0.1:4173',
    reuseExistingServer: !process.env.CI,
  },
  projects: [
    { name: 'android-chrome', use: { ...devices['Pixel 7'] } },
    {
      name: 'whatsapp-ios',
      use: {
        ...devices['iPhone 13'],
        userAgent: `${devices['iPhone 13'].userAgent} WhatsApp/2.24.10`,
      },
    },
  ],
})
```

`workers: 1` and `fullyParallel: false` are not negotiable: there is one seeded database, and parallel
workers writing to the same squad make the count assertions meaningless. At this suite size the wall-clock
cost is a minute.

`retries: 1` exists to distinguish a flake from a failure in the report, not to launder one. AC15 is the
gate that keeps it honest.

### Fixtures

`tests/e2e/fixtures.ts` extends the base `test` with the [S7.1](S7.1-state-coverage-audit.md)
`failOnPageError` auto fixture and adds:

```ts
export const RUN = String(process.env.GITHUB_RUN_NUMBER ?? Date.now()).slice(-5).padStart(5, '0')
export const newPlayerPhone = `+3538990${RUN}`   // reserved range (D58, as amended)

export async function signIn(page: Page, phone: string, password: string): Promise<void>
export function adminClient(): SupabaseClient<Database>   // service-role, setup and read-back only
```

Seeded users are imported from one place, `supabase/seed/fixtures.ts`, which the
[S1.2](S1.2-profile-provisioning-and-seed.md) seed script also imports: `ADMIN`, `MANAGERS`, `PLAYERS`,
`SEED_PASSWORD`, `TEAM_FIRSTS`. There is no second fixture set ([D15](../00-decisions.md)). The expected
squad size is **derived from those constants**, never typed as a literal: the S1.2 layout gives Firsts
manager 1, players 1–10 and the multi-team player, so `seededSquadSize` is 12 and the assertion breaks
loudly if the seed layout changes.

`adminClient()` is the service-role client [S1.2](S1.2-profile-provisioning-and-seed.md) already ships as
`tests/helpers/admin.ts`, reading the local stack's published service-role key from `.env.test`. Import it,
do not write a second one; this story widens its permitted importers from `tests/db/**` to
`tests/db/**` and `tests/e2e/**`, which is an amendment to note against S1.2's AC27. It is used for setup
and for reading back what the UI wrote (AC9). It is never used to perform a user action the journey is
supposed to prove, and it is never imported under `src/`
([D15](../00-decisions.md), [D38](../00-decisions.md)).

### Capturing the share

`navigator.share` does not exist in headless Chromium, and [S5.2](S5.2-share-action.md) falls back to
`wa.me`. Stub it so both paths are provable and neither opens WhatsApp:

```ts
await managerPage.addInitScript(() => {
  ;(window as unknown as { __shared: string[] }).__shared = []
  Object.defineProperty(navigator, 'share', {
    value: async (d: ShareData) => {
      ;(window as unknown as { __shared: string[] }).__shared.push(d.text ?? '')
    },
    configurable: true,
  })
})
```

After tapping Share, read `window.__shared[0]`, assert the [D13](../00-decisions.md) shape, and extract the
URL with `/https?:\/\/\S+#\/event\/([0-9a-f-]{36})/`. A second, cheaper assertion covers the fallback: with
`navigator.share` deleted instead of stubbed, [S5.2](S5.2-share-action.md)'s `shareText()` falls through to
`waMeUrl()`, so spy on `location.assign` and assert the URL starts `https://wa.me/?text=` and contains
`%23%2Fevent%2F` ([D52](../00-decisions.md)).

### Choosing Saturday

`starts_at` is computed in the test as the next Saturday at 14:00 Europe/Dublin, always in the future, so
the [D12](../00-decisions.md) response cut-off never bites. Compute it once, feed the date and time into
the [S4.1](S4.1-create-event.md) form, and assert the resulting share line equals
`formatEventTime(startsAtIso, 'share')` by importing the real helper from `@/lib/time` into the spec. Do not reimplement the
formatting in the test; that is how two wrong things agree.

The event is created with `notes` set to a sentinel string — `SECRET-NOTES-DO-NOT-LEAK` — so AC4 can assert
the preview does not contain it.

### Waiting for the counts to move

D23 is polling, not push: the manager view sets `refetchInterval: 30_000` with
`refetchIntervalInBackground` left at `false`, so a backgrounded tab does not poll at all. The sequence is
`await managerPage.bringToFront()` — which fires the focus that triggers `refetchOnWindowFocus` — then a
web-first assertion with a raised timeout so the 30-second poll is a fallback rather than a failure:

```ts
await expect(managerPage.getByTestId('count-available')).toHaveText('1', { timeout: 35_000 })
```

The raised timeout is on this assertion only; the config default of 10 seconds stays everywhere else, and
`page.waitForTimeout` is still banned (AC14).

### Selectors

`getByRole` everywhere it is unambiguous: `getByRole('button', { name: 'Yes' })`,
`getByRole('link', { name: 'Join Firsts' })`. The four count tiles are the exception: they are a number
above a label inside a shadcn `Card` ([S4.3](S4.3-manager-event-view.md)'s `EventCountsPanel.tsx`), with no
role to query and no accessible name tying the number to the word. This story adds four attributes to that
component — `data-testid="count-available"`, `count-unavailable`, `count-awaiting`, `count-squad` — and
nothing else. It is the only product file this story touches, it changes no behaviour, and the change is
noted in the PR against S4.3. No CSS class selectors anywhere; a Tailwind class is not a contract.

### The two conditional-surface legs

**Escape prompt, `whatsapp-ios`.** WebKit does not support Playwright's `clipboard-read` permission, so do
not read the clipboard. [S2.7](S2.7-escape-the-whatsapp-browser.md)'s `copyText()` in `src/lib/clipboard.ts`
calls `navigator.clipboard.writeText` first, so capture that instead:

```ts
await page.addInitScript(() => {
  ;(window as unknown as { __copied: string[] }).__copied = []
  Object.defineProperty(navigator, 'clipboard', {
    value: { writeText: async (t: string) => { (window as unknown as { __copied: string[] }).__copied.push(t) } },
    configurable: true,
  })
})
```

Assert `__copied[0]` equals `` `${baseURL}/#/` `` — the app root, not the event URL ([D47](../00-decisions.md)) —
and assert the prompt copy contains "You'll sign in once more". Assert the install guide's absence by its
own test id or heading, with `toHaveCount(0)`, not by a screenshot.

**Install guide, `android-chrome`.** `beforeinstallprompt` never fires in headless Chromium, so dispatch a
synthetic one before the response, shaped as the S2.8 handler expects:

```ts
await page.evaluate(() => {
  const e = new Event('beforeinstallprompt') as Event & {
    prompt: () => Promise<void>
    userChoice: Promise<{ outcome: 'accepted' | 'dismissed' }>
  }
  e.prompt = async () => {}
  e.userChoice = Promise.resolve({ outcome: 'accepted' as const })
  window.dispatchEvent(e)
})
```

The fallback path is the same spec with nothing dispatched: wait for the written steps with a web-first
assertion whose timeout clears the 3-second classification window ([D45](../00-decisions.md)), never a
`waitForTimeout`. The Install button click is asserted only as far as `promptInstall()` resolving; the
real install is [S7.4](S7.4-device-pass.md)'s job.

### The service-worker check is not here

[D43](../00-decisions.md)'s stale-shell check belongs to [S0.4](S0.4-pwa.md) AC5, which already builds
twice and asserts the second build's shell wins after the `controllerchange` reload, in the `pwa` job.
Running the same two-build check again here would cost two extra builds and a second web server to prove
something that has been green since build-order position 6. This story asserts nothing about the service
worker.

The release string is exposed as `<meta name="pfc-release" content="%VITE_SENTRY_RELEASE%">` in
`index.html` and mirrored to `document.documentElement.dataset.release`. It renders nothing on screen. If
[S0.6](S0.6-observability.md) did not add it, this story adds the one line; the
[S0.5](S0.5-deployment.md) post-deploy smoke job ([D17](../00-decisions.md)) reads the same attribute.

### The `e2e` CI job

[S2.5](S2.5-deep-link-return-path.md) created the `e2e` job with its single deep-link spec. This story
extends it: the extra Playwright projects and the browsers they need. No secrets
([D14](../00-decisions.md)). The job, in full, after this story:

```yaml
e2e:
  runs-on: ubuntu-latest
  env:
    TZ: UTC
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with: { node-version-file: .nvmrc, cache: npm }
    - run: npm ci
    - uses: supabase/setup-cli@v1
      with: { version: '${{ env.SUPABASE_CLI_VERSION }}' }   # S0.7 AC8
    - run: supabase start
    - run: npm run db:reset            # migrations + seed (S1.1, S1.2)
    - run: npx playwright install --with-deps chromium webkit
    - run: npm run build -- --mode test
    - run: npx playwright test
    - uses: actions/upload-artifact@v4
      if: failure()
      with: { name: playwright-report, path: playwright-report/ }
```

`--mode test` makes Vite read `.env.test`, which carries `VITE_SUPABASE_URL=http://127.0.0.1:54321`, the
CLI's fixed local anon key, and `VITE_APP_BASE_URL=http://127.0.0.1:4173`. That last one matters: the
share message the test parses is built from it ([D13](../00-decisions.md)), so the extracted URL is one
the preview server can actually serve.

### Failure triage

On failure the job uploads the HTML report with traces and video. A trace on the journey spec is the
fastest route from "CI is red" to "the Join button moved", which is the whole reason the report is
uploaded rather than just the exit code.

## Data and API surface

No migration, no new RPC, no new Zod schema, no new query key. One product file changes: four
`data-testid` attributes on `EventCountsPanel.tsx`. The spec exercises, through the UI only:

## UI states

Not a UI story. It adds no screen. It asserts states other stories built, on these routes: `/login`,

are in [S7.1](S7.1-state-coverage-audit.md)'s table and are not restated here.

## Test plan

- **Unit** — None. Every helper this spec imports (`formatEventTime`, the share generator, `deriveCounts`)
  is already covered by [S7.2](S7.2-unit-tests.md) and its owning story; importing the real helper into the
  spec is deliberate, so a formatting change breaks in one place.
- **Integration / RLS** — None added. [S1.4](S1.4-rls-test-suite.md) runs in the separate `db` job and must
  still pass. If the journey needs a policy change to go green, the policy is wrong, not the test.
- **E2E** — The three specs above, on two projects. `journey.spec.ts` and `install-guide.spec.ts` on
  `android-chrome`; `escape-prompt.spec.ts` on `whatsapp-ios`.
- **Manual** — Run the suite with `--headed --project=android-chrome` once and watch it, before trusting
  it. A green E2E suite that nobody has ever watched is a suite that asserts nothing interesting.

## Open questions

1. **[D14](../00-decisions.md) says the `e2e` CI job is added by S7.3, but
   [S2.5](S2.5-deep-link-return-path.md) is built twenty-one places earlier and must run a Playwright test
   in CI to meet the definition of done.** The config file is not in question:
   [S0.5](S0.5-deployment.md) creates `playwright.config.ts` at build-order position 4 and
   [S0.4](S0.4-pwa.md) already extends it. Proposed default: S2.5 adds the `e2e` **job** to
   `.github/workflows/ci.yml` and one `e2e` project to the existing config, with its single spec; this
   story extends both with the device projects, the shared fixtures and the two additional specs.
   Recorded as an amendment to D14.
2. **Does the journey record attendance on an event that has not happened yet?** Proposed default: yes.
   [S4.5](S4.5-record-attendance.md) places no time restriction on recording, and inventing one to make the
   test tidier would be new product behaviour. The spec notes it in a comment.
3. **Should the suite also run on WebKit for the non-WhatsApp legs?** Proposed default: no. Two projects is
   the budget. iOS Safari coverage is [S7.4](S7.4-device-pass.md), on a real phone, where it means something.
