## Goal

A manager can fix a wrong time, move a fixture to a different pitch, or call a session off, without
losing the answers players have already given. Cancelling marks the event and keeps everything; it never
deletes. Destroying an event outright is an admin action behind a typed confirmation, and it is the only
path in the app that throws history away.

## Context

The brief's S4.2. Story 30 in the build order ([D20](../00-decisions.md)), immediately after
[S4.1](S4.1-create-event.md), whose `EventForm` and `eventFormSchema` this story reuses rather than
copying. Decisions that settle what would otherwise be guesswork:

- **[D31](../00-decisions.md)** — a manager may insert, select and update events for teams they manage;
  `DELETE` on `events` requires `is_admin()`. `event_responses.event_id` and `attendance.event_id` are
  `on delete cascade`, so an admin hard delete destroys that event's responses and attendance. That
  consequence is stated on screen, behind a typed confirmation.
- **[D12](../00-decisions.md)** — the response cut-off is an RLS `WITH CHECK`: a cancelled or already
  started event refuses new and changed responses, while existing rows are untouched and stay readable.
  So "existing responses survive an edit" is a property of the schema, not something this story codes.
  What this story must not do is delete or rewrite response rows on any edit path.
- **[D60](../00-decisions.md)** — a cancelled event never occupies the player's next-event card, still
  appears in the list marked cancelled, and shows "This one's off." with the controls disabled on the
  detail screen. That rendering is owned by Epic 3 and already built; this story only sets the status.
- **[D34](../00-decisions.md)** — the route list is fixed and contains no edit route. Edit is a shadcn
  `Dialog` over the screen the manager is already on, not a page.

**Flagged widening.** The brief gives `cancelled` no way back. A manager who cancels the wrong fixture
would otherwise have to create a replacement, which mints a new event id and kills the WhatsApp link
already sitting in the squad group — the journey's entry point. This story therefore adds **Reinstate**,
a single status update back to `scheduled`, allowed only while `starts_at > now()`. It is the exact
inverse of a verb the brief already asks for and adds no column, no route and no RPC. Raised as open
question 1, with "in, as specified" as the default so nothing is blocked.

## Scope

**In**
- Edit any field of an existing event: type, title, date, start time, location, notes.
- Cancel an event: confirmed, sets `status = 'cancelled'`, deletes nothing.
- Reinstate a cancelled event whose start is still in the future: confirmed, sets `status = 'scheduled'`.
- Hard delete, visible to admins only, behind a typed confirmation naming the event.
- The overflow menu on `EventListRow`, so all four actions are reachable from `/manage` the moment this
  story ships and before [S4.3](S4.3-manager-event-view.md) exists.
- `useUpdateEvent()`, `useSetEventStatus()` and `useDeleteEvent()` in `src/api/events.ts`.

**Out**
- Changing an event's `team_id`. Fixed at creation, not editable anywhere.
- Editing a whole recurring series at once — [S4.6](S4.6-recurring-training.md), where the rule is that
  editing or cancelling one occurrence leaves the others untouched and never reads `series_id`.
- Notifying players that something changed. No push, no automated WhatsApp. A manager who moves a
  fixture re-shares it with [S5.2](S5.2-share-action.md).
- Optimistic concurrency control. Two managers editing the same event at the same moment is a last-write-
  wins race, accepted deliberately at this size and stated in open question 2.
- Clearing or resetting responses on edit. Never, on any path.
- An undo for hard delete. There is none; that is what the typed confirmation is for.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [x] **AC1** — The overflow menu on any event row on `/manage` offers Edit, then Cancel or Reinstate as
      appropriate, and Delete for an admin only. Every item is at least 44px high.
- [x] **AC2** — Edit opens a dialog pre-filled with the event's current values, with all six fields —
      type, title, date, start time, location, notes — editable, and the team shown as read-only text.
      The date and time fields show the Dublin wall-clock values derived through `utcIsoToDublinParts()`:
      an 18:30Z July event shows 19:30. Saving a change to each of the six fields persists it, checked
      field by field in the E2E case.
- [x] **AC3** — Saving an edit updates exactly one `events` row and zero rows in `event_responses` and
      `attendance`. Asserted by counting both tables before and after in an integration test, with at
      least one existing response on the event.
- [x] **AC4** — Changing only the start time of an event that already has five responses leaves all five
      rows present, unmodified, and still visible to the manager.
- [x] **AC5** — Edit applies the identical validation to create: the same `eventFormSchema`, the same
      messages, the same length and 365-day rules, and the same injected `serverNow()`. The single
      difference is `requireFuture`, which is `false` when the edit leaves `date` and `time` untouched.
      One schema, two callers.
- [x] **AC6** — Cancel asks first. The confirmation names the event and reads "Cancel {title}? Players
      will see it marked off. Their answers are kept." Dismissing changes nothing.
- [x] **AC7** — After cancelling, the row on `/manage` shows a Cancelled badge, the event is not deleted,
      and a player attempting to respond is refused by the database, not merely by the UI — the existing
      [S1.4](S1.4-rls-test-suite.md) test for a cancelled event still passes.
- [x] **AC8** — Reinstate is offered only for a cancelled event whose `starts_at` is later than
      `serverNow()`, is confirmed before it applies, and returns `status` to `scheduled`. A cancelled
      event that has already started offers no Reinstate item at all, and a device clock set an hour
      behind does not make one appear ([D48](../00-decisions.md)).
- [x] **AC9** — Delete is absent from the menu for a manager who is not an admin. If a non-admin reaches
      the mutation anyway, RLS returns zero affected rows and the UI renders "You can't delete events.",
      not a crash ([D31](../00-decisions.md)).
- [x] **AC10** — The delete confirmation states the consequence — "This deletes the event and every
      response and attendance record for it. It cannot be undone." — and its button stays disabled until
      the admin types the event title exactly.
- [x] **AC11** — After any of the four writes, `/manage` reflects the change without a manual refresh,
      and so does the player-side list, because every event mutation invalidates `eventKeys.all`.
- [x] **AC12** — Editing an event that another manager deleted in the meantime affects zero rows and
      renders "That event no longer exists." with a control to refresh the list. No unhandled rejection.
- [x] **AC13** — Each of the four actions is disabled while its mutation is in flight, and a double tap
      performs it once.

## Implementation notes

### Components

All under `src/features/events/`:

- `EventFormDialog.tsx` — shadcn `Dialog` wrapping [S4.1](S4.1-create-event.md)'s `EventForm` with
  `mode="edit"`. Props: `event: EventRow`, `open`, `onOpenChange`. It owns the `useUpdateEvent()` call;
  `EventForm` stays mutation-free so both callers keep using it.
- `CancelEventDialog.tsx` — shadcn `AlertDialog`. Handles cancel and reinstate from one component with a
  `to: 'cancelled' | 'scheduled'` prop, since they differ only in copy and target status.
- `DeleteEventDialog.tsx` — shadcn `AlertDialog` with an `Input` for the typed confirmation. Rendered
  only when `useCurrentUser().isAdmin`.
- `EventRowMenu.tsx` — shadcn `DropdownMenu`, mounted by `EventListRow`. Decides which items to show from
  `status`, `starts_at` and `isAdmin`.

Default values for the edit dialog:

```ts
const defaults: EventFormValues = {
  teamId:   event.team_id,
  type:     event.type,
  title:    event.title,
  location: event.location,
  notes:    event.notes ?? '',
  ...utcIsoToDublinParts(event.starts_at),   // { date, time }
}
```

`teamId` is rendered read-only in edit mode — the team name as static text, no select — because
`team_id` is not editable.

One deliberate exception to AC5's "identical validation": an event that has already started can still be
edited, so the future-only rule would block correcting a typo in last night's location.
[S4.1](S4.1-create-event.md)'s schema is a factory, `eventFormSchema({ requireFuture, now })`, always
given `now: serverNow()`: `requireFuture` is true for create and for any edit that changes `date` or
`time`, false when the instant is unchanged. Recompute the resolver when the date or time field changes,
so a manager who opens a past event and then moves it forward is still held to a future instant. The length and
365-day rules stay on in both cases. One flag on one schema, not a second schema.

### Mutations

`src/api/events.ts`, alongside [S4.1](S4.1-create-event.md)'s:

```ts
export function useUpdateEvent(): UseMutationResult<EventRow, PostgrestError, { id: string; values: EventFormValues }>
export function useSetEventStatus(): UseMutationResult<EventRow, PostgrestError, { id: string; status: EventStatus }>
export function useDeleteEvent(): UseMutationResult<{ id: string }, PostgrestError, { id: string }>
// resolves with the deleted id; rejects when the delete returns an empty array (refused, or already gone)
```

Each is a plain PostgREST call under RLS. No RPC; [S1.3](S1.3-rls-policies-and-rpcs.md) already carries
the policies.

```ts
// update
supabase.from('events')
  .update({ type, title, location, notes, starts_at })
  .eq('id', id)
  .select()
  .single()

// cancel / reinstate
supabase.from('events')
  .update({ status })
  .eq('id', id)
  .select()
  .single()

// delete — admin only, cascades to event_responses and attendance
supabase.from('events').delete().eq('id', id).select('id')
```

`updated_at` is maintained by the `before update` trigger from [S1.1](S1.1-schema.md). The client never
writes it. `team_id`, `created_by`, `created_at` and `series_id` are never in an update payload — omitting
`series_id` is what makes "editing one occurrence leaves the others untouched"
([D30](../00-decisions.md)) true by construction.

An update or delete that RLS refuses returns **zero rows, not an error**
([S1.3](S1.3-rls-policies-and-rpcs.md)). `.single()` therefore raises `PGRST116`; map it to AC12's copy.
For the delete, check the returned array length: an empty array means refused or already gone. The hook
rejects in that case, so the dialog has one failure path and never branches on `data.length` itself.
`DeleteEventDialog` renders AC9's fixed line, "You can't delete events.", for any rejection from
`useDeleteEvent`: both failure modes leave the admin with the same next step, and neither is worth
distinguishing on screen.

Everything else extends [S4.1](S4.1-create-event.md)'s helper rather than adding a second one:

```ts
// eventWriteErrorMessage, additional cases
// PGRST116 → "That event no longer exists."      (an update whose .single() found no row — AC12)
// 42501    → "You can't change events on that team."
```

All four mutations call `queryClient.invalidateQueries({ queryKey: eventKeys.all })` in `onSettled`, so a
failed write also re-syncs.

### Menu rules

```
Edit       — always, for a manager of the team
Cancel     — status === 'scheduled'
Reinstate  — status === 'cancelled' && starts_at > now
Delete     — isAdmin
```

`now` is `serverNow()` from `src/lib/serverClock.ts` ([S3.3](S3.3-event-detail-screen.md)) — the device
clock plus the skew captured from the `Date` response header — never `Date.now()`, matching
[D48](../00-decisions.md)'s rule for the player side. A device with a wrong clock must not be able to
reveal or hide an action.

These are convenience checks. RLS decides: a non-admin delete affects zero rows, and a manager editing
another team's event affects zero rows, both already asserted in [S1.4](S1.4-rls-test-suite.md).

### Handover to [S4.3](S4.3-manager-event-view.md)

`EventFormDialog`, `CancelEventDialog` and `DeleteEventDialog` are mounted again, unchanged, in the
manager event view header. There is one implementation of each; [S4.3](S4.3-manager-event-view.md) adds a
second mount point and nothing else. After a delete from the event view, that screen navigates back to
`/manage`; from the list, it stays put.

## Test plan

- **Unit** — `EventRowMenu` item visibility across the four combinations of status, past/future start and
  admin/manager, with `serverNow` stubbed so the cases are deterministic;
  `eventFormSchema({ requireFuture: false, now })` accepts a past instant and still rejects an
  over-long title; `eventWriteErrorMessage()` for `PGRST116` and `42501`; the delete confirmation enables
  only on an exact title match, including surrounding whitespace.
- **Integration / RLS** — Seeded event with responses and attendance: a manager update leaves both child
  tables byte-identical (AC3, AC4); a manager delete affects zero rows (already in
  [S1.4](S1.4-rls-test-suite.md), re-asserted here at the API layer); an admin delete removes the event
  and both child rows; a cancelled event refuses a player response (existing
  [S1.4](S1.4-rls-test-suite.md) test, confirmed still passing).
- **E2E** — Playwright: manager edits every one of the six fields on a seeded event in a single save —
  type, title, date, start time, location, notes — and asserts each change on the reloaded list row and in
  a service-role read of the row (AC2);
  manager cancels it and asserts the Cancelled badge; manager reinstates it; a player session loads the
  same event mid-flow and sees the cancelled banner and disabled controls.
- **Manual** — On a real phone: the overflow menu is tappable one-thumbed at 375px, the confirmation
  dialogs fit without scrolling, and the typed-confirmation input does not autocapitalise the first
  letter and so block an exact match.

## Open questions

1. **Is Reinstate wanted?** Proposed default, already specified: yes, bounded to cancelled events that
   have not yet started. Without it a mis-cancel kills the WhatsApp link already in the squad group. If
   the club says no, delete `CancelEventDialog`'s `to: 'scheduled'` branch and one menu rule; nothing
   else changes.
2. **Do two managers ever edit the same event at once?** Proposed default: assume not. Last write wins,
   no version column, no conflict UI. Two managers and twenty players does not justify optimistic
   locking. Revisit only if it actually happens.
3. **Should a manager be able to edit an event that has already started?** Proposed default, already
   specified: yes for everything except moving the start time, so last night's location typo is fixable
   while the record of when it happened is not quietly rewritten.
