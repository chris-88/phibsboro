## Goal

A manager opens one screen for Saturday's match and sees, at a glance, how many are in, how many are out,
how many have not answered, and how big the squad is. It is the screen they return to after every share,
and the frame the response list, the attendance toggles and the share button all hang off.

## Context

This is the "Manager sees counts" step of the journey: everything after it —
[S4.4](S4.4-player-response-list.md), [S4.5](S4.5-record-attendance.md) and
[S5.2](S5.2-share-action.md) — mounts inside this screen. It is the brief's S4.3, story 31 in the build order ([D20](../00-decisions.md)). The brief's two criteria both
needed a ruling before they could be built, and both have one:

- **[D22](../00-decisions.md)** defines squad: every current `team_members` row for that team, regardless
  of role. Managers are counted and may respond; at this level managers play, and the composite primary
  key allows one role per user per team, so there is no other way to count a playing manager. Awaiting is
  squad size minus responses from current members. Responses belonging to people who have since left are
  retained in the database, excluded from every count, and not listed. Counts are computed as-of now, not
  as-of `starts_at`. Count derivation is a **pure function in `src/lib/`**, so
  [S7.2](S7.2-unit-tests.md) can test it with no database, and it asserts
  `available + unavailable + awaiting === squad`.
- **[D23](../00-decisions.md)** rules out Supabase Realtime — it is not in the stack table, and a
  websocket for a squad of twenty is infrastructure nobody asked for. "Live" means polling. The brief's
  "Counts update live after any response change" is restated as: counts refresh within 30 seconds and
  immediately on window focus.

Two more that shape the reads:

- **[D8](../00-decisions.md)** — other people's names never come from `profiles`. The squad comes from
  the security-definer RPC `team_member_directory(p_team_id)`. This story needs the count of rows and
  nothing else from it; [S4.4](S4.4-player-response-list.md) needs the names.
- **[D33](../00-decisions.md)** — the manager read policy on `event_responses` is scoped by the owning
  event's team, never by the responder's current membership, so a leaver's rows come back in the query
  and must be filtered out by the count function, not by the database.

**[D49](../00-decisions.md)** fixes this screen's empty state: a squad with no members shows "No one has
joined this team yet" plus a route to the team's join link.

## Scope

**In**
- Route `/manage/event/:id`, the manager's view of one event.
- Header: type badge, title, `formatEventTime(starts_at, 'share')`, location, notes, and a Cancelled
  banner when the status says so.
- The four counts: Available, Unavailable, Awaiting, Squad.
- `deriveCounts()` in `src/lib/counts.ts`, pure, with the summing invariant.
- Polling and focus refetch per [D23](../00-decisions.md).
- Mounting [S4.2](S4.2-edit-and-cancel-event.md)'s Edit, Cancel/Reinstate and Delete dialogs in the
  header, and changing [S4.1](S4.1-create-event.md)'s post-create destination to this route.
- Navigation into the screen from every `/manage` row.

**Out**
- The per-player list. [S4.4](S4.4-player-response-list.md) fills the slot this screen leaves for it.
- Attendance toggles and the bulk action — [S4.5](S4.5-record-attendance.md).
- The share and reminder buttons — [S5.2](S5.2-share-action.md) and [S5.3](S5.3-reminder-share.md). This
  story reserves the header slot and renders nothing in it.
- A manager's own YES / NO controls. Managers respond on the player side, `/#/event/:id`, which already
  exists from [S3.3](S3.3-event-detail-screen.md). This screen links there rather than duplicating the
  controls.
- Any count as-of `starts_at`, any historical squad snapshot, any chart. Four numbers.
- Realtime subscriptions of any kind.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — `/manage/event/:id` resolves after a hard refresh on the deployed site, as
      [D34](../00-decisions.md) requires of every route.
- [ ] **AC2** — The header shows type badge, title, the date line from
      `formatEventTime(starts_at, 'share')`, location, and notes when present. Notes are omitted entirely,
      with their whitespace, when null.
- [ ] **AC3** — Four counts render, labelled Available, Unavailable, Awaiting and Squad, each at least
      44px tall and readable at 375px without horizontal scroll.
- [ ] **AC4** — `deriveCounts()` satisfies `available + unavailable + awaiting === squad` for every input,
      including an empty squad, a squad where nobody has answered, a squad where everybody has, and an
      event carrying a response row from a user who is no longer a member. Asserted in Vitest with no
      database.
- [ ] **AC5** — A response row belonging to a non-member is excluded from all four counts and does not
      change Squad. A manager who is a member is included in Squad and may appear in Available.
- [ ] **AC6** — After a player changes their answer, the counts on this screen update within 30 seconds
      with the tab focused, and immediately when the tab regains focus. Polling stops while the tab is
      hidden.
- [ ] **AC7** — When the manager is themselves the responder, the counts update immediately, because the
      response mutation invalidates `eventKeys.responses(eventId)`, which is the same key this screen
      reads.
- [ ] **AC8** — A cancelled event shows a banner reading "This one's off." above the counts. The counts
      still render; nothing is hidden.
- [ ] **AC9** — Edit, Cancel or Reinstate, and Delete for an admin, are reachable from this screen's
      header and behave exactly as on `/manage`, because they are the same components. A delete from here
      navigates back to `/manage`.
- [ ] **AC10** — An unknown event id, or an event belonging to a team the caller does not manage, renders
      the same "Event not found" screen with a link to `/manage`. RLS returns zero rows for the second
      case, so the two are indistinguishable to the client by design.
- [ ] **AC11** — A player who navigates here is redirected by the
      [S2.9](S2.9-auth-guard-and-role-context.md) guard. The guard is convenience; RLS is the enforcement
      layer and returns them nothing regardless.
- [ ] **AC12** — A team with no members renders all four counts as `0` — a truthful answer, not a blank
      panel — and renders "No one has joined this team yet." once, in the Who's in section, with a link to
      `/manage/team/{teamId}/members` where [S6.2](S6.2-team-join-links.md)'s join link lives. The message
      sits in the section [S4.4](S4.4-player-response-list.md) later fills, so nothing moves when S4.4
      ships ([D49](../00-decisions.md)).
- [ ] **AC13** — A failed load of either the event, the squad or the responses renders one inline message
      with a Retry button. A partial failure — say responses load but the directory does not — shows the
      header and the inline message in place of the counts, never a half-wrong number.
- [ ] **AC14** — Creating an event from [S4.1](S4.1-create-event.md) now lands the manager on this screen,
      not on `/manage`.

## Implementation notes

### The count function

`src/lib/counts.ts`. Pure, no imports from `src/api/`, no Supabase types in the signature, so
[S7.2](S7.2-unit-tests.md) tests it with plain objects.

```ts
export type SquadMember = { readonly userId: string }
export type ResponseRow = { readonly userId: string; readonly response: AvailabilityResponse }
export type Counts = {
  readonly available: number
  readonly unavailable: number
  readonly awaiting: number
  readonly squad: number
}

/** Counts as of now. Responses from users not in `squad` are ignored (D22, D33). */
export function deriveCounts(
  squad: readonly SquadMember[],
  responses: readonly ResponseRow[],
): Counts
```

Implementation is a `Set` of squad ids, one pass over responses counting only members, and
`awaiting = squad.length - available - unavailable`. Do not compute `awaiting` by iterating the squad and
looking for a response; the subtraction is what makes the invariant hold by construction. A duplicate
`userId` in `responses` cannot occur — `(event_id, user_id)` is the primary key — so the function takes
last-row-wins and never throws. [S7.2](S7.2-unit-tests.md) adds cases against this exact signature; it
must not change once shipped.

### Reads

Three queries, two of which already exist. Nothing new is added to `src/api/` but `useEventResponses`:

```ts
// src/api/events.ts — S3.3 already owns this one. Reuse it; do not add a second single-event hook.
export function useEventDetail(eventId: string): UseQueryResult<EventDetail | null>
// key eventKeys.detail(eventId). S3.3's EVENT_SELECT, including the
// .eq('event_responses.user_id', userId) filter its AC15 protects, and .maybeSingle():
// RLS returns zero rows for another team's event, and that is AC10, not an error.
// A second hook on the same key with a different select would collide in the cache and serve
// whichever query resolved last. There is one single-event read in the app.

export function useEventResponses(eventId: string): UseQueryResult<EventResponseRow[]>
// supabase.from('event_responses').select('user_id, response, updated_at').eq('event_id', eventId)
// Manager policy is scoped by the owning event's team (D33), so leavers' rows come back here.

// src/api/members.ts — S6.4 already owns this one (built at position 22, before this story).
export function useTeamMembers(teamId: string): UseQueryResult<MemberDirectoryRow[]>
// supabase.rpc('team_member_directory', { p_team_id: teamId }), parsed with
// memberDirectoryRowSchema from src/features/teams/schema.ts  (D8)
// → user_id, name, role, joined_at, phone (phone non-null only for a manager of that team, or an admin)
```

**There is one directory hook in the app.** [S6.4](S6.4-member-administration.md) ships
`useTeamMembers(teamId)` on the key `teamKeys.members(teamId)`; this story imports it rather than adding a
second hook, a second schema or a second key for the same RPC. `useTeamDirectory` and
`teamKeys.directory(teamId)` do not exist and must not be written.

`useEventResponses` is new here, and parses with
[S1.5](S1.5-typed-data-layer-and-shared-helpers.md)'s `eventResponseRowSchema`.

Both row types are snake_case, and `deriveCounts()` is keyed on `userId`, so the screen maps at the call
site and the pure function keeps a shape that owes nothing to PostgREST:

```ts
const squad     = useMemo(() => members.data?.map((m) => ({ userId: m.user_id })), [members.data])
const responded = useMemo(
  () => responses.data?.map((r) => ({ userId: r.user_id, response: r.response })),
  [responses.data],
)
```

The keys this screen reads, none of them declared here:

| Key | Shape | Owner |
|---|---|---|
| `eventKeys.detail(eventId)` | `['events', 'detail', eventId]` | [S3.3](S3.3-event-detail-screen.md) |
| `eventKeys.responses(eventId)` | `['events', 'responses', eventId]` | [S1.5](S1.5-typed-data-layer-and-shared-helpers.md), consumed here |
| `teamKeys.members(teamId)` | `['teams', teamId, 'members']` | [S1.5](S1.5-typed-data-layer-and-shared-helpers.md), consumed by [S6.4](S6.4-member-administration.md) and here |

The first two sit under the `['events']` prefix that `invalidateQueries({ queryKey: eventKeys.all })`
reaches, which is what makes AC7 work without this screen knowing anything about the player's response
mutation. The members key does not, and does not need to: squad size changes only through S6.4's own
mutations, which invalidate it and the counts key themselves.

The counts are derived in the component from the squad and the responses, not fetched:

```ts
const counts: Counts | null = useMemo(
  () => (squad && responded ? deriveCounts(squad, responded) : null),
  [squad, responded],
)
```

`null` until both queries have data, and the panel renders the skeleton or the inline error while it is
`null`. No `?? []` fallback: a count built from one loaded query and one empty default is a wrong number
on screen, which AC13 forbids.

### Polling

[D23](../00-decisions.md), applied to `useEventResponses` and `useTeamMembers` on this route only:

```ts
{ refetchInterval: 30_000, refetchOnWindowFocus: true }
```

`refetchIntervalInBackground` stays at its default of `false`, so TanStack Query already stops polling
when the tab is hidden — AC6's last clause needs no extra code, only a test. Pass the options from the
screen, not from the hook's own defaults, so the player screens do not inherit a 30-second poll.

`useEventDetail` does not poll. An event only changes when a manager changes it, and that invalidates
`eventKeys.all` already ([S4.2](S4.2-edit-and-cancel-event.md)).

### Loading and error handling

Three queries means four honest states, not a spinner over everything:

| Condition | Render |
|---|---|
| `useEventDetail` loading | Skeleton header, skeleton counts |
| `useEventDetail` resolved `null` | "Event not found" screen, link to `/manage` (AC10) |
| event loaded, either other query loading | Real header, skeleton counts |
| event loaded, either other query errored | Real header, inline "Couldn't load the responses." with Retry that refetches both, in place of the counts (AC13) |
| directory loaded and empty | Real header, four zeros, and the empty message in the Who's in section (AC12) |
| all loaded | Header plus four counts |

Every error state is an inline message with a retry control, never a blank screen; the
[S0.6](S0.6-observability.md) error boundary is the last resort, not the design
([D49](../00-decisions.md)).

## Test plan

- **Unit** — `deriveCounts()`: empty squad; squad of twenty with zero responses; all available; a mix; a
  response from a non-member; a member with no response. The invariant
  `available + unavailable + awaiting === squad` asserted in every case, not just checked by hand. The
  non-member case is the one [D22](../00-decisions.md) and [S7.2](S7.2-unit-tests.md) both call out.
- **Integration / RLS** — Already covered by [S1.4](S1.4-rls-test-suite.md): a manager reads every
  response row for events on teams they manage, including rows from users who have left; a manager of
  another team reads none; `team_member_directory` returns zero rows to a non-member. This story adds no
  policy and so no new RLS test, but its API tests run against the seeded database to confirm the query
  shapes return what `deriveCounts()` expects.
- **E2E** — Playwright: manager opens a seeded event and asserts the four counts against the seed's known
  numbers; a second browser context signs in as a seeded player and responds; the manager's screen shows
  the new counts after a focus event, without a reload. A second case asserts the squad-of-zero empty
  state on a seeded team with no members.
- **Manual** — On a real phone: the four tiles fit side by side two-up at 375px without truncation, the
  header actions are tappable one-thumbed, and the numbers are legible at arm's length in daylight.

## Open questions

1. **Should Squad count managers?** Answered: yes, [D22](../00-decisions.md), and it is deferred question
   Q1 for the club. If they say no, the change is one filter in `deriveCounts()` and one new unit test;
   nothing else in the screen moves.
2. **Is 30 seconds the right poll?** Proposed default, already specified: yes. It is cheap at this squad
   size and the focus refetch covers the case a manager actually notices — putting the phone down,
   sharing to WhatsApp, coming back. Tune the constant, not the design.
3. **Should the counts be as-of `starts_at` rather than as-of now, so a squad change after the event does
   not move a historic number?** Proposed default, already specified: as-of now
   ([D22](../00-decisions.md)). A stored snapshot would be a new column and a new write path, and nobody
   has asked for one.
