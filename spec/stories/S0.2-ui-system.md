## Goal

Every screen built after this one gets its layout, its colours, its component library and its four empty,
loading and error states from the same place. A manager on a 375px phone in a car park sees buttons big
enough to hit with a thumb, and a developer adding a screen writes no colour, no spacing scale and no
hand-rolled button.

## Context

`CLAUDE.md` section 2 makes shadcn/ui plus Tailwind the mandatory default and forbids hand-rolling
anything shadcn provides. Section 3 requires 375px correctness, 44px touch targets and theme tokens
defined once with no hardcoded hex in components.

Decisions this story depends on, from [00-decisions.md](../00-decisions.md):

- **D40** — shadcn's default `button`, `input`, `select` and `toggle` heights are below 44px. The `size`
  variants are overridden **once, here**, and a spacing token is defined alongside the colour tokens. This
  is the whole reason the story carries risk.
- **D41** — the brief's "bottom nav or header appropriate to role" is settled: a fixed bottom nav for every
  role, padded with `env(safe-area-inset-bottom)`, with page content bottom-padded to clear it. Items are
  Home and History for a player, plus Manage for a manager, plus Admin for an admin. Deep-link routes hide
  the nav so the large YES / NO buttons are never underneath it.
- **D49** — empty and error states are specified per screen from now on, so [S7.1](S7.1-state-coverage-audit.md) is a check and not a
  rework story. This story ships the three shared state components those screens use.
- **D42** — the manager response list is cards, not a table, at all widths. That constraint is why the
  component set below includes a segmented control and no table.
- **D55, D56** — the Epic 0 shell is exempt from the [S1.4](S1.4-rls-test-suite.md) gate, because it touches no team data.

The nav needs to know the viewer's role, and roles do not exist until [S2.9](S2.9-auth-guard-and-role-context.md). This story therefore takes the
role as an input and ships a pure function; S2.9 wires `useCurrentUser()` into it.
Any role logic here is presentation convenience only — RLS is the enforcement layer, always.

## Scope

**In**

- Tailwind v4 installed and wired into Vite.
- shadcn/ui initialised, with `components.json`, `cn()` and the first component set generated.
- One token stylesheet: colour, radius and the tap-target spacing token, defined once.
- The 44px `size` overrides on every interactive shadcn primitive (D40).
- `AppShell`, `AppShellSkeleton` and `BottomNav` (D41), including safe-area padding and the `chrome` seam
  that [S0.3](S0.3-routing.md) uses to hide the nav on deep-link routes.
- `LoadingState`, `EmptyState` and `ErrorState`, the three components every later screen composes (D49).
- `--pwa-theme-color` and `--pwa-background-color` in the token block, which [S0.4](S0.4-pwa.md)'s
  manifest test reads.
- `navItemsForRole()`, a pure function, unit tested.
- Testing Library plus jsdom, so component tests are possible from here on.
- The hardcoded-hex check appended to `scripts/check-conventions.mjs`.

**Out**

- Routing. `AppShell` renders `children`; it knows nothing about routes — [S0.3](S0.3-routing.md).
- Authentication, sessions and the real role — S2.9. The nav takes a role prop.
- Any product screen. Home, event detail, manage and admin are Epics 3, 4 and 6.
- Dark mode. See open question 2.
- An icon set beyond the handful the nav needs.
- A component gallery, Storybook, or a visual regression tool. Not in the stack table, not built.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [x] **AC1** — At a 375 x 667 viewport the shell renders with no horizontal scrollbar:
      `document.documentElement.scrollWidth <= 375`. Checked in a component test and again by the [S7.4](S7.4-device-pass.md)
      device pass.
- [x] **AC2** — Every generated shadcn primitive that a finger touches — `button`, `input`, `select`
      trigger, `toggle`, `toggle-group` item — has a default `size` variant at least 44px tall. A Vitest
      test renders each at its default size and asserts the rendered class list carries the tap-target
      utility (D40).
- [x] **AC3** — `npm run lint` fails if a hex colour literal appears anywhere under `src/` other than the
      token stylesheet and `src/pwa/manifest.ts`, which [S0.4](S0.4-pwa.md) adds and which must repeat the
      two `--pwa-*` values because a manifest cannot read CSS. Those two paths are the whole allowlist.
      The check lives in `scripts/check-conventions.mjs`.
- [x] **AC4** — Every colour used by a component resolves through a semantic token
      (`bg-background`, `text-foreground`, `bg-primary`, `text-destructive`, and so on). Changing the brand
      hue is a one-line edit in `src/index.css` and visibly changes the primary button, with no other file
      touched.
- [x] **AC5** — The bottom nav is fixed to the bottom of the viewport, does not scroll with content, and
      its bottom padding includes `env(safe-area-inset-bottom)`. On an iPhone with a home indicator no nav
      item sits under the indicator.
- [x] **AC6** — Page content is bottom-padded so the last element of a long page is fully readable above
      the nav, and a primary action at the bottom of a page is never covered by it.
- [x] **AC7** — `navItemsForRole('player')` returns Home and History; `'manager'` returns Home, History and
      Manage; `'admin'` returns Home, History, Manage and Admin. Unit tested, all three cases.
- [x] **AC8** — `<AppShell chrome="bare">` renders no bottom nav and shows a back affordance at least 44px
      square. `<AppShell chrome="nav">` renders the nav. Both are unit tested.
- [x] **AC9** — `LoadingState`, `EmptyState` and `ErrorState` exist, are exported from
      `@/components/states`, and `ErrorState` renders a message plus a retry control that calls the
      `onRetry` prop. No later screen writes its own spinner or its own blank-screen error.
- [x] **AC10** — The active nav item is visually distinct, and distinct by something other than colour
      alone, so it survives a greyscale screenshot.
- [x] **AC11** — Text and icon contrast against their backgrounds meets WCAG AA (4.5:1 for body text,
      3:1 for large text and icons), checked on the shell, the nav and the three state components.
- [x] **AC12** — `index.html` carries `<meta name="viewport" content="width=device-width,
      initial-scale=1, viewport-fit=cover">`, so `env(safe-area-inset-*)` has non-zero values on a notched
      device.
- [x] **AC13** — No component in `src/components/` or `src/features/` imports a Tailwind arbitrary value
      for spacing or size where a token exists; the 44px floor is `min-h-tap`, never `min-h-[44px]` and never
      `min-h-11`. A control that is deliberately taller than the floor — a two-line row, the YES / NO pair —
      uses Tailwind's own scale (`min-h-14`) and is not a violation.
- [x] **AC14** — The PR contains a screenshot of the shell at 375 x 667 with the nav rendered for each of
      the three roles.

## Implementation notes

**Tailwind v4, CSS-first.** Install `tailwindcss` and `@tailwindcss/vite`, add the plugin to
`vite.config.ts`. There is no `tailwind.config.js`; the theme lives in CSS. Add
`prettier-plugin-tailwindcss` so class order is mechanical and never a review topic.

**shadcn/ui.** `npx shadcn@latest init` — style `new-york`, base colour `neutral`, CSS variables on. It
writes `components.json`, `src/lib/utils.ts` (`cn()`), and installs `clsx`, `tailwind-merge`,
`class-variance-authority` and `lucide-react`. Generated components land in `src/components/ui/` and are
**ours**: they are edited in place, committed, and never regenerated over. A regeneration would silently
undo the D40 overrides, so the header comment on each overridden file says so.

First component set, generated now because Epics 2 to 4 all need them and generating on demand scatters
the override work:

```
button  input  label  form  card  badge  skeleton  separator
dialog  alert-dialog  select  toggle  toggle-group  sonner
```

`form` pulls in React Hook Form and `@hookform/resolvers`; that matches the stack table, and [S4.1](S4.1-create-event.md) is the
first story to use it. `sonner` is the toast surface. No `table` component — D42 settled that the one
list that looked like a table is cards.

**Tokens.** One file, `src/index.css`:

```css
@import 'tailwindcss';

@theme {
  --spacing-tap: 2.75rem;          /* 44px. The minimum touch target. D40 */
  --radius: 0.625rem;
}

:root {
  color-scheme: light;
  --background: ...;  --foreground: ...;
  --card: ...;        --card-foreground: ...;
  --primary: ...;     --primary-foreground: ...;   /* the club colour, open question 1 */
  --secondary: ...;   --secondary-foreground: ...;
  --muted: ...;       --muted-foreground: ...;
  --accent: ...;      --accent-foreground: ...;
  --destructive: ...; --destructive-foreground: ...;
  --success: ...;     --success-foreground: ...;   /* the YES answer and the available pill */
  --border: ...;      --input: ...;  --ring: ...;

  /* Read by S0.4's manifest test, which asserts the manifest's theme_color and
     background_color equal these two. Hex, not OKLCH: a manifest takes hex. */
  --pwa-theme-color: #......;
  --pwa-background-color: #......;
}
```

Values are OKLCH, as the shadcn v4 generator writes them. The brand hue appears in `--primary` and
nowhere else, so open question 1 is a one-line change when the club answers it. `--success` is added
beyond the shadcn set because availability has a positive state and rendering "Available" in the primary
brand colour makes it indistinguishable from a button.

**The 44px overrides (D40).** Edit the `cva` size variants in the generated files. shadcn's `new-york`
defaults are `h-9` on the button and input, `h-8` on `sm`, `h-10` on `lg`, `size-9` on `icon`. Replace
with, at minimum:

```ts
// src/components/ui/button.tsx — DO NOT REGENERATE, see decision D40
size: {
  default: 'min-h-tap px-4 py-2',
  sm:      'min-h-tap px-3',        // smaller horizontally, never shorter
  lg:      'min-h-12 px-6 text-base',
  icon:    'size-tap',
}
```

`sm` staying 44px tall is the point: a variant that is allowed to be short will end up on a real screen.
Apply the same to `input` (`min-h-tap`), the `select` trigger, `toggle` and each `toggle-group` item. The
AC2 test walks a list of these components so adding a new primitive without an override fails the suite.

**Shell.** Two components, no router import:

```tsx
// src/components/app-shell.tsx
export type Chrome = 'nav' | 'bare'
export interface AppShellProps {
  chrome: Chrome
  role: AppRole                   // 'player' | 'manager' | 'admin'
  title?: string
  onBack?: () => void
  children: React.ReactNode
}

/** Chrome only: header bar and nav shapes as skeletons, no content slot.
 *  [S2.9](S2.9-auth-guard-and-role-context.md) renders this while the session resolves, so there is no
 *  flash of the login screen and no full-screen spinner. Takes no props. */
export function AppShellSkeleton(): React.JSX.Element

// src/components/bottom-nav.tsx
export function BottomNav(props: { role: AppRole; currentPath: string }): React.JSX.Element
```

`chrome="bare"` is what [S0.3](S0.3-routing.md) passes for `/event/:id`, `/register`, `/join/:token`,
`/reset/:token` and `/login` (D41). D41 names the first four; `/login` and the 404 screen join them for
the same reason — nothing to navigate to yet — and [S0.3](S0.3-routing.md)'s route table is where that
mapping is fixed and tested. `currentPath` is a plain string so the nav has no router dependency
and stays unit testable; [S0.3](S0.3-routing.md) supplies it from `useLocation()`.

Layout: `<div class="min-h-dvh flex flex-col">`, main content `flex-1` with
`pb-[calc(var(--spacing-tap)+env(safe-area-inset-bottom)+1rem)]` when `chrome="nav"`, nav
`fixed inset-x-0 bottom-0` with `pb-[env(safe-area-inset-bottom)]`. Use `min-h-dvh`, not `min-h-screen`:
`100vh` is wrong in mobile Safari with a visible URL bar, and the difference is exactly the height of a
YES button.

**Nav items.** A pure function, in `src/lib/nav.ts`, so AC7 is a unit test with no DOM:

```ts
export type AppRole = 'player' | 'manager' | 'admin'
export interface NavItem { label: string; to: string; icon: LucideIcon }
export function navItemsForRole(role: AppRole): NavItem[]
```

Player: Home `/`, History `/history`. Manager adds Manage `/manage`. Admin adds Admin `/admin`. Routes
are the D34 paths; `to` values are plain strings here and are replaced with the
[S0.3](S0.3-routing.md) `paths` helpers when that story lands.

The role passed in is a display convenience. Write that in a comment above the function, because it will
otherwise read like an authorisation check to the next person: **RLS is the enforcement layer**, and a
player who forces their way to `/manage` sees no data regardless of what the nav renders.

**State components (D49).** `src/components/states/`:

```tsx
export function LoadingState(props: { rows?: number; label?: string }): React.JSX.Element
export function EmptyState(props: { title: string; body?: string; action?: React.ReactNode }): React.JSX.Element
export function ErrorState(props: { title?: string; body?: string; onRetry: () => void }): React.JSX.Element
```

`LoadingState` composes shadcn `skeleton` in the shape of a card list, not a centred spinner, so the
screen does not jump when data arrives. `ErrorState` defaults to "Something went wrong." with a
"Try again" button and always renders the retry control — D49 forbids a blank error screen anywhere in the
app, and making retry non-optional is how that is enforced in types rather than in review.

**Testing setup.** Add `@testing-library/react`, `@testing-library/jest-dom`, `@testing-library/user-event`
and `jsdom`. Set `test.environment: 'jsdom'` and `test.setupFiles: ['src/test/setup.ts']` in
`vitest.config.ts`; the setup file imports `@testing-library/jest-dom/vitest` and registers a
`matchMedia` stub, because jsdom has none and D44's `isStandalone()` helper will call it.

**Gotchas**

- jsdom does not compute layout. AC1's "no horizontal scroll" test can only assert that no element carries
  a fixed width greater than the viewport; the real check is the AC14 screenshot and the S7.4 device pass.
  Say so in the test file rather than pretending the assertion is stronger than it is.
- `env(safe-area-inset-bottom)` is zero unless `viewport-fit=cover` is set (AC12). The nav will look
  correct in a desktop browser and wrong on an iPhone if that meta tag is missed.
- Tailwind v4 generates utilities from `@theme` keys: `--spacing-tap` yields `min-h-tap`, `size-tap`,
  `p-tap`. Do not also define a `--tap-target` custom property; one name, one mechanism.
- `sonner` renders its own portal and must sit inside `AppShell`, above the nav in z-order, or a toast
  will appear behind it.

## Open questions

1. **What are the club's colours in hex?** Proposed default: ship a neutral shadcn `neutral` base with a
   single placeholder brand hue in `--primary`, and change that one line when the club answers. Nothing
   else in the codebase encodes a colour, so the answer costs one commit whenever it arrives. This is not
   one of the deferred questions in [00-decisions.md](../00-decisions.md) — Q7 is the team names — so add
   it to that table when it goes to the club.
2. **Dark mode?** Proposed default: no. Light only in v1, `color-scheme: light`, no `.dark` token block.
   Tokens are semantic, so adding dark later is one new block and no component change. Building it now
   doubles the contrast checking on every screen for a feature nobody asked for.
3. **Does the shell need a top header at all, given D41 fixes a bottom nav?** Proposed default: a minimal
   one — a title line on `chrome="nav"` pages and a back affordance on `chrome="bare"` pages, both plain
   text, no logo, no actions. Screens that want a header action put it in their own content.
4. **Which icon set?** Proposed default: `lucide-react`, because the shadcn CLI installs it and the nav
   needs four glyphs. No second icon dependency is added for any reason.
