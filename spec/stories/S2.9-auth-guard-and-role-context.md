## Goal

The app knows who is signed in, which teams they belong to and what role they hold on each, and it stops
a player wandering into a manager screen. A player who taps Manage lands back on their home screen
rather than a broken page. A manager sees the Manage tab; everyone else does not.

## Context

Fifteenth in the build order (D20), and the first story in Epic 2. It is built before registration and
sign-in exist, so at build time the only way to obtain a session is programmatically with a seeded user.
That is deliberate: the guard and the role context are the foundation the six auth screens sit on, and
building them first means [S2.1](S2.1-registration.md) and [S2.2](S2.2-sign-in.md) have somewhere to land.

Decisions this story rests on, from [00-decisions.md](../00-decisions.md):

- **D2** — admin is a club-wide flag on `profiles.is_admin`, not a membership role. `member_role` is
  `'player' | 'manager'` only. So "role" is two things, not one: a per-team role and a club-wide boolean,
  and the hook exposes both separately.
- **D8** — a user may select exactly their own `profiles` row. This story reads that row and nothing else
  from `profiles`. Other people's names come from `team_member_directory` in
  [S4.4](S4.4-player-response-list.md) and [S6.4](S6.4-member-administration.md), never from here.
- **D9** — clients have no write of any kind on `team_members`. Nothing in this story writes memberships.
- **D34** — the route list is the twelve routes plus the 404. This story wraps the protected subset.
- **D37** — the registration gate is UX. The real gate is membership, enforced by RLS. Every role check
  added here is convenience only and must say so in the source.
- **D41** — a fixed bottom nav for every role: Home and History for a player, plus Manage for a manager,
  plus Admin for an admin. This story supplies the role data that decides which items render.
- **D59** — session longevity is configuration, owned by [S2.6](S2.6-session-persistence.md). This story
  owns only the subscription to auth state and the "no login flash while restoring" rule.
- **D1** — the intended route lives in `localStorage` under `pfc.intendedRoute`. This story writes it
  before redirecting to `/login`; [S2.5](S2.5-deep-link-return-path.md) owns reading it back after auth
  and the cold-start Playwright coverage.

[S6.1](S6.1-teams.md) and [S6.2](S6.2-team-join-links.md) ship earlier in the build order with no route
guard, and S6.1's AC1 already reads `useCurrentUser().isAdmin`. Until this story lands, that hook is
stubbed in their tests; this story supplies the real one and adds the `/admin` guard both of them assume.

## Scope

**In**
- `SessionProvider`: the app's single `supabase.auth.onAuthStateChange` subscription, with a three-state
  status so no screen has to guess whether auth is still restoring.
- `useCurrentUser()` returning a discriminated union of loading, signed out, error and ready, and a
  `CurrentUser` carrying profile, memberships and per-team role helpers.
- A single TanStack Query fetching the own `profiles` row and the caller's `team_members` rows with team
  names, keyed and invalidatable.
- `RequireAuth`, `RequireManager` and `RequireAdmin` wrappers, applied to S0.3's route table by its
  declared `guard` level.
- Intended-route capture on the redirect to `/login`.
- Role-driven bottom nav items in the S0.2 shell: deriving `AppRole` from `CurrentUser` and passing it to
  `AppShell`.
- The app-shell header menu, which S0.2 does not build (its Open question 3 leaves the header with no
  actions), carrying "Sign out" — and later S2.8's "Add to home screen".
- Sign out, and Sentry user identification by uuid only.
- The empty state for a signed-in user who belongs to no team.

**Out**
- Registration, sign-in and set-password screens. S2.1, S2.2 and S2.3.
- Restoring the intended route after successful auth. S2.5 reads the key this story writes.
- Supabase auth client configuration — JWT lifetime, refresh rotation, `persistSession`,
  `autoRefreshToken`, `detectSessionInUrl`. S2.6, per D59. The one exception is pinning `storageKey`,
  below, because the E2E fixture needs a stable key now.
- The splash markup, the long-background resume, the refresh-failure path and the full sign-out teardown.
  [S2.6](S2.6-session-persistence.md) wraps this provider in its own `AppBoot` gate
  (`src/app/app-boot.tsx`) and hardens the teardown; it adds no second subscription, and
  [S2.5](S2.5-deep-link-return-path.md) adds the restore hook inside the router. One provider, one
  vocabulary — `SessionState` below is the shape all three stories use.
- Any change to who may do what in the database. RLS is settled in [S1.3](S1.3-rls-policies-and-rpcs.md)
  and proved in S1.4. Nothing here is a security boundary.
- A profile screen, a name or number edit, or an account menu beyond sign out and the S2.8 menu item.
  Q11 in the decision record: there is no profile edit in v1.

### Session, not server state

The session is a subscription, not a fetch, so it does not belong in TanStack Query and it certainly does
not belong in Zustand, which is UI state only. It lives in a small context.

```ts
// src/features/auth/session-provider.tsx
export type SessionState =
  | { status: 'loading'; session: null }
  | { status: 'signedOut'; session: null }
  | { status: 'signedIn'; session: Session }

export function SessionProvider(props: { children: React.ReactNode }): JSX.Element
export function useSession(): SessionState
```

`SessionProvider` mounts in `src/main.tsx` above `<RouterProvider>`, calls `supabase.auth.getSession()`
once, then subscribes with `supabase.auth.onAuthStateChange`. It starts in `loading` and leaves it only
when `getSession()` settles — this is what AC8 rests on. Unsubscribe in the effect cleanup. This is the
only subscription in the app (AC16, and S2.6's AC8): S2.6 adds the splash gate and the full teardown
around it, and S2.5 adds the route restore inside the router, neither by subscribing again.

Event handling:

| Event | Action |
|---|---|
| `INITIAL_SESSION`, `SIGNED_IN` | set the session; `setSentryUser(session.user.id)` |
| `TOKEN_REFRESHED` | replace the session object, change nothing else (S2.6 owns refresh) |
| `USER_UPDATED` | replace the session, invalidate `userKeys.current()` |
| `SIGNED_OUT` | clear the session, `queryClient.clear()`, `setSentryUser(null)` |

Pin the storage key on the client created in S1.5, so the Playwright fixture below has something stable
to write:

```ts
// src/lib/supabase.ts — S1.5 owns the file; this story pins one option
createClient<Database>(url, anonKey, {
  auth: { storageKey: 'pfc.auth' },   // S2.6 owns persistSession, autoRefreshToken
})                                    // and detectSessionInUrl: false (D59)
```

### The current user

One query, two selects in parallel, under one key.

The key is S1.5's, not a new one: `userKeys.current()` from `src/api/queryKeys.ts`, which
[S2.1](S2.1-registration.md), [S2.3](S2.3-password-reset-by-manager.md) and
[S2.4](S2.4-join-by-link.md) already invalidate by that name. Do not invent a second key here; the cache
is emptied on sign-out (AC11), so it does not need the uuid in the key.

```ts
// src/api/current-user.ts
export async function fetchCurrentUser(userId: string): Promise<CurrentUserRow> {
  const [profile, memberships] = await Promise.all([
    supabase.from('profiles').select('id, name, phone, is_admin').eq('id', userId).single(),
    supabase.from('team_members')
      .select('team_id, role, joined_at, teams!inner(name)')
      .eq('user_id', userId),
  ])
  ...
}
```

The `profiles` select is scoped to one row by RLS anyway (D8); the `.eq` there is belt and braces.

The `.eq('user_id', userId)` on `team_members` is not. The S1.3 policy limits that table to *rows of teams
the caller belongs to* — the whole squad, not the caller's own rows (see the access matrix in
[data-model.md](../data-model.md)). Without the filter, `memberships` would list every member of every team
and AC2 would fail. It is a correctness filter, not a security one: dropping it leaks nothing, it just
returns the wrong thing. The embedded `teams!inner(name)` resolves under the teams read policy (D8).

Query options: `enabled: session.status === 'signedIn'`, `staleTime: 5 * 60_000`,
`refetchOnWindowFocus: true`, `retry: 3`. The retry matters on one path only: a fresh `signUp` can return
before PostgREST observes the S1.2 trigger's `profiles` row, and a retry costs nothing.

### Exposed shape

```ts
import type { Database } from '@/lib/database.types'
type MemberRole = Enums<'member_role'>   // 'player' | 'manager'

export type TeamMembership = {
  teamId: string
  teamName: string
  role: MemberRole
  joinedAt: string            // ISO, rendered only through formatEventTime() (D35)
}

export type CurrentUser = {
  id: string
  name: string
  phone: string               // E.164, own row only. Never rendered next to anyone else's.
  isAdmin: boolean
  memberships: readonly TeamMembership[]
  managedTeams: readonly TeamMembership[]
  isManagerOfAny: boolean
  roleForTeam: (teamId: string) => MemberRole | null
  isManagerOf: (teamId: string) => boolean     // role === 'manager' || isAdmin
}

export type CurrentUserState =
  | { status: 'loading' }
  | { status: 'signedOut' }
  | { status: 'error'; error: Error; refetch: () => void }
  | { status: 'ready'; user: CurrentUser }

export function useCurrentUser(): CurrentUserState     // safe anywhere, including public routes
export function useSignedInUser(): CurrentUser         // only below RequireAuth; throws otherwise
```

Build `roleForTeam` with `memberships.find(m => m.teamId === teamId)?.role ?? null`. Under
`noUncheckedIndexedAccess` never index the array directly. Memoise the derived object on the query data so
the helper identities are stable across renders.

`managedTeams` is `memberships.filter(m => m.role === 'manager')` for a manager. For an admin it is every
team the admin is a member of — an admin who manages the club is not automatically in the nav-level sense
a member of every team, and the all-teams picker is [S6.3](S6.3-all-teams-view.md)'s job, not this hook's.

### Guards

S0.3's route table is a flat, typed array (`AppRouteMeta`, with `chrome` and `guard`), not a JSX tree, so
the guards are children wrappers rather than `<Outlet />` layouts.

```tsx
// src/features/auth/guards.tsx
export function RequireAuth(props: { children: React.ReactNode }): JSX.Element
export function RequireManager(props: { children: React.ReactNode }): JSX.Element
export function RequireAdmin(props: { children: React.ReactNode }): JSX.Element
```

`RequireAuth`:

1. `loading` → `<AppShellSkeleton />`, S0.2's chrome-only component, built for exactly this. Not a
   spinner over the login form, not `null`; AC8.
2. `signedOut` → `setIntendedRoute(location.pathname + location.search)` then
   `<Navigate to={paths.login()} replace />`. `replace`, so Back does not bounce.
3. `error` → `<AppShell chrome="nav" role="player"><ErrorState title="Couldn't load your account."
   onRetry={refetch} /></AppShell>` (D49). Never a blank screen. `role="player"` is the safe floor when
   the memberships did not load: the nav shows Home and History and no manager affordance.
4. `ready` → `{children}`.

`RequireManager` and `RequireAdmin` wrap inside `RequireAuth`, so they only ever see `ready`. They check
`user.isManagerOfAny || user.isAdmin` and `user.isAdmin` respectively, and on failure call
`toast("You don't manage a team.")` from `sonner` (S0.2) in an effect and return
`<Navigate to={paths.home()} replace />`. Redirect, never render-then-hide: AC4 says not even for a
frame.

There is no per-team guard on `/manage/event/:id`, because the team id is not in the URL. A manager of
team A opening an event on team B gets zero rows from the S1.3 read policy and the screen shows its
not-found state. That is the enforcement, and it is the database's, not the guard's.

`/manage/team/:teamId/members` does have the team in the URL. Use
`useSignedInUser().isManagerOf(teamId)` inside the screen and render the not-found state when false;
it is still convenience, and `team_member_directory` returns zero rows regardless (D8).

### Nav and the header menu

`AppRole` is a display value, derived once where `AppShell` is rendered for a route — S0.3's root route
element, which already reads `chrome` and `title` from the route table — and never recomputed per screen:

```ts
// Convenience only. RLS is the enforcement layer (S1.3, proved by S1.4).
const role: AppRole = user.isAdmin ? 'admin' : user.isManagerOfAny ? 'manager' : 'player'
```

It is passed to S0.2's `AppShell`, which passes it to `BottomNav`, which calls `navItemsForRole(role)`.
Neither S0.2 signature changes: the case where the role is not yet known is `AppShellSkeleton`, which
renders the nav shape and no items, so the bar keeps its height and nothing jumps.

`AppShell` gains the header menu on `chrome="nav"` routes. S0.2 builds no header actions — its Open
question 3 leaves the header as plain text — so this story adds it:

```tsx
// src/components/app-shell-menu.tsx
export function AppShellMenu(): JSX.Element   // shadcn DropdownMenu, 44px trigger, aria-label "Menu"
```

One item now, "Sign out", calling `useSignOut()`. [S2.8](S2.8-add-to-home-screen-guide.md) appends "Add to
home screen" beneath it. No submenu, no settings screen, no profile screen (Q11).

### Route wiring

S0.3 owns `src/routes.tsx` and the route list (D34), and each entry already declares its `guard`
level. This story supplies the wrappers and the one map that applies them, so no route can be guarded by
accident or left unguarded by omission:

```tsx
// src/routes.tsx — S0.3 owns the table; this story maps guard level to a wrapper
const GUARDS: Record<GuardLevel, (el: React.ReactNode) => React.ReactNode> = {
  public:  el => el,
  authed:  el => <RequireAuth>{el}</RequireAuth>,
  manager: el => <RequireAuth><RequireManager>{el}</RequireManager></RequireAuth>,
  admin:   el => <RequireAuth><RequireAdmin>{el}</RequireAdmin></RequireAuth>,
}
```

Applied where the route objects are built: `element: GUARDS[meta.guard](<Screen />)` for eager routes, and
inside the `lazy()` callback for the code-split `/manage/*` and `/admin` routes —
`return { Component: () => GUARDS[meta.guard](<m.ManageScreen />) }` — so a lazily loaded manager chunk is
still wrapped. The guard levels of record, from S0.3's table: `public` for `/login`, `/register`,
`/join/:token`, `/reset/:token`, `/event/:id` and `*`; `authed` for `/` and `/history`; `manager` for
`/manage`, `/manage/event/new`, `/manage/event/:id` and `/manage/team/:teamId/members`; `admin` for
`/admin`.

`/event/:id` is public on purpose: D7's `get_event_preview` is the cold-arrival read and D6 makes the link
a standing join credential. Guarding it would break the one journey that matters.

### Intended route

```ts
// src/lib/intended-route.ts — the path S2.5 names; S2.5 adds validation, TTL and peek()
const KEY = 'pfc.intendedRoute'

/** Path only, e.g. "/history". No origin, no "#". Waypoints are ignored. */
export function setIntendedRoute(path: string): void
/** Reads, clears, returns. Null when absent or malformed. */
export function takeIntendedRoute(): string | null
export function clearIntendedRoute(): void
```

Stored as `{"path":"/history","at":1757600000000}` from the first commit, so S2.5's TTL lands as a read
check rather than a format change. `setIntendedRoute` ignores anything starting `/login`,
`/register`, `/join/` or `/reset/`: those are waypoints, and returning to one after signing in is a loop.

Every call wraps `localStorage` in try/catch — private-mode Safari throws on write — and a failure degrades
to "no intended route", never to an exception. This story writes and clears; S2.5 adds the route allowlist
and the TTL, calls `takeIntendedRoute` after a successful `signUp` or `signInWithPassword`, and owns the
cold-start test.

### Sign out

```ts
export function useSignOut(): { signOut: () => Promise<void>; isPending: boolean }
```

Calls `supabase.auth.signOut()`, then `queryClient.clear()`, `clearIntendedRoute()`,
`setSentryUser(null)`, and navigates to `paths.login()`. The `SIGNED_OUT` event does the same teardown,
because a refresh failure signs the user out without anyone tapping anything; keep the teardown in one
function that both paths call. [S2.6](S2.6-session-persistence.md) extends it with `pfc.pendingJoin`. The
sign-out item lives in `AppShellMenu` — the only account affordance in v1, alongside the "Add to home
screen" item [S2.8](S2.8-add-to-home-screen-guide.md) adds later.

### Role checks are not security

Every call site that hides or shows something by role carries this comment, once:

```ts
// Convenience only. RLS is the enforcement layer (S1.3, proved by S1.4).
```

AC13 is checkable by grep. If a reviewer cannot find the comment next to a role check, the story is not done.

## Data and API surface

**Tables read** — `profiles` (own row, D8), `team_members` (rows for teams the caller belongs to),
`teams` (embedded name, teams the caller belongs to). No writes anywhere in this story.

**RPCs called** — none.

**Zod schemas** — none added. `CurrentUser` is derived in TypeScript from the S1.5 row types; it is not a
table and gets no schema. `TeamMembership.role` is typed from
`Enums<'member_role'>` (D24).

**Query keys** — `userKeys.current()` from S1.5's `src/api/queryKeys.ts`, resolving to `['currentUser']`.
No new key factory. Invalidated after registration ([S2.1](S2.1-registration.md)), by the join RPCs in
[S2.4](S2.4-join-by-link.md), and by `set_member_role` / `remove_member` in
[S6.4](S6.4-member-administration.md).

**Mutations** — none. Sign out is an auth call, not a table write.

## Open questions

1. **Where does sign out live?** No story gives the shell an account menu. Proposed default, already
   written above: one overflow item in the app-shell header, reading "Sign out", joined later by S2.8's
   "Add to home screen". No profile screen, no settings screen (Q11).
2. **Should an admin see every team in `memberships`?** Proposed default: no. `memberships` is literally
   the `team_members` rows. The admin's all-teams picker is S6.3's, fetched separately, so this hook stays
   one query and one meaning.
3. **What does the Manage tab do for a manager of two teams?** Proposed default: `/manage` lists the
   teams they manage and they pick one. If they manage exactly one, it renders that team directly with no
   picker. Confirmed in S4.3's spec; noted here because the nav item is defined in this story.
