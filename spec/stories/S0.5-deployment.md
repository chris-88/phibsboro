## Goal

A merge to `main` puts the new build on `https://app.phibsborofc.com` with any new migrations already
applied to the production database. A manager can send a WhatsApp link that works from a phone, on a real
HTTPS origin, which is the precondition for every deep-link, PWA and share story after this one.

## Context

The brief's S0.5 asks for a GitHub Actions workflow publishing to Pages with a CNAME for
`app.phibsborofc.com`, and for "Env vars injected from repo secrets". Four decisions change what that
means, and this story is written from them.

- [D18](../00-decisions.md) — the workflow gains a `migrate` job that runs before, and gates, the publish.
  Without it the first schema change breaks the live site.
- [D38](../00-decisions.md) — `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` are **repository variables**,
  not secrets. They ship inside a public bundle; calling them secret produces bad reasoning downstream.
  This contradicts the brief's wording, deliberately. The real secrets are `SUPABASE_ACCESS_TOKEN`,
  `SUPABASE_PROJECT_REF`, `SUPABASE_SERVICE_ROLE_KEY` and `SENTRY_AUTH_TOKEN`.
- [D14](../00-decisions.md) — S0.7 owns the test pipeline. This workflow **does not re-run tests**. `main`
  is protected and `check`, `db`, `e2e` and `pwa` are required checks, so a merge is already green.
- [D17](../00-decisions.md) — Playwright never drives the live site except for one read-only post-deploy
  smoke job, which signs in to nothing and writes nothing. This story therefore lands
  `playwright.config.ts` and its first project, `smoke-deployed`. S0.4 adds `pwa` to the same file and
  S7.3 adds `e2e`; there is one harness. (S0.1's test-plan note that "Playwright arrives with S7.3"
  predates D17 and is superseded here.)
- [D16](../00-decisions.md) — the build uploads sourcemaps to Sentry and the published artifact carries
  none. The release identifier is the commit SHA.

[D20](../00-decisions.md) puts this story fourth, ahead of routing and the PWA, so that their criteria —
hard refresh on a deep link, installability, standalone launch — are checkable on a real origin rather
than on `localhost`.

Q12 in [00-decisions.md](../00-decisions.md) is the one open dependency outside the repo: the domain must be
registered and its DNS ours to point. Nothing else blocks this story.

## Scope

**In**
- `.github/workflows/deploy.yml`: `migrate` → `build` → `deploy` → `smoke`, on push to `main` and on
  `workflow_dispatch`.
- Forward-only migration apply to the production Supabase project.
- Production build with env injected from repository variables and the release set to the commit SHA.
- Sourcemap upload to Sentry, and a published artifact with no `*.map` in it.
- GitHub Pages custom domain, CNAME file, HTTPS enforcement, DNS record documented.
- A read-only post-deploy smoke check against the live site.
- A parity check between the `build` job's `VITE_` env block and the `.env.example` S0.1 committed.

**Out**
- Running the unit, RLS or E2E suites. That is S0.7, and it happens on the pull request.
- Staging or preview environments. One production project, one site.
- Rollback automation. Rollback is a revert commit or a re-run of an earlier deploy, and schema is never
  rolled back — a mistake is corrected by a new migration.
- Seeding the production database. The seed script (S1.2) is for local and CI only.
- Any Sentry configuration beyond passing the token and release through. That is S0.6.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [x] **AC1** — A push to `main` results in the new bundle being live at `https://app.phibsborofc.com`,
      with no manual step. The workflow is the only path that publishes.
- [x] **AC2** — The published `index.html` carries `<meta name="pfc-release" content="…">` whose value is
      the exact 40-character commit SHA of the merge. Two consecutive merges produce two different values.
- [x] **AC3** — The `migrate` job runs before the publish and gates it. A merge containing a new migration
      has that migration applied to the production database before the new bundle is served. A failing
      migration fails the workflow and leaves the previous bundle live.
- [x] **AC4** — `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_APP_BASE_URL`, `VITE_SENTRY_DSN`,
      `SENTRY_ORG` and `SENTRY_PROJECT` come from repository **variables**; `SUPABASE_ACCESS_TOKEN`,
      `SUPABASE_PROJECT_REF` and `SENTRY_AUTH_TOKEN` come from repository **secrets**. No value carrying a
      `VITE_` prefix is a secret. ([D16](../00-decisions.md) calls `SENTRY_ORG` and `SENTRY_PROJECT`
      secrets in passing; [D38](../00-decisions.md) fixes the secret list and wins — an org slug is not a
      credential.)
- [x] **AC5** — `SUPABASE_SERVICE_ROLE_KEY` is never referenced by the `build` job, never reaches a
      `VITE_` variable, and `grep -r SERVICE_ROLE src/` returns nothing.
- [x] **AC6** — The publish step fails if `find dist -name '*.map'` matches anything. No sourcemap is
      served from the public origin.
- [x] **AC7** — The bundle contains no value from the secret list. The workflow greps the built `dist/`
      for the first eight characters of `SUPABASE_ACCESS_TOKEN` and of `SENTRY_AUTH_TOKEN` and fails on a
      match.
- [ ] **AC8** — `https://app.phibsborofc.com` serves over HTTPS with a valid certificate, and the plain
      HTTP URL redirects to it. "Enforce HTTPS" is on in the repository's Pages settings.
- [ ] **AC9** — `dist/CNAME` is present in every published artifact and contains exactly
      `app.phibsborofc.com`, so a deploy never drops the custom domain.
- [x] **AC10** — The `smoke` job runs after the publish, against the live origin, and asserts: the site
      returns 200; the `pfc-release` meta equals `github.sha`; every route in [D34](../00-decisions.md)
      resolves after a hard reload without hitting the 404 screen; and an unknown route renders the 404
      screen. It performs no sign-in and no write. The unknown-route target is `/#/nope` until
      [S3.3](S3.3-event-detail-screen.md) ships a real not-found state, at which point it becomes
      `/#/event/00000000-0000-0000-0000-000000000000` ([S0.3](S0.3-routing.md) notes the same swap; the
      comment lives in the spec file, not only here). This story builds before S0.3 ([D20](../00-decisions.md)), so on the first deploy the
      `ROUTES` list contains only `/` and the 404 assertion is skipped; S0.3 fills the list and the skip
      is removed in the same PR. That expansion is an S0.3 criterion (D34), checked by this job.
- [x] **AC11** — Two merges landing within a minute do not interleave. The workflow declares
      `concurrency: { group: 'pages', cancel-in-progress: false }`, and the later commit is the one left
      live.
- [x] **AC12** — `workflow_dispatch` re-deploys the current `main` without a code change, so a
      configuration fix can be shipped without an empty commit.
- [x] **AC13** — The workflow runs no test job. Its total wall time from merge to live is under five
      minutes.
- [x] **AC14** — `.env.example` (committed by [S0.1](S0.1-project-scaffold.md) AC9) and the `build` job's
      `env:` block declare the same set of `VITE_` keys. `scripts/check-env-parity.mjs` parses both and
      fails on any key present in one and missing from the other, so adding a variable to the workflow
      without documenting it breaks CI. It runs in the `check` job (S0.7).
- [x] **AC15** — A failure in any job leaves the previously deployed site untouched and serving.

## Build notes — deviations from this spec

| Spec said | Built as | Why |
|---|---|---|
| `public/CNAME` containing `app.phibsborofc.com` (AC9) | no CNAME file | DNS for the domain is not pointed at Pages. A CNAME file would make Pages serve from a hostname that does not resolve, taking the site offline. `scripts/verify-dist.sh` enforces AC9 automatically the moment `public/CNAME` appears. |
| `https://app.phibsborofc.com` with enforced HTTPS (AC1, AC8) | `https://chris-88.github.io/phibsboro/` | Same reason. HTTPS is enforced on the project page already. AC8 is unticked until the domain is live. |
| `vite.config.ts` sets `base: '/'` | `base: process.env.VITE_BASE_PATH ?? '/'` | A Pages project page serves from `/phibsboro/`, the custom domain from `/`. Driving it from a repository variable means switching domains is a variable change, not a code change. |
| `migrate` applies migrations unconditionally | guarded, skips when `SUPABASE_ACCESS_TOKEN` or `SUPABASE_PROJECT_REF` is absent, or when `supabase/migrations` does not exist | Supabase CI credentials are not provisioned and S1.1 has not created the migrations directory. Unguarded, every deploy would fail. **The guard must be revisited when S1.1 merges** — see docs/deployment.md. |
| Sourcemap upload to Sentry (AC6 partner step) | not built | S0.6 owns Sentry and has not run. `verify-dist.sh` already fails on any `*.map` reaching `dist/`, so the "no sourcemap is served" half of D16 holds today. |
| `actions/checkout@v4`, `actions/setup-node@v4` | `@v5` | v4 targets Node 20, which GitHub now warns is deprecated on every run. |
| `SUPABASE_CLI_VERSION: '2.22.6'` | `'2.108.0'` | 2.22.6 was an assumed version. 2.108.0 is what the dev machine runs; CI and local must not drift. |

**AC14 subtlety.** `VITE_SENTRY_RELEASE` is in `.env.example` but is deliberately outside the parity
markers in the workflow, because it comes from `${{ github.sha }}` rather than a repository variable.
`scripts/check-env-parity.mjs` exempts it in that one direction via `SET_BY_WORKFLOW`.

**Unticked and why.** AC8 and AC9 both depend on the custom domain and are ticked by the three-step
switch in `docs/deployment.md`. Everything else is verified.

## Implementation notes

### Files

```
.github/workflows/deploy.yml
public/CNAME                     app.phibsborofc.com, one line, no trailing content
scripts/verify-dist.sh           AC6, AC7, AC9
scripts/check-env-parity.mjs     AC14
playwright.config.ts             created here, project `smoke-deployed`; S0.4 and S7.3 add theirs
tests/e2e/smoke.deployed.spec.ts       read-only, live origin only
docs/deployment.md               DNS record, Pages settings, variable and secret inventory
```

The variable and secret inventory, which `docs/deployment.md` repeats:

| Name | Kind | Value |
|---|---|---|
| `VITE_SUPABASE_URL` | variable | production project URL |
| `VITE_SUPABASE_ANON_KEY` | variable | production anon key — public, D38 |
| `VITE_APP_BASE_URL` | variable | `https://app.phibsborofc.com`, used by the share link, D13 |
| `VITE_SENTRY_DSN` | variable | public, ships in the bundle |
| `VITE_SENTRY_ENVIRONMENT` | variable | `production` |
| `VITE_SENTRY_RELEASE` | neither | set by the workflow to `${{ github.sha }}` |
| `SENTRY_ORG` | variable | org slug |
| `SENTRY_PROJECT` | variable | project slug |
| `SENTRY_AUTH_TOKEN` | secret | sourcemap upload only |
| `SUPABASE_ACCESS_TOKEN` | secret | CLI auth for `db push` |
| `SUPABASE_PROJECT_REF` | secret | production project ref |
| `SUPABASE_SERVICE_ROLE_KEY` | secret | local and CI only; never referenced by this workflow, AC5 |

`vite.config.ts` sets `base: '/'` — the site is served from the root of a custom domain, never from a
project path.

### The release meta tag

Vite substitutes `%VITE_*%` in `index.html` at build time. Put this in `index.html` once; S0.6 reads the
same variable for the Sentry release and S0.4's staleness test reads the tag.

```html
<meta name="pfc-release" content="%VITE_SENTRY_RELEASE%" />
```

### Workflow shape

```yaml
name: deploy
on:
  push: { branches: [main] }
  workflow_dispatch:
permissions: { contents: read, pages: write, id-token: write }
concurrency: { group: pages, cancel-in-progress: false }

jobs:
  migrate:
    runs-on: ubuntu-latest
    env:                                    # job level: `link` needs the token too
      SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
      SUPABASE_PROJECT_REF:  ${{ secrets.SUPABASE_PROJECT_REF }}
    steps:
      - uses: actions/checkout@v4
      - uses: supabase/setup-cli@v1
        with: { version: latest }
      - run: supabase link --project-ref "$SUPABASE_PROJECT_REF"
      - run: supabase db push

  build:
    needs: migrate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version-file: .nvmrc, cache: npm }
      - run: npm ci
      - run: npm run build
        env:
          VITE_SUPABASE_URL:      ${{ vars.VITE_SUPABASE_URL }}
          VITE_SUPABASE_ANON_KEY: ${{ vars.VITE_SUPABASE_ANON_KEY }}
          VITE_APP_BASE_URL:      ${{ vars.VITE_APP_BASE_URL }}
          VITE_SENTRY_DSN:         ${{ vars.VITE_SENTRY_DSN }}
          VITE_SENTRY_ENVIRONMENT: ${{ vars.VITE_SENTRY_ENVIRONMENT }}
          VITE_SENTRY_RELEASE:     ${{ github.sha }}
          SENTRY_AUTH_TOKEN:       ${{ secrets.SENTRY_AUTH_TOKEN }}
          SENTRY_ORG:              ${{ vars.SENTRY_ORG }}
          SENTRY_PROJECT:          ${{ vars.SENTRY_PROJECT }}
      - run: ./scripts/verify-dist.sh          # AC6, AC7, AC9
        env:                                   # the grep needs the values it is grepping for
          SENTRY_AUTH_TOKEN:     ${{ secrets.SENTRY_AUTH_TOKEN }}
          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
      - uses: actions/upload-pages-artifact@v3
        with: { path: dist }

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: { name: github-pages, url: https://app.phibsborofc.com }
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4

  smoke:
    needs: deploy
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version-file: .nvmrc, cache: npm }
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test --project=smoke-deployed
        env:
          SMOKE_BASE_URL: https://app.phibsborofc.com
          SMOKE_RELEASE:  ${{ github.sha }}
```

`scripts/verify-dist.sh` is three assertions and an exit code:

```sh
#!/usr/bin/env bash
set -euo pipefail
test -f dist/CNAME
grep -qx 'app.phibsborofc.com' dist/CNAME
if find dist -name '*.map' | grep -q .; then echo 'sourcemap in dist' >&2; exit 1; fi
for v in "${SENTRY_AUTH_TOKEN:-}" "${SUPABASE_ACCESS_TOKEN:-}"; do
  if [ -n "$v" ] && grep -rqF "$(printf %.8s "$v")" dist; then
    echo 'secret prefix found in dist' >&2; exit 1
  fi
done
```

The `if` form matters: under `set -e` a bare `[ -n "$v" ] && …` list fails the script whenever `$v` is
empty, which is every fork build. The script must pass with no secrets set.

### Migrations

Forward only. Never edit an applied migration; correct it with a new one. `supabase db push` applies
everything in `supabase/migrations/` not yet recorded in the project. The `migrate` job is a no-op when
there is nothing new, which is the normal case, and it still gates the publish so the ordering is never
in question. Until S1.1 lands there are no migrations and the job succeeds trivially — build it now so the
first schema change does not need a workflow change too.

### Pages and DNS

- Repository → Settings → Pages → Source: **GitHub Actions**. Custom domain `app.phibsborofc.com`.
  Enforce HTTPS on, once the certificate is issued.
- DNS: one `CNAME` record, `app` → `<github-owner>.github.io`. No apex records; this is a subdomain.
- `public/CNAME` is the source of truth — Vite copies `public/` verbatim into `dist/`. Setting the domain
  only in the Pages UI loses it the first time the artifact is replaced, which is AC9.

### Post-deploy smoke spec

`playwright.config.ts` is created here, with `testDir: 'tests/e2e'` — the one directory every Playwright
spec in the repo lives in. One project, `smoke-deployed`, `testMatch: /smoke\..*\.spec\.ts/`, with no
`webServer` (the origin is live) and `use: { timezoneId: 'Europe/Dublin' }` ([D53](../00-decisions.md)). It reads `SMOKE_BASE_URL` and `SMOKE_RELEASE` from the environment. The
top-level `webServer` block that S0.4 needs is added by S0.4, guarded so it does not start for this
project.

```ts
const ROUTES = ['/', '/login', '/register', '/join/x', '/reset/x', '/event/x', '/history',
                '/manage', '/manage/event/new', '/manage/event/x',
                '/manage/team/x/members', '/admin'] as const
```

Until S0.3 lands, `ROUTES` is `['/']`. For each, `page.goto(`${base}/#${route}`)`, then `page.reload()`,
then assert the 404 screen's test id is absent. The routes carrying a placeholder segment resolve to a real screen — loading, error or a redirect
to `/login` — but never to the 404 screen. The release assertion reads
`meta[name="pfc-release"]` and compares to `SMOKE_RELEASE`.

### Rollback

Revert the offending commit and let the workflow run. There is no rollback of schema: a bad migration is
fixed by a new migration. This is written into `docs/deployment.md` so nobody goes looking for a button.

## Data and API surface

No tables, no RPCs, no Zod schemas, no query keys. The `migrate` job applies whatever migrations S1.1 and
S1.3 have added to `supabase/migrations/`; it neither reads nor writes application data.

## UI states

Not a UI story. It adds no screen. The smoke job asserts against screens owned by S0.3.

## Test plan

- **Unit** — `scripts/check-env-parity.mjs` has a Vitest case for each direction: a key in `.env.example`
  and not in `deploy.yml` fails, and the reverse fails (AC14). `scripts/verify-dist.sh` is asserted by its
  own exit code in the workflow, not by Vitest, and is run once locally against a `dist/` with a planted
  `.map` and once with no secrets in the environment to prove both branches (AC6, AC7).
- **Integration / RLS** — none.
- **E2E** — `tests/e2e/smoke.deployed.spec.ts`, the `smoke-deployed` Playwright project, run only by this
  workflow against the live origin. Read-only: no sign-in, no writes, no Supabase calls beyond whatever
  the app makes for an anonymous visit.
- **Manual** — first deploy only: confirm the certificate is issued, "Enforce HTTPS" is on, the plain HTTP
  URL redirects, and the site loads on a phone over mobile data rather than office wifi.

## Open questions

1. **Is `app.phibsborofc.com` registered and is its DNS ours to point?** (Q12.) Default: assume yes.
   If not, the workflow ships unchanged and the site is reachable at the `github.io` origin until the
   record exists; `VITE_APP_BASE_URL` is the only value that changes, and it is a repository variable
   precisely so that change is not a code change.
2. **Which Supabase plan, and does it allow `db push` from CI on a free project?** Default: yes, the CLI
   uses the access token and needs no extra entitlement. If it does not, the `migrate` job becomes a manual
   `supabase db push` run before the merge, documented in `docs/deployment.md`, and AC3 becomes a checklist
   item rather than a job.
3. **Should the deploy run on a tag rather than on every merge to `main`?** Default: every merge. One squad,
   one site, and "one story per PR" already makes each merge a small, reviewed change. Revisit only if a
   bad deploy costs a Saturday.
