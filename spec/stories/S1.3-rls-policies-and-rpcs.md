## Goal

After this story the database defends itself. A player can read their own team's events and set their own
availability and nothing else. A manager can run the teams they manage and nothing else. A stranger
holding an event link can read a one-line preview of that event and join the team it belongs to, and
nothing else. Every privileged action a screen will later need — join, invite, reset, role change,
directory lookup — exists as a named function with its authorisation written into it.

## Context

The brief's S1.3 lists nine bullets. This story implements those plus everything the later stories turned
out to need, all of it settled in [00-decisions.md](../00-decisions.md) and in
[data-model.md](../data-model.md), which wins on schema.

Decisions this story is built on, and where each contradicts the raw brief:

- **D2** — the brief's `team_members.role` includes `'admin'`. It does not. Admin is club-wide,
  `profiles.is_admin`, and `member_role` is `player|manager`.
- **D3** — eight tables, not six. RLS is enabled on all eight.
- **D7** — the brief has no anonymous read path, yet the journey starts with a stranger reading an event.
  `get_event_preview` is that path.
- **D8** — the brief never mentions `profiles` or `teams` policies. Without them the public anon key
  hands out the club's phone directory.
- **D9** — the brief forbids only client INSERT on `team_members`. Clients get no INSERT, UPDATE or
  DELETE.
- **D10** — the brief says both "a member of their team" and "players on teams they manage". The narrow
  rule wins, in the RPC.
- **D11** — password reset is redeemed in Postgres. There is no Edge Function and no service-role key in
  the browser.
- **D12** — the `starts_at` cut-off S3.4 promises is an RLS `WITH CHECK` here, not UI code.
- **D31** — a manager cannot DELETE an event. Managers cancel; admins destroy.
- **D32, D33** — a player reads only their own response and attendance rows; a leaver's rows stay
  readable to the manager, because manager reads are scoped by the event's team, never by the responder's
  current membership.
- **D50** — `teams.active = false` refuses joins and event inserts, in SQL.
- **D37** — the invite gate in S2.1 is UX, not a boundary. Anyone with the anon key can create an account.
  The real gate is membership, and it lives in this file.

Nothing here is enforced anywhere else. Role checks in the UI, when they arrive in S2.9, are convenience.

## Scope

**In**
- `enable row level security` on all eight tables, plus `revoke`/`grant` of table privileges per the
  access matrix in [data-model.md](../data-model.md).
- Five security-definer helper functions: `is_admin()`, `is_team_member()`, `is_team_manager()`,
  `event_team_id()` and `has_event_row()`, plus the internal token generator `new_token()`, granted to
  nobody.
- The complete policy set for `profiles`, `teams`, `team_members`, `events`, `event_responses`,
  `attendance`.
- Zero policies on `team_invites` and `reset_tokens`, with privileges revoked so they are unreachable.
- All fourteen security-definer RPCs listed in [data-model.md](../data-model.md), with their grants.
- The fixed error vocabulary the UI maps to copy.

**Out**
- Tests. Every policy and every RPC in this story is asserted in [S1.4](S1.4-rls-test-suite.md), which
  lands immediately after and before any feature UI (D55).
- Any TypeScript. The typed client, Zod schemas and query hooks are [S1.5](S1.5-typed-data-layer-and-shared-helpers.md).
- Any screen. The screens that call these RPCs are S2.x, S6.x and S4.6.
- Hashing tokens. Rejected: a manager must be able to re-copy a live join link (D62).
- Supabase Realtime, publication or trigger work for live counts. Counts poll (D23).
- The `handle_new_user` trigger and the seed. Those are S1.2.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — `select tablename from pg_tables where schemaname = 'public' and not rowsecurity`
  returns zero rows.
- [ ] **AC2** — `team_invites` and `reset_tokens` have zero rows in `pg_policies`, and `anon` and
  `authenticated` hold no privilege on either (`has_table_privilege` false for select, insert, update
  and delete).
- [ ] **AC3** — `anon` holds no privilege on any table in `public`. Anonymous reach is exactly
  `get_event_preview`, `lookup_team_invite` and `redeem_reset_token`, and nothing else.
- [ ] **AC4** — every function in `public` is `security definer` with `set search_path = ''`, fully
  qualifies every object it touches, and has `execute` revoked from `public` and granted only to the
  roles named in the grant table below. The three helpers the brief names exist with exactly those
  names and signatures — `is_admin()`, `is_team_member(p_team_id uuid)`,
  `is_team_manager(p_team_id uuid)` — and no policy expresses membership or management any other way.
- [ ] **AC5** — a player selecting `profiles` with no filter gets exactly one row: their own. Selecting
  another user's id returns zero rows, not an error. Admins are not exempt.
- [ ] **AC6** — a player selects only teams they are a member of and only while `teams.active` is true.
  An admin selects all teams. No role has DELETE on `teams`.
- [ ] **AC7** — a player selects `team_members` rows only for teams they belong to, and has no INSERT,
  UPDATE or DELETE on that table. A player attempting to update their own row to `manager` gets a
  privilege error and the stored role is unchanged.
- [ ] **AC8** — a player selects events for their own teams, plus any event for which they hold an
  `event_responses` or `attendance` row, and no others. A direct PostgREST call filtered on another
  team's id returns `[]` with a 200, not an error.
- [ ] **AC9** — a manager can INSERT, SELECT and UPDATE events for teams they manage, and only those:
  an INSERT naming a team they do not manage is refused, and an UPDATE of another team's event affects
  zero rows and leaves the stored row unchanged. `insert` for a team with `active = false` is refused.
  `delete` by a manager affects zero rows; `delete` by an admin succeeds and cascades that event's
  responses and attendance.
- [ ] **AC10** — a player may INSERT and UPDATE only their own `event_responses` row, and only while the
  event is `scheduled` and `starts_at > now()`. A write after `starts_at`, a write to a cancelled event,
  a write carrying another user's `user_id`, and any DELETE are all refused.
- [ ] **AC11** — a player selects only their own `event_responses` and `attendance` rows. Selecting a
  teammate's row returns zero rows, not an error. A player has no INSERT, UPDATE or DELETE on
  `attendance` at all.
- [ ] **AC12** — a manager selects every `event_responses` and `attendance` row for events on the teams
  they manage, including rows belonging to users who have since been removed from the team.
- [ ] **AC13** — a manager writes `attendance` only for events on teams they manage: INSERT, UPDATE and
  DELETE against an event on any other team are refused or affect zero rows. A manager writing
  `attendance` must set `recorded_by` to their own uid; a row carrying anyone else's uid is refused.
- [ ] **AC14** — `get_event_preview` returns exactly `team_id, team_name, type, title, location,
  starts_at, status` for `anon` and for a signed-in non-member, returns zero rows for an unknown id, and
  exposes `notes`, `created_by`, counts and member lists nowhere.
- [ ] **AC15** — `lookup_team_invite` returns zero rows — never an error — for an unknown, expired,
  revoked or inactive-team token, so nothing distinguishable is returned to a token prober.
- [ ] **AC16** — `join_team_by_token` grants the role held on the invite row and ignores any client
  argument; is idempotent, leaving `joined_at` untouched on a second call; consumes a manager invite by
  setting `active = false`; and raises `invalid_invite` for every failure.
- [ ] **AC17** — `join_team_by_event` joins the caller as `player`, and raises `invalid_invite` for an
  unknown event, an inactive team, or an event that started more than seven days ago.
- [ ] **AC18** — `create_team_invite` mints a 43-character base64url token; a manager may mint only a
  `player` invite and is refused `manager` with `not_authorised`; issuing replaces the existing live
  invite for that `(team_id, role)` in one transaction, so the partial unique index never trips.
- [ ] **AC19** — `issue_reset_token` refuses, with `not_authorised`, a manager targeting: a user who is
  not a `player` on that team, a user holding `manager` anywhere, and an admin. Issuing revokes every
  live token for that user.
- [ ] **AC20** — `redeem_reset_token` sets the password, marks `used_at`, revokes the user's other live
  tokens, deletes the user's `auth.refresh_tokens` rows, and returns the user's E.164 phone. A second
  call with the same token raises `invalid_token`, as do expired, revoked and unknown tokens, and a
  password under 8 characters.
- [ ] **AC21** — `team_member_directory` returns `phone` only to a manager of that team or an admin, null
  to everyone else, and zero rows to a non-member.
- [ ] **AC22** — `set_member_role` and `set_member_phone` are `is_admin()` only; `remove_member` lets a
  manager remove only a `player` on a team they manage; `remove_member` deletes the `team_members` row
  and no response or attendance row.
- [ ] **AC23** — every failure path in every RPC raises one of exactly six messages: `invalid_invite`,
  `invalid_token`, `not_authorised`, `phone_taken`, `series_too_long`, `starts_in_past`. No Postgres
  constraint name,
  column name or token value ever reaches the client.
- [ ] **AC24** — `supabase db reset` applies S1.1, S1.2 and this story's migrations from empty with no
  error, and `supabase db push` applies them to a project that already has S1.1 and S1.2.
- [ ] **AC25** — the brief's "Admin can administer everything" resolves to exactly the admin column of the
  access matrix in [data-model.md](../data-model.md), proved one case per object: SELECT, INSERT and
  UPDATE on any `teams` row; SELECT on any `team_members` row; SELECT, INSERT, UPDATE and DELETE on any
  `events` row and on any `event_responses` and `attendance` row, on a team the admin is not a member of;
  and EXECUTE on all fourteen RPCs. It stops at two places, and both are deliberate: on `profiles` an
  admin still selects their own row only (AC5), and `team_invites` and `reset_tokens` stay unreadable to
  every role including admin (AC2).
- [ ] **AC26** — `get_team_invite` returns the one live invite row for a manager of that team when
  `p_role = 'player'`, and for an admin for either role. It returns zero rows — never an error — for a
  player, for a manager of another team, for a manager asking for the `manager` role, for a revoked or
  expired invite, and for `anon`. Added to close [S6.2](S6.2-team-join-links.md) open question 1; the
  body is specified there and implemented in this story's migration.

## Implementation notes

Three forward-only migrations under `supabase/migrations/`, timestamped by the CLI
(`supabase migration new rls_helpers`, `... rls_policies`, `... rpcs`). Never edit an applied migration;
correct with a new one (D18).

### Conventions that apply to every function in this story

```sql
create or replace function public.<name>(...) returns <t>
language sql|plpgsql
stable|volatile
security definer
set search_path = ''            -- forces full qualification; a missing schema prefix fails loudly
as $$ ... $$;

alter function public.<name>(...) owner to postgres;
revoke execute on function public.<name>(...) from public;
grant  execute on function public.<name>(...) to authenticated;   -- or anon, per the grant table
```

`search_path = ''` means `gen_random_bytes`, `crypt` and `gen_salt` must be called as
`extensions.gen_random_bytes(...)` etc., because Supabase installs `pgcrypto` into the `extensions`
schema. `gen_random_uuid()` is core and resolves as `public`-independent `pg_catalog.gen_random_uuid()`.

A security-definer body runs as `postgres` and therefore **bypasses RLS**. There is no policy backstop
inside these functions; every authorisation check is the explicit `if not ... then raise` at the top.

### 1. Helpers — `<ts>_rls_helpers.sql`

```sql
create or replace function public.is_admin() returns boolean
language sql stable security definer set search_path = '' as $$
  select coalesce((select p.is_admin from public.profiles p where p.id = auth.uid()), false);
$$;

create or replace function public.is_team_member(p_team_id uuid) returns boolean
language sql stable security definer set search_path = '' as $$
  select exists (
    select 1 from public.team_members m
    where m.team_id = p_team_id and m.user_id = auth.uid()
  );
$$;

create or replace function public.is_team_manager(p_team_id uuid) returns boolean
language sql stable security definer set search_path = '' as $$
  select public.is_admin() or exists (
    select 1 from public.team_members m
    where m.team_id = p_team_id and m.user_id = auth.uid() and m.role = 'manager'
  );
$$;

-- The event's team, read past RLS. Used by the response and attendance policies.
create or replace function public.event_team_id(p_event_id uuid) returns uuid
language sql stable security definer set search_path = '' as $$
  select e.team_id from public.events e where e.id = p_event_id;
$$;

-- "I hold a row for this event", read past RLS. D33: a leaver keeps their own history.
create or replace function public.has_event_row(p_event_id uuid) returns boolean
language sql stable security definer set search_path = '' as $$
  select exists (select 1 from public.event_responses r
                  where r.event_id = p_event_id and r.user_id = auth.uid())
      or exists (select 1 from public.attendance a
                  where a.event_id = p_event_id and a.user_id = auth.uid());
$$;
```

`is_team_manager` returns true for an admin on every team, so no policy needs a separate admin branch for
event writes. That is deliberate and is why AC9's admin cases pass with the manager policies.

**Why `event_team_id` and `has_event_row` exist at all.** Writing those `exists` clauses inline inside the
policies creates a cycle: the `events` select policy would read `event_responses`, whose own select policy
reads `events`, and Postgres aborts with *infinite recursion detected in policy for relation*. A
security-definer helper breaks the cycle because it does not re-enter RLS. Do not "simplify" them back
into the policies.

Wrap `auth.uid()` as `(select auth.uid())` in every policy expression so the planner treats it as an
InitPlan and evaluates it once per statement rather than once per row.

### 2. Privileges and policies — `<ts>_rls_policies.sql`

Start by removing whatever the platform's default privileges granted:

```sql
revoke all on all tables in schema public from anon, authenticated;

grant select on public.profiles, public.teams, public.team_members to authenticated;
grant select, insert, update, delete on public.events            to authenticated;
grant select, insert, update, delete on public.event_responses   to authenticated;
grant select, insert, update, delete on public.attendance        to authenticated;
-- team_invites and reset_tokens: nothing, to anybody.
-- anon: nothing, on anything.
```

Privilege and policy are both required: a policy without the grant returns a privilege error; a grant
without a policy returns nothing. The `delete` grants on `events` and `event_responses` exist so the
admin policies can use them; the non-admin denial comes from the policy, which is why AC9's manager
delete reports zero rows rather than an error.

Then, table by table. `alter table ... enable row level security;` precedes each block.

```sql
-- profiles (D8). Own row only, for everyone, admins included.
create policy profiles_select_own on public.profiles
  for select to authenticated using (id = (select auth.uid()));
-- No insert, update or delete policy at all. The S1.2 trigger and set_member_phone are definers.

-- teams (D8, D50)
create policy teams_select_member on public.teams
  for select to authenticated
  using ((public.is_team_member(id) and active) or public.is_admin());
create policy teams_insert_admin on public.teams
  for insert to authenticated with check (public.is_admin());
create policy teams_update_admin on public.teams
  for update to authenticated using (public.is_admin()) with check (public.is_admin());
-- No delete policy. Teams are never hard deleted; every FK to teams is on delete restrict.

-- team_members (D9). Read only, ever.
create policy team_members_select_team on public.team_members
  for select to authenticated
  using (public.is_team_member(team_id) or public.is_admin());

-- events (D31, D33, D50)
create policy events_select on public.events
  for select to authenticated
  using (public.is_team_member(team_id) or public.is_admin() or public.has_event_row(id));
create policy events_insert_manager on public.events
  for insert to authenticated
  with check (
    public.is_team_manager(team_id)
    and exists (select 1 from public.teams t where t.id = team_id and t.active)
  );
create policy events_update_manager on public.events
  for update to authenticated
  using (public.is_team_manager(team_id)) with check (public.is_team_manager(team_id));
create policy events_delete_admin on public.events
  for delete to authenticated using (public.is_admin());

-- event_responses (D12, D32, D33, D61)
create policy event_responses_select_own on public.event_responses
  for select to authenticated using (user_id = (select auth.uid()));
create policy event_responses_select_manager on public.event_responses
  for select to authenticated
  using (public.is_team_manager(public.event_team_id(event_id)));
create policy event_responses_insert_own on public.event_responses
  for insert to authenticated
  with check (
    user_id = (select auth.uid())
    and exists (
      select 1 from public.events e
      where e.id = event_id
        and e.status = 'scheduled'
        and e.starts_at > now()
        and public.is_team_member(e.team_id)
    )
  );
create policy event_responses_update_own on public.event_responses
  for update to authenticated
  using (user_id = (select auth.uid()))
  with check ( /* the identical expression as insert_own */ );
create policy event_responses_admin_all on public.event_responses
  for all to authenticated using (public.is_admin()) with check (public.is_admin());
-- No delete policy for players or managers (D61).

-- attendance (D25, D32, D33)
create policy attendance_select_own on public.attendance
  for select to authenticated using (user_id = (select auth.uid()));
create policy attendance_manager_all on public.attendance
  for all to authenticated
  using (public.is_team_manager(public.event_team_id(event_id)))
  with check (
    public.is_team_manager(public.event_team_id(event_id))
    and recorded_by = (select auth.uid())
  );
```

Permissive policies OR together, so `event_responses_select_own` and `event_responses_select_manager`
coexist without either widening the other. The D12 `exists` on `events` is evaluated under the caller's
own `events` policy, which is satisfied for a member and fails for everyone else — that is a second,
harmless belt on the same rule. Keep the insert and update `with check` expressions byte-identical; if
they drift, a player can edit a row they could not have created.

`recorded_by = (select auth.uid())` in the attendance check stops a manager attributing a record to
someone else, and is why S4.5 must always send `recorded_by` on insert and on update.

### 3. RPCs — `<ts>_rpcs.sql`

Token generation, internal, not granted to anyone:

```sql
create or replace function public.new_token() returns text
language sql volatile security definer set search_path = '' as $$
  select rtrim(translate(encode(extensions.gen_random_bytes(32), 'base64'), '+/', '-_'), '=');
$$;
revoke execute on function public.new_token() from public;
```

43 characters of base64url. S1.4 asserts the length, so do not change the byte count without changing
that test.

Failure convention, used by every function below:

```sql
raise exception using errcode = 'P0001', message = 'invalid_invite';
```

The whole vocabulary is six strings — `invalid_invite`, `invalid_token`, `not_authorised`,
`phone_taken`, `series_too_long`, `starts_in_past` — and the client maps them to copy in
`src/lib/errors.ts` (S1.5). A
lookup that fails returns **zero rows** and never raises, so tokens cannot be probed; an action that fails
always raises. Never include the token, the user id or the reason in the message.

Signatures and the rules each one enforces. Bodies follow directly from
[data-model.md](../data-model.md) and are not repeated here.

```sql

  returns table (team_id uuid, team_name text, type public.event_type, title text,

public.lookup_team_invite(p_token text)

public.create_team_invite(p_team_id uuid, p_role public.member_role) returns text

  -- stable. grant to authenticated. The read path D62 assumes: a manager re-copies a live link.

  -- Validate: used_at is null and revoked_at is null and expires_at > now()
```

`redeem_reset_token` is the only function that writes outside `public`. It must be owned by `postgres`,
which holds rights on `auth`. `auth.refresh_tokens.user_id` is `varchar`, not `uuid`: cast, or the delete
silently matches nothing and a stolen link leaves a live session behind. The phone it returns carries the
leading `+`; `auth.users.phone` does not (D35), which is why the return reads from `profiles`.

### Grant table

| Function | anon | authenticated |
|---|---|---|
| `get_event_preview` | yes | yes |
| `lookup_team_invite` | yes | yes |
| `redeem_reset_token` | yes | yes |
| `team_member_directory`, `join_team_by_token`, `join_team_by_event`, `create_team_invite`, `revoke_team_invite`, `get_team_invite`, `issue_reset_token`, `set_member_role`, `remove_member`, `set_member_phone`, `generate_training_series` | no | yes |
| `is_admin`, `is_team_member`, `is_team_manager`, `event_team_id`, `has_event_row`, `new_token` | no | no |

The helpers are not granted to anybody. Policies call them as the table owner, so no client grant is
needed, and withholding it keeps them off the PostgREST RPC surface.

### Known consequence, stated so nobody treats it as a bug

A member of a **deactivated** team can still read that team's events (the `events` policy keys on
membership, not on `teams.active`) but can no longer read the `teams` row. Screens that render a team name
for a non-admin must therefore tolerate a missing team row, or take the name from `get_event_preview`.
Admins see both. This is the intended reading of D50 and S1.4 asserts it.
