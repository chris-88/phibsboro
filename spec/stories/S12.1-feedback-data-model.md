## Goal
The database can hold a feedback report tied to its reporter, with the row-level security that lets a user
file only as themselves and only an admin read the lot. Nothing user-facing yet.

## Context
[W1](../00-decisions-v1.2.0.md) puts feedback in an in-app admin inbox; [W2](../00-decisions-v1.2.0.md) makes
it insert-only for users, admin read/resolve, with auto-captured context. This is the blocking schema/RLS
story for Epic 12 — the same "data model + RLS before UI" order as S1.1→S1.4. See
[data-model-v1.2.0.md](../data-model-v1.2.0.md) for the table.

## Scope
**In**
- Migration creating the `feedback` table, the `feedback_category` and `feedback_status` enums, and the
  `feedback(status, created_at desc)` index (see data-model-v1.2.0).
- RLS: insert `with check (user_id = auth.uid())` for `authenticated`; select-own for a user; select-all and
  update-`status` for `is_admin()`; no client delete.
- Regenerated `src/lib/database.types.ts`; a `feedbackRowSchema` (Zod) with the S1.5 parity test.
- RLS test rows (S1.4 grows): a user files as self and cannot forge `user_id`, reads own only; an admin reads
  all and resolves; anon cannot insert or read.

**Out**
- Any UI (S12.2 submits, S12.3 reads).
- Notifications of new feedback.

## Acceptance criteria
- [ ] **AC1** — Migration runs clean on the live DB; existing rows unaffected; `supabase db diff` empty after.
- [ ] **AC2** — A signed-in user can insert a feedback row for themselves; an insert with a different
  `user_id` is refused (`42501`), not silently rewritten.
- [ ] **AC3** — A user reading `feedback` sees only their own rows; an admin sees every row.
- [ ] **AC4** — A user cannot update or delete any feedback row; an admin can set `status` to `resolved`
  (stamping `resolved_at`/`resolved_by`), and cannot rewrite `message`/`user_id`.
- [ ] **AC5** — anon cannot insert or select `feedback`.
- [ ] **AC6** — `feedbackRowSchema` matches the generated `Tables<'feedback'>` (S1.5 parity test passes).

## Implementation notes
- Enums in their own statements; `check (char_length(btrim(message)) between 1 and 2000)`.
- Restrict the admin update to `status`/`resolved_at`/`resolved_by`: either a `before update` trigger that
  rejects changes to other columns, or a narrow `resolve_feedback(p_id)` security-definer RPC that S12.3
  calls (preferred — mirrors the S1.3 RPC pattern and keeps the write auditable). Record which in build notes.
- `resolved_by` defaults from `auth.uid()` in the RPC, never trusted from the client.

## Data and API surface
`feedback` table + two enums (data-model-v1.2.0). Zod `feedbackRowSchema`. Optional `resolve_feedback` RPC.
No query hooks yet (S12.2/S12.3 add them).

## UI states
Not a UI story.
