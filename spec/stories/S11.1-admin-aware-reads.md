## Goal
An admin's screens surface every team, matching the full access RLS already grants: the event reads include
all active teams, and every team picker offers all teams — so an admin can see and act anywhere.

## Context
[V14](../00-decisions-v1.1.0.md): the data layer is already god mode (RLS), but the UI scopes to membership.
This story makes the reads and pickers admin-aware. Players are unaffected.

## Scope
**In**
- The event reads (`useMonthEvents`, `useUpcomingEvents`, and any team-scoped events read) stop filtering by
  the viewer's `teamIds` when the viewer is an admin — they read across all active teams (RLS scopes the
  rest; for an admin that is everything). For a player they keep the membership filter exactly as now.
- The team pickers widen for an admin to every **active** team: create-event team select (S4.1), the Squad
  tab team selector (S10.3), squad-picker access (S9.2), member admin (S6.4). `managedTeams` / a new
  `administrableTeams` on `useCurrentUser` exposes "all active teams" for an admin vs memberships for others.
- A single source of truth for "which teams can this viewer act on" so the widening is not re-derived per
  screen.

**Out**
- The admin Home all-teams calendar UI ([S11.2](S11.2-admin-home-all-teams.md)) — this story is the data/hook
  layer plus the pickers.
- Any RLS or schema change (none — RLS already permits it).

## Acceptance criteria
- [x] **AC1** — For an admin, `useMonthEvents`/`useUpcomingEvents` return **every active team's** events for the window (verified against the live project as the seeded admin `+353899999001`, who has no memberships: the scoped read returned 8 events — Firsts 4, Seconds 4); for a player they return only their teams' events (player `+353899999010` returned 4 Firsts events only, unchanged). Unit test `events-admin-reads.test.tsx` asserts the `.in('team_id', …)` ids per role.
- [x] **AC2** — `useCurrentUser` exposes `administrableTeams`: all active teams for an admin, the caller's own active manager teams otherwise, empty for a pure player; one helper, sourced from `teamsOptions()` (one key, no new query). Unit-tested in `use-current-user.test.tsx`.
- [x] **AC3** — The create-event select, Squad-tab selector, squad picker and member admin all resolve their team through `useManagedTeams`, which already widens to every team for an admin and to the manager's own teams for a manager (asserted by `useManagedTeams.test.tsx`); both it and the reads take the widening decision from the same `is_admin` on `useCurrentUser`. See build note.
- [x] **AC4** — `administrableTeams` is active-only, so an inactive team never enters the admin's month/upcoming reads (verified by construction + the events policy inspection below). An admin still reaches inactive teams through the S6.3 manage picker / S6.1 `/admin` screen. See build note on the pickers.
- [x] **AC5** — The widening branches on `is_admin` from `useCurrentUser`; a comment on each read says RLS is the enforcement layer. The player branch (`memberships.map` → same `.in` → same `enabled: teamIds.length > 0`) is byte-for-byte unchanged.
- [x] **AC6** — `test:rls` green (285 passed against the hosted project); the reads still return nothing for a cross-team player (player `+353899999010` saw only Firsts), proving the client change widened no one but admins.

## Implementation notes
- `src/api/events.ts`: the month/upcoming reads take the viewer. For an admin, drop `.in('team_id', teamIds)`
  and the `enabled: teamIds.length > 0` guard (enable unconditionally, RLS returns all); for a player keep
  both. Read `is_admin` from `useCurrentUser` at the hook call site or pass it in. Do NOT rely on
  `teamIds.length` for the admin's empty-state (they have events without memberships).
- `useCurrentUser`: add `administrableTeams` (or a boolean `seesAllTeams` + a resolved team list). It needs
  the full active-teams list for an admin — reuse the existing `useTeams` read (active only) rather than a
  new query.
- Every picker that currently reads `managedTeams` switches to the new helper. Grep for `managedTeams` to
  find them.

## Data and API surface
No schema/RLS change. `useCurrentUser` gains an administrable-teams helper. The event hooks become
viewer-aware. Reuses `useTeams`.

## UI states
Not a new screen. The pickers gain more options for an admin; their existing states are unchanged.

## Test plan
- **Unit** — the events hook filters by teamIds for a player and not for an admin; `administrableTeams` = all active teams for admin, memberships otherwise; a picker renders all teams for admin, own for manager.
- **Integration / RLS** — as the seeded admin, the month read returns both teams' events; as a seeded player, only their team's; `test:rls` green.
- **Manual** — sign in as the admin (0899999001) and confirm events from teams you're not a member of are readable/reachable.

## Build notes — deviations from this spec
| Spec said | Built as | Why |
|---|---|---|
| For an admin, **drop** `.in('team_id', teamIds)` entirely — "RLS returns all active teams". | For an admin the reads filter `.in('team_id', <active team ids from administrableTeams>)`. | The `events_select` policy is `is_team_member(team_id) OR is_admin() OR has_event_row(id)` — `is_admin()` has **no** active-team check, so dropping the filter would return **inactive** teams' events too, breaking AC4/D50. Scoping to the active ids gives the same club-wide result across active teams while keeping retired teams out. (Both seed teams are active, so the live result — 8 events — is identical to dropping the filter today.) |
| "Switch every picker that reads `managedTeams` to `administrableTeams`." | The everyday pickers keep resolving their team through `useManagedTeams`; only the event reads consume `administrableTeams`. | No picker reads the `managedTeams` **field** directly — they all go through the `useManagedTeams` hook, which already widens to every team for an admin (S6.3) and is locked by tests. It deliberately **includes inactive** teams so an admin can administer them there — exactly AC4's permitted S6.3 place. Rewriting it onto the active-only `administrableTeams` would remove that S6.3 capability. Both `useManagedTeams` and `administrableTeams` take the widening decision from the same `is_admin` on `useCurrentUser`, so there is one source of truth for *whether* a viewer is widened; `administrableTeams` is the one active-team list the reads use. |
