## Goal
On an event, a player sees who's in — the names of teammates who've said they're Available, and a count line
for the rest — so the squad can see the side taking shape and it nudges the undecided to answer.

## Context
[W3/W5](../00-decisions-v1.2.0.md). A "Who's in" section on the event detail screen (S3.3), beneath the
availability control, fed by `event_availability` (S13.1). Event detail only in v1.2.0 — not the calendar day
rows or the Home card (W5), to keep the calendar light.

## Scope
**In**
- A "Who's in" section on the event detail screen: the available members' names, and a summary line
  "{available} in · {unavailable} out · {awaiting} awaiting".
- Fed by a `useEventAvailability(eventId)` query over the S13.1 RPC.
- Four states: loading (skeleton), empty ("No one's responded yet." when nobody is available *and* nobody has
  answered), error (inline, non-blocking — the availability control above still works), populated.
- Shown to any team member viewing the event (players and managers). Hidden for a cancelled event.
- The viewer's own name appears in the list when they're Available (optionally marked "you").

**Out**
- Names of decliners/non-responders (W3) — counts only for those.
- "Who's in" anywhere but the event detail (W5).
- A manager change — the manager view (S4.3/S4.4) is untouched; this section is additive on the shared detail.

## Acceptance criteria
- [ ] **AC1** — The section lists exactly the members who responded Available, by name, for the viewer's team
  event.
- [ ] **AC2** — A summary line shows the three counts; `awaiting = squad − available − unavailable`, matching
  the manager view.
- [ ] **AC3** — No decliner or non-responder name appears anywhere in the section.
- [ ] **AC4** — Four states handled; an RPC error shows an inline message and does **not** break the
  availability Yes/No control above it.
- [ ] **AC5** — Hidden on a cancelled event; on an event where the viewer isn't a team member the section does
  not render (the RPC returns nothing).
- [ ] **AC6** — The list updates after the viewer changes their own response (the query invalidates with the
  response mutation).

## Implementation notes
- `src/features/availability/` — a `WhosInSection` component; `useEventAvailability` in
  `src/api/availability.ts` (or `events.ts`) calling `event_availability`, parsed by a Zod schema.
- Invalidate `useEventAvailability(eventId)` from the existing response mutation's `onSettled` so "who's in"
  reflects the viewer's own change (AC6). Keep it its own query key.
- Render names as a simple wrapped list; the summary as one muted line. Reuse the S3.5/S4.3 count vocabulary.
- Skeleton and empty copy consistent with the rest of the app; the empty state is "No one's responded yet."

## Data and API surface
Read via `event_availability` (S13.1). `useEventAvailability` query; invalidated by the response mutation. No
write.

## UI states
| Screen | Loading | Empty | Error | Populated |
|---|---|---|---|---|
| Event detail → Who's in | skeleton | "No one's responded yet." | inline note; Yes/No above still works | names list + "{n} in · {n} out · {n} awaiting" |

## Test plan
- **Unit** — the section's four states off a mocked hook; that only available names render; the summary line
  formats the counts; changing the own response invalidates the query.
- **Integration / RLS** — S13.1 covers the data/privacy; nothing new here.
- **E2E** — optional: two seeded players, one says yes, the other sees them in the list (local stack).
- **Manual** — on a phone, mark yourself available and see your name appear; confirm no decliner names show.
