## Goal

After this story, nobody has to take the security model on trust. Every policy and every RPC in
[S1.3](S1.3-rls-policies-and-rpcs.md) has a test that proves it permits what it should and a test that proves it
refuses what it should, run as a real signed-in user against a real Postgres, on every pull request
including from a fork. This is the gate: no screen that touches team data ships until it is green.

## Context

The brief calls this a blocking story. D55 narrows the wording, because the build order puts the Epic 0
shell, routing and PWA ahead of it: **no feature UI that reads or writes team data ships before this
passes**. The shell touches no data and is exempt.

Decisions this story is built on:

- **D54** — coverage defined only per listed policy lets a table with RLS off pass by having no test.
  Two structural tests close that: every `public` table has `rowsecurity` true, and every table has at
  least one policy unless it is on the deny-all list (`team_invites`, `reset_tokens`).
- **D37** — there is a fourth role: a signed-in user with zero `team_members` rows. The registration gate
  in S2.1 is UX, so this user genuinely exists in production. They are denied everywhere except
  `get_event_preview` and the join RPCs.
- **D15** — the seed is a Node script owned by S1.2, creating real Auth users this suite signs in as. One
  fixture set serves S1.1, S1.4 and S7.3; there is no second one.
- **D14** — the `db` job runs the Supabase CLI local stack with its published fixed keys. No repository
  secret is required, so pull requests from forks run the gate.
- **D38** — the anon key is a public value, committed in `.env.example`. The service-role key is a real
  secret and appears only in `tests/helpers/admin.ts` — the single service-role client
  [S1.2](S1.2-profile-provisioning-and-seed.md) ships — never under `src/`, never in an assertion.
- **D53** — `TZ=UTC` in the job and in the Vitest config, so the `starts_at` cut-off tests do not depend
  on the runner's clock or the time of year.
- **D12, D31, D33, D50, D10, D28, D6, D7, D8, D9** — each contributes named cases to the matrix below.

## Scope

**In**
- A Vitest project `rls`, separate from the unit project, running serially against the local stack.
- Five client factories: anonymous, player, manager, admin, and stranger (no memberships).
- Assertion helpers that distinguish the three shapes a denial takes in PostgREST, so a silent no-op can
  never read as a pass.
- One test file per table and one per RPC group, covering the matrix below positively and negatively.
- The two structural guards from D54.
- The `rls` Vitest project added to the **existing** `db` job in `.github/workflows/ci.yml`, which
  [S1.1](S1.1-schema.md) created. This story adds the seed step and `npm run test:rls`, and nothing else.

**Out**
- Any change to policies or functions. If a test fails, the fix is a new migration in a follow-up to
  S1.3, not a softened assertion.
- UI, component or hook tests. Those ship with their own stories (D57).
- Playwright. E2E is [S7.3](S7.3-end-to-end-journey.md), a separate job.
- Performance or load testing. Twenty players.
- Testing Supabase Auth itself: password hashing, JWT issuance and rate limits are the platform's. What
  this suite tests is what our policies do with the resulting `auth.uid()`.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

  matrix below is implemented. A matrix row showing `—` in the positive column is a denial-only rule
  whose permitted path is covered positively by another row against the same policy; no policy has a
  negative test alone. Each test name states the role, the object and the expected outcome, e.g.
  `player cannot update another player's event_response`.
- [x] **AC3** — the structural guard fails the build if any table in `public` has `rowsecurity` false.
- [x] **AC4** — the structural guard fails the build if any table in `public` has zero policies, unless it

- [x] **AC6** — every denial is asserted by shape, using the helper for that shape: filtered-away reads
  and filtered-away updates/deletes assert **zero rows and no error**, and are paired with a service-role

- [ ] **AC9** — the `db` job runs on `pull_request` and on `push` to `main`, brings up the Supabase CLI

- [ ] **AC10** — `db` is a required check on `main`, so no merge reaches the deploy workflow without it.
- [ ] **AC11** — the full suite completes in under three minutes on a standard GitHub runner, excluding

- [x] **AC12** — the suite is deterministic: no test depends on wall-clock date beyond the fixed instants

- [x] **AC13** — any row written by a test is either written under a fixture that `supabase db reset`

- [x] **AC14** — the token-shape assertion: tokens returned by `create_team_invite` and

`package.json`: `"test:rls": "vitest run --config vitest.rls.config.ts"`. The default `npm test` runs the
unit project only, so a developer without Docker is not blocked.

```ts
// vitest.rls.config.ts
export default defineConfig({
  test: {
    include: ['tests/rls/**/*.test.ts'],
    globalSetup: ['tests/rls/globalSetup.ts'],
    fileParallelism: false,      // one database, one writer at a time
    testTimeout: 20_000,
    env: { TZ: 'UTC' },          // D53
  },

```

`globalSetup.ts` runs `supabase db reset --local` and then the S1.2 seed
(`npx tsx supabase/seed/seed.ts`) with `execFile`, and fails loudly if either exits non-zero. It does not
start the stack; the job does that, and a developer runs `supabase start` once.

### Clients

```ts
export type Fixture = 'admin' | 'managerFirsts' | 'managerSeconds'
                    | 'playerFirsts' | 'playerFirstsOther' | 'playerSeconds' | 'stranger'

export function anonClient(): SupabaseClient<Database>
export async function signInAs(f: Fixture): Promise<SupabaseClient<Database>>
```

Each client is created with `createClient(URL, ANON_KEY, { auth: { persistSession: false,
autoRefreshToken: false } })` and signed in with `signInWithPassword({ phone, password })` using the seed
fixtures. Sessions are memoised for the run; clients are never shared between fixtures, because a shared
client carrying the wrong JWT is exactly the bug this suite exists to catch.

**Fixtures the seed must provide** (S1.2 owns them; if any is missing, S1.2 is the fix, not this story):
an admin; a manager of Firsts and a manager of Seconds; two players on Firsts and one on Seconds; a
signed-in user with no memberships (D37); per team, one scheduled future event, one past event and one
cancelled event (D3, D12). The reserved E.164 range `+3538990…` is for E2E (D58) and is not used here.

### The three denial shapes, and why they need separate helpers

PostgREST does not fail uniformly, and this is the single most likely way for this suite to be
accidentally useless:

| What happened | Response | Helper |
|---|---|---|
| `select` filtered out by `using` | `200`, `data: []`, `error: null` | `expectEmpty` |
| `update`/`delete` filtered out by `using` | `200`/`204`, zero rows affected, `error: null` | `expectEmpty` **and** `expectRowUnchanged` |
| `insert`, or `update` failing `with check` | `403`, `error.code === '42501'` | `expectRlsDenied` |
| no table privilege granted at all | `401`/`403`, `error.code === '42501'` or `42501`-shaped permission denied | `expectRlsDenied` |
| RPC raised | `400`, `error.message` is one of the six | `expectRpcError(res, 'not_authorised')` |

```ts
export const expectEmpty = (res: PostgrestResponse<unknown>) => {
  expect(res.error).toBeNull()
  expect(res.data ?? []).toHaveLength(0)
}
export const expectRlsDenied = (res: { error: PostgrestError | null }) => {
  expect(res.error).not.toBeNull()
  expect(res.error?.code).toBe('42501')
}
export const expectRpcError = (res: { error: PostgrestError | null }, message: string) => {
  expect(res.error?.message).toContain(message)
}
export const expectRowUnchanged = async (
  table: 'events' | 'event_responses' | 'attendance' | 'team_members' | 'profiles' | 'teams',
  match: Record<string, string>,
  expected: Record<string, unknown>,
) => { /* re-read with the service-role client and assert every key */ }
```

Every negative update and delete test calls `expectRowUnchanged`. A test that only asserts "no rows came
back" proves nothing, because that is also what a successful write returns when `.select()` is omitted.

Always send `.select()` on writes, so the response carries the rows, and use `{ count: 'exact' }` on the
reads where the count is the assertion.

### CI

[S1.1](S1.1-schema.md) already created the `db` job, and [S1.2](S1.2-profile-provisioning-and-seed.md)
already runs the seed in it. This story appends two steps to that job and changes nothing else — in
particular it keeps `fetch-depth: 0`, which S1.1 AC20 needs, and the three structural steps S1.1 added:

```yaml
      # appended to the existing `db` job, after S1.1's steps
      - run: npx tsx supabase/seed/seed.ts
      - run: npm run test:rls
```

The job's shape is S1.1's: `actions/checkout@v4` with `fetch-depth: 0`, `actions/setup-node@v4` with
`node-version-file: .nvmrc`, `supabase/setup-cli@v1` pinned to `${{ env.SUPABASE_CLI_VERSION }}`
([S0.7](S0.7-ci-pipeline.md) AC8), `env: { TZ: UTC }`.

`supabase start` publishes the stack on `http://127.0.0.1:54321` with the CLI's fixed local anon and
service-role keys, which are published constants committed in `.env.example` (D38). No secret is read, so
this job runs on pull requests from forks. `pull_request_target` is never used.

`db` is already a required status check on `main` alongside `check` ([S0.7](S0.7-ci-pipeline.md)
AC9); this story only confirms it is, now that the job does more than structural assertions.

## Open questions

1. **Does the suite run against a hosted Supabase project as well as the local stack?** Proposed default:
   no. Local only (D14). A hosted run needs a secret, which breaks fork pull requests, and the schema is
   identical because the deploy applies the same migrations (D18).
2. **Where do the seed's phone numbers and passwords live so both the seed and the suite see one copy?**
   Proposed default: exported as named constants from `supabase/seed/fixtures.ts`, imported by both.
   They are fixtures, not secrets, and the story says so.
3. **What happens when a later story adds a table?** Proposed default: the D54 structural guard fails
   until that story adds RLS, a policy and its matrix rows. That is the intended cost and it is why the
   guard enumerates `pg_tables` rather than a hand-written list.
