## Goal

A manager sets up Tuesday training once and gets a term of sessions in the list, each one a real event
that can be shared, answered and cancelled on its own. It removes the weekly chore of creating the same
event again, and puts no recurrence logic anywhere near a read query.

## Context

`CLAUDE.md` S4.6: day, time, location and a horizon in; concrete event rows out; no recurrence logic in
read queries; editing or cancelling one occurrence leaves the others alone; a cap on the horizon.
Decisions in [00-decisions.md](../00-decisions.md) that settle what the brief left open:

- **D30** — `events.series_id uuid null`, set only on generated rows, and **no read query filters on it**.
  The partial unique index `(team_id, starts_at) where series_id is not null`, shipped by
  [S1.1](S1.1-schema.md), makes a re-run idempotent. The cap is 16 weeks and at most 20 events per run,
  enforced in the Zod schema and again in the function. The confirm step states the number.
- **D34** — the route list is fixed and contains no recurrence route. This is therefore a mode of
  `/manage/event/new`, not a new screen, and no route is added.
- **D50** — generation is refused for a deactivated team, in the function, not the UI.
- **D35 / D53** — every date shown goes through `formatEventTime()`, pinned to `Europe/Dublin`, and CI runs
  at `TZ=UTC` so the tests mean something in January as well as July.

`generate_training_series` is owned by [S1.3](S1.3-rls-policies-and-rpcs.md), which shipped it with the
other twelve RPCs so S1.4 covers each exactly once. That story's sketch has one defect this story must
correct, and one gap it must fill:

- It adds `p_first_starts_at + (n * interval '7 days')` to a `timestamptz`, which is 168 hours of absolute
  time. A 7.30pm session generated in February becomes 8.30pm Dublin after the March clock change and
  players turn up an hour late. Generation must add weeks in Dublin wall-clock time.
- It has no guard against a first session in the past, so a mistyped year quietly seeds twelve events into
  last winter.

Both are fixed here by a forward-only `create or replace` migration, which is how D18 says a mistake is
corrected — never by editing an applied migration. S1.4 gains the matching cases.

The past-date guard raises `starts_in_past`. It is already the sixth word in
[S1.3](S1.3-rls-policies-and-rpcs.md) AC23's vocabulary, already in [S1.5](S1.5-typed-data-layer-and-shared-helpers.md)'s
`APP_ERROR_CODES` and `mapRpcError`, and already covered by [S1.4](S1.4-rls-test-suite.md) matrix row 37.
This story adds no error word and amends no earlier story; it raises that one and no other new string.

## Scope

**In**
- A "Repeat weekly" switch on `/manage/event/new`, shown only when type is `training`.
- A horizon control, a confirm step naming the number of sessions, and a result line naming the number
  actually created.
- `weeklySlots()`, the client-side twin of the function's date arithmetic, used for the preview.
- `useGenerateTrainingSeries()`, `trainingSeriesSchema`, and the error-to-copy mapping.
- One migration correcting the interval arithmetic and adding the past-date guard.
- A check that `series_id` is invisible to every read path.

**Out**
- Any cadence other than weekly. No fortnightly, no "every other Tuesday", no two days a week.
- Editing, cancelling or deleting a whole series. Each occurrence is handled on its own through
  [S4.2](S4.2-edit-and-cancel-event.md), which needs no change.
- Recurring **matches**. Fixtures are not regular and are not generated.
- `notes` on generated events. The function takes no notes argument; a manager adds notes to one
  occurrence by editing it.
- A background job topping the series up as the horizon rolls forward. The manager runs it again.
- Any read query, list or filter that knows a series exists (D30).

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — `/manage/event/new` shows a "Repeat weekly" switch when type is `training` and hides it
      when type is `match`. Switching the type to `match` with the switch on clears it back off.
- [ ] **AC2** — With the switch on, the form collects first session date, start time, title, location and
      a horizon in whole weeks. The day of the week comes from the first session's date; it is not a
      separate field.
- [ ] **AC3** — The horizon offers 4, 8, 12 and 16 weeks and nothing above 16. A payload with
      `weeks > 16`, `weeks < 1` or a non-integer fails `trainingSeriesSchema` client-side **and** raises
      `series_too_long` in the function. Both are tested.
- [ ] **AC4** — A horizon of N weeks creates exactly N events, one per week, the first at the time given.
      12 weeks produces 12 rows.
- [ ] **AC5** — Every generated row has `type = 'training'`, `status = 'scheduled'`, the same `title`,
      `location` and `series_id`, `created_by` set to the acting manager, and `notes` null.
- [ ] **AC6** — **The clock change.** A series whose first session is 19:30 Dublin in February still starts
      at 19:30 Dublin in April. Asserted on fixed UTC instants across the March and October boundaries:
      the stored `timestamptz` values differ by an hour in UTC and are identical under
      `formatEventTime(iso, 'time')`.
- [ ] **AC7** — Re-running the generator over an overlapping window creates no duplicates. The same
      12-week request twice leaves 12 events, and the second run reports "0 created, 12 already existed."
- [ ] **AC8** — Before anything is written, a confirm dialog states the count and the span, in the exact
      shape `formatEventTime(iso, 'share')` produces: a heading "This creates 12 training sessions." (D30),
      then "First: Tuesday 16 September, 7.30pm" and "Last: Tuesday 2 December, 7.30pm". Cancelling
      writes nothing and issues no request.
- [ ] **AC9** — After a run an inline line states what happened: "12 sessions created." or "10 created, 2
      already existed." The manager lands back on the team's event list with the new rows present, because
      the mutation invalidates `eventKeys.all`.
- [ ] **AC10** — Cancelling or editing one occurrence changes that row only. A test cancels occurrence 3
      and asserts occurrences 1, 2 and 4 to N are untouched, `series_id` included.
- [ ] **AC11** — A first session at or before `now()` is refused, in `trainingSeriesSchema` and again with
      `starts_in_past` in the function.
- [ ] **AC12** — A manager may generate only for a team they manage; a player is refused; a team with
      `active = false` is refused. All three are enforced in the function and tested in S1.4, not in the
      UI.
- [ ] **AC13** — `series_id` appears in the repository only in the S1.1 migration, this story's migration
      and the generated `src/lib/database.types.ts`. An ESLint `no-restricted-syntax` rule — written the
      way S1.5's `Intl.DateTimeFormat` ban is written — fails any `series_id` string literal or property
      access under `src/` outside `database.types.ts`, so `npm run lint` in CI is the check and no
      `select`, `filter`, `eq` or `order` can reference it (D30).
- [ ] **AC14** — Loading, empty, error and populated states render as specified below, including a named
      message for every error the function raises.

## Implementation notes

### Migration

`supabase/migrations/<timestamp>_generate_training_series_dst.sql` — a `create or replace` of S1.3's
function. Signature, grants, security-definer settings and error vocabulary are all unchanged; only the
body moves, to get the DST arithmetic right.

```sql
create or replace function public.generate_training_series(
  p_team_id         uuid,
  p_first_starts_at timestamptz,
  p_weeks           int,
  p_title           text,
  p_location        text
) returns setof uuid
language plpgsql
security definer
set search_path = ''
as $$
declare
  v_series_id uuid := gen_random_uuid();
  v_local     timestamp;
begin
  if not public.is_team_manager(p_team_id)
     or not exists (select 1 from public.teams t where t.id = p_team_id and t.active) then
    raise exception 'not_authorised' using errcode = '42501';
  end if;

  -- Horizon cap (D30). Cadence is weekly, so rows = p_weeks <= 16, inside the 20-per-run ceiling.
  if p_weeks is null or p_weeks < 1 or p_weeks > 16 then
    raise exception 'series_too_long' using errcode = 'P0001';
  end if;

  if p_first_starts_at <= now() then
    raise exception 'starts_in_past' using errcode = 'P0001';
  end if;

  -- Add weeks in Dublin wall-clock time, not absolute time, so 7.30pm stays 7.30pm across a clock
  -- change. Adding interval '7 days' to a timestamptz shifts every session after the change by an hour.
  v_local := p_first_starts_at at time zone 'Europe/Dublin';

  -- The insert is a data-modifying CTE because plpgsql opens a RETURN QUERY statement as a cursor, and
  -- an INSERT is not cursorable. `return query insert ... returning id` fails at runtime.
  return query
  with ins as (
    insert into public.events
      (team_id, type, title, location, starts_at, series_id, created_by)
    select p_team_id,
           'training'::public.event_type,
           btrim(p_title),
           btrim(p_location),
           (v_local + (g.k * interval '7 days')) at time zone 'Europe/Dublin',
           v_series_id,
           auth.uid()
    from generate_series(0, p_weeks - 1) as g(k)
    on conflict do nothing
    returning id
  )
  select ins.id from ins;
end;
$$;
```

Two sharp edges, worth knowing before the first bug report:

- The unique index is on `(team_id, starts_at) where series_id is not null`, so two *different* series on
  the same team at the same instant collide and the second is silently skipped. That is deliberate: one
  team cannot train twice at once. A one-off event created by [S4.1](S4.1-create-event.md) at that time
  does **not** block generation, because the index is partial — the manager ends up with two events at
  that time and cancels one.
- A slot landing in the spring-forward gap (01:00–01:59 on the last Sunday in March) is resolved by
  `at time zone` rather than special-cased. Nobody trains at 1.30am; if it ever matters, it is a new
  decision, not a silent fix.

### Client

Schema, added to [S4.1](S4.1-create-event.md)'s existing `src/features/events/schemas.ts` — the one schema
file for this feature. It is a factory taking `now`, for the same reason `eventFormSchema` is: the clock is
injected, never read inside the schema, so S4.1's ban on `Date.now()` and bare `new Date()` under
`src/features/events/` still holds and the unit tests can pin an instant.

```ts
export function trainingSeriesSchema(opts: { now: Date }) {
  return z.object({
    teamId:        z.string().uuid(),
    firstStartsAt: z.string().datetime({ offset: true }),  // dublinLocalToUtcIso(date, time), S4.1
    weeks:         z.number().int().min(1, 'Pick at least one week.')
                            .max(16, 'Pick 16 weeks or fewer.'),
    title:         z.string().trim().min(1, 'Give it a title.').max(80),
    location:      z.string().trim().min(1, 'Where is it?').max(120),
  }).refine((v) => Date.parse(v.firstStartsAt) > opts.now.getTime(), {
    path: ['firstStartsAt'],
    message: 'Pick a date in the future.',
  })
}
export type TrainingSeriesInput = z.infer<ReturnType<typeof trainingSeriesSchema>>
```

The form calls `trainingSeriesSchema({ now: serverNow() })`, matching S4.1's
`eventFormSchema({ requireFuture: true, now: serverNow() })`.

Hook, in `src/api/events.ts` beside `useCreateEvent()`:

```ts
export function useGenerateTrainingSeries():
  UseMutationResult<string[], Error, TrainingSeriesInput>
// supabase.rpc('generate_training_series', {
//   p_team_id: teamId, p_first_starts_at: firstStartsAt,
//   p_weeks: weeks, p_title: title, p_location: location,
// })  →  string[] of created ids. length < weeks means some already existed (AC7, AC9)
```

`onSuccess` invalidates `eventKeys.all`, matching S4.1 and S4.2, so the list, the counts and the player
screens all pick the new rows up. Nothing else is invalidated.

Error mapping. `callRpc` already turns the raised word into an `AppError` with a typed code (S1.5), and
`mapRpcError` already has generic copy for `not_authorised` and `series_too_long`. This form sharpens two
of those lines because it knows the context, so the override is a local record beside the form and
anything unlisted falls through to `mapRpcError`:

```ts
// src/features/events/TrainingSeriesFields.tsx
const SERIES_ERROR_COPY: Partial<Record<AppErrorCode, string>> = {
  not_authorised:  "You can't create training for this team.",
  series_too_long: 'Pick 16 weeks or fewer.',
  starts_in_past:  'Pick a date in the future.',
}
const line = SERIES_ERROR_COPY[err.code] ?? mapRpcError(err.code)
// 'unknown' therefore reads "Something went wrong. Try again."
```

`starts_in_past` is the code this story adds to `APP_ERROR_CODES` and `mapRpcError` in
`src/lib/errors.ts`; its generic line there is "Pick a date in the future." No raw Postgres text ever
reaches a manager.

`not_authorised` deliberately covers both the wrong-team case and the deactivated-team case: S1.3 raises
one code for both, and a manager who has been removed from a team does not need to be told which it was.

### Form and confirm

The switch is the shadcn `Switch`, inside the S4.1 form under the type field, `min-h-tap`. With it on, the
submit button reads "Create sessions" instead of "Create event", and the horizon appears as a shadcn
`Select` offering 4, 8, 12 and 16, defaulting to 12.

Submit opens a shadcn `AlertDialog` before any write. Its body is built from the same arithmetic the
function uses, so the dialog and the database agree:

```ts
// src/lib/series.ts — pure, no Supabase, no clock, testable against the SQL in S1.4
export function weeklySlots(firstIso: string, weeks: number): string[]
// Dublin wall-clock arithmetic through S4.1's helpers in src/lib/time.ts. No new dependency:
//   const { date, time } = utcIsoToDublinParts(firstIso)
//   for k in 0..weeks-1: add 7*k days to `date` as a plain calendar date, then
//   dublinLocalToUtcIso(thatDate, time)
// Adding days to the date string rather than to the instant is what keeps 7.30pm at 7.30pm across a
// clock change — the same move the SQL makes with `at time zone`. Throws a RangeError outside 1..16.
```

The dialog names `weeklySlots(...).length`, then `formatEventTime(first, 'share')` and
`formatEventTime(last, 'share')` on the first and last slots, which is AC8's two labelled lines. The
result line after the run compares `ids.length` with `weeks` to produce AC9's two variants.

Both halves of the form share one submit path: the switch decides whether it calls S4.1's insert or this
RPC. Do not fork the form into two components, and do not duplicate S4.1's title-defaults-by-type
behaviour — it already sets "Training".

## Test plan

- **Unit** — Vitest on `weeklySlots()`: 12 slots from one input; identical Dublin wall-clock time across
  the March and October boundaries, as fixed UTC instants; `weeks = 1` returns the input alone;
  `weeks = 17` and `weeks = 0` throw. Vitest on
  `trainingSeriesSchema({ now: new Date('2026-03-14T12:00:00Z') })`: `weeks = 16` passes, `weeks = 17`
  and `weeks = 1.5` fail on the `weeks` path, and an instant before the pinned `now` fails on the
  `firstStartsAt` path. Vitest on `SERIES_ERROR_COPY`: each of the three codes returns its sharpened
  line and `unknown` falls through to `mapRpcError`.
- **Integration / RLS** — added to the S1.4 suite, since S1.4 owns this RPC's coverage: a manager
  generates for their own team and gets N ids; the same call twice returns N then 0; a player gets
  `not_authorised`; a manager of team A generating for team B gets `not_authorised`; a deactivated team
  gets `not_authorised`; `p_weeks = 17` gets `series_too_long`; a past first session gets
  `starts_in_past`; and one assertion compares the stored instants with `weeklySlots()`'s output for the
  same input across a clock change, so the two implementations cannot drift.
- **E2E** — Playwright with `timezoneId: 'Europe/Dublin'`: as a manager, turn on Repeat weekly, pick a
  Tuesday evening, choose 12 weeks, confirm the dialog names 12, submit, assert 12 rows in the event list
  all showing the same time; cancel the third through S4.2 and assert the other 11 are unchanged.
- **Manual** — none beyond the [S7.4](S7.4-device-pass.md) device pass. It is a form a manager uses once a
  term.

## Open questions

1. Is 12 weeks the right default horizon? **Default: 12**, roughly a term, comfortably inside D30's cap of
   16. Q4 in [00-decisions.md](../00-decisions.md) already fixes 16 as the ceiling; this is only the
   pre-selected value.
2. Should the generator skip a week the manager knows is off, say the Christmas break? **Default: no.**
   Generate the run and cancel the odd week through S4.2. A skip-dates control is a second calendar UI for
   a twice-a-year problem.
3. Should a manager be warned when a generated slot collides with an existing one-off event at that time?
   **Default: no warning in v1.** The partial index permits it, both events show in the list, and the
   manager cancels one.
