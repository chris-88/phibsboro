## Goal

A manager standing in a car park taps one button on the event they just created, picks the squad group,
and the [S5.1](S5.1-message-generator.md) message lands in WhatsApp ready to send. Where the browser has
no share sheet, the same tap opens WhatsApp with the message already filled in. The manager presses send.
The app never does.

## Context

This is the second step of the only journey that matters (CLAUDE.md §1). Everything before it is a form,
everything after it depends on players seeing a link. If this button is awkward the manager goes back to
typing the details out by hand and the link never reaches the group.

Decisions this story rests on, from [00-decisions.md](../00-decisions.md):

- **D52** — pass the message to `navigator.share({ text })` with **no `url` field**, so the link stays
  inside the message body where WhatsApp renders it as one block. The fallback is
  `` `https://wa.me/?text=${encodeURIComponent(message)}` ``, built by `waMeUrl()` in S5.1. An unencoded
  body is truncated at the `#`, and that failure is invisible on a laptop.
- **D40** — shadcn's default button height is under 44px; S0.2 has already overridden the size variants.
  Use the default variant and do not re-style it here.
- **D41** — `/manage/event/:id` sits inside the fixed bottom nav, so the share button must clear it. Use
  the page padding S0.2 established rather than a fixed-position bar of your own.
- **D22 / D23** — the manager event view already holds the event and its counts. This story adds no query.
- **D16** — Sentry must not be handed anything resembling a phone number. The share message is club
  content, not personal data, but there is no reason to ship it to Sentry either. Breadcrumbs record the
  transport used, never the body.

The brief's "the app never attempts to send a message itself" is not a nicety. Automated WhatsApp sending
is on CLAUDE.md's out-of-scope list, and the Business API needs a paid number and a template approval
process. There is no code path to it and none is left stubbed.

## Scope

**In**
- `src/lib/share.ts` — `shareText(message)`, the one place `navigator.share` is called.
- `src/features/events/components/ShareButton.tsx` — a shadcn button rendering an anchor, taking a
  pre-built message and a label.
- The primary "Share to WhatsApp" control on `/manage/event/:id`.
- A secondary "Copy message" fallback for the case where neither a share sheet nor WhatsApp is present.
- Failure copy, and the deliberate silence on user cancellation.

**Out**
- The message text. [S5.1](S5.1-message-generator.md) owns every character of it.
- The reminder variant and its button. [S5.3](S5.3-reminder-share.md).
- Any share control for players. Sharing is a manager action (CLAUDE.md §4); a player who wants to forward
  the link uses WhatsApp's own forward.
- A Web Share **Target** entry in the manifest. We share out, never in. Nothing is added to
  `manifest.webmanifest`.
- Sharing a team join link. [S6.2](S6.2-team-join-links.md) owns that button and its copy, and it predates
  this story in the build order.
- Any queueing, retrying, scheduling or record of "was this shared". No `shared_at` column, no table.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — `/manage/event/:id` renders one primary "Share to WhatsApp" control into the empty
      `data-slot="share"` that [S4.3](S4.3-manager-event-view.md)'s `EventHeaderCard` ships. At least 44px
      high, occupying the full width of the header action row at 375px, and visible without scrolling.
- [ ] **AC2** — Where `navigator.share` exists, tapping it opens the native share sheet with exactly the
      `buildShareMessage()` output as `text`, no `url` field and no `title` field.
- [ ] **AC3** — Where `navigator.share` does not exist, the same control is a real anchor whose `href` is
      `waMeUrl(message)`, so the tap is an ordinary navigation and is never eaten by a popup blocker.
      Opening it prefills a WhatsApp message identical to the generated string, link intact past the `#`.
- [ ] **AC4** — The message is built during render, not inside the click handler. No `await` runs before
      `navigator.share()`, so the user gesture is still live when it is called.
- [ ] **AC5** — A user dismissing the share sheet (`AbortError`) produces no error message, no toast, no
      Sentry event, and leaves the button enabled.
- [ ] **AC6** — Any other rejection falls back to navigating to `waMeUrl(message)` in the same tap, and if
      that too fails renders an inline line under the button: "Couldn't open WhatsApp. Copy the message
      instead." The button stays enabled.
- [ ] **AC7** — A "Copy message" secondary control is always present and puts the exact same string on the
      clipboard via `copyText()` from `src/lib/clipboard.ts`, confirming inline with "Copied" for three
      seconds. It is a text-weight button, visually subordinate to the primary. When `copyText()` returns
      `false` — no Clipboard API, insecure context, or a rejected write — a read-only, self-selecting
      `<input>` holding the message is rendered in its place so the manager can long-press and copy by
      hand. No error is thrown and nothing is logged.
- [ ] **AC8** — The control is not rendered when the event is `cancelled`, and not rendered once
      `starts_at` has passed, judged by `serverNow()` from `src/lib/serverClock.ts` (D48), never by
      `Date.now()`. There is nothing useful to share about either.
- [ ] **AC9** — The control appears only for a manager of that team or an admin. This mirrors the route
      guard from [S2.9](S2.9-auth-guard-and-role-context.md) and is convenience only — RLS is the
      enforcement layer, and there is nothing to enforce here anyway, since sharing writes nothing.
- [ ] **AC10** — The app makes no network request of any kind as part of sharing.
      `grep -riE "graph.facebook|api.whatsapp|business.whatsapp" src/` returns nothing, and there is no
      server-side component, Edge Function or webhook in the repository.
- [ ] **AC11** — Works from mobile Safari, Android Chrome, and the installed PWA. Verified by hand in
      [S7.4](S7.4-device-pass.md); the two code paths are covered by Playwright.
- [ ] **AC12** — A Sentry breadcrumb records `share.invoked` with `{ method: 'native' | 'wa.me' |
      'clipboard' }` and nothing else. The message body is never attached to a breadcrumb or an event.

## Implementation notes

**The transport.** One module, no React, so it is unit-testable with a stubbed `navigator`:

```ts
// src/lib/share.ts
import { waMeUrl } from '@/lib/shareMessage'

export type ShareMethod = 'native' | 'wa.me' | 'clipboard'
export type ShareOutcome =
  | { status: 'shared'; method: ShareMethod }
  | { status: 'cancelled' }        // user dismissed the sheet — say nothing
  | { status: 'failed' }           // nothing worked — show the inline line

export function canShareNatively(): boolean
// typeof navigator.share === 'function' && window.isSecureContext

export async function shareText(message: string): Promise<ShareOutcome>
```

`shareText` is:

1. If `canShareNatively()`, `await navigator.share({ text: message })`. Resolve → `shared: 'native'`.
2. Catch. If `err instanceof DOMException && err.name === 'AbortError'` → `cancelled`. Nothing else.
3. Otherwise `window.location.assign(waMeUrl(message))` → `shared: 'wa.me'`.
4. If that throws, `failed`. The caller then offers the copy control.

Every non-cancelled outcome drops one breadcrumb, and only the transport goes in it (AC12, D16):

```ts
import * as Sentry from '@sentry/react'

function breadcrumb(method: ShareMethod): void {
  Sentry.addBreadcrumb({
    category: 'share',
    message: 'share.invoked',
    level: 'info',
    data: { method },          // never the message body, never an event id
  })
}
```

`captureException` is never called from this module. A failed share is a breadcrumb and an inline line on
screen, nothing more (Open question 2).

**The button.** Render an anchor inside a shadcn `Button` with `asChild`, so the no-`navigator.share` case
is a plain link and needs no JavaScript at all:

```tsx
// src/features/events/components/ShareButton.tsx
type ShareButtonProps = {
  message: string
  label: string                 // "Share to WhatsApp" here; S5.3 passes its own
  variant?: 'default' | 'secondary'
}

<Button asChild className="w-full" variant={variant ?? 'default'}>
  <a href={waMeUrl(message)} onClick={handleClick} rel="noopener noreferrer">
    {label}
  </a>
</Button>
```

`handleClick` calls `event.preventDefault()` **only** when `canShareNatively()` is true, then awaits
`shareText(message)` and sets local state from the outcome. When native sharing is unavailable it does
nothing and lets the browser follow the `href`. This is the whole trick: one element, two behaviours, no
popup blocking, and the fallback works with JavaScript broken.

Do not use `target="_blank"`. On iOS it spawns a blank tab behind WhatsApp that the manager has to close.

**Placement.** [S4.3](S4.3-manager-event-view.md)'s `EventHeaderCard` already ships an empty
`data-slot="share"` in its action row, beside [S4.2](S4.2-edit-and-cancel-event.md)'s `EventRowMenu`. Fill
that slot; do not move it, and do not add a second action row. The manager arrives on this screen straight
from [S4.1](S4.1-create-event.md)'s success navigation, so *create → share* is two taps.

**Copy fallback.** Reuse `copyText(text): Promise<boolean>` from `src/lib/clipboard.ts`, created by
[S6.2](S6.2-team-join-links.md) for its join-link panel and already used by
[S2.7](S2.7-escape-the-whatsapp-browser.md). It returns `false` rather than throwing on a missing
API, an insecure context or a rejection. This story consumes it and adds nothing to it. On `false`, render
the same read-only, self-selecting `<input>` S2.7 uses, holding the message, so the manager can long-press
and copy by hand.

**Gotchas.**

- `navigator.share` rejects with `NotAllowedError` when the user gesture has expired. That is why AC4
  forbids any `await` before the call. Building the message from cached query data during render costs
  nothing.
- `navigator.canShare` is not a permission check and is not needed for a plain `{ text }` payload. Do not
  gate on it; some Android builds return false for text-only shares that then succeed.
- `window.isSecureContext` is false on `http://` origins other than localhost, and the whole API is then
  absent. That is correct behaviour and the `wa.me` path covers it.
- Inside the WhatsApp in-app webview `navigator.share` is usually missing, and `wa.me` re-enters the app
  the manager is already standing in. Both are fine. Do not add webview-specific handling here;
  [S2.7](S2.7-escape-the-whatsapp-browser.md) owns webview detection and it is a player-side concern.
- Desktop Chrome has no share sheet, so `wa.me` opens WhatsApp Web. Acceptable, and it is how a manager at
  a laptop will use it.

## Data and API surface

No new tables, no RPCs, no mutations and no Zod schemas. Sharing writes nothing and records nothing.

Reads: the event row the manager event view already holds, under `eventKeys.detail(eventId)` from the
factory in `src/api/queryKeys.ts`. This story adds no query key, no hook in `src/api/` and no
`invalidateQueries` call.

## Test plan

- **Unit** — `src/lib/share.test.ts`, Vitest with a stubbed `navigator`:
  - `navigator.share` resolving → `{ status: 'shared', method: 'native' }` and the payload is exactly
    `{ text: message }`, asserted with `toStrictEqual` so an added `url` fails.
  - rejecting with `new DOMException('', 'AbortError')` → `{ status: 'cancelled' }`, and no navigation.
  - rejecting with any other error → falls through to `wa.me` with a spied `location.assign`.
  - `navigator.share` undefined → straight to `wa.me`, never calling the native path.
  - `ShareButton` (Testing Library): with native sharing available the click is prevented and
    `shareText` is called; without it the anchor's `href` equals `waMeUrl(message)` and the click is not
    prevented.
- **Integration / RLS** — none. This story touches no policy, so the [S1.4](S1.4-rls-test-suite.md) suite
  is unchanged and must still pass.
- **E2E** — `tests/e2e/share.spec.ts`, Playwright against `vite preview` (D17), signed in as the seeded
  manager:
  1. `page.addInitScript` defines `navigator.share` to record its argument on `window.__shared`. Tap the
     button, assert `window.__shared.text` equals the expected message string exactly and that
     `'url' in window.__shared` is false.
  2. A second test deletes `navigator.share` in an init script, asserts the anchor `href` starts with
     `https://wa.me/?text=` and contains `%23%2Fevent%2F`, and asserts the decoded body equals the
     message. The link is never actually followed; no external request leaves CI.
  3. `navigator.share` rejecting with an `AbortError` leaves no error text on screen.
- **Manual** — part of [S7.4](S7.4-device-pass.md). On a real iPhone (Safari and the installed PWA) and a
  real Android (Chrome and the installed PWA): tap share, pick a real WhatsApp group, confirm the message
  arrives whole, the link is tappable, the emoji renders, and nothing is truncated at the `#`. Then the
  same on a phone with WhatsApp uninstalled, confirming the copy fallback.

## Open questions

1. **Should the share control also appear on the event the manager has just created, as a success step?**
   **Proposed default: no separate step.** [S4.1](S4.1-create-event.md) already navigates to
   `/manage/event/:id` on success, where this button is the first thing under the counts. One button in
   one place beats the same button in two.
2. **Should a failed share be reported to Sentry?** **Proposed default: no.** A breadcrumb only (AC12).
   Share failures are overwhelmingly "no WhatsApp installed" and "user changed their mind"; an alert
   stream of those teaches the team to ignore Sentry.
3. **Does `src/lib/clipboard.ts` exist by the time this story is built?** Yes — D20 puts
   [S6.2](S6.2-team-join-links.md), which creates it, at position 14 and this story at 36. If it somehow
   does not, this story creates `copyText()` with that exact signature rather than inlining a second copy
   routine.
