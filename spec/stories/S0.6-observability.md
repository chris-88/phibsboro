## Goal

When the app breaks on a player's phone on a Saturday morning, we find out, and the stack trace names a
real file and a real line rather than `index-4f8a.js:1`. A crash renders a plain screen with a reload
button instead of a white page. No phone number, name or join token ever reaches Sentry.

## Context

The brief's S0.6 asks for Sentry with release tagging and an error boundary at the app root, checked by
"A thrown test error appears in Sentry with a readable stack trace". A minified Vite bundle produces no
readable trace on its own, and nothing in the brief uploads a sourcemap or names a release.
[D16](../00-decisions.md) settles all of it:

- The release is the commit SHA. Build with `build.sourcemap: 'hidden'` and `@sentry/vite-plugin`.
- The S0.5 workflow supplies `SENTRY_AUTH_TOKEN` (a repository secret), `SENTRY_ORG` and `SENTRY_PROJECT`
  (repository variables — an org slug is not a credential, [D38](../00-decisions.md)) and
  `VITE_SENTRY_RELEASE: ${{ github.sha }}`, and the published artifact carries no `*.map`.
- `sendDefaultPii: false`. The user is identified by auth uuid only — never phone, never name.
- `beforeSend` and `beforeBreadcrumb` redact anything matching an E.164 or Irish mobile pattern, and
  truncate anything after `/#/join/` and `/#/reset/`. The scrubber is a pure function with Vitest coverage.
- The criterion is verified once per release by a console `captureException` on the deployed site. **No
  throw-on-purpose route ships** — that was considered and rejected.

Two project facts make the scrubbing non-optional. The phone number is the account identifier
(`CLAUDE.md` section 5), so it appears in sign-in form state, in auth request URLs and in breadcrumbs.
And tokens are stored in plaintext and must never be logged ([D62](../00-decisions.md)) — a reset token in
a Sentry URL is a full account takeover sitting in a third-party dashboard.

S0.6 builds after S0.5 ([D20](../00-decisions.md)) because the sourcemap upload happens in the deploy
build, and the release check is performed against the deployed site.

## Scope

**In**
- `@sentry/react` initialised once, before React renders, with a no-op path when no DSN is configured.
- Release tagging from `VITE_SENTRY_RELEASE`, matching the `pfc-release` meta tag S0.5 publishes.
- `@sentry/vite-plugin` sourcemap upload, with the maps deleted after upload.
- A pure PII scrubber applied through `beforeSend` and `beforeBreadcrumb`.
- `setSentryUser(userId | null)`, called later by [S2.9](S2.9-auth-guard-and-role-context.md), which owns
  every call site.
- An error boundary at the app root with a real fallback screen.

**Out**
- Performance tracing and Session Replay. Both are off: replay would record the phone number on the
  sign-in screen, and tracing is infrastructure for a problem a squad of twenty does not have.
- User feedback dialogs, alerting rules, on-call, dashboards and Slack integrations. Configured in the
  Sentry UI if anyone wants them; nothing in the repo.
- A throw-on-purpose route or a debug page ([D16](../00-decisions.md)).
- Server-side or Postgres logging. There is no server runtime; RPC failures surface as client errors.
- Per-route error boundaries. One at the root, per the brief. Screen-level error states are each story's
  own job ([D49](../00-decisions.md)) and the boundary is the last resort, not the design.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [ ] **AC1** — Sentry is initialised in `src/main.tsx` before the first React render, and with no
      `VITE_SENTRY_DSN` set it is a no-op that throws nothing, so a clean local checkout and a fork pull
      request both run.
- [ ] **AC2** — Every event carries `release` equal to the 40-character commit SHA, identical to the value
      in the `pfc-release` meta tag published by S0.5 (AC2 there).
- [ ] **AC3** — A captured exception from the deployed build shows a stack trace naming a `src/` file with
      a line number and a function name, not a minified bundle frame. Verified once per release by running
      `window.__pfcSentry.captureException(new Error('sentry smoke'))` in the browser console on
      `https://app.phibsborofc.com` and opening the resulting issue.
- [ ] **AC4** — No `*.map` is served from the public origin. The plugin deletes them after upload and the
      S0.5 publish step fails if any survive.
- [ ] **AC5** — A component that throws during render produces the fallback screen — heading, one line of
      copy, a Reload button at 44px — rather than a blank page, and sends exactly one event. Asserted with
      Vitest and Testing Library.
- [ ] **AC6** — An unhandled promise rejection produces one Sentry event. `initSentry` leaves Sentry's
      default `globalHandlersIntegration` in place (nothing is removed from `integrations`), and
      `sentry.test.ts` dispatches an `unhandledrejection` event on `window` after init against a mocked
      transport and asserts one captured event. This is the S7.1 criterion's enforcement point.
- [ ] **AC7** — The scrubber redacts, in message text, exception values, breadcrumb messages and
      breadcrumb data, request URLs and request bodies, and transaction names: `+353871234567`,
      `+353 87 123 4567`, `087 123 4567`, `0871234567`, and a number embedded in a query string. Each is a
      named Vitest case.
- [ ] **AC8** — The scrubber truncates the token from `/#/join/<token>` and `/#/reset/<token>` wherever
      either appears, including inside a full URL and inside a transaction name, leaving `/#/join/[token]`.
- [ ] **AC9** — `sendDefaultPii` is `false`, `tracesSampleRate` is `0`, and both replay sample rates are
      `0`. Asserted by a unit test on the exported options object, so turning one on requires changing a
      test.
- [ ] **AC10** — `setSentryUser(id)` sets `{ id }` and nothing else; `setSentryUser(null)` clears the user.
      The signature accepts only `string | null`, and a rule in `scripts/check-conventions.mjs` (S0.2)
      fails `npm run lint` if `Sentry.setUser(` or `setUser(` appears anywhere under `src/` outside
      `src/lib/sentry.ts`, so no caller can widen the payload.
- [ ] **AC11** — Scrubbing preserves event shape: exception type, value structure and stack frames survive,
      so Sentry still groups issues. A unit test asserts a scrubbed event still has
      `exception.values[0].type` and a non-empty frame list.
- [ ] **AC12** — The scrubber terminates. A deeply nested or self-referential object does not hang or blow
      the stack: depth is capped at 8 and a seen-set guards cycles. Asserted with a cyclic fixture.
- [ ] **AC13** — No route, button or menu item exists that throws on purpose. The route table in
      `src/routes.tsx` still matches the [D34](../00-decisions.md) list exactly — asserted by the S0.3
      route test, which this story does not modify — and `grep -rniE 'sentry.?(test|smoke|boom|debug)' src/`
      returns nothing outside `src/lib/sentry.ts` and the test files.
- [ ] **AC14** — The error boundary's fallback renders at a 375px viewport with no horizontal scroll
      (`document.documentElement.scrollWidth <= 375`), its Reload control carries `min-h-tap`
      ([D40](../00-decisions.md)), and it contains no hex literal, which the S0.2 AC3 lint rule already
      enforces. Asserted in `AppErrorBoundary.test.tsx`.

### Init

```ts
// src/lib/sentry.ts
import * as Sentry from '@sentry/react'

export const sentryOptions: Sentry.BrowserOptions = {
  // The one module besides src/lib/env.ts permitted to read import.meta.env (S1.5 AC6): Sentry must
  // be up before env.ts parses, so that a malformed environment is itself reported.
  dsn: import.meta.env.VITE_SENTRY_DSN,
  enabled: Boolean(import.meta.env.VITE_SENTRY_DSN),
  release: import.meta.env.VITE_SENTRY_RELEASE,
  environment: import.meta.env.VITE_SENTRY_ENVIRONMENT ?? 'production',
  sendDefaultPii: false,
  tracesSampleRate: 0,
  replaysSessionSampleRate: 0,
  replaysOnErrorSampleRate: 0,
  beforeSend: scrubEvent,
  beforeBreadcrumb: scrubBreadcrumb,
}

export function initSentry(): void {
  if (!sentryOptions.enabled) return
  Sentry.init(sentryOptions)
  ;(window as Window & { __pfcSentry?: unknown }).__pfcSentry = {
    captureException: Sentry.captureException,
  }
}

export function setSentryUser(id: string | null): void {
  Sentry.setUser(id === null ? null : { id })
}
```

`__pfcSentry` exists solely so AC3 can be performed from a console on a minified build. It exposes one
function and no configuration; the DSN it would reveal is already a public value baked into the bundle.
Without it there is no way to hand-verify a release, and the alternative — a throw-on-purpose route — is
rejected in [00-decisions.md](../00-decisions.md).

Tracing and replay are zeroed rather than omitted so the values are visible and testable.
`import.meta.env.VITE_SENTRY_DSN` is a repository variable, not a secret ([D38](../00-decisions.md)
reasoning applies: it ships in a public bundle).

### The scrubber

Pure, exported, no Sentry import, so it unit tests with no SDK.

```ts
// src/lib/sentry-scrub.ts
const E164        = /\+\d{8,15}/g                       // +353871234567
const SPACED_E164 = /\+\d{1,3}(?:[ -]\d{2,4}){2,4}/g    // +353 87 123 4567
const IE_NATIONAL = /\b0\d{2}[ -]?\d{3}[ -]?\d{3,4}\b/g // 087 123 4567, 0871234567
const TOKEN_PATH  = /(\/#\/(?:join|reset)\/)[^/?#\s"']+/g

export const PHONE_MASK = '[phone]'
export const TOKEN_MASK = '[token]'

export function scrubString(input: string): string
export function scrubDeep<T>(value: T, depth?: number, seen?: WeakSet<object>): T
export function scrubEvent<T extends SentryEventLike>(event: T): T
export function scrubBreadcrumb<T extends BreadcrumbLike>(crumb: T): T
```

The two hook functions are generic and return the same type they were given, so
`beforeSend: scrubEvent` and `beforeBreadcrumb: scrubBreadcrumb` assign to Sentry's
`(event: ErrorEvent) => ErrorEvent | null` and `(crumb: Breadcrumb) => Breadcrumb | null` without a cast
and without `any`. `SentryEventLike` and `BreadcrumbLike` declare every field they touch as optional, so
Sentry's own types are assignable to them. Neither hook ever returns `null`: dropping an event loses the
bug, and scrubbing is what makes keeping it safe.

`scrubString` applies the token rule first (so a token containing digits is not partially masked as a
phone number), then the three phone patterns. `scrubDeep` walks strings, arrays and plain objects to a
depth of 8, guarding cycles with a `WeakSet`, and leaves everything else untouched. The Irish national
pattern is deliberately broad: it will occasionally mask a nine-digit number that is not a phone number,
and a false positive in an error report costs nothing while a false negative is a data leak.

`scrubEvent` runs `scrubDeep` over `message`, `exception.values[].value`, `request.url`, `request.data`,
`request.headers`, `transaction`, `extra`, `tags`, `contexts` and `breadcrumbs`, and reduces `user` to
`{ id }` — dropping `email`, `username`, `ip_address` and anything else, whatever set it.

`scrubBreadcrumb` returns the scrubbed crumb, and additionally strips `data` down to `method` and
`status_code` for any `fetch` or `xhr` crumb whose URL contains `/auth/v1/`, because that is the request
carrying the password and the number.

Types are declared locally as structural `…Like` interfaces rather than imported from the SDK, so the test
file needs no Sentry runtime and no `any`.

### Error boundary

```tsx
// src/components/AppErrorBoundary.tsx
<Sentry.ErrorBoundary fallback={({ resetError }) => <CrashScreen onReload={resetError} />}>
  {children}
</Sentry.ErrorBoundary>
```

Wraps the router in `src/App.tsx`, inside the providers so the fallback gets theme tokens, outside the
routes so it catches any screen. `CrashScreen` composes `ErrorState` from `@/components/states` (S0.2
AC9), which already supplies the retry control at the S0.2 tap-target size: heading "Something went
wrong.", one line — "Reload the app. If it keeps happening, tell your manager." — and a full-width Reload
button whose `onRetry` calls `resetError()` then `window.location.reload()`. British English, no apology
paragraph, no error text on screen, no hex.

### Build

```ts
// vite.config.ts
build: { sourcemap: 'hidden' },
plugins: [
  // …
  process.env.SENTRY_AUTH_TOKEN
    ? sentryVitePlugin({
        org: process.env.SENTRY_ORG,
        project: process.env.SENTRY_PROJECT,
        authToken: process.env.SENTRY_AUTH_TOKEN,
        release: { name: process.env.VITE_SENTRY_RELEASE },
        sourcemaps: { filesToDeleteAfterUpload: ['dist/**/*.map'] },
      })
    : null,
]
```

`'hidden'` emits maps with no `sourceMappingURL` comment, so a browser never requests one even if a map
were left behind. The plugin is conditional on the token so local builds and fork pull requests, which
have no secret, build normally. S0.5's `verify-dist.sh` is the belt to this braces.

## Data and API surface

None. No table, no RPC, no Zod schema, no query key. `setSentryUser` takes the auth uuid
[S2.9](S2.9-auth-guard-and-role-context.md) already holds; it reads nothing from the database, and in
particular it never reads `profiles`.

## UI states

One screen: the root error boundary's fallback. It has no route of its own — it replaces whatever route
was rendering.

| Screen | Loading | Empty | Error | Populated |
|---|---|---|---|---|
| Root error boundary fallback (any route) | Never rendered during loading; the boundary reacts to a render error only, and a pending query shows that screen's own loading state | Not applicable; the fallback has no data and so has no empty state | This **is** the error state: heading, one line of copy, a 44px Reload button, S0.2 tokens only | Children render normally and the boundary is invisible |

Every other screen keeps its own inline error state with a retry control ([D49](../00-decisions.md)). The
boundary is what catches the ones nobody predicted.

## Test plan

- **Unit** — `sentry-scrub.test.ts` is the bulk of it: one case per phone format (AC7), token truncation
  in a URL and in a transaction name (AC8), a nested breadcrumb `data` object, an `/auth/v1/token`
  breadcrumb reduced to method and status, a `user` object carrying an email reduced to `{ id }` (AC10),
  event shape preserved (AC11), and a cyclic object (AC12). Plus `sentry.test.ts` asserting the options
  object — `sendDefaultPii: false`, `tracesSampleRate: 0`, both replay rates `0` (AC9) — the no-DSN no-op
  (AC1), `release` equal to `import.meta.env.VITE_SENTRY_RELEASE` (AC2), that `integrations` is not
  overridden and an `unhandledrejection` dispatched on `window` yields one event (AC6), and
  `setSentryUser('abc')` then `setSentryUser(null)` calling `Sentry.setUser` with `{ id: 'abc' }` then
  `null` (AC10). `AppErrorBoundary.test.tsx` renders a throwing child and asserts the fallback, exactly one
  captured event (AC5), `scrollWidth <= 375` and the `min-h-tap` class on the Reload control (AC14).
  [D53](../00-decisions.md) pins `TZ=UTC` for all of it.
- **Integration / RLS** — none.
- **E2E** — none. The deployed release check is manual by decision, and the S0.5 smoke job already asserts
  that the release string reaching the browser is the commit SHA.
- **Manual** — once per release, and written into the S7.4 device pass the first time: open
  `https://app.phibsborofc.com`, run `window.__pfcSentry.captureException(new Error('sentry smoke'))` in
  the console, then in Sentry confirm the issue exists, its release equals the commit SHA, its top frame
  names a `src/` file with a line number, and neither the event nor its breadcrumbs contain a phone number
  or a token.

## Open questions

1. **Which Sentry plan and quota?** Default: the free developer tier. A squad app throwing more than 5,000
   events a month has a bug worth fixing rather than a plan worth buying. If the quota is hit, lower the
   sample rate before widening the budget.
2. **Should errors be reported at all before Epic 2, when nobody is signed in?** Default: yes, from day
   one. Events carry no user until `setSentryUser` is called, which is exactly the anonymous cold arrival
   path from a WhatsApp link — the leg of the journey we least want to be blind on.
3. **Does the scrubber's Irish national pattern mask too much?** Default: accept the false positives. If a
   masked value turns out to matter for debugging, narrow the pattern to `0(8[3-9]|1)` prefixes rather than
   removing it, and add the narrowed case to the test file in the same commit.
