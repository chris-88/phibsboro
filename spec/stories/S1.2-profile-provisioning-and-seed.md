## Goal

A person signing up gets a `profiles` row automatically, with their name and their number in E.164, and a
second person cannot take a number that is already registered. A developer or a CI runner gets a club
in a known state — two teams, an admin, two managers, twenty players, real events, real responses — with
one command. After this story the RLS suite has somebody to sign in as, and Epic 2 has a proved auth
mechanism instead of an assumption.

## Context

Section 1.2 of the brief asks for a trigger; [00-decisions.md](../00-decisions.md) adds three things it
did not say.

- **D19 — the phone-auth spike, and it is a hard gate on Epic 2.** The brief asserts "Phone confirmation
  is disabled in Supabase Auth config, so no SMS is ever sent". Supabase normally wants an SMS provider
  configured before phone sign-up works at all, confirmations off or not. If that holds, nine stories
  cannot be built as written. The **first task of this story** is to prove it on the real project. Whether
  it worked is recorded as an amendment in [00-decisions.md](../00-decisions.md) before any Epic 2 work
  starts.
- **D15 — the seed moves here, and it is a Node script.** [S1.1](S1.1-schema.md) is migrations only. Auth
  users have passwords and live in the `auth` schema; SQL cannot create them correctly, and
  [S1.4](S1.4-rls-test-suite.md) must sign in as each of them. One seed artifact serves S1.1, S1.4 and
  S7.3. There is no second fixture set.
- **D4 / D35** — `profiles.id` is the `auth.users` id, and `auth.users.phone` is stored by Supabase
  **without** the leading `+`. The trigger prepends it, so `profiles.phone` is always full E.164 with the
  `+`. Everything above the database — `toE164()`, the forms, the RPCs — uses the `+` form only.
- **D3** — the brief's seed criterion reads "one club, two teams". There is no `clubs` table and there
  never will be; the club is implicit and the team is the top-level unit. The criterion is satisfied by
  seeding two teams and nothing above them.

Two things this story must not imply. A phone number here is **not proof of identity**: confirmations are
off, no SMS is ever sent, and nothing in the app may read `phone_confirmed_at` or treat a number as
verified (brief section S1.2, third bullet). And account creation is **open by construction** — anyone
with the public anon key can call `auth.signUp` directly, so the invite gate in
[S2.1](S2.1-registration.md) is a gate on **membership**, never on account creation (D37). The seed
therefore includes a signed-in user with zero memberships, because that is a real state a real stranger
can reach, and S1.4 asserts they are denied everywhere.

## Implementation notes

### Order of work

The spike first. Do not write the trigger, the seed or the tests until AC1 and AC3 are settled, because
the fallback in AC2 changes where `phone` comes from at signup. The trigger below is written so that both
D19 outcomes work without a second migration, but the `config.toml` block and `src/lib/auth.ts` are not.

### The trigger

The migration, created the same way, for example `supabase/migrations/20260913101500_profile_provisioning.sql`:

```sql
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = ''
as $$
declare
  v_name  text;
  v_phone text;
begin
  v_name := nullif(btrim(coalesce(new.raw_user_meta_data ->> 'name', '')), '');
  if v_name is null then
    raise exception 'profile_name_required' using errcode = '23514';
  end if;

  -- Supabase stores auth.users.phone without the leading '+'. Under the D19
  -- fallback the column is null and the number arrives in metadata instead.
  v_phone := case
    when coalesce(new.phone, '') <> '' then '+' || new.phone
    else nullif(btrim(coalesce(new.raw_user_meta_data ->> 'phone', '')), '')
  end;

  if v_phone is null or v_phone !~ '^\+[1-9][0-9]{7,14}$' then
    raise exception 'profile_phone_invalid' using errcode = '23514';
  end if;

  insert into public.profiles (id, name, phone)
  values (new.id, left(v_name, 80), v_phone);

  return new;
exception
  when unique_violation then
    raise exception 'phone_taken' using errcode = '23505';
end;
$$;

create trigger on_auth_user_created
  after insert on auth.users
  for each row execute function public.handle_new_user();
```

Notes on the choices, so they are not relitigated:

- **Raise, do not paper over.** A signup with no name is a malformed client, not a user to be given a
  placeholder. The raise aborts the whole insert, so GoTrue returns an error and no orphan auth user
  survives. [S2.1](S2.1-registration.md)'s form always sends a name, so a real player never sees it.
- **`left(v_name, 80)`** keeps a long name from hitting the check constraint with a confusing error. The
  form caps it first; this is the backstop.
- **The `exception` block** converts the `profiles.phone` unique violation into a named error. It matters
  only under the D19 fallback, where `auth.users.phone` is null and GoTrue's own uniqueness never fires.
  On the phone path GoTrue rejects first with `phone_exists` and the trigger never runs. `profiles_phone_key`
  is the only unique constraint the insert can breach — `new.id` comes straight from the `auth.users` row
  that was just created, so the primary key cannot collide — which is why catching `unique_violation`
  wholesale is safe here.
- **`after insert`**, not `before`. The `profiles` foreign key targets `auth.users(id)`, so the auth row
  must exist first. Both run inside GoTrue's transaction, so a raise rolls the lot back.
- **`security definer`** because `authenticated` has no rights on `public.profiles` for insert and never
  will (D9's spirit: no client writes a membership, no client writes a profile).

Error mapping, owned here and consumed by [S2.1](S2.1-registration.md):

| Raised | Measured at the client (2026-09-13, hosted project, supabase-js 2.116) | Copy |
|---|---|---|
| GoTrue duplicate number (was predicted as `phone_exists`) | `signUp`: HTTP 422, `code: 'user_already_exists'`, `name: 'AuthApiError'`, message "User already registered". No second auth user, no second profile | "That number is already registered." + sign-in link |
| `phone_taken` (trigger, metadata-phone path only) | `auth.admin.createUser`: HTTP 500, `code: undefined`, `name: 'AuthRetryableFetchError'`, message "Database error creating new user". The raised name does **not** reach the client | Unreachable from S2.1's form on the phone path; the fallback line if ever seen |
| `profile_name_required` | `signUp`: HTTP 500, `code: undefined`, `name: 'AuthRetryableFetchError'`, message "Database error saving new user"; `auth.users` count unchanged. The raised name does **not** reach the client | "Could not create that account. Ask your manager." — a form bug if seen; S2.1 parses nothing |
| `profile_phone_invalid` | `auth.admin.createUser`: HTTP 500, as above, "Database error creating new user"; no orphan | the same fallback line — a form bug if seen |
| — (GoTrue, after `password_min_length` 8) | `signUp`: HTTP 422, `code: 'weak_password'`, `name: 'AuthWeakPasswordError'`, message "Password should be at least 8 characters." | "Use at least 8 characters." |

The table above is measured, not predicted: `tests/db/profile-provisioning.test.ts` prints each payload
on every run. GoTrue flattens every trigger `raise` into a 500 with `code: undefined` and a generic
message, so [S2.1](S2.1-registration.md) matches on exactly two codes — `user_already_exists` and
`weak_password` — and renders the single fallback line for any other error. Nothing parses a message
string. `AuthRetryableFetchError` is supabase-js's class for a 5xx; S2.1 must not retry it in a loop.

### The seed

`supabase/seed/fixtures.ts` holds every constant; `supabase/seed/seed.ts` does the work. Run with `tsx`,
no build step. Both are outside `src/`, so the service-role key never enters the bundle's module graph.

```ts
// supabase/seed/fixtures.ts — fixtures, not secrets. Local and CI only.
export const SEED_PASSWORD = 'phibsboro-seed-1234'

// Irish mobile shape, +353 89 9999 NNN. The +3538990… range is reserved for
// E2E registration runs (D58); every number here starts +3538999 and so cannot
// collide with it.
export const ADMIN   = { phone: '+353899999001', name: 'Chris Quinn' }
export const MANAGERS = [
  { phone: '+353899999002', name: 'Declan Ward' },  // manages Firsts, plays for Seconds
  { phone: '+353899999003', name: 'Niamh Doyle' },  // manages Seconds
]
export const PLAYERS  = [ /* 20 entries, +353899999010 .. +353899999029 */ ]
export const NO_TEAM  = { phone: '+353899999040', name: 'Sean Kelly' }
export const LEAVER   = { phone: '+353899999041', name: 'Mark Traynor' }

export const TEAM_FIRSTS  = { id: '00000000-0000-4000-8000-000000000001', name: 'Firsts' }
export const TEAM_SECONDS = { id: '00000000-0000-4000-8000-000000000002', name: 'Seconds' }
export const EVENTS = [ /* fixed uuids, offsets from a single captured `now` */ ]
```

Team names are Q7. The first admin is Q6. Player names are twenty plain first-and-last names in a fixed
array; no generator.

`seed.ts`, in order:

1. Read `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` from the environment, defaulting to the CLI's local
   stack values committed in `.env.example`. Enforce AC24 and AC25 before writing anything.
2. Capture `const now = new Date()` once. Every event time is an offset from it, so the seed is
   deterministic within a run and the "past" and "imminent" fixtures stay meaningful whenever it runs.
3. Create all 25 accounts with
   `admin.auth.admin.createUser({ phone, password: SEED_PASSWORD, phone_confirm: true, user_metadata: { name } })`.
   `phone_confirm: true` means "created already confirmed"; it does not mean verified, and no SMS is sent
   (D15). Under the D19 fallback, swap to `email` plus `email_confirm: true` with the number in
   `user_metadata.phone` — one branch, in one place, driven by the same helper
   [S2.1](S2.1-registration.md) uses.
4. Insert the two teams with their fixed ids, then memberships, then events, then responses, then
   attendance, with a service-role client. All of it bypasses RLS by design, which is why this is a setup
   tool and never an assertion (D15).
5. `update public.profiles set is_admin = true where phone = ADMIN.phone`.
6. For the leaver: insert the membership, insert their response and attendance, then delete the membership
   row. That is the only supported way to get an orphaned history row, and it mirrors what `remove_member`
   does (D33).
7. Print a short summary — counts per table, the two team ids, the admin number — so a developer can see
   the state without opening Studio. Never print a token or a password.

Squad layout, fixed so the counts in [S4.3](S4.3-manager-event-view.md) have a known answer: Firsts gets
manager 1 plus players 1–10 and the multi-team player; Seconds gets manager 2, manager 1 as a **player**,
and players 11–20. Every member counts toward the squad regardless of role (D22).

only), and `teams`, `team_members`, `events`, `event_responses`, `attendance` by the seed with a
service-role client. `team_invites` and `reset_tokens` are left empty; their write paths are RPCs in

`auth.users`. No RPC, no policy, no Zod schema, no TanStack Query key. Configuration changed:
the phone provider block of `supabase/config.toml`.

   above already reads the number from `raw_user_meta_data ->> 'phone'` when `auth.users.phone` is null,

2. **Should the trigger accept a signup with no name instead of raising?** *Default: raise. A nameless

   ours. Revisit only if GoTrue's 500 response proves unreadable in practice.*
