## Goal

A player who is handed a link in the squad WhatsApp group ends up a member of the right team with the
right role, whether they tap a join link or an event link, whether they already have an account or not.
Before this story a person can register and sign in but belongs to nothing, so every screen in Epic 3 is
empty for them.

## Context

Two links circulate. The squad join link, `/#/join/{token}`, is generated in
[S6.2](S6.2-team-join-links.md) and pasted into the group. The event link, `/#/event/{id}`, is generated
by the share message in [S5.1](S5.1-message-generator.md) and is the entry point of the one journey that
matters. Both must create a `team_members` row for a stranger.

Decisions this story stands on, from [00-decisions.md](../00-decisions.md):

- **D6** — the event link is a deliberate bearer join credential. `events.id` is a `uuid`, never
  sequential, and joining by it is a supported path, not a leak. No token is appended to the share link.
- **D7** — an anonymous or non-member visitor reads the event through `get_event_preview` and sees one
  primary button, "Join {team name}". **A signed-in user is never joined silently.**
- **D9** — clients have no INSERT, UPDATE or DELETE on `team_members`. Joining is only ever
  `join_team_by_token` or `join_team_by_event`.
- **D26** — `team_members.joined_at` is set once. The join RPCs insert `on conflict do nothing`, so an
  idempotent re-join does not reset it.
- **D28** — the player link is multi-use and lives 90 days; the manager link is single-use, lives 24
  hours, and is spent on the first successful join.
- **D37** — the registration gate is **UX, not a security boundary**. Anyone holding the public anon key
  can call `auth.signUp` directly. The real gate is on membership, enforced by RLS. Nothing in this story
  may be described or designed as if only invitees have accounts.
- **D50** — an inactive team refuses both joins.

The brief's line "`/#/event/{id}` from an unknown user does the same" is honoured with one change, from
D7: the stranger sees the event first and taps Join. They are never added to a squad without asking.

`src/features/auth/pendingJoin.ts` is delivered earlier, by [S2.1](S2.1-registration.md), because its
route gate needs to read the pending credential. S2.1 fixes both variants, the key name and the 24-hour
TTL; this story adds no signature to it and changes none. What this story owns is the resume: the cold
start, the sign-in path, and the ordering against [S2.5](S2.5-deep-link-return-path.md).

S2.1's register mutation already performs the join inline as its step 2 and clears the key, so the resume
is not a second join on the registration path — it finds nothing and returns `done`. The resume exists for
the paths S2.1 does not cover: sign-in ([S2.2](S2.2-sign-in.md) does no join), and a cold start where the
session is restored with the key still set.

## Scope

**In**
- The `/#/join/:token` screen: lookup, team name, role, join, and one invalid-link screen.
- The join panel on `/#/event/:id` for anonymous and signed-in non-members, added to the S3.3 screen.
- `src/api/joins.ts` — query and mutation hooks over `lookup_team_invite`, `join_team_by_token` and
  `join_team_by_event`.
- Resuming a pending join after registration, after sign-in, and after a cold start.
- Idempotency, single-use manager links, and one shared failure screen for every bad-token case.

**Out**
- Generating, revoking or regenerating tokens. That is [S6.2](S6.2-team-join-links.md).
- The registration form and the sign-in form. Those are [S2.1](S2.1-registration.md) and
  [S2.2](S2.2-sign-in.md); this story only hands them a pending join and reads the result.
- Deciding which screen the user lands on afterwards. That is
  [S2.5](S2.5-deep-link-return-path.md); this story only guarantees the join has finished first.
- The event detail screen itself, including the preview rendering. That is
  [S3.3](S3.3-event-detail-screen.md).
- Leaving a team, changing a role, or the member list. Those are
  [S6.4](S6.4-member-administration.md).
- Any team switcher. A user's screens span every team they belong to; there is no active-team concept.

### The pending join

One key, `pfc.pendingJoin`, holding JSON. Never a query string, never route state alone — route state
does not survive a cold start, and a WhatsApp tap is very often a cold start.

```ts
// src/features/auth/pendingJoin.ts — signatures fixed by S2.1. Do not rename them here.
export type PendingJoin =
  | { kind: 'token'; token: string }
  | { kind: 'event'; eventId: string }

export function setPendingJoin(join: PendingJoin): void  // writes { ...join, savedAt: Date.now() }
export function readPendingJoin(): PendingJoin | null    // null if absent, unparseable, or savedAt > 24h old
export function clearPendingJoin(): void
```

Twenty-four hours, not the 60 minutes [S2.5](S2.5-deep-link-return-path.md) gives `pfc.intendedRoute`, and
deliberately so: the two keys answer different questions. A stale destination lands a player on the wrong
screen; a stale join credential only ever produces the membership the link was handed out to produce.

Every read is wrapped in `try/catch`: iOS Safari in private mode throws on `localStorage.setItem`. On a
throw, fall back to a module-level variable, which survives navigation within the tab but not a cold
start. Malformed JSON is treated as absent, never thrown.

[S3.3](S3.3-event-detail-screen.md) ships `useJoinTeamByEvent` in `src/api/teams.ts` because it lands

The RPC returns `team_id, team_name` whether the row was inserted or the `on conflict do nothing` swallowed
it, so the client cannot tell a first join from a repeat. Do not try. The success copy is neutral —
"You're in, {team}." — and reads correctly either way.

### Error mapping

Postgres errors arrive as `PostgrestError`. Map on `message`, which the RPCs set to a single opaque code
per the failure convention in [data-model.md](../data-model.md):

```ts
// src/features/teams/joinErrors.ts
export type JoinFailure = 'invalid' | 'network'
export function classifyJoinError(e: unknown): JoinFailure
// 'invalid_invite' -> 'invalid'   ->  <InviteInvalid />, clear pfc.pendingJoin
// anything else    -> 'network'   ->  inline "Couldn't join. Try again." + Retry, keep pfc.pendingJoin
```

`'invalid'` is not reported to Sentry. `'network'` is reported as a breadcrumb only. Neither ever logs the
token: D62 and the D16 scrubber truncate anything after `/#/join/`, and this story must not defeat it by
putting the token in a message body.

### The resume, and its order

Mounted once, by `PendingJoinGate` in the router's root route element, inside
[S2.6](S2.6-session-persistence.md)'s session gate and above
[S2.5](S2.5-deep-link-return-path.md)'s restore. It is inside the router because it renders a full-screen
state over the routed content; the session status comes down from S2.9's `useSession()`:

```ts
export function usePendingJoinResume(): { status: 'idle' | 'joining' | 'done'; teamName: string | null }
```

1. Wait for `useSession().status` (S2.9) to be `signedIn`. `loading` is not a signal to act, and
   `signedOut` means wait too: an anonymous visitor keeps their pending join until they authenticate.
2. `readPendingJoin()`. Null, or expired past S2.1's 24 hours, means nothing to do — return `done`
   immediately. This is also the registration path's outcome, because S2.1's mutation has already joined
   and cleared the key.
3. Fire the matching mutation once. Guard with a `useRef` so React 18 strict-mode double effects do not
   send two calls; the RPC is idempotent anyway, but a doubled network request in a car park is not free.
4. On success or `invalid_invite`, `clearPendingJoin()`, then return `done`.
5. Only when `done` may [S2.5](S2.5-deep-link-return-path.md) consume the intended route. This ordering
   is the reason the deep-linked event screen renders as a member rather than as a preview; it is asserted
   in S2.5 AC7.

While `status === 'joining'`, the gate renders a full-screen state reading "Joining {team}…" — the team
name is available from the invite lookup for the token path, and is not available for the event path, so
the event path reads "Joining…".

### `/join/:token`

```
loading            -> spinner, "Checking your link…"
data null          -> <InviteInvalid />
data, member       -> "You're already in, {team_name}." + Go to home        (AC20)
data, not a member -> team name, role line if role === 'manager' ("You'll join as a manager."),
                      primary <Button size="lg"> "Join {team_name}", secondary link, back affordance
```

Membership is read from `useCurrentUser().memberships` (S2.9), which is convenience only; the RPC is
idempotent either way (D26).

Signed in, the primary button calls `useJoinTeamByToken()` directly and is disabled while pending. Signed
out, it writes `pfc.pendingJoin` and navigates to `/#/register`. There is no auto-join on load in either
case: one deliberate tap, always, matching D7's rule on the event link so a reader never has to hold two
models in their head.

### The event-link path

`JoinTeamPanel` is rendered by [S3.3](S3.3-event-detail-screen.md) whenever the viewer holds no
`team_members` row for `preview.team_id`. Anonymous and signed-in non-member differ only in what the
button does — navigate to register, or call the mutation — so it is one component with one prop:

```tsx
<JoinTeamPanel teamName={preview.team_name} onJoin={...} pending={...} />
```

Anonymous: write `pfc.pendingJoin` as `{ kind: 'event', eventId }` on **both** exits — the primary
button to `/#/register` and S3.3's "Already registered? Sign in" link to `/#/login` (AC19) — and let S2.5 write
`pfc.intendedRoute` as `/event/{id}` at the same moment. Two keys, two owners, on purpose: one answers
"which team do you belong to", the other answers "which screen do you land on". Do not derive one from the
other — a user can have an intended route with no pending join, and the reverse.

## Data and API surface

**Tables** — none written directly. `team_members` is written only inside the RPCs (D9).

**RPCs called**

| RPC | Grant | Used by |
|---|---|---|
| `lookup_team_invite(p_token text)` | `anon`, `authenticated` | `/join/:token` |
| `join_team_by_token(p_token text)` | `authenticated` | `/join/:token`, resume |
| `join_team_by_event(p_event_id uuid)` | `authenticated` | event join panel, resume |

`get_event_preview` is called by S3.3, not here.

**Zod schemas** (S1.5 owns the file; this story adds these two if absent)

```ts
export const TeamInviteLookupSchema = z.object({
  team_id: z.string().uuid(),
  team_name: z.string().min(1),
  role: MemberRoleSchema,            // z.enum(['player','manager']), D24
})
export const JoinResultSchema = z.object({
  team_id: z.string().uuid(),
  team_name: z.string().min(1),
})
```

**Query keys** — `teamKeys.lookup(token)` from S1.5's factory. Mutations invalidate `userKeys.current()`
and `eventKeys.all`.

**Client state** — `pfc.pendingJoin` in `localStorage`. No Zustand store: this is not UI state and it must
survive a cold start.

## Open questions

1. **Should joining a second team change what the app shows by default?** Proposed default: no. There is
   no active-team concept and no switcher in v1. Home and History span every team the user belongs to,
   sorted by `starts_at`; the manager screens are scoped per team by the route. If two squads turn out to
   be confusing on one screen, that is a change to [S3.1](S3.1-home-screen-with-next-event.md), not here.
2. **Should the join screen say which role a player link grants?** Proposed default: only when the role is
   `manager`. "You'll join as a player" is noise for the ninety per cent case.
3. **What happens if a removed member taps the old squad link again?** Proposed default: they rejoin, with
   a fresh `joined_at`, and their historic responses and attendance reattach on their own because they
   were never detached (D33). No warning, no special case.
