## Goal
The player Home becomes a calendar: a condensed next-event card on top, a month view with a coloured dot per
event per day, and — when a day is tapped — that day's events listed below with the Yes/No controls.

## Context
[V10](../00-decisions-v1.1.0.md): the calendar replaces the v1.0.0 chronological upcoming list (S3.2 on Home).
Dots use the team colour (S10.1). Keeps the next-event card (condensed) and the one-tap Yes/No (S3.1).
Cancelled events show hollow/grey and struck-through (existing cancelled styling).

## Scope
**In**
- Install shadcn Calendar (react-day-picker) — the first calendar in the app.
- Home layout: (1) condensed next-event card (type badge, title, day+time, Yes/No, current answer); (2) the
  month calendar with, on each day that has events, a team-coloured dot per event (multiple events → multiple
  dots, capped/summarised sensibly); (3) below the calendar, the selected day's events as cards with Yes/No
  and status, reusing S3.1's response mutation and the event row.
- Month navigation (prev/next). Default selected day = today (or the next event's day if today is empty).
- The month events query: the player's teams' events within the visible month (reuse the events hook,
  windowed by month; the `events(team_id, starts_at)` index serves it).
- Cancelled events: hollow/grey dot; struck-through in the day list. Social/training/match dots use team
  colour; the type is shown in the day list, not the dot.
- Four states: loading (calendar skeleton), empty (member of a team but no events this month / not on a team
  yet), error, populated.

**Out**
- Manager/admin calendars (player Home only, V10 scope). The upcoming-list route/behaviour elsewhere is
  untouched; only Home changes.
- Changing the response rules (S3.4 still governs the cutoff).

## Implementation notes
- `src/components/ui/calendar.tsx` via `npx shadcn add calendar` (pulls react-day-picker); pin the version.
- Custom day content: a `DayWithDots` render that reads the month's events grouped by day and renders up to N
  team-coloured dots (summarise ">N" if a day is busy). Colours from the team read (S10.1); never a hardcoded
  hex — use the team colour token/value.
- Month query: `useMonthEvents({ teamIds, month })` in `src/api/` (or extend the existing events hook) —
  `starts_at` within `[monthStart, monthEnd)` and `team_id in teamIds`, ordered. Group by Dublin day via the
  time helper (a month boundary in Dublin, converted to UTC for the query).
- Reuse S3.1's `NextEventCard` (condensed variant) and the day-card = the existing event row + Yes/No.
- Selected-day state is UI state (Zustand or local) — not server data.

## Data and API surface
Reads: `useMonthEvents` (player's teams, visible month) + team colours (S10.1). Writes: the existing S3.1
response mutation. No schema change. New calendar dependency.

## Build notes — deviations from this spec
| Spec said | Built as | Why |
|---|---|---|
| Selected-day state via Zustand or local | Derived, no stored default: `userSelected`/`userMonth` overrides, default = next event's day (or today) computed in render | `react-hooks/set-state-in-effect` forbids seeding state from an effect; deriving the default avoids the effect entirely and keeps the seed reactive to the next-event read |
| `useMonthEvents({ teamIds, month })` | `useMonthEvents(monthKey: string)` — reads teams from `useSignedInUser` itself, like `useUpcomingEvents` | Matches the existing hook's shape; the screen passes only the `YYYY-MM` it controls |
| Reuse S3.1's response mutation as-is | Extended `useSetResponse` to also patch/rollback every `eventKeys.month(user, …)` cache | The day card reads from a month cache, not `upcoming`; without it the optimistic fill (AC6) would not reach the day card |
| `npx shadcn add calendar` (pin the version) | Added `react-day-picker@10.0.1` (exact), removed the redundant top-level `date-fns` (RDP depends on it transitively), reverted the CLI's clobber of `button.tsx` (D40/A16 44px overrides), and stripped two `toLocale*` calls from the generated `calendar.tsx` (the app bans them, D35) | The CLI rewrote `button.tsx` and emitted lint-banned `toLocale*`; kept the 44px button floor and the one-formatter rule intact |
| — | `new Date(y, m, d)` used in `calendar-month.ts` for react-day-picker day coordinates | RDP's day type is a local-midnight `Date`; this is a UI coordinate, never a stored timestamp (that path stays `dublinLocalToUtcIso`), so the D48 rule does not apply. Documented in the module header |

No migration, RPC, or DB write path was added or changed (the actual `event_responses` upsert is untouched — only client-side optimistic caching was extended), so `test:rls` was not run per the gate rule.
