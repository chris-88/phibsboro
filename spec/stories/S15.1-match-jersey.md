## Goal
A manager picks the kit for a match — Black, Light Blue or White — on the match form; it shows on the event
and is published in the WhatsApp teamsheet, so players know what to wear.

## Context
[W7](../00-decisions-v1.2.0.md). A `jersey` enum column on `events`, match-only and nullable, alongside the
other match fields (V2). See [data-model-v1.2.0.md](../data-model-v1.2.0.md). `sky` is the stored value for
"Light Blue".

## Scope
**In**
- Migration: `jersey` enum (`black`|`sky`|`white`) + the nullable `events.jersey` column + the
  `jersey is null or type = 'match'` check. Regenerate types; add to the events Zod schema.
- The match create/edit form (S8.2) gains a jersey picker (Black / Light Blue / White, plus "Not set");
  training/social forms are unchanged. Existing responses survive an edit (S4.2).
- The event detail (S3.3) shows the jersey for a match when set.
- The WhatsApp match teamsheet (`buildMatchShareMessage`, S9.3) gains a `Jersey: {label}` line when set — a
  D13/V8 amendment — and omits it when unset. Byte-for-byte tests updated.
- The label map: `black → Black`, `sky → Light Blue`, `white → White`, shared by the form, detail and share.

**Out**
- A jersey on training/social (W7 = matches only).
- Per-team default kits, kit clash logic, or more than the three colours.

## Acceptance criteria
- [ ] **AC1** — Migration runs clean; `jersey` is nullable, match-only (the check rejects a jersey on a
  non-match); `supabase db diff` empty after.
- [ ] **AC2** — The match form sets/clears the jersey; training/social forms show no jersey field.
- [ ] **AC3** — The event detail shows "Jersey: Light Blue" (etc.) for a match with one set, and nothing when
  unset.
- [ ] **AC4** — The match share includes a `Jersey: {label}` line when set and omits it when unset —
  asserted byte-for-byte, with and without a squad.
- [ ] **AC5** — The three labels render as Black / Light Blue / White everywhere, from one map.
- [ ] **AC6** — Editing a match's jersey leaves its responses and squad intact.

## Implementation notes
- Place the `Jersey:` line in the teamsheet after the venue line (with KO/Meet and Home/Away), before the
  blank line + Squad, so it reads with the fixture facts. Confirm placement in the byte-for-byte test.
- Add `jersey` to `MatchShareEvent`/`ShareEvent` picks as needed and to `EventActionData`.
- One label map `JERSEY_LABEL: Record<Jersey,string>` in the events feature, imported by form/detail/share.
- Form control: a small select or toggle-group with a "Not set" option that writes null.

## Data and API surface
`events.jersey` column + `jersey` enum. The event create/edit mutation carries `jersey`. The share generator
reads it. No RLS change (column on `events`).

## UI states
| Screen | Loading | Empty | Error | Populated |
|---|---|---|---|---|
| Match form | n/a | "Not set" is the default | inline validation | jersey chosen |
| Event detail (match) | (with the event) | no jersey line when unset | (with the event) | "Jersey: {label}" |

## Test plan
- **Unit** — `buildMatchShareMessage` byte-for-byte with/without jersey and with/without squad; the label map;
  the form writes the enum / null.
- **Integration / RLS** — none (column on an already-policied table); regenerate-types check covers the schema.
- **E2E / Manual** — optional: set a jersey, share, confirm the line in WhatsApp.
