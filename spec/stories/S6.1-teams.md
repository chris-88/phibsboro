## Goal

An admin can create the club's teams, rename one, and deactivate a team that has stopped playing.
Nothing else in the app exists without a team: no join link, no membership, no event, no availability.
This is the first screen that writes to the database, and it is story 13 in the build order for that
reason.

## Context

`CLAUDE.md` section 4 gives the admin "creates teams" and nothing in the brief says how. The brief's own
S6.1 is one sentence with no acceptance criteria, which [D50](../00-decisions.md) fixes: admin-only
screen, create takes a name and nothing else, the name is unique case-insensitively and non-empty, rename
is inline, deactivating is confirmed before it applies.

Decisions this story rests on:

- [D2](../00-decisions.md) — admin is a club-wide flag on `profiles.is_admin`, not a membership role.
  There is no team to be an admin *of* before the first team exists, which is the whole reason the flag
  is club-wide.
- [D50](../00-decisions.md) — `teams.active = false` means: hidden from every non-admin list, event insert
  refused, `join_team_by_token` and `join_team_by_event` both refused. Existing events, responses and
  attendance stay readable to admins and to members. Enforced in RLS and the RPCs, not in this UI.
- [D8](../00-decisions.md) — `teams` select is limited to teams you belong to, plus `is_admin()`; insert
  and update are `is_admin()` only; clients have no delete.
- [D31](../00-decisions.md) — every FK to `teams` is `on delete restrict`. Teams are never hard deleted.
  Deactivation is the only retirement path.
- [D34](../00-decisions.md) — `/admin` is a route of record.
- [D49](../00-decisions.md) — this screen's empty state is "No teams yet."
- [D40](../00-decisions.md), [D41](../00-decisions.md) — 44px minimum, fixed bottom nav with an Admin item.

The build order ([D20](../00-decisions.md)) puts this story ahead of sign-in (S2.2, story 17). Nobody can
reach `/admin` in a browser yet. That is dealt with in Open question 1 and it does not change what gets
built.

## Scope

**In**

- The `/admin` screen: a create form and two lists, Active and Inactive.
- Create a team from a single name field.
- Rename a team inline.
- Deactivate a team, behind a confirmation naming it.
- Reactivate a team, one tap, no confirmation.
- The `teams` Zod schema, query hooks and mutation hooks in `src/api/teams.ts`.
- Clean handling of the case-insensitive duplicate-name constraint.

**Out**

- Deleting a team. There is no control, no RPC and no policy. Say so on screen rather than leaving a
  reader to wonder.
- Members, roles and join links — [S6.2](S6.2-team-join-links.md) and
  [S6.4](S6.4-member-administration.md).
- Events — [S6.3](S6.3-all-teams-view.md) adds the link from a team to its manage view.
- Promoting anyone to admin. Admin is not grantable through the app at all (D2). The first admin is set
  by a one-line migration.
- Any team attribute beyond name and active: no age group, no colours, no kit, no season, no crest.
- A migration. Every table, policy and index this story needs already exists from S1.1 and S1.3.

## Acceptance criteria

Each criterion is independently checkable by a person or a test.

- [x] **AC1** — `/#/admin` renders the teams screen when the signed-in profile has `is_admin = true`. A
      signed-in non-admin is redirected to `/`, not shown a broken screen. At build order 13 the check is
      the inline one from Open question 3; [S2.9](S2.9-auth-guard-and-role-context.md) later swaps it for
      `RequireAdmin` reading `useCurrentUser().isAdmin`, with no change in behaviour. Either way the
      redirect is convenience; the enforcement is that a non-admin insert or update on `teams` affects
      zero rows (S1.4).
- [x] **AC2** — Submitting a name of 1 to 60 characters after trimming creates a row with `active = true`,
      clears the field, and the new team appears in the Active list without a page reload.
- [x] **AC3** — An empty or whitespace-only name is rejected inline before any request is sent. A name
      over 60 characters is rejected inline.
- [x] **AC4** — Creating "firsts" when "Firsts" exists shows the inline message "There's already a team
      called that." under the name field, creates no row, and never surfaces a Postgres unique-violation
      string. Checked with differing case and surrounding whitespace.
- [x] **AC5** — Rename is inline on the team row: tap the name, edit, Enter or blur saves, Escape restores
      the previous name and sends nothing. The same validation and the same duplicate message as AC3 and
      AC4 apply.
- [x] **AC6** — Deactivate opens a confirmation naming the team and stating what deactivation does:
      no new events, join links stop working, existing history stays. Cancel changes nothing. Confirm sets
      `active = false` and moves the row to the Inactive section.
- [x] **AC7** — Reactivate sets `active = true` and moves the row back. No confirmation.
- [x] **AC8** — Teams are listed Active section first, then Inactive, each sorted by name
      case-insensitively with `Intl.Collator('en-IE', { sensitivity: 'base' })`.
- [x] **AC9** — No delete control exists anywhere on the screen, and the Inactive section carries one line
      explaining that teams are kept, never deleted.
- [x] **AC10** — All four UI states are handled as specified in the table below.
- [x] **AC11** — At 375px every interactive element is at least 44px tall and no horizontal scroll appears.
- [x] **AC12** — A failed create, rename or toggle leaves the UI consistent: the optimistic change is
      rolled back, an inline message with a Retry control is shown, and no unhandled promise rejection
      reaches the console.

## Implementation notes

No migration. No RPC. This story is the client half of policies S1.3 already shipped.

Files:

```
src/features/teams/routes/AdminTeamsScreen.tsx
src/features/teams/components/CreateTeamForm.tsx
src/features/teams/components/TeamRow.tsx
src/features/teams/components/DeactivateTeamDialog.tsx
src/api/teams.ts
src/features/teams/schema.ts
src/lib/errors.ts                 // extended: isUniqueViolation() beside S1.5's toAppError()
```

Schema, in `src/features/teams/schema.ts`:

```ts
export const teamNameSchema = z
  .string()
  .transform((s) => s.trim())
  .pipe(z.string().min(1, 'Give the team a name.').max(60, 'Keep it under 60 characters.'))

export const createTeamInput = z.object({ name: teamNameSchema })
export type CreateTeamInput = z.infer<typeof createTeamInput>
```

The row type is `Tables<'teams'>` from the generated types (S1.5). Never
hand-write it.

Hooks, in `src/api/teams.ts`, all TanStack Query:

```ts
export function useTeams(): UseQueryResult<Team[]>            // select('*'), RLS decides the rows
export function useCreateTeam(): UseMutationResult<Team, PostgrestError, CreateTeamInput>
export function useRenameTeam(): UseMutationResult<Team, PostgrestError, { id: string; name: string }>
export function useSetTeamActive(): UseMutationResult<Team, PostgrestError, { id: string; active: boolean }>
```

No new query key. [S1.5](S1.5-typed-data-layer-and-shared-helpers.md) already exports `teamKeys.all` from
the `teamKeys` factory in `src/api/queryKeys.ts`, and its AC15 forbids a fourth factory or a literal key
anywhere else. This story is that key's first consumer; `teamKeys.detail(teamId)` is left to
[S6.3](S6.3-all-teams-view.md) and [S6.4](S6.4-member-administration.md).

`useTeams` sorts in the `select` option, not in the component, so every consumer gets the same order:

```ts
select: (rows) => [...rows].sort(byActiveThenName)
```

Rename and the active toggle are optimistic, following the rollback pattern fixed in
[D48](../00-decisions.md): `onMutate` snapshots `teamKeys.all`, `onError` restores it and shows
the inline message, `onSettled` invalidates. Create is not optimistic — it needs a server-generated id —
so it shows a pending state on the submit button and invalidates on success.

Duplicate-name mapping. The constraint is `teams_name_key`, a unique index on `lower(btrim(name))`, so
Postgres returns `23505`. Add one shared helper rather than string-matching in components:

```ts
// src/lib/errors.ts — added beside toAppError() (S1.5). No second error module.
import type { PostgrestError } from '@supabase/supabase-js'

function isPostgrestError(e: unknown): e is PostgrestError {
  return typeof e === 'object' && e !== null && 'code' in e && 'message' in e
}

export function isUniqueViolation(e: unknown, constraint: string): boolean {
  return isPostgrestError(e) && e.code === '23505' && e.message.includes(constraint)
}
```

React Hook Form surfaces it with `setError('name', { message: "There's already a team called that." })`.

shadcn components only: `Card`, `Input`, `Button`, `AlertDialog`, `Skeleton`, `Alert`, `Badge`, and the
`Form` primitives. The size overrides from [D40](../00-decisions.md) already make the default variants
44px; do not add per-component height classes.

Inline rename is a controlled `Input` swapped in for the name text on tap, not a dialog. Keep the row a
single flex line: name on the left, one action button on the right, labelled "Deactivate" or "Reactivate".
No dropdown menu — with one action per row, a hidden menu costs a tap and buys nothing.

Gotcha: an admin who belongs to no team still sees every team, because the select policy is
`is_team_member(id) or is_admin()`. Do not filter the list by membership anywhere in this feature.

## Test plan

- **Unit** — Vitest + React Testing Library. `teamNameSchema` accepts `"  Firsts  "` as `"Firsts"` and
  rejects `""`, `"   "` and 61 characters. `byActiveThenName` orders `["seconds", "Firsts"]` with an
  inactive team last. `isUniqueViolation` matches a `23505` on `teams_name_key` and not a `23503`.
  Rendering: duplicate error maps to the field, not to a toast; Escape during rename restores the old
  name and fires no mutation; deactivate does nothing until the dialog is confirmed; each of the four
  list states renders its specified content.
- **Integration / RLS** — extends `tests/rls/teams.spec.ts` from S1.4. As admin: insert, rename and
  toggle `active` all succeed. As manager and as player: insert affects zero rows, update of another
  team's `name` affects zero rows, and a select returns only their own teams. As the fourth role from
  [D37](../00-decisions.md), a signed-in user with no memberships, a select returns zero rows. A delete
  as admin through PostgREST affects zero rows, because `teams` has no delete policy at all (D8); and a
  delete run with the service-role key against a team that owns an event fails with `23503` on the
  `on delete restrict` FK. Together those two prove deactivation is the only retirement path.
- **E2E** — none in this story. There is no sign-in screen at build order 13. The admin path through
  `/admin` is walked by the Playwright test added in [S6.3](S6.3-all-teams-view.md).
- **Manual** — at 375px in mobile Safari: create, rename, deactivate, reactivate. Checked in the same PR
  as S2.2 once sign-in exists, per Open question 1.

## Open questions

1. **How does an admin reach `/admin` before sign-in ships?** They cannot: this is story 13 and S2.2 is
   story 17. Proposed default, already assumed above: this story is verified by the integration tests and
   by component tests that render the screen against a mocked authenticated client, and the first manual
   browser pass happens in the S2.2 PR. No temporary sign-in form, no dev-only backdoor, nothing to
   remove later.
2. **Does deactivating a team cancel its future events?** Proposed default: no. Deactivation blocks new
   events and new joins only. Existing scheduled events stay scheduled and stay visible to members, and a
   manager cancels them one by one if that is what they want. Bulk-cancelling on deactivation is a
   destructive side effect hidden behind an unrelated toggle.
3. **Should the route guard live here or wait for S2.9?** Proposed default: this story ships a minimal
   `isAdmin` check inline, and [S2.9](S2.9-auth-guard-and-role-context.md) replaces it with the shared
   route guard without changing behaviour. The check is labelled convenience in a comment so nobody
   mistakes it for enforcement.
4. **Two teams at launch, "Firsts" and "Seconds" (Q7).** Proposed default: the seed creates both
   (S1.2); production teams are created through this screen.
