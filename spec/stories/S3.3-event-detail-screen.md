## Goal

A player who taps `/#/event/{id}` in the squad WhatsApp group lands on that event and answers YES or NO. A
member sees the full event and the availability buttons. A stranger, or a signed-in user who is not on
that team, sees a read-only summary of the event and one button to join the team. Nobody sees a stack
trace, a blank screen, or somebody else's data.

## Context

`CLAUDE.md` describes this screen in one line — "The deep link target. Full event info plus availability
controls" — and adds "Renders correctly for a player who arrived cold from WhatsApp". The cold arrival is
the hard part, and the brief's own RLS rule ("Player can read events only for teams they belong to") makes
it impossible as written. [00-decisions.md](../00-decisions.md) settles it:

- **D7** adds `get_event_preview(p_event_id uuid)`, granted to `anon` and `authenticated`, returning team
  name, type, title, location, `starts_at` and `status` and nothing else. The cold arrival and the
  signed-in non-member both get this summary plus one primary button, "Join {team name}". A signed-in user
  is never joined silently.
- **D6** the event id is a `uuid` and the link is a deliberate bearer join credential, with the same trust
  basis as the squad WhatsApp group. `join_team_by_event(p_event_id)` joins the caller as `player`.
- **D32** a player selects only their own `event_responses` rows. A manager selects every row for events on
  teams they manage — which changes the shape of the embedded read on this screen. See the gotcha below.
- **D48** fixes the optimistic-update contract and requires the cut-off to be computed against a server
  timestamp, never the device clock.
- **D49** fixes this screen's states: event not found is the 404 screen; event on another team or unknown
  user is the preview plus a single Join button; a cancelled event shows a banner with the controls
  disabled; after `starts_at` the controls are disabled with a line.
- **D60** a cancelled event shows "This one's off." and the D12 RLS check already blocks the write.
- **D41** this is a full-screen deep-link route: the bottom nav is hidden and a back affordance is shown,
  so the large YES / NO buttons are never underneath the nav.
- **D34** `/event/:id` is in the route list and must resolve after a hard refresh.

This story is built before [S3.1](S3.1-home-screen-with-next-event.md) and
[S3.4](S3.4-changing-a-response.md) (build order D20, position 19), so it owns the shared pieces they both
consume: the event query hooks, the availability mutation, the `AvailabilityButtons` component and the
server clock. S3.4 extends the same component with the after-`starts_at` disabled state; it is not
rewritten there.

Boundary with [S2.4](S2.4-join-by-link.md): this story ships the **event-link** join, because it cannot
render its own non-member state without it. S2.4 owns `/#/join/:token`, the token entry point, the shared
"ask your manager for a new link" screen, and the idempotency tests across both entry points.

### Query keys

No key is declared here. [S1.5](S1.5-typed-data-layer-and-shared-helpers.md) already ships the whole
`eventKeys` factory in `src/api/queryKeys.ts`, and its AC15 forbids a fourth factory or a literal key

```ts
// src/api/queryKeys.ts — S1.5, imported here, not redeclared
  all:      ['events'] as const,
  detail:   (eventId: string) => ['events', 'detail', eventId] as const,
  preview:  (eventId: string) => ['events', 'preview', eventId] as const,
  upcoming: (userId: string)  => ['events', 'upcoming', userId] as const,
```

This story is the first consumer of `detail`; `preview` is the key S1.5's own `useEventPreview` reads,
and `upcoming` is consumed by [S3.1](S3.1-home-screen-with-next-event.md), so both stories invalidate
the same key.

### The two reads, and the gotcha

One PostgREST select covers the member view. The team name and the caller's own response come back as
embedded resources, so it is a single round trip.

```ts
const EVENT_SELECT =
  'id, team_id, type, title, location, notes, starts_at, status, teams!inner(name), event_responses(response, user_id)'

const { data, error } = await supabase
  .from('events')
  .select(EVENT_SELECT)
  .eq('id', eventId)
  .eq('event_responses.user_id', userId)   // <- required, see below
  .maybeSingle()
```

**The gotcha.** `event_responses(...)` is a to-many embed and PostgREST applies RLS to it. For a player
D32 returns at most one row, so the naive embed looks correct in development. For a **manager** of that
team the select policy returns every squad member's row, so the embed comes back as an array of twenty and
`rows[0]` is an arbitrary teammate's answer. Managers play (D22) and will use this screen. The
`.eq('event_responses.user_id', userId)` filter on the embedded resource is therefore not an optimisation,
it is correctness. AC15 exists to catch its removal. Normalise with
`data.event_responses[0]?.response ?? null` and never assume the array is non-empty.

`teams!inner(name)` is an inner join, so an event whose team row the caller cannot read is dropped rather
than returned with a null team.

`maybeSingle()` returns `data: null` with no error when RLS filters the row out, which is exactly the
"not a member" signal. Do not use `.single()`, which raises.

The preview is the RPC:

```ts
const { data, error } = await supabase
  .rpc('get_event_preview', { p_event_id: eventId })
  .maybeSingle()
// → { team_id, team_name, type, title, location, starts_at, status } | null
```

### Sequencing the two queries

Run detail first and gate the preview on it, so a member never sees the preview flash:

```ts
const session = useSession()                       // S2.9: { status: 'loading' | 'signedOut' | 'signedIn' }
const signedIn  = session.status === 'signedIn'
const signedOut = session.status === 'signedOut'

const detail  = useEventDetail(eventId)   // enabled: signedIn
const preview = useEventPreview(eventId)  // enabled: signedOut || (detail.isSuccess && detail.data === null)
```

`useSession()` returns an object in every state, so `Boolean(session)` is always true — branch on
`session.status`, never on the object. While `status` is `'loading'` neither query runs and the screen
shows the skeleton; that is what stops a member seeing the preview flash on a cold start (S2.6).

Render order in `EventDetailScreen`, first match wins:

1. `detail.isError || preview.isError` → inline error with Retry.
2. `session.status === 'loading'`, or either enabled query is pending with no data → skeleton.
3. `detail.data` → member view.
4. `preview.data` → preview view.
5. both queries settled successfully and both returned `null` → 404 screen.

Error is first so a failed load never reads as "no such event"; the 404 is last so it is only reached
when the server has actually answered "no rows" twice.

### Server clock (D48)

The cut-off must not be judged by the phone's clock. No new RPC is needed: every PostgREST response
carries a `Date` header. Capture it in the client's `fetch`.

```ts
// src/lib/serverClock.ts
let skewMs = 0
export function recordServerDate(header: string | null): void {
  if (!header) return
  const t = Date.parse(header)
  if (Number.isNaN(t)) return
  skewMs = t - Date.now()
}
export function serverNow(): Date {
  return new Date(Date.now() + skewMs)
}
```

```ts
// src/lib/supabase.ts — passed to createClient({ global: { fetch } })
const trackingFetch: typeof fetch = async (input, init) => {
  const res = await fetch(input, init)
  recordServerDate(res.headers.get('Date'))
  return res
}
```

`skewMs` starts at zero, so before the first response `serverNow()` is the device clock. That is fine:
nothing on this screen is decided before the first response arrives. `recordServerDate` and `serverNow`
are pure over an injected clock in tests.

### Availability mutation (D48, D61)

```ts
// src/api/availability.ts
export type SetResponseVars = {
  eventId: string
  response: Enums<'availability_response'>
}
export function useSetResponse(): UseMutationResult<void, PostgrestError, SetResponseVars>
```

- `mutationFn` — `supabase.from('event_responses').upsert({ event_id, user_id, response },
  { onConflict: 'event_id,user_id' })`, throwing `error` when present.
- `onMutate` — `await queryClient.cancelQueries({ queryKey: eventKeys.all })`, snapshot
  `eventKeys.detail(eventId)` and `eventKeys.upcoming(userId)`, then write the new response into both
  caches with `setQueryData`.
- `onError` — restore both snapshots. The component renders `mutation.isError` as an inline line,
  "Couldn't save. Tap again.", inside an `aria-live="polite"` region. Buttons stay enabled.
- `onSettled` — `queryClient.invalidateQueries({ queryKey: eventKeys.all })`. That prefix also covers the
  manager counts key added by S4.3, so a response taken on this screen refreshes those counts (D23).
- No `retry`. A rejection here is usually the D12 policy refusing a started or cancelled event, and
  retrying it silently would hide the reason. The refetch triggered by `onSettled` brings back the state
  that makes the disabled control correct.
- There is no offline queue and no DELETE. `AvailabilityButtons` returns early when the tapped value equals
  the current value, so no request is fired (D61).

### Anonymous branch

```ts
import { setPendingJoin } from '@/features/auth/pendingJoin'        // S2.1
import { setIntendedRoute } from '@/lib/intended-route'             // S2.9 delivers it, S2.5 finalises it

function goToAuth(path: '/register' | '/login', eventId: string, navigate: NavigateFunction) {
  setPendingJoin({ kind: 'event', eventId })   // pfc.pendingJoin  — which team you end up on
  setIntendedRoute(`/event/${eventId}`)        // pfc.intendedRoute — which screen you land on
  navigate(path)
}
```

Two keys, two owners, on purpose (S2.4): one answers "which team do you belong to", the other "which
screen do you land on". Do not derive one from the other and do not write either key by hand — both
helpers already wrap `localStorage` in `try/catch` (iOS private browsing throws on `setItem`) and both
store a JSON envelope with a timestamp, so a raw string write would be read back as absent. Writing them
is all this story does; consuming them belongs to [S2.1](S2.1-registration.md) and
[S2.5](S2.5-deep-link-return-path.md).

`setPendingJoin` is not optional decoration. Without it, [S2.1](S2.1-registration.md)'s AC1 gate sees no
pending join, renders "ask your manager for a new link" instead of the form, and the only journey that
matters stops at its first step.

### Layout and navigation

- The route is registered in the S0.3 route table inside the full-screen layout group, so D41's bottom nav
  is not rendered.
- Back control: `const canGoBack = (window.history.state?.idx ?? 0) > 0`, then `navigate(-1)` or
  `navigate('/')`. React Router writes `idx` into history state, so a cold WhatsApp arrival correctly
  reports `0` and goes home.
- `id` is read with `useParams<{ id: string }>()`. Validate it with `z.string().uuid()` before querying; a
  malformed id short-circuits to the 404 screen without a network call (AC13).

### Freshness

`staleTime: 30_000`, `refetchOnWindowFocus: true`, no `refetchInterval`. A player returning from WhatsApp
gets a fresh read; a player staring at the screen does not poll. Polling belongs to the manager view (D23).

## Data and API surface

**Tables read (via RLS, no direct writes except the one below)**
- `events` — select by id, member path.
- `teams` — embedded `teams!inner(name)`.
- `event_responses` — embedded, filtered to `user_id = auth.uid()`.

**Table written**
- `event_responses` — `upsert` on `(event_id, user_id)`. Subject to the D12 `WITH CHECK`: scheduled,
  `starts_at > now()`, and the caller is a member of the event's team.

**RPCs called**
- `get_event_preview(p_event_id uuid)` — anon and authenticated (D7), through S1.5's `useEventPreview`.
- `join_team_by_event(p_event_id uuid)` — authenticated (D6).

**Zod schemas** (added to `src/features/events/schema.ts`, alongside the S1.5 entity schemas)

```ts
export const eventWithResponseSchema = eventRowSchema
  .pick({ id: true, team_id: true, type: true, title: true, location: true, notes: true,
          starts_at: true, status: true })
  .extend({
    teams: z.object({ name: z.string() }),
    event_responses: z.array(z.object({ response: availabilityResponseSchema })).max(1),
  })
export type EventWithResponseRow = z.infer<typeof eventWithResponseSchema>

// eventPreviewSchema and EventPreview are S1.5's, delivered with useEventPreview:
//   { team_id, team_name, type, title, location, starts_at, status }
// Import them. Do not redeclare them here, and do not add `notes` to them (D7).
```

`.max(1)` on the embedded array is deliberate: it fails loudly in tests if the `user_id` filter is ever
dropped. Both schemas are `parse`d at the API boundary inside the hooks, and the hooks return a flat
camelCase view model so no component touches a snake_case row.

**Query keys introduced** — none. This story is the first consumer of `eventKeys.detail(id)` and
`eventKeys.upcoming(userId)` from S1.5's factory; `eventKeys.preview(id)` is the key S1.5's own
`useEventPreview` reads.

**Mutations introduced** — `useSetResponse`, `useJoinTeamByEvent`.

## Open questions

1. Should the preview show a signed-in non-member the event's notes once they join, without a reload?
   **Default:** yes — `useJoinTeamByEvent` invalidates `eventKeys.all` and the member query refetches, so
   notes appear with the rest of the member view. No extra work.
2. `formatEventTime` style `'share'` is the right shape for this screen ("Saturday 14 March, 7.30pm") but is
   named for the WhatsApp message. Rename it to `'long'`? **Default:** no. D35 fixes the three style names;
   renaming churns S5.1 and S1.5 for nothing. This story notes the reuse and moves on.
3. What does a signed-in non-member see if the event's team is inactive? `get_event_preview` still returns
   the row, but `join_team_by_event` will refuse. **Default:** render the preview as normal and let the
   button surface "Ask your manager for a new link." on failure. Pre-empting it would mean leaking team
   state to a non-member.
4. Should an anonymous visitor be able to read the event at all after it has started? **Default:** yes. The
   preview is harmless and the join RPC already refuses past seven days (D6). No extra rule.
